## 1. 共识项（10 条；每条注明提出方，无人反对）

- **A**：真库 357 KP 中 **132 条（37.0%）snippet 在文档内不唯一**；文档前插 50 行后 **67 条（18.8%）静默钉到错误行且 `ok=True`**。根因 `locator.py` 全用"位置"判据。
- **A（补件）**：F-A（"若 agent 从不读 KP 则降级"）**证伪失败** —— agent 确实在读：`read_kp` 6 次 + `search_kb` 命中行也用 `line_hint` 7 次 ⇒ **13/92 = 14.1% 的读取路径踩在会漂的锚点上**。
- **语料（现场事故链）**：产品自己的"划高亮"`replace_lines` 改写了 ch03:302 的量化定义句 ⇒ 该 KP snippet 锚点当场失效；随后插入笔记使行号漂移，补一条漏一条；`linear-pcm-error-performance` 的 `end="$$"` 导致 **range 反转（2788→2748，span=0）**，无人报错。

### C2 先接现有检索栈，不新造索引层
- **A**：`search_kernel` 已有 4 模式 + RRF（`use_rrf` L61、`semantic` L63-66），但 `tools/kb.py:248` **硬编码 `modes="lexical"`** ⇒ agent 只用 1/4 能力。

### C3 索引单元 = 带预算的切片，**不是 KP**；KP 降为语义锚
- **B**：KP 实测 p50 **526 字**、p90 2,918、max 18,198；**20.3% <200 字**、9.3% >3000 字。主张「带预算的学习切片」(file, heading_path, range) 200–1200 字，复用 `section` 的预算切分 + `next_cursor`；KP id 保留给 FSRS/link/图谱，**不迁移 id**。

### C5 索引分层 + 预算硬约束，绝不整库注入
- **B**：357 KP 名字全量 ≈4.8k 字；加首行 preview ≈19k 字（13–19k tok）= 单次工具上限 65–95%。主张 L0 概览 ≤1.5k tok → L1 outline ≤800 → L2 候选切片 ≤4k。

### C6 证据绑定 + 同事务重算
- **A**：文件级 `sha256` **不能**做 per-KP stale 判据 —— 真库实测"末尾加一行 ⇒ 357/357 全判 stale，实际受影响 0"（过度失效 ∞ 倍）。必须块级 hash，文件级降为第一层粗筛。
- **外部**：建议 `description` 绑定 `{block_sha256, char_range}`；陈旧检测用块级 hash diff（**别学 AOCI 的 83s 级全库检查**）；stale 时降级"读原文 + 标 unverified"。
- **语料**：正文写入必须**同事务重算 range**（现场事故已证明）。

### C7 工具结果必须有预算
- **D**：工具结果**放大系数 10.94×**（第 k 轮产生的工具结果在后续每轮重发）。
- **D**：单次最大工具结果是 **grep（34,249 字符 ≈15.6K tok）**，不是 read_document（8,857 字符 ≈4K tok），**差 4.9 倍**；根因 `GREP_MAX_MATCHES = 250` 且无 token 预算。
- **外部**：成熟做法 = **预算封顶 + 放不下的给 locator-only + 记账 + 错误永不截断**（XERJ 工具契约）；LightRAG 分阶段 `max_entity_tokens/max_relation_tokens` 截断+记账；Aider `map_tokens=1024` + PageRank 个性化 + 二分拟合。

### C8 目标函数改为 iterations/answer + 答对率
- **C（实测）**：19 轮 / 93 iterations / 105 calls = **1.994 元**，输出占 **66.75%**；敏感性：prompt×0.5 = −16.63%，**轮数×0.75 = −25%**，轮数砍半 = −50%；**省 1 iteration/轮 ≈ 0.41 元 ≈ −20.5%** ＞ prompt 砍半；prompt 全归零上限仅 **33.25%**。
- **D**：独立算出同一结论方向 —— 输出单价高 4–8 倍；主张 **P0 单次工具结果上限 + P0 轮次数**，P2 才是 prompt 总量；"不做：提高缓存命中"（已 94.17%）。
- **D**：命中率实测 **94.17%**（19 轮）⇒「缓存命中低」前提**不成立**，提升空间仅 5.8%。

### C9 OCR/PPT 提取的 `img/*` 不该按知识点建
- **语料**：285 条里过"可描述"闸门仅 **22.5%**，**42.1% 硬性不可描述**（formula-only 53 / image-only 5 / too-small 60 / toc 2），**32 组同名全在这里**。→ 不按知识点建，或只建 page 级 + `source_kind=slide` + 禁入"先读索引"路径。
- 纯公式块（3,557）/ 图片块（984）只作附件；目录/答案页标 `nav`；公式密集但仍有散文的 111 条（31%）降级。

### C10 外部方案的处理结论
- **不搬**：GraphRAG 全局检索（LightRAG 在 Legal 5.08M tok 实测 **610,000 tokens/查询** + 数百次 API 调用，一次吃掉约 2.7 轮预算）；RAPTOR 递归摘要树（建树成本无公开数据）；Self-RAG/Adaptive-RAG（**都要训练**）；语义切分（成本不抵收益，arXiv:2410.13070）。
- **搬**：LlamaIndex「小单元匹配/大单元阅读」（SentenceWindow + Hierarchical + AutoMergingRetriever，MIT）；AOCI 逐文件 `sha256`/`normalized_sha256` 基线 + 语义变更门禁；XERJ/Graphiti **双时态边**（`valid_at/invalid_at` + `as_of` + 软失效，Apache-2.0）；Aider 的 `map_tokens` 预算拟合。

## 2. 覆盖策略：经反事实证明后修正（附证据）

**原结论（语料，R13 初版）**：20% 预算下「教材按书序」覆盖 11/11 = 100%，中心度 18.2% ≈ 随机，公式密度 45.5% ⇒ 建议书序。

**Lead 提出的质疑**（2026-10-27）：19 问全部落在第 3 章，从第 1 章建到第 3 章当然 100% ⇒ 疑似过拟合。

**反事实检验结果（语料 `R13-COUNTERFACTUAL.md`）**：

| 场景 | A 按章序 | B 前沿+前置 | B-frac 章内按节 | C 随机 |
|---|---|---|---|---|
| S1（ch3，真实使用） | 100%（需 114,371 tok=18.2%） | 100%（需 **56,991=9.1%**） | 100% | 21.3% |
| S2（ch5–7，假设） | **0%**（需 62.2%） | **56.3%**（需 31.4%） | **62.9%** | 15.4% |
| S3（ch8，假设） | **0%**（需 81.8%） | **100%**（需 19.6%） | 100% | 7.8% |

**真实 4 库实测（更硬）**：

| KB | A 按章序 | B 前沿+前置 | top 使用章位置 |
|---|---|---|---|
| 现代操作系统 | **9.7%** | **75.3%** | ch3 / 23.1% |
| 计算机网路 | **15.2%** | **39.0%** | ch5 / **55.6%** |
| 软件工程概论 | 89.8% | 89.8% | ch3 / 20.0% |
| 数字通信原理 | 100% | 100% | ch3 / 23.1% |

⇒ **2/4 真实库 B 显著胜、2/4 平、0/4 A 胜**。S1 那个 100% 需 2 倍预算，其中 59,105 tok（其花费 50.9%）花在不需要的 ch1–2 上。

**现状审计**：现代操作系统已建章 = ch{3,10}；计算机网路 = ch{2,3,5} —— 与使用 top 章完全重合；**没有任何库是按书序建的**。

**修正结论**：
- 主策略 = **前沿优先**；「按书序」降级为**冷启动兜底（保留）**。
- 前沿信号（实测）：`score = 3×复习卡 + 2×会话读 + 1×批注` → argmax；复习卡 `cards.json` 的 `file` 字段与实际使用 top 章 **2/2 完全一致**；mtime 有噪声、sidecar mtime 不可用（反映建索引非使用）；全 0 回退书序。信号成本 ≈ 一次全库扫描（秒级、零 LLM token）。
- **必须允许章内按节建**：计算机网路 top 章单章成本 93,519 tok > 该库 20% 预算 71,531 ⇒ 整章建不下（B0=0%），按节建才有 32–46%。
- **20% 预算不够**：100% 覆盖需 S1 9.1% / S3 19.6% / **S2 31.4%**；真实库全量覆盖需 **3.1–5.2 倍** 20% 预算。「只建 20%」是讨论设定，不是可落地目标。

## 3. 冲突项（留给 Phase 3 交叉异议）

### K1 先修锚点还是先建索引
- **A**：锚点是 P0 前置；不修就是建在 37% 有歧义的键上。
- **C** 的方案（露 `kp_id` 提升 `read_kp` 采用率）**假设 kp_id 正确可用**；若锚点不准，露出去的 id 会指向错切片。
- **待裁**：0.5.x 第一批做哪个？还是并行（露 id 是两行代码，锚点修复是重建任务）？

### K2 索引单元：section / 块 / 两层叠加
- **语料**：块不是"比标题更可靠"，而是另一种可靠 —— 标题给语义边界（373 标题/300 可解析编号；编辑后 section 数不变），空行块给精确边界（14,560 块；改一行只改 1 块 = 0.1%；但 24.4% 是 formula-only 不能当语义单元）。主张**两层叠加**：`section_number` + 块 hash 范围 + 唯一 snippet。
- **B**：主张 200–1200 字预算切片。
- **C**：主张 read_kp 补 `offset/limit` 复用 section 切片。
- **待裁**：三者在实现上是同一件事的不同描述，还是真的要三层结构？

### K3 索引由谁建：agent 现场建 / 系统懒建 / 人工策展
- **现状（语料实测）**：`notes/非均匀量化噪声推导-附录.md` 12:00:28 建、sidecar 12:00:47 出现（**19 秒**）⇒ 索引是"写时顺手建"的派生数据；且 agent 在用户要求后现场建了 28 KP + 20 边。
- **B**：主张人写 `note`（人读字段）以维持动机。
- **外部**：AOCI 路线 = 模型策展 + 验证回环 ⇒ ledger 实测 `maintain` 中位 **48.3s** 且 **32/34 次 repair_required**，累计机器时间 2.8h（不含模型 token）；XERJ 路线 = 确定性 detector + 双时态边，无需重新策展。
- **待裁**：取"AOCI 的证据身份 + XERJ 的软失效"，弃 AOCI 的重写回环 —— 但是否成立需裁决。

### K4 目标函数：iterations 还是 prompt
- **C + D** 独立同向：iterations/answer 更值钱（省 1 iteration ≈ −20.5%）。
- **但**：D 明确写"我无法从本次数据量化'少一轮省多少'，需 A/B"；C 的 −20.5% 是基于"轮数×0.75"的线性外推，**未做 A/B**。
- **待裁**：把 iteration 作为**主 KPI**是否过早？还是双指标并列（iterations + prompt 峰值），等 A/B 再定主次？

### K5 预算口径（新增，来自 S2/S3 反事实）
- 同一实验两口径：`20%×全库建造成本` vs `20%×正文 token`，S3 结论差极大（B=100% vs B=0%）。
- **待裁**：口径必须唯一并写进验收；否则"A 还是 B 好"可被口径操纵。
