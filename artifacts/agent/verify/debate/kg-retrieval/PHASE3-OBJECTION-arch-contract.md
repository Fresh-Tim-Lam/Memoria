## 攻击对象一：C 方（agent-arch）「露 kp_id 是两行代码、可独立 A/B」

**原文主张**（`PROPOSAL-agent-arch.md#L12 / #L61-L75`）：
> 在 read_document 知识点行（kb.py#L318）与 search_kb 命中行（#L276）各加一行 `[kp_id]`，
> 0 schema 变更，即可提升 read_kp 采用率（现状 6 vs read_document 37）。

### 异议 O1-A：露 id 是「把错误放大」，不是「把能力打开」——C 方的诊断对，但解法前提不成立

C 方的**诊断我完全认同**（且我独立核实过事实）：
`loop.py#L367-L369` 确实只把 `result.content` 入 history，`anchors` 里的 kp_id **不发给模型**。
→「id 不可见」是真的。

**但露 id 的解法有一个 C 方自己没有算进账的前提**：

> 露 `[kp_id]` 让模型能调 `read_kp` 的前提是：**这个 id 背后的 range 指向正确的内容**。
> 而 A 方实测（`r4-wrongpin-probe`，真库 357 KP）：**18.8% 的 KP 在文档前插 50 行后静默钉错且 `ok=True`**；
> 语料方现场事故（PHASE2-MERGE C1）进一步证明：`end.snippet="$$"` 会导致 **range 反转 2788→2748，span=0**，无人报错。

→ **C 方的方案会让模型从「现在不知道 id 所以去 grep 全篇」变成「拿到 id 后自信地调 read_kp，读一个错位切片」**。
前一态是**低效但正确**（grep 至少能看到原文），后一态是**高效但可能错且无感知**。

**这恰恰是我在 KG 辩论里反复批判的"看起来有实际没有"的镜像**：露 id 让"锚点错了"从"不可用"变成"可被静默误用"。

**证据**：
- `ev:file:src/memoria/range/locator.py#L43-L49`（hint 命中直接采信，不验唯一性）
- `ev:bench:r4-wrongpin-probe.json`（67/357 静默钉错）
- `ev:file:artifacts/agent/verify/debate/kg-retrieval/PHASE2-MERGE.md#L31`（语料方 range 反转事故）

**我建议改成什么**：
露 id **必须与锚点修复同批上线**，或至少先上"锚点 fresh/未漂移"校验。
具体：`read_kp` 返回里如果 `resolve_range` 返回 `start_candidates > 1`（歧义）或 `range_repaired`，
**必须显式告知模型这段内容可能对应不准**，而不是裸返回。

**撤回条件**：若 C 方能证明「露 id 后 read_kp 的错位率与 grep 的错位率相同甚至更低」
（即露 id 没有引入新的错误），本异议撤回。

### 异议 O1-B：采用率提升 ≠ 效果提升；C 方把"6 次用太少"当成"应该用的多"，缺一个反方向 falsifier

C 方 §1 明确把"read_kp 6 次 vs read_document 37 次"当成**要修的问题**（采用率低 = 坏）。

**但有个 C 方自己表格里就藏着的数据，反驳了这个方向**（`PROPOSAL-agent-arch.md#L33`）：
> read_kp 平均 **1,431 tok/次**；read_document 平均 **904 tok/次**。

即：**read_kp 每次比 read_document 贵 58%**（1431 vs 904），却未必更贴题 —— 因为语料方实测
（PHASE2-MERGE C4）**93.3% KP 起点是标题行**，一个 KP 可能跨几十上百行，而问题常常是行级的
（C 方自己 §L52 承认 2/19 问题需行级定位）。

→ **采用率 6/37 未必是"缺陷"，可能是模型在做正确的事：遇到行级问题就 read_document，遇到"这块整体"才 read_kp。**
C 方的 falsifier F3 只测「采用率是否升」，**没有测「答对率是否降」** —— 这是它作为检索方案最该测的，反而漏了。

**证据**：`ev:file:artifacts/agent/verify/debate/kg-retrieval/PROPOSAL-agent-arch.md#L33`（1431 vs 904）

**我建议改成什么**：露 id 的 A/B **必须同时测 read_kp 采用率 和 答对率/迭代数**，
且**明确写"若答对率降则放弃露 id"**（不是"采用率升就算赢"）。

**撤回条件**：若 C 方给出「露 id 后答对率不降 且 迭代数降」的实测，本条撤回。

### 异议 O1-C：K1 顺序问题要明确表态 —— **露 id 不能把我的"锚点 P0"降级成 P1**

Lead 提示④要求我不含糊。我的表态：

**露 id 和修锚点不是"谁先谁后"的并行关系，而是"前者依赖后者正确性"的串行关系。**

- 若先露 id 不修锚点 ⇒ 18.8% 错位率 + span=0 反转 会被露 id 放大成"模型自信地读错"（O1-A）；
- 若先修锚点再露 id ⇒ 露 id 才是"把已存在的 read_kp 变成可发现入口"，纯收益。

**所以锚点仍是 P0，露 id 是 P1（在锚点修复之后立即做，因为它便宜）**。
C 方把"露 id"和"锚点"并列成 K1 的两种顺序，本质上是**把依赖关系误当成并列关系**。

**证据**：`ev:file:artifacts/agent/verify/debate/kg-retrieval/PHASE2-MERGE.md#L115-L118`（K1 把两者并列）

**我建议改成什么**：PHASE3 议题 P3-1 应裁决为"串行 = 锚点先行；并行否决"，
理由不是"锚点更重要"，而是"露 id 的价值由锚点正确性承载"。

**撤回条件**：若有人证明"露 id 即便在锚点有 18.8% 错位时也不会放大错误"（等同 O1-A 的撤回）。

## 攻击对象二：语料方（corpus-analyst）「块级 hash + 前沿优先」

**原文主张**（`INDEXING-R9R10R13R14.md#L63 / #L153-L157`）：
> 空行块 = 精确层级，改一行只改 1 块（0.1%）；前沿优先 `score=3×复习卡+2×会话读+1×批注`。

### 异议 O2-A：块级 hash 的「内容寻址」与「偏移平移」在同一段里自相矛盾

语料方 L63 **同一格**写了两句**互相排斥**的话（我逐字读原文，不是转述）：

1. 「内容寻址：改一行只改 **1 块**（0.1%）」
2. 「删一个空行合并 2 块（2 个身份消失）；**插入会使其后所有块的偏移整体平移**」

**矛盾点**：如果块是"内容 hash 寻址"，那么插入一行**只该改变它所在的块、最多再新增/合并相邻 1 块**，
其余块 hash 不变——"后续所有块的偏移整体平移"这个说法**根本不该出现在内容寻址语义里**，
因为"偏移平移"是**位置语义（offset）**，不是**内容语义（hash）**。

→ 这说明语料方的"块"实际上**混用了两套定位**：
- 计算 hash 时用内容（稳定），
- 但把它落进 range 时又依赖行偏移（不稳定）。

这正是我 R4 提案里**明确否决的"位置锚"**没被真正替换掉，只是换了个名字叫"块"。

**证据**：`ev:file:artifacts/agent/verify/debate/kg-retrieval/INDEXING-R9R10R13R14.md#L63`

**我建议改成什么**：块若真做内容寻址，就必须**只存 content_hash，不存 range 偏移作为身份**；
定位时用 hash→扫描文件找到块，行号只是"顺带返回给引用"（与我的提案 §4.4 一致）。
否则"块级 hash"只是"行号锚"加了一层 hash 缓存，漂移问题原样保留。

**撤回条件**：若语料方能澄清"偏移平移"指的是**引用显示的行号**而非"块的定位依据"（即它不靠偏移定位块），本条撤回。

### 异议 O2-B：「改一行只改 1 块 = 0.1%」不能外推到"持续编辑整本教材"——这个是 Lead 提示②，我实测补一刀

语料方用「改一行 → 1 块变（0.1%）」论证块级 hash 的增量成本低。
**但这是"单点编辑"的测量，不是"持续编辑"的累积**。

A 方已有直接反证（`r3_stale_precision_probe` 的镜像逻辑）：
- **追加一行在文末**：内容 hash 只变"末尾块"（0.1%），✅ 语料方对；
- **但在文首插入一个标题**（最常见的教材编辑）：**其后所有** heading 块的**父级 heading 不变但行号全变**，
  若用 `line` 定位则全部失效；若用 hash 定位则不失效 —— **结论完全依赖"你用什么定位"**。

→ 语料方把这个"依赖定位方式"的结论，包装成了"块级 hash 一定稳"的绝对断言，**掩盖了它自己 §256 也承认的"每次写入同事务重算 range 并校验 snippet"这个必要前提**（如果块级 hash 真那么稳，为何还要"每次写入重算 range"？）。

**证据**：`ev:file:artifacts/agent/verify/debate/kg-retrieval/INDEXING-R9R10R13R14.md#L256`（"每次写入同事务重算 range"）
+ A 方 `ev:bench:r4-wrongpin-probe`（前插必漂）

**我建议改成什么**：把结论从「块级 hash 稳」改成「块级 hash **在以下前提下**稳：身份=content_hash、range=派生、写入同事务重算」。
这三条缺一不可，而语料方把它们散落在不同段落，读起来像"块级 hash 天然稳"。

**撤回条件**：若语料方明确其方案中"块身份=content_hash、range 不是身份而是派生引用、写入同事务"三条件全部成立，本条撤回（那它的方案等于我的 R4，只是表述不同）。

### 异议 O2-C：前沿信号 `3×复习卡+2×会话读+1×批注` 在冷启动库上等于 0，而 R13-B 的"书序兜底"又被它自己反事实推翻了

这是 Lead 提示③，而且**语料方自己已经埋了这条线的两个雷**：

1. **信号缺失**（`PHASE2-MERGE.md#L222` 诚实边界⑧）：「复习卡只有 2/5 库有」「批注被 agent 代写污染（ch3 的 45 个高亮含 agent 代写）」。
   → **冷启动库（新导入、无复习卡、无会话、无批注）上，三个信号全 0** ⇒ 前沿优先**退化为"全 0 → 回退书序"**（L157）。

2. **但"书序兜底"又被它自己的反事实推翻了**（`R13-COUNTERFACTUAL.md`）：
   按书序在 S2（ch5–7）/S3（ch8）**覆盖 0%**，因为预算花在前几章、真实使用在后面。

→ **组合起来是死结**：冷启动时信号全 0 → 只能书序 → 而书序对"从中间章开始学"的用户（真实 4 库里 2/4 是这种情况，PHASE2-MERGE §2 表）**覆盖 0%**。

→ 语料方的"前沿优先"结论只在**"已经用了一阵、有复习卡/会话/批注"的成熟库上成立**，对**冷启动库没有给出可用的策略**——而冷启动恰恰是"建索引"最该先解决的时候（你总得先建才有信号）。

**证据**：
- `ev:file:artifacts/agent/verify/debate/kg-retrieval/PHASE2-MERGE.md#L222`（诚实边界⑧）
- `ev:file:artifacts/agent/verify/debate/kg-retrieval/INDEXING-R9R10R13R14.md#L157`（R13-B 书序冷启动兜底）
- `ev:file:artifacts/agent/verify/debate/kg-retrieval/PHASE2-MERGE.md#L94-L99`（真实 4 库：2 库书序覆盖 <20%）

**我建议改成什么**：冷启动策略必须**单列**，不能"全 0 → 书序"一句话带过。
至少给一个不依赖使用信号的**结构信号**替代：例如"章节里 KP 覆盖密度 / 公式密度 / 前言引用数"——
或者**诚实承认"冷启动阶段没有好的覆盖策略，需要用户显式指定起始章"**（这可能才是对的答案）。

**撤回条件**：若语料方能给出「冷启动库（0 复习卡/0 会话/0 批注）下，书序兜底在真实 4 库里也能达到 ≥50% 覆盖」的实测，本条撤回。
