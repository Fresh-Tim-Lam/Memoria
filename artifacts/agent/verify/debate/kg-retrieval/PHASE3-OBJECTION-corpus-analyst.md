## D-2（守）块身份：**对方对，这是表述错误；给出三层定义 + 实测**

**对方指控**（`PHASE3-OBJECTION-arch-contract.md#L96-L119`）：同一格同时写「内容寻址：改一行只改 1 块」与「插入会使其后所有块偏移平移」⇒ 混用身份与位置，块只是行号锚加 hash。

**回应：这确实是我表述错误，不是两套设计。** 正确写法应把三层拆开：

```
identity   = sha256(file_rel + '\x00' + normalize(block_text))   # 只用于 stale/dedup/cache
location   = (file_rel, char_start, char_end)                     # 每次 build 重算；读的时候用；不是身份
anchor     = (section_number, ordinal_in_section, identity)       # 跨 build 重定位；重复块靠 ordinal 消歧
line/range = 派生引用（显示给人看）                                # 不是身份
```
- 我原文「插入会使其后所有块偏移整体平移」指的是 **location（读取位置）**，不是 identity——这正是 O2-A 的撤回条件；**满足撤回条件**。
- 同时满足 O2-B 的三条件：**① 身份 = content_hash ② range = 派生、非身份 ③ 写入同事务重算 range**。这三条我在原文散落多处（`INDEXING-R9R10R13R14.md#L63`、`#L256`），确实是「读起来像块 hash 天然稳」，我接受你的建议把三条件写死。

**为什么必须是 composite anchor 而不是单 hash（实测）**：
- 目标库 **14,395 块，unique hash 13,260 → 重复 hash 率 7.9%**；重复内容 top：`$$`、`<details>…`、`## 目录`、`## 连续时间Fourier变换的性质`。⇒ 单 hash 不唯一，`(section, ordinal, identity)` 才唯一。
- 插入 40 行模拟：**原始 938 块中 893 块 hash 保留（95.2%）**，被插行后的块 location 整体 +40 行。⇒ identity 稳、location 必须重算，二者分工明确。

**建议改成什么**：把 `INDEXING-R9R10R13R14.md` §10.1 的「稳定性（编辑后）」一格改成三行：identity / location / anchor，并注明「单 hash 7.9% 重复，必须 composite」。
**撤回条件（我的）**：若实现无法维护 `ordinal_in_section`（整章重排/自动格式化把序号打乱），composite anchor 退化 ⇒ 此时接受「块 hash 只是性能层，锚点仍靠 section+校验」的定性。

**证据**：`data/phase3-objections.json`（`a2dfc347…` D2 段）；`scripts/11_phase3_objections.py#d2_blocks`。

## A-1（攻）外部研究「GraphRAG 610k/query ⇒ 不可行」：结论对，但证据不可比

**被攻主张**（`PROPOSAL-external-research.md#L28` E02、`#L17` R11、`PHASE2-MERGE.md` 相关转述）：
> Legal 数据集（5,081,069 tokens/94 文档）GraphRAG 检索生成 1,399 社区、用 610 个 level-2、每报告约 1,000 tokens ⇒ **610,000 tokens/查询 + 数百次 API 调用**；且「UltraDomain 428 本大学教材…与 Memoria 教材同域」。

**攻击 1：两个子集被拼接。** 610k 是 **Legal 子集**（94 份法律文档）上的 GraphRAG **global** 检索；「同域（教材）」来自 UltraDomain 的**教材子集**。用「教材同域」给「610k」背书，等于把 A 子集的数字贴到 B 子集的场景上。论文没给教材子集的 610k 数。
**攻击 2：量级不可线性外推到我们。** Legal 5.08M tok / 我们 0.607M tok = **8.37×**；GraphRAG 的 community report 数随语料/社区规模变化（Legal 1,399 社区取 610 个）。按语料规模线性外推 ≈ **73k/query**（**这是推算，不是实测**，标注清楚）——比 610k 小一个量级。用 610k 断言「我们的教材 KB 也这样」高估约 8×。
**攻击 3：问题结构不同，机制前提不存在。** 我们的真实问题：单书、**97.5% 的 read_document 落在同一章（ch03）**、19/20 问落 ch03；Legal 是多文档多跳。GraphRAG global 社区报告解决的正是「跨文档多跳」，这个前提在我们这里不成立 → 不是「太贵所以不搬」，而是「**问题不需要全局图，搬了也没有收益**」。
**我们自己的实测对照**（D 方冻结快照 `phase3-session-snapshot.jsonl`，只读复算）：21 轮 / prompt 合计 5,724,271 / 峰值 845,926 / 每轮 prompt **272,584** / 每轮新上下文 **14,390**。⇒ 610k = **2.24× 每轮全 prompt**，但 = **42.4× 每轮新上下文**。所以「610k 一次吃掉约 2.7 轮预算」只在 prompt 口径成立；**它不等于我们每轮的检索成本**，也不该被当成「GraphRAG 在我们场景的成本」。

**建议改成什么**：
1. 把「不搬 GraphRAG」的理由从**成本**改为**机制不匹配**：单书 + 问题集中（97.5% 同章）⇒ 全局社区检索无收益前提；成本论证只适用于跨文档/多跳场景。
2. 凡引用 610k 必须写「Legal 子集 / 94 文档 / 跨文档多跳」；若要说我们的数字，用**我们自己的实测**（每轮新上下文 14.4k）或明确标注「线性推算 ~73k」。
3. 保留「不搬」结论（判断不变），但把 falsifier 写死（见下）。
**撤回条件**：若知识库变成多书/多文档（>2M tok）或真实问题中跨章多跳占比 >30% ⇒ 必须用我们自己的数据重测 GraphRAG/局部子图成本，届时「不搬」结论可能反转。

**证据**：`PROPOSAL-external-research.md#L17,L28,L141`；`data/phase3-coldstart.json` D5 段（`1f04311b…`，本脚本对冻结快照的复算）。
