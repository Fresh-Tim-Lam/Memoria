## 1. 【O-1】放大系数 10.94× —— 我错了，真实是 1.16×

### 1.1 攻击成立：我的算法漏了 compaction 的 shadowed

**我原来的算法**：
```
repeat_cost = Σ_k (tool_delta[k] × (总轮数 - k - 1))
```
**隐含假设**：第 k 轮产生的工具结果会**一直活到会话结束**。

**这个假设错了**：compaction 会 `shadowed` 旧事件（实测 9 次 compaction，最后几次遮蔽 300K+ 字符），**被遮蔽后该结果不再进入后续 prompt**。

**⇒ 正确口径应按【存活轮数】算。**

### 1.2 两种口径的实测结果（同一批工具结果）

**基准**：tool result 单次合计 = **137,075 token**（135 个）

| 口径 | 定义 | 重发额外量 | **放大系数** |
|---|---|---|---|
| **A 剩余轮数**（我原来的）| 活到会话结束 | 1,431,964 tok | **10.45×** |
| **B 存活轮数**（修正后）| 活到第一次被 shadow | 158,606 tok | **1.16×** |
| **差异** | — | **1,273,358 tok（88.9% 被 compaction 消掉）** | **0.111×** |

**⇒ 我的 10.94×（本轮重算是 10.45×）应该修正为 1.16×。差 9 倍。**

### 1.3 逐工具对照（暴露更严重的问题）

| 工具 | n | 单次 tok | 剩余口径系数 | **存活口径系数** |
|---|---|---|---|---|
| grep | 32 | 54,032 | 12.45× | **1.59×** |
| read_document | 50 | 54,599 | 8.19× | **0.67×** |
| validate_kb | 4 | 5,917 | 7.16× | **3.81×** |
| skill | 1 | 1,061 | 19.00× | 3.00× |
| read_kp | 6 | 10,723 | 12.82× | **0.28×** |
| search_kb | 7 | 2,984 | 15.62× | 0.87× |
| outline | 3 | 1,277 | 12.30× | **0.00×** |
| glob | 7 | 919 | 0.26× | **0.00×** |

**⚠️ 存活系数 <1（如 read_document 0.67×、read_kp 0.28×）意味着：这些结果在被 shadow 之前，平均存活不到 1 轮。**
**⇒ 说明它们产生后很快就进了 compaction，几乎没被"重发"过。**

### 1.4 ⭐ 第二重打击：即使放大 10×，也只作用在 24.7% 的费用上

**这是比"系数算错"更根本的问题——我把"token 放大"误当成了"费用放大"。**

**实测费用构成（21 轮，高峰档）**：

```
prompt=5,724,271  hit=5,422,080  miss=302,191  comp=203,009
费用: 命中 0.2169 + 未命中 0.6044 + 输出 1.6241 = 2.4453 元
构成: 输出 66.4% / 未命中 24.7% / 命中 8.9%
```

**关键机制**：命中单价 0.04 元/M vs 未命中 2.00 元/M ⇒ **差 50 倍**。
- 工具结果被重发时，**94.7% 命中缓存**（单价 1/50）
- **⇒ 重发 143 万 token 的费用 ≈ 143万 × 0.04/1e6 ≈ 0.057 元**（占总费用 2.3%）

**⇒ 我原来把"1,431,964 token 的重发"当成了"27.7% 的成本"，实际只有 2.3%。**

### 1.5 O-1 的修正建议

| 项 | 原（我的）| 改成 |
|---|---|---|
| 放大系数 | 10.94× | **1.16×（存活口径）**，且必须标注口径 |
| C7 的 P0 排序 | 工具结果预算是 P0 | **降为 P1** |
| 理由 | "放大 10.94×，是最大杠杆" | **"放大器只作用于未命中那 24.7%，且实际存活放大仅 1.16×"** |

**那么工具结果预算还该不该做？我的新立场：**

```
该做，但理由变了：
  ❌ 原理由：放大 10.94× ⇒ 省 1 tok 省 10 tok（错）
  ✅ 新理由：grep 单次 15,638 tok 会【一次性挤进 prompt】，
            推高峰值（M3），且这一轮必然全量 miss（新内容）
            ⇒ 它伤的是【峰值上下文】和【当轮 miss】，不是"重复计费"
```

**⇒ 工具结果预算的价值是"防峰值"，不是"省重发"。这个价值仍然成立，但杠杆量级小得多。**

### 1.6 撤回条件（O-1）

| 断言 | 什么证据能推翻我这次的修正 |
|---|---|
| 存活口径 1.16× 才是对的 | 若证明被 shadow 的内容仍以某种形式进入 prompt（如 summary 保留了 90% 细节）⇒ 存活系数应上调，需重算 |
| 放大只作用于 24.7% 费用 | 若在**低命中会话**（命中率 <50%）中实证，放大系数的费用杠杆会显著上升 ⇒ 我的"降级"结论只在"高命中场景"成立 |

## 2. 【O-2】C8「省 1 iteration ≈ −20.5%」是算术外推，不是测量

### 2.1 攻击成立：这是缩放现有账单，不是"少一轮的真实成本"

**C8 的 −20.5% 来源**（`PHASE2-MERGE.md#L63`）：
```
轮数×0.75 = −25%
⇒ 省 1 iteration/轮 ≈ 0.41 元 ≈ −20.5%
```

**这是**：把现有账单按"轮数比例"线性缩放。
**这不是**：让 agent 真的少一轮之后实测花了多少。

### 2.2 我确实把算术当成了测量——这是我的错

我在 Phase 1 §7.2 写了：
> 「我无法从本次数据量化'少一轮省多少'——因为不知道理想情况下需要几轮 ⇒ 需要 A/B 实验才能量化」

**但 §1 摘要第 3 条又写**：
> 「真正的杠杆是「工具结果体量 × 10.94 倍重复计费」和「轮次数」」

**⇒ 我一边说"无法量化"，一边把"轮次数"列为杠杆。这是内部矛盾。**

### 2.3 为什么线性外推不成立（两个方向都可能）

**少一轮的净效应取决于"这一轮为什么消失"**：

| 机制 | prompt 变化 | completion 变化 | 净效应 |
|---|---|---|---|
| **A 少做一次工具调用** | −该工具结果 | −该轮 assistant 输出 | **明确为负（省）** |
| **B 靠索引第一轮就答对** | **第一轮可能变长**（索引 tokens 注入） | −后续轮输出 | **不确定** |
| **C 靠索引减少往复** | 首轮 +索引，后续 −N 轮 | −N 轮输出 | 取决于索引大小 vs 轮数 |

**⇒ 机制 B/C 下，省下的可能是负数（索引成本 > 省的轮次成本）。**

### 2.4 能区分 A/B/C 的实验设计（Lead 要求）

```
实验：三臂对照（同一问题集、同一 KB、同一模型）
  Arm-0 基线：现状（无索引）
  Arm-1 索引注入：无索引 + 少量"提示性摘要"（模拟机制 B，但只加 token 不改行为）
      ⇒ 用来测"仅增加索引 token 而不改轮数"的成本
  Arm-2 索引驱动：完整索引（目标是减少轮数）
  
三臂各测：轮次数 / prompt 峰值 / 完成率 / 费用

判读：
  · 若 Arm-1 费用 > Arm-0 且轮数不变 ⇒ 索引本身是纯成本
  · 若 Arm-2 轮数 < Arm-0 且 费用 < Arm-0 ⇒ 机制 A/C 成立，索引净收益为正
  · 若 Arm-2 轮数 < Arm-0 但 费用 > Arm-0 ⇒ 省轮次的收益被索引成本吃掉（机制 B）
  · Arm-1 是关键对照：它把"索引 token 成本"与"索引行为收益"分离
```

**⇒ 没有 Arm-1 这个对照，就无法区分"省了轮数"和"用更大首轮换来更少轮数"。**

### 2.5 C8 的处理建议

**我的明确表态：C8 应从「共识」降级为「候选 KPI」。**

理由：
1. **−20.5% 是算术，不是测量**（无 A/B）
2. **我自己在 Phase 1 就写了"无法量化"**
3. **机制 A/B/C 的净效应方向不确定**

**改成什么**：
```
C8（降级）：候选 KPI —— iterations/answer
  当前状态：**方向性假设**，无实测支撑
  支撑证据：仅"输出占总费用 66.4%"（实测）+ "轮数线性外推 −20.5%"（算术）
  必须先做：三臂 A/B（含 Arm-1 索引成本对照）才能升级为主 KPI
  在此之前：**只用 iterations 作为【观察指标】，不作为【验收阈值】**
```

### 2.6 撤回条件（O-2）

- 若三臂 A/B 实测显示 Arm-2 轮数显著下降且费用显著下降 ⇒ C8 可恢复为主 KPI
- 若实测显示"省 1 轮 ≈ −20%"（线性成立）⇒ 我的"算术≠测量"指控可减轻

### 3.2 攻击一：均值被高命中轮拉高了吗？

| 分组 | n | 加权命中率 | 算术平均 |
|---|---|---|---|
| **大轮（>300K）** | 6 | **95.82%** | 95.60% |
| **小轮（≤300K）** | 15 | **93.26%** | 91.75% |

**⇒ 确实存在"大轮命中率更高"的效应，差 2.56pp。**

**但**：
- **中位数 94.30% ≈ 总量 94.72%** ⇒ 均值没有被极端拉高
- **只有 1/21 轮 <85%**
- **stdev 4.90pp** ⇒ 分布不算离散

**⇒ 判定：攻击部分成立（有 2.56pp 的大小轮差异），但"94.17% 严重误导"不成立。**

**修正表述**：
```
不能说：「命中率 94.17%，没问题」
应该说：「命中率中位 94.30%，但小轮（≤300K）加权只有 93.26%，
        低于大轮 95.82% 共 2.56pp。单轮最低 75.76%。」
        ⇒ 不是"没问题"，是"整体良好，小轮次略差"
```

### 3.3 攻击二：「提升空间只有 5.8%」是否过窄？

**Lead 的质疑完全正确。**

**我的"5.8% 上限"只在「prompt 结构不变」前提下成立。但索引会改变 prompt 结构：**

| 索引带来的变化 | 对命中率的影响 | 方向 |
|---|---|---|
| 首轮注入索引描述 | 首轮变长且**全 miss** | **变差** |
| 索引使后续轮少读整章 | 后续轮 prompt 变短，**前缀更短** | **可能变好**（前缀越短越容易全命中） |
| 索引内容随源变化更新 | 索引本身**变成变动前缀** | **变差**（每次更新都破坏缓存）|
| compaction 时机改变 | 若索引减少了内容，compaction 更少 | **变好**（少一次前缀重写）|

**⇒ 索引对命中率的影响是**双向的**，不能假设"命中率不变"。**

**修正建议**：
```
❌ 原：「不做 提高缓存命中」（已 94.17%，天花板 5.8%）
✅ 改：「**不以"提高命中率"为目标**，但**必须监控索引对命中率的影响**」
     新增指标 M12：索引上线后命中率变化 Δhit（必须 ≥ −5pp）
     理由：索引可能破坏前缀稳定性（每次源变化都改索引 ⇒ 破坏缓存）
```

**⇒ 这是一条**新增的否决条件**：若索引让命中率掉超过 5pp，等于用"省 token"换"缓存失效"，净收益可能为负。**

### 3.4 撤回条件（O-3）

- 若给出"索引不改变前缀稳定性"的机制证明（如索引单独放在 system 末尾且不随内容变）⇒ 我的 M12 可放宽
- 若小轮样本扩大后差异 >5pp ⇒ 我的"整体良好"判断需改
