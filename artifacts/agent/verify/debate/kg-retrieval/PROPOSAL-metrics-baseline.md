## 1. 结论摘要（≤10 行）

1. **R8 的核心不是"设计指标"，是"指标怎么在实验前被冻结、实验后无法被改"。** 本项目已因"达不到就改指标"返工多次（KG 辩论判死"最大分组占比"、撤回"边利用率 15%"）。
2. **实测推翻了一个前提**：缓存命中率 **94.17%**，每轮真正新增只 **5.83%** ⇒ **"提高缓存命中"上限仅 5.8%，不是杠杆**。
3. **真正的杠杆是「工具结果体量 × 10.94 倍重复计费」**：单次工具结果会在后续每轮重发。
4. **最反直觉的实测**：单次最大工具结果是 **`grep` 15,638 tok**，是 `read_document` 单次最大（3,171）的 **4.9 倍** ⇒ **"限制读整章"可能不是首要优化点**。
5. **agent 不是"完全不会用 KP"**：`read_kp` 被真实调用 **6 次**（轮 7/8/9），但 **`aliasing` 被重复读 2 次** ⇒ A/B 基线要按「6 次/19 轮」记，**不能假设 0**。
6. **「答对率不能降」必须是**不可协商的硬约束**，且判分必须是**机器可判 + 人工抽检双轨**（纯人工不可复跑，纯机器易被过拟合）。
7. **我否决「用总 prompt tokens 作唯一指标」**（三条数据理由），改用三元组。
8. **我否决「用各轮算术平均命中率」**（92.47%），统一用**总量命中率 94.17%**（反映真实成本）。
9. **指标冻结机制**：预登记 JSON + 哈希 + 三方签署，改动即 `baseline_mutation` 事件并重开实验。
10. **我明确不做**：声称"A 方案省 X%"（本轮无对照）、用合成语料、样本 <30 的百分比断言。

## 2. R8 专章：怎么证明「索引驱动检索」真正提升 agent

### 2.1 先把问题问准（这是我最想纠正的一点）

**错误问法**：「索引驱动检索能不能省 token？」
**为什么错**：省 token 不等于有用。可以省 90% token 但答错。

**正确问法（三条，缺一不可）**：
```
Q-R8-1 在【答对率不降】的前提下，能否把【单轮 prompt 峰值】与【轮次数】压下来？
Q-R8-2 若答对率下降，下降多少？在哪些题型上下降？
Q-R8-3 省下的 token 是否与"答对率持平"来自同一个机制？（防"省 token 靠少读，答对靠多读"的自相矛盾）
```

**⇒ R8 的验收是一个【约束优化问题】：**
```
minimize (峰值 prompt, 轮次数, 单次工具结果 max)
subject to  答对率 ≥ 基线 - 允许下降量
```
**「答对率不能降」是约束，不是目标。任何以"答对率下降"换"token 下降"的方案直接判负。**

### 2.6 统计力（这是我最该诚实的地方，**已实测计算，不是估计**）

**用两比例检验公式实算（α=0.05 双侧，power=0.8，基线 90%）：**

| 要检测的差异 | 每组所需 n |
|---|---|
| 5pp（90% vs 85%）| **683** |
| 10pp（90% vs 80%）| **197** |
| 20pp（90% vs 70%）| **59** |
| **n=30 时能检测的最小差异** | **≈30pp** |

**⇒ 我必须如实说：n=30 的问题集，连 20pp 的差异都测不出（只能检测 30pp）。**

**更糟的是非劣性检验（我想证明"没差太多"）**：

| n/组 | 差的标准误 | **能守住的非劣界** | 能否守 10pp |
|---|---|---|---|
| **30** | 7.75pp | **21.7pp** | ❌ |
| 50 | 6.00pp | 16.8pp | ❌ |
| 100 | 4.24pp | 11.9pp | ❌ |
| **200** | 3.00pp | **8.4pp** | ✅ |

**⇒ 要证明「答对率下降不超过 10pp」，最小需要 n=200/组（共 400 题）。**

**我要求的补救（修正后，三条）**：
1. **承认现实**：n=30 的实验，**只能做"证伪"（抓重大退化 ≥30pp），不能做"证明"（证明无退化）**
2. **分级验收**：
   - **n=30（最小可行）**：只能判 `F-1/F-2` 中"灾难性退化"（≥30pp）
   - **n≥200（推荐）**：才可判 10pp 非劣性
3. **报告必须给置信区间，不给单一百分比**

**⇒ 我的诚实结论（修正后更严厉）**：
> **n=30 时这个实验的"证伪能力"也有限（只能抓 30pp），"证明能力"几乎没有。**
> **若人要求实质证明"答对率不降"，n 必须 ≥200。**
> **若只给 n=30，则 R8 只能作为"冒烟测试"，不能作为"索引驱动有效"的验收依据。**

**这就是我为什么在 §2.5 把 M1 阈值写成"非劣性"而不是"必须更好"** —— 承认现实比假装严谨有用。

### 2.7 证伪条件（写死在实验前）

**实验开始前，写死以下"失败即回滚"条件：**

```
【n=30 档（最小可行，只能做冒烟测试）】
F-1  A' 答对率 < A − 30pp              ⇒ 回滚（这是 n=30 唯一能可靠抓到的退化幅度）
F-2  A' 编造率 > A + 20pp              ⇒ 回滚（安全优先，立即）
F-3  A' 召回 < A − 10pp                ⇒ 回滚（检索质量退化）
F-4  A' 峰值 prompt > A 峰值            ⇒ 回滚（"优化后更爆"）
F-5  A' 轮次数 > A 轮次数               ⇒ 回滚（"更省"变成"更啰嗦"）
F-6  A' 费用 > A 费用                  ⇒ 回滚（不管 token 怎么变，钱不能变多）

【n≥200 档（可做实质验收，额外可判）】
F-7  A' 答对率 < A − 10pp（非劣性界）   ⇒ 回滚（这才是有统计意义的判据）
```

**⚠️ 我特意把 F-6 放在最后并写成"费用"**：因为 token 与费用的关系在**缓存命中 94%**的情况下是扭曲的——省了 1 万未命中 token 比省 10 万命中 token 更值钱。**只看 token 可能得出错误结论。**

## 3. 逐 R1–R8 回答（我的视角：可测性）

### R1 索引单元：最小可用单元是什么？

**我的立场：不表态选哪种，但要求「单元必须可机判边界」。**

| 候选 | 可测性 | 我的判据 |
|---|---|---|
| KP（现有 id+range）| ✅ 已有 `start_line/end_line`，可机判 | **首选**：已有锚点，无需新数据 |
| 段落 | ⚠️ 段落边界需 parser 判定 | 需证明 parser 稳定 |
| chunk（固定 token 窗口）| ✅ 易于机判 | 但**破坏语义边界**，对 T2 跨节任务不利 |
| 小节（heading）| ✅ `scan_headings` 已有 | 粒度可能过大 |

**我的硬要求**：**任何索引单元必须能回答「这个单元的 token 数是多少」**（否则 M6/M7 无法计算）。
`ev:file:src/memoria/services/agent/section_index.py`（24.5 KB，已有 `estimate_tokens`）

### R2 description 的可判性

**我的立场：这是 R8 之外最需要可测的地方，且它有一个漂亮的可测形式。**

**可判据（我提出的）**：
```
description 的可判性 = 让 agent 只读 description、不读原文，能否正确回答
  「这个问题需要读这个单元吗？」（是/否）
⇒ 这是一个【二分类任务】，可机判（用预登记的"该读/不该读"标注集）
指标：description 判别准确率（Description Sufficiency Rate, DSR）
```

**⚠️ 关键**：这个指标**可以离线测，不需要跑完整 agent** ⇒ **成本极低**。
**⇒ 我建议 R2 的验收就用 DSR，样本 ≥50 个（单元 × 问题）对。**

### R3 证据绑定与失效

**我的立场：必须绑定 `source_sha256`（块级，不是全库）。**

**可测判据**：
```
失效检测的【漏检率】= 源已变但索引未标 stale 的单元数 / 源变动的单元数
失效检测的【误报率】= 源未变但被标 stale 的单元数 / 未变单元数
目标：漏检率 = 0（安全优先），误报率 ≤ 5%
```
**测试方法**：构造 N 个单元，改动其中 k 个，看 stale 标记是否精确 —— **可机判，可复跑**。

### R4 锚点稳定性

**我的立场：这是可测的，且有一个现成的失败模式要抓。**

```
锚点稳定性指标 = 在同一文件内，做 m 次随机编辑后，
  未受影响单元的锚点保持正确的比例
目标：100%（未编辑的单元锚点绝不能漂）
```
**可机判**：给定"编辑哪一行"，未受影响单元的行号应平移相同量。

### R5 检索路径与预算

**我的立场：预算必须可测，且要给"索引本身的成本"单独记账。**

```
索引开销比 = (索引自身占用的 token) / (索引带来的 prompt 节省)
若 > 0.5 ⇒ 索引太贵，不值得
```
**现状参照**：tools schema 4,998 token / 峰值 prompt 656,818 = **0.76%**（很便宜）
**⇒ 索引若 ≤ 峰值 5%（≈33,000 token）都可接受。**

### R6 与现有检索栈融合

**我的立场：必须证明"不重复造能力"，判据是"两个通道的相关性"。**

```

```
**可机判**：对同一问题集，分别用两通道取 top-k，算集合交并比。

## 4. 我【否决】的方案（至少 1 个，我给 3 个）

### 4.1 ❌ 否决：用「总 prompt tokens」作为唯一优化指标

**三条数据理由**：

1. **94.17% 是重复发送的缓存命中内容** —— 压低总数最直接方式是"少轮次"，但这不是该指标能指导的
2. **会被"更啰嗦的回答"反向激励** —— 若优化后 completion +50%，prompt 不变但总费用上升
3. **掩盖真正杠杆** —— 单次工具结果 108,995 tok 只占总量 2.5%，但 **×10.94 放大 = 1,191,874 tok（27.7%）**

**⇒ 替代：三元组 `(轮次数, 单次工具结果 max, 答对率)`。**

### 4.2 ❌ 否决：用「各轮算术平均命中率」（92.47%）

**理由**：算术平均把"0 命中但 prompt 很小"的轮次等权放大。
**实测**：总量 94.17% vs 算术 92.47%，**差 1.70pp**。
**⇒ 只有总量口径反映真实成本。这是 Lead 要求统一的口径，我确认：用 94.17%。**

### 4.3 ❌ 否决：用「本会话内 A/B 对比」代替「跨会话 A/B」

**理由**：单会话内有**天然的顺序效应**（后跑的臂受益于已建立的缓存/KP 缓存）。
**证据**：本会话前缀稳定占比中位 **91.19%**，18/18 轮完全稳定 ⇒ **同会话第二臂会白捡第一臂的缓存红利**。
**⇒ 必须每臂开新会话。**

## 8. 一句话总结

> **R8 不是"选几个指标"，而是"建立一个实验前冻结、实验后无法改的判据装置"。**
> **实测给出的三个硬事实**：缓存命中已 94.17%（不是杠杆）、工具结果放大 10.94×（才是杠杆）、grep 是最大单次消耗（不是 read_document）。
> **"答对率不能降"必须是不可协商的硬约束，但判据的严格程度受样本量限制。**
> **我实算过**：n=30 只够抓出 **30pp** 的退化；要守住 10pp 非劣界需要 **n=200/组**。
> **诚实的结论是：n=30 的实验只能当冒烟测试，不能作为"索引驱动有效"的验收依据。**
