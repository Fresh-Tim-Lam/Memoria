## 0. 先给结论（一句话）

**重切边界本身是确定性工作 = 0 LLM token / 0 元（脚本级 <1 分钟）；真正要花 token 的是"顺手写 description"，一本书 ≈ 1.33–1.45 元（高峰）/ 0.66–0.72 元（空闲，405 个可描述切片）。**
**但重切会把三个东西一起改掉：L1 的"清单内容"、`read_kp` 的"返回体积"、`read_document` 的"知识点清单语义"——这三处不跟着改，重切后检索路径会违反现有预算（`read_kp` 今天就能返回 7,711 tok，已超 L2 4,000 上限）。**

## 1. 问题：重切后，检索路径要付什么代价？

**统一事实**（复跑数据 `q1-agent-cost.json`，14 章 / 606,720 tok / 374 个 section）：

```
全书正文             606,720 tok（14 章；≈608,157 tok，与 coverage.json 差 0.2%）
section（标题边界）   374 个（全书骨架 ≈ 374×6 = 2,244 tok，与设计文档 2,227 tok 一致）
切片（section + >3000 tok 再拆）  估算 477 片（其中 前言/目录 71 片、附录 1 片属 nav，可描述切片 ≈ 405）
每章切片 p50 30 片；最大单章 68 片（第 8 章 120,633 tok）
```

### 选项 A：只重算 `end`（保守，KP/切片数不变）

| 检索侧代价 | 数字 | 结论 |
|---|---|---|
| `read_kp` 返回体积 | 教材角色 p50 **726 → 1,265 tok（+74.2%）**、p90 **3,972 → 5,336 tok（+34.3%）** | **p90 直接超过 L2 4,000 tok 上限** ⇒ `read_kp` 必须加 span cap/cursor，否则预算被自身工具突破 |
| L1（单文件索引 ≤800） | KP 数不变（358），清单 token 不变 | **预算不用改**，但 L1 仍是"粗 KP 清单"（不解决找不到切片的问题） |
| L2（候选切片 ≤4,000） | 无切片可给；只能给"更长的 KP" | **不解决"KP 太粗"**；最坏情况：单次读变大 → 峰值更难压 |
| `read_document` 知识点清单 | 行号变化，行数不变 | 语义不变 |

### 选项 B：全面重切 + 迁移 `kp_id`（激进）

| 检索侧代价 | 数字 | 结论 |
|---|---|---|
| `read_kp` 语义 | 切片替代 KP ⇒ 单次返回 ≤3,000 tok（符合 L2） | 预算自动满足，但**一个概念可能跨 1–3 片 ⇒ read_kp 调用次数上升**（每次调用=1 个 iteration 的成本，见 §1.1） |
| L1（单文件索引） | 单文件切片 最大 68 片：紧凑行（6 tok/片）= **408 tok** ✓ <800；完整行（行号+id+name≈15 tok/片）= **1,020 tok** ✗ >800 | **L1 必须改成"section 骨架 + top-k 切片"或加 cursor**，不能整列切片 |
| `read_document` 知识点清单 | 358 → 477 行（全书），单文件最多 68 行 | 输出契约变化（行数↑），且清单可能超 L1 800 预算 |
| 引用/历史锚 | 旧 `kp_id` 全部失效（A 方已算：1,590 KP 迁移 / 276 links / 22 cards） | agent 历史会话里的 anchors、`history.py` 的 `(file,line,kp_id)` 去重、外部引用都断 ⇒ **检索侧需兼容层/墓碑映射**，否则旧会话引用变成悬空 |

### 选项 C：不动 KP，另建切片视图层（推荐，与 R2 已裁一致）

| 检索侧代价 | 数字 | 结论 |
|---|---|---|
| L0（≤300 tok） | 文件数/章节数不变；`kb_overview` 的"知识点合计"仍显示 358（KP 不变） | **不改** |
| L1（≤800 tok） | 建议 L1 = **section 骨架**（全书 374 条/2,244 tok、单章最大 70 条/420 tok ✓），切片不进 L1 全量清单 | **预算不变，内容改为 section 级**（新增 0 成本；`outline` 已有同类能力） |
| L2（≤4,000 tok） | 切片作为候选，单次读取走 `section/snippet/read_document`；切片条目必须带 `kp_ids[]` + `anchor_verified` | **预算不变**；只需新增"按 slice_id 读"入口（或给 section/snippet 增加 slice 参数） |
| `read_kp` 语义 | **不变**（KP range 一字不动） | **零兼容成本**；但 `read_kp` 现状 max 18,198 字 = **7,711 tok > L2 4,000** 的违规仍然存在（与重切无关，需单独加 cap） |
| descriptions 挂载 | 挂在 **slice** 上（KP 不变） | L1 不列 description（68 片×48 tok=3,264 > 800）⇒ description 只能经检索结果/候选返回 |

**⇒ 检索路径的最小改动集合（按选项）**

| 改动项 | A 只改 end | B 全面重切 | C 视图层 |
|---|---|---|---|
| L0 预算 | 不改 | 不改（计数显示变） | 不改 |
| L1 内容 | 不改 | **改**（切片 compact 清单 + cursor） | **改**（section 骨架；切片不进 L1 全量） |
| L2 预算/读取入口 | `read_kp` 加 cap（必须） | 新 KP 自动 ≤3,000，但需 slice→KP 映射 | **新增 slice 读取入口**；`read_kp` 不改 |
| `read_kp` 语义 | 体积 +74%（p50），需 offset/limit | id 全换 + 跨片读 | **不变** |
| 引用/历史锚兼容 | 不变 | **需要墓碑/映射层** | 不变 |
| 新增工作量（检索侧，估算） | 0.5 人日（cap+cursor） | 1.5–2 人日（L1 改造 + 兼容层） | **0.5–1 人日**（slice 读取入口 + anchor_verified 透传） |

### 1.1 一个关键取舍：切片会不会让"往返"变多？

- 现状：`read_kp` 平均 **1,787 tok/次**（21 轮冻结快照 10,723/6），`read_document` 平均 **1,092 tok/次**（54,599/50）；
- 切到 405 片后（均 608,157/405 ≈ **1,502 tok/片**）⇒ 单次读约 1.5k tok（更接近 L2 预算且更贴题），但**一个概念若跨 2 片，就要 2 次工具调用 = 2 个 iteration**；
- 对 C 的 KPI（iters/answer）这是**双刃**：切片让每次读更准（少读无关正文），但可能增加调用次数。**检索侧的对策**：切片结果一次返回 **top-k 相邻片**（同一 section 的连续片合并返回，上限 L2 4,000 tok），把"跨片"在工具层合并，而不是让模型多次调用。这一条必须写进实现契约，否则切片会把省下的 token 换成多出来的往返。

## 2. 重切一次的 token 成本（0.4237 tok/字）

### 2.1 成本拆解（确定性 vs LLM）

| 工作 | 是否用 LLM | token 成本 | 钱（高峰 / 空闲） | 时间（估算） |
|---|---|---|---|---|
| 重算 range / 切 section / 切块 / hash / 映射 | **否**（脚本） | **0 LLM token** | **0 / 0 元** | 块级 hash 全库 **88.42ms**（59 md/30,986 块；`u2-block-hash-bench.json`）+ range 重算 <1s ⇒ **<1 分钟** |
| 校验（anchor gate / inverted / span 检查） | 否（脚本） | 0 | 0 | 秒级 |
| **顺手写 description**（405 个可描述切片，nav 的 72 片不写） | 是 | 输入 = 正文 606,720 tok（读一遍）；输出 = 405×34 = **13,770 tok**；+ 调用开销 | **1.33 元 / 0.66 元**（按章批量）；**1.45 / 0.72 元**（按片调用） | 按章 14 次调用 ≈ 5–10 分钟；按片 405 次 ≈ 14–27 分钟 |
| 只写"骨架"（374 section 标题） | 否 | 0（标题已存在） | 0 | 秒级 |

> **口径**：input 按未命中价（首次读）；output 34 tok/片 = 80 汉字×0.4237；调用开销按经验估计（按片 150 tok/次、按章 150 tok/次）。若 description 走多次重试/校验，成本按比例上浮。

**⇒ 回答"重切一次花多少"：**
- **若重切只做确定性切分（A/C 选项的必需部分）：0 token、0 元、<1 分钟。**
- **若重切时顺手把 description 也写了：一本书 ≈ 1.33 元（高峰）/0.66 元（空闲），5–27 分钟**（405 个可描述切片；nav 切片不写）。
- 这两种的成本差 **~2 个数量级**，所以**不要把"重切"和"写 description"捆成一个决策**（R7.1 拍"重切"时不必顺带拍 description；后者属 R7.4 的 C2 深化成本）。

## 3. 我的推荐（C 角度）

**推荐 = A（止血：只修坏事 end/反转/span=0）→ C（切片视图层），B 只作为"将来必须换 id"时的迁移候选。**

理由（只列检索侧的）：
1. **C 的检索侧改动最小且可回滚**：L0/L1/L2 预算一个都不用改，`read_kp` 语义零变化；只需新增"按 slice_id 读/按 section 合并 top-k"的入口（0.5–1 人日）。
2. **B 的检索侧代价不止迁移**：L1 要改成切片清单（单文件最多 1,020 tok > 800 需 cursor）、`read_document` 清单行数 ×1.33、历史会话 anchors 悬空需兼容层；**这些和 A 方算的 3–5 人日叠加**，且一旦错映射是静默错位。
3. **A 不是终局但必须做**：不修 end/反转，C 的切片会继承坏边界；而 A 的检索副作用（`read_kp` +74% 体积、p90 超 L2）**必须用 cap 抵消**——这个 cap 无论选哪个选项都要做（现状 max 7,711 tok 已超 L2）。
4. **成本上 A/C 的"重切"本身 0 token**；把 description 留给 R7.4 的 C2 lazy 深化（按章、按需，成本 1.33 元/全书上限，实际只深化被命中的章 ⇒ 首章约 0.1–0.3 元级）。

**一句话给 Lead**：**重切边界本身不贵（0 token，<1 分钟）；贵的是配套的 description 和"让检索路径跟着变"的改造。选 C：预算零改动、`read_kp` 零改动、检索侧 0.5–1 人日；选 B：检索侧再加 1.5–2 人日且引入历史锚兼容层。**

## 4. 若错了会怎样（每选项的失败信号与补救）

| 选项 | 失败信号（可观测） | 补救 | 用户数据影响 |
|---|---|---|---|
| **A** | `read_kp` 返回 token p50 726→1,265、p90 3,972→5,336；峰值 prompt 继续上升；"KP 太粗"问题仍在（69% >1200 字） | 停下即可；range 可回滚（A 方：整批撤销 txid）；`read_kp` cap 保留 | 无 |
| **B** | 旧会话 `kp_id` 悬空数 >0（可机检 history anchors）；L1 单文件清单超 800 需 cursor；外部引用失效 | 需墓碑映射 + 旧快照整体回滚（A 方：3–5 人日，期间新复习记录会丢） | **有**（id 全换、图谱节点重建） |
| **C** | L1 是否被切片塞爆（机检：单文件清单 ≤800 ✓ 因 L1=section）；`kp_ids[]` 孤儿率>20%（corpus 方阈值）；两套边界长期并存 | **删 `slices[]` 字段即零损失回滚**（A 方实测） | 无 |
| **不做** | `read_kp` max 7,711 tok 持续 > L2 4,000（现状已违规）；粗 KP 继续把"读一次=读半章"带入 agent 上下文 | 至少先做 `read_kp` cap（0.5 人日） | 无 |
