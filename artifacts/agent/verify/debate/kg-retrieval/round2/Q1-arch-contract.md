## 1. 三个选项（Lead 指定）

### 选项① 只重算 `end` 边界、不动 `start`（保守）

**做法**：保留每个 KP 的 `start`（及其 `kp_id`），只把 `end` 重算为"下一同级标题前"或"1200 字预算截断"。

| 维度 | 内容 |
|---|---|
| **迁移步骤** | 1. 对每个侧车逐 KP 跑"新 end 算法"→ 得到 `new_end`<br>2. 与旧 `end` 比对，只写有变化的<br>3. 同一事务内更新 sidecar（复用 `document.py#L373-L473` 已有的"保存后重锚"管线） |
| **失败回滚** | **最简单**：`start` 与 `kp_id` 不变 ⇒ 只需**旧 `end` 快照**即可逐 KP 回滚。已有 `.memoria/backups/**` 事务机制（`ev:file:src/memoria/services/agent/backup.py`）。**回滚 = 整批撤销一个 txid** |
| **用户可感知变化** | ① **KP 变长**（end 后移到下一标题）⇒ `read_kp` 单次返回 token 上升；② 图谱里 KP 节点**覆盖范围变大**（`contain` 关系派生受影响）；③ **`kp_id` 不变 ⇒ FSRS/卡片/链接全不动** |
| **工作量** | **可脚本 100%**（1590/1590 有 hint）。代码改动：1 个 end 重算函数 + 1 个迁移脚本。**估算 0.5–1 人日** |
| **主要风险** | ⚠️ **治标不治本**：语料方实测 **69.0% 教材 KP >1200 字**，只改 end 会让 KP **更长**，不解决"KP 太粗"。且 `start` 若本身错（93.3% 是标题行 ⇒ start 大体对）则无法修 |

---

### 选项② 全面重切 + 迁移 `kp_id`（激进）

**做法**：按新粒度（如 1200 字预算 / 标题层级）重新切分，**重算 `kp_id`**，并把用户数据迁到新 id。

| 维度 | 内容 |
|---|---|
| **迁移步骤** | 1. 全量重切 → 新 KP 集合（新 id）<br>2. **建立 old_id → new_id 映射表**（按 start 行区间重叠度）<br>3. 改 `cards.json` 的 **22** 个 `kp_id`<br>4. 重映射 sidecar `links[]` 的 **276** 条<br>5. 消歧 **1** 个重名 id<br>6. 重写 `progress.json`？**不需要**（绑 card_id）<br>7. 生成旧 id 的**墓碑表**（供外部引用兜底） |
| **失败回滚** | **最复杂**：需要 **3 份**快照（旧 sidecar / 旧 cards.json / 旧 links）+ 映射表。回滚必须**整体原子**：任一环节失败 ⇒ 全部回退。**风险点**：若回滚时用户已在新 id 上产生新复习记录 ⇒ **新数据会丢**。⇒ 必须"迁移时锁定写入"（建库期间禁写） |
| **用户可感知变化** | ① **`kp_id` 全变** ⇒ 外部引用（笔记里的 `[[kp_id]]`、agent 历史会话里提到的 id）**全部失效**；② 卡片仍在但指向新 id（用户无感）；③ **图谱节点全换** ⇒ 用户熟悉的"节点"消失重建；④ 复习进度保留（绑 card_id）但"这周该复习哪些"的**内容可能变**（id 变了，卡对应的正文范围变了） |
| **工作量** | **重切（可脚本）+ 映射（可脚本 90%，因 1590/1590 有 hint）+ 1 个重名人工 + 回滚机制（需新建）**。**估算 3–5 人日**（含回滚机制） |
| **主要风险** | ⚠️ **不可逆的用户可见变化**：用户学了半年的 `kp_id` 全部作废。**且 276 条链接 + 22 张卡要全部正确映射**，错一条就是静默错位 |

---

### 选项③ 不动现有 KP，另建切片视图层（最保守，与 R2 已裁一致）

**做法**：现有 KP（id + range）**一字不改**；另建"切片"作为**独立层**（`slices[]`），带自己的 id 与 range，KP 通过**映射表**关联到 0..N 个切片。

| 维度 | 内容 |
|---|---|
| **迁移步骤** | 1. **零迁移**：不动任何现有数据<br>2. 新增 sidecar 字段 `slices[]`（schema 增量，非破坏）<br>3. 新增 `kp_id ↔ slice_id` 映射（1:N）<br>4. agent 检索读切片，用户图谱仍读 KP |
| **失败回滚** | **最简单且最安全**：`slices[]` 是**纯增量字段** ⇒ **回滚 = 删掉该字段**，现有 KP / FSRS / links / 图谱**从未被碰过**。**无损回滚** |
| **用户可感知变化** | **零**（用户图谱、复习、链接全部照旧）。agent 侧读到更细的切片（这是**收益**不是变化） |
| **工作量** | 新增 schema + 切分器 + 映射 + 检索接入。**估算 1.5–2.5 人日**（切分算法本身 corpus-analyst 已实测过） |
| **主要风险** | ⚠️ **两套边界并存**：长期存在"KP range 与 slice range 不一致"的认知负担；必须有一天收敛（否则永久双轨）。且若将来要改 KP 粒度仍要回到选项② |

| **`kp_id` 变化** | **0** | **1,590** | **0** |
| **FSRS 进度丢失** | 0 | 0（绑 card_id） | 0 |

## 3. 我的推荐：**选项③ 先做，选项② 永久否决，选项① 仅作过渡**

### 理由（按重要性）

1. **回滚成本差 5 倍以上，而用户可感知变化差 0 vs 全变**。
   选项② 要动的 276 条链接 + 22 张卡，每一条错映射都是**静默错位**（我在 Phase 1 已实测
   37% snippet 歧义 + 18.8% 静默钉错，说明这套锚点体系的容错能力本来就弱）。
   **在一个已知不稳的锚点体系上做 1,590 个 id 的迁移，失败面太大。**

2. **选项③ 的"双轨并存"代价是可控的**，因为它可以**用数据回答何时收敛**：
   若切片层上线后，agent 检索的答对率/往返次数达标 ⇒ 再考虑把 KP 对齐到切片（那时是**有证据的迁移**）；
   若不达标 ⇒ 删字段即可，**零损失**。**选项③ 本质是一个"带免费回滚的大实验"**。

3. **选项① 唯一的价值是"止血"**：语料方现场事故（range 反转 span=0）需要立刻修。
   但选项① **不解决**"69% KP >1200 字"，所以它只能是**过渡**，不能当终局。

### 推荐路线（分两步，可单独拍板）

```
第 1 步（立即，0.5–1 人日）：选项① —— 只修坏事（span=0 / end 反转），让现状不再恶化
第 2 步（Q1 通过后，1.5–2.5 人日）：选项③ —— 加切片视图层，KP 一字不动
永久否决：选项② —— 除非将来有"必须换 id"的硬理由（例如 KP 粒度模型根本性改变）
```

## 4. 若错了会怎样（每个选项的失败后果）

| 选项 | 若我推荐错了（选了③但不对） | 补救 |
|---|---|---|
| **①** | 停下来看到 KP 变长、token 上升，但**数据无损** | 整批撤销 txid，回到原状 |
| **②** | **用户半年学习数据里的 id 全废**，且 276 条链接若有错映射 ⇒ 静默错位 | 只能靠"墓碑表 + 旧快照"回滚，**但期间新产生的复习记录会丢**。**这是唯一有不可逆风险的选项** |
| **③** | 两套边界长期并存，团队认知负担上升；若一直不收敛 ⇔ 永久双轨 | 删 `slices[]` 字段 ⇒ **零损失**回滚 |

**⇒ 选项③ 的"错了会怎样"是唯一一个"无损失"的答案。这是它作为首选的决定性理由。**
