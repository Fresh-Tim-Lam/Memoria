## 4. Q4 link 类型 vs edge 类型：一个枚举还是两个

### 代码事实
```
ev:file:src/memoria/graph/edge_types.py#L3
   「sidecar links[].edge_type / edges[].type：唯一权威来源」  ⇒ 现在是【同一个】
```

### 各方主张
**A**：**该拆，但不是「两个枚举」，是「两个字段」**
```
link.type  = 链接语义（为什么这段文字能跳过去）
edge.type  = 图谱语义（这两个知识点是什么关系）
硬证据：EDGE_TYPES 3 种 vs PLAN_EDGE_TYPES 2 种 ⇒ 同一个枚举的两端【已经不对称】
但 0.5 不拆：数据为 0 时拆字段收益无法验证；先修"枚举不对称"这个可立刻修的契约债
```

**B**：从「用户点一下想要什么」角度 —— link 是「跳转」，不承诺语义，**不该进语义边集**。

**C**：**分开有意义，但类型属于 edge，不属于 link**
```
link = 正文锚点（带 instances 行号）
edge = 语义关系（纯边无行号；link 投影时才有）
现在 links[].edge_type 是【同一语义的第二事实源】
且两套归一化器允许集合不同：contain 在 link 上被静默改写成 reference
```

**D**：给了「分开是对的」怎么测：
```
M-08 映射保真度 = link 有类型声明时生成 edge 类型一致的比例    <95% ⇒ 分开有信息丢失
M-09 反向覆盖率 = edge 类型能在 link 层找到对应声明的比例      某类型 100% 无 link 来源 ⇒ 需单独论证
```

### 并集结论
```
✅ 多根共识（A/B/C 三独立根 + D 的判据）：
   · 现在 Link 与 edge 共用一套枚举是【设计缺陷】，不是"要不要解耦"（A: 代码已解耦；C: 第二事实源）
   · 类型在语义上属于 edge，不属于 link（B、C）
   · 两端枚举已不对称，这是缺陷的显式证据（A 实测）
🔴 待裁（C4）：
   0.5 该【只文档化 link.type ⊂ edge.type】+ 断言测试（A）
   还是【agent 面去掉 edge_type 参数 + 统一归一化器】（C）
   还是【两者都做】（并集自然结果，但需裁决）
```
