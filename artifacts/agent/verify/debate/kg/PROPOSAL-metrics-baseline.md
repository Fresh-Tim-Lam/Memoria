## 1. 立场摘要（≤10 行）

1. **人问的"边该不该存在 / 类型是否等于链接类型"是设计问题；但设计问题必须先变成"能红能绿"的判据，否则辩论会退化为审美投票。**
2. **现有指标（叶子率、平均度、最大分组占比、reference 占比）全部只测"动作发生了"，一个都没测"动作有用"。**
3. **"边有没有用"当前**在实现层面不可测**——不是没人想到，是 `nodeClick` 事件存在但零埋点（`app.js:1438→1451`，无任何统计消费）。这是本次最大发现，也是我要给的第一优先级修复项。**
4. **"边的存在性"不能靠"看起来该有/不该有"判**，只能靠**两条可证伪判据**：可达性增益（去掉这条边，是否存在原本可达的路径变成不可达）+ 决策命中（这条边是否被用于一次成功导航）。
5. **边类型空间不该在"上线后看数据再撤"**，必须**上线前可判定**：我给一个「类型准入三闸」机制，任一闸不过就不加。
6. **task-86 的 `最大分组占比 99.2% → <40%` 是自欺指标**：它测"分组算法改了"，完全没测"用户导航成功了"。它作为**前置必要条件**有效，作为**验收充分条件**无效。
7. **叶子率上升也不必然意味着图变好**——它可能是"边被误删"的假象。必须配「可达性不下降」的守卫指标。
8. **辩论本身也要有可测验收**：我给出「提案质量机检 + 独立性机检 + 裁决溯源机检」三组检查。
9. **我明确不做**：主观"图好不好看"评分、无埋点的"用户满意度"问卷、样本量不足时的百分比断言。
10. **我的判据整体可被证伪**：若某个指标我给了阈值但拿不出数据源，我承认那是空指标（见 §7 自检）。

## 3. ⭐ Q2 专节【边界（边）价值怎么测】—— 当前最大盲区

### 3.1 先说清楚：为什么现在测不了

**我实测确认了"边有没有用"的完整链路，以及它在哪断了：**

| 环节 | 是否存在 | 证据 |

| 图节点可点击 | ✅ | `graph-view-2d.js:521` `this.engine._emit("nodeClick", {...})`；3D 同 `graph-view-3d.js:998` |
| 点击有消费者 | ✅ | `app.js:1438` `const onGraphNodeClick = ({ node }) => {...}` |

**⇒ 任何"边有没有用"的主张，在加埋点前**都只能靠主观判断，不构成 E1 证据**。**

### 3.3 ⭐「边的存在性」怎么测（两条可证伪判据）

**判据一：可达性增益（纯数据，M 类，不需要埋点）**

对每条边 `e = (u, v)`：
```
gain(e) = |{ w : reachable(u→w) in G }| - |{ w : reachable(u→w) in G \ {e} }|
```
- `gain > 0` ⇒ 该边**承担了不可替代的可达性** ⇒ 有存在理由
- `gain = 0` ⇒ 冗余（有其它路径）
- **可证伪形式**：「我们认为边 e 可删」= 断言 `gain(e) = 0` **且** 无导航命中。**只要找到一次通过 e 的成功导航，该断言即被证伪。**

**判据二：决策命中（需埋点，I 类）**

`e` 是否在任一次成功导航中被走过。**这是"边的价值"的直接证据，不是代理。**

**⚠️ 我要明确反对一种常见误判**：
> 「`gain=0` 就可以删」

**不对。** `gain=0` 只说明"有其它路径"，不说明"那条路径对用户同样有意义"。例如 454 条 reference 边中大部分 `gain=0`（因为词条之间已经通过中心词连通），但删掉后**直接链接消失**，用户需要多点 2 跳。**所以判据一必须配一个"路径长度增幅"守卫**：

```
cost(e) = 删除 e 后，原本最短路经过 e 的 (u,w) 对，其最短路长度的平均增量
```
- `gain=0 且 cost(e)=0` ⇒ 真冗余（可删）
- `gain=0 但 cost(e)>0` ⇒ **不冗余**（删了会绕路）

**⇒ 完整判据：`gain(e)=0` **且** `cost(e)=0` **且** 零导航命中 ⇒ 可删（三重条件，任一不满足即保留）。**

### 3.4 边爆炸如何量化（对现有指标的评价）

**现有 5 个指标我都保留，但要标注各自测什么、不测什么：**

| 指标 | 当前值（AAA_Vocab）| 测的是什么 | **不测什么** |
|---|---|---|---|

### 3.5 「边的价值」的**反直觉**判据（我认为辩论应正视）

**最强的"边有用"证据不是"边多"，而是：**
> **删掉这条边，用户/agent 的导航成功率下降。**

这是**因果**判据，可用 A/B 实测：同一批导航任务，在"含该边"与"不含该边"两个图版本下跑。**这需要埋点 + 可复跑的导航任务集。**

## 4. ⭐ Q3 专节【上线前可判定的"不该加这个类型"机制】

### 4.1 问题重述

现状：**479/479 reference**（phase2/3 实测；AAA_Vocab 454/454）。
痛点：加了个类型，上线后发现 100% 落默认值，然后撤 —— **这是"上线后看数据再撤"的滑坡。**

**要做的是：上线前就能判定。**

### 4.2 我设计的【类型准入三闸】

**新增一个 edge 类型 `T` 前，必须通过三闸。任一不过 ⇒ 不加（记为 `not_doing` + 理由）。**

#### 闸 1：**区分度闸**（上线前，纯数据可算）

```
distinction(T) = 在候选数据集中，能被打上 T 而**不会**同时满足默认类型条件的边数
```
- 若 `distinction(T) = 0`（即所有候选边都同时是 reference）⇒ **T 与 reference 不可区分** ⇒ **不该加**
- 阈值：`distinction(T) ≥ 10` **或** `≥ 5% 的候选边`

**实测应用（现有三类型）**：
| 类型 | 行政法 | examples | AAA_Vocab | 判定 |
|---|---|---|---|---|
| `contain` | 21 | 28 | **0** | 在词典型库不可用 ⇒ **不该对词典型库宣称有 contain** |
| `extend` | 0 | 11 | 0 | 只在 examples 有用 ⇒ 类型存在合理，但不是全局 |
| `reference` | 23 | 44 | 454 | 默认值，无需闸 |

**⇒ 闸 1 直接推出一个设计结论**：`contain` 对 1 文件 1 KP 的库**结构上不可产生**，所以**在词典型库上"加 contain"是伪需求**。这是上线前就能判的。

#### 闸 2：**relevance 异质度闸**（上线前，纯数据可算）

```
heterogeneity(T) = 该类型边的 relevance 值标准差
```
- 若 `heterogeneity(T) = 0` 且值 = 默认值（0.7）⇒ **该类型无信息量**（所有边一样重）⇒ **不该加**
- 阈值：`heterogeneity ≥ 0.05`（即至少不是全部同一值）

**为什么这条重要**：phase2 已实测 **`relevance` 100% 为默认值**。**类型分化了但权重没分化 ⇒ 类型只是标签，不承载决策。**

#### 闸 3：**决策绑定闸**（上线前，需**设计文档写明**）

**新类型 `T` 必须回答：它服务哪个具体决策？并给出该决策的可测判据。**

- 例：`prerequisite` 服务"我该先学什么" ⇒ 判据 = "给定目标 KP，用户/agent 是否先访问其 prereq 源节点，比例 ≥ X%"
- 若答不出决策 ⇒ **不该加**（这是"每条边必须服务一个具体决策"的直接应用）

**⚠️ 闸 3 是唯一需要人判断的闸**，我要说明为什么它不能机判：**"服务哪个决策"是语义主张，不是数据属性。** 但我可以要求它**必须配一个可测判据**（否则视同未通过）。

### 4.3 三闸的机检实现（可复跑）

```bash
# 闸 1 + 闸 2 可完全机检
python scripts/benchmark/maintenance/kg_edge_type_admission.py \
  --kb docs/example/AAA_Vocab --kb docs/example/行政法 --kb docs/example/examples \
  --candidate-type contain
# 输出：distinction(contain) per KB, heterogeneity, PASS/FAIL per gate
```

**⇒ 这个脚本我可以在实现阶段写（需 Lead 批准写域），它让"该不该加类型"变成一条可复跑命令。**

### 4.4 「类型空间」的另一个可测判据：**类型熵**

```
H(types) = -Σ p(t) log p(t)
```
- 全部一个类型 ⇒ `H = 0`
- 均匀分布 ⇒ `H = log(n_types)`

**用途**：跨库对比类型分化程度。AAA_Vocab `H=0`，行政法 `H≈0.69`（2 类 52/48），examples `H≈0.95`（3 类）。
**⇒ 这是一个"一行数字"的跨库可比指标，比"reference 占比"更信息密集。**

**但我要诚实标注**：`H` 上升**不必然好**（可能只是噪声分化）。**必须配闸 1/2 的语义校验，不能单看熵。**

## 5. Q4/Q5/Q6 回答

### 5.1 Q4：link 类型 vs edge 类型分开后，怎么测"分开是对的"

**两个方向都要测（M-08 / M-09）：**

| 方向 | 指标 | 若失败说明什么 |
|---|---|---|
| **正向（link → edge）** | 映射保真度 ≥95% | link 上标了 `prerequisite`，生成的 edge 却成 `reference` ⇒ 分开造成信息丢失 |
| **反向（edge → link）** | 反向覆盖率 | 某 edge 类型 100% 无 link 来源 ⇒ 该类型是"凭空推导"，需单独论证合理性 |

**⚠️ 现状关键事实（phase1 引用）**：`479/479 reference`。
**⇒ 反向覆盖率当前 = 0%（所有 edge 都是默认类型，无法区分"link 声明的"和"推导的"）。**
**⇒ "分开是对的"当前**不可测**——因为分开后的产物 100% 退化为同一值，没有可比的差异可测。**

**这是我要强调的**：「分开是否对」这个设计主张，**必须先有类型分化才能验证**。否则只是架构上"看起来更清晰"。

### 5.2 Q5：决策命中率怎么测

**定义**：
```
decision_hit_rate = (被至少一次成功导航使用过的边数) / (总边数)
```
**数据源**：§3.2 埋点。

**分层报告**（关键，不能只报一个总数）：
- 按 `edge_type` 分（哪类边真被用）
- 按 `domain` 分（哪些域之间的边被用）
- 按度数分（枢纽边是否真的被用，还是只是视觉上醒目）

**⚠️ 阈值我先不敢给死**：因为**没有基线**（从未采集过）。我要诚实说：**这个指标的第一版只能是"建立基线"，不能是"验收"。** 给出了阈值但没有基线，就是空指标。

### 5.3 Q6：2D/3D 方向性误读怎么量化

**不能靠"看着乱"。我给三个可测代理：**

| 指标 | 定义 | 数据源 |
|---|---|---|
| **方向误读率** | 沿边 A→B 后 ≤2s 内回退到 A 的比例 | 埋点 |
| **方向任务成功率** | 给定"A 的后继是什么"，点击正确的比例 | 埋点 + 任务集 |
| **双向边混淆率** | 对单向边，用户是否点了反向 | 埋点 |

**⚠️ 我必须声明局限**：这三个都是**行为代理**，不是"方向被正确理解"。**真要测理解需要眼动/出声思考，超出本环境能力。**
**登记 unknown：2D/3D 的"可读性"差异无法在本环境可靠测量。**

## 7. 对 task-86 现有指标的 judge（哪些有效、哪些是自欺）

### 7.1 逐指标判定

| 指标 | 有效性 | 判定 |
|---|---|---|
| 叶子率 | ⚠️ **半有效** | 测"图是否全连通"有效；**但"叶子率高=好"是错的**——边被误删也会让叶子率上升。**必须配"可达性不下降"守卫** |
| 平均度 | ✅ 有效 | 纯结构，无歧义，作为"稀疏度"指标合适 |
| 最大度 | ✅ 有效 | 直接测"是否有超级枢纽"，与毛球直接相关 |
| 度≥10 占比 | ✅ 有效 | 同上 |
| reference 占比 | ⚠️ **半有效** | 测"类型是否分化"，**不测"分化后有用"** |

| `edge_type_fallback` 计数 | ✅ **优秀** | 这是唯一"让失败可见"的指标（D3 要求）。**它测的不是成功，是失败被记录**，这恰恰最诚实 |

### 7.2 为什么「最大分组占比 99.2% → <40%」是自欺指标

**Lead 的判断正确，我给出三条具体理由：**

#### 理由一：它测的是"分组算法改了"，不是"分组有用"

- 把 `computeGraphGroups` 的分组依据从"连通分量"换成"域"，**这个数字必然从 99.2% 掉到 ~5%（6 个域/133 节点）**
- **但即使掉到 5%，用户可能仍然看不到任何改善**——因为：
  - 域节点摆出来了，但用户不知道要切到这个视图（phase3 §13 已意识到这个问题）
  - 切过去了，但域之间的边仍然是毛球
- **⇒ 它测的是"我改了代码"，不是"用户受益了"**

#### 理由二：它是**必要**条件，不是**充分**条件

- 分组占比 99.2% ⇒ 分组**肯定**没生效（充分判断失败）
- 分组占比 5% ⇒ 分组**可能**生效了，**但用户是否用得上完全未知**
- **⇒ 只能用于"判定没修好"，不能用于"判定修好了"**

**我的建议表述**：
> `最大分组占比 <40%` **是 0.5 发布的门槛条件（gate），不是验收条件（acceptance）。**
> 通过它只说明"可以继续测下一步"，不说明"这件事做成了"。

#### 理由三：它的阈值 `<40%` 没有推导依据

- 为什么是 40% 而不是 20% 或 60%？
- phase3 只写了"从 99.2% 降到 <40%"，**没有给"40% 对应什么用户体验"的推导**
- **⇒ 这是一个"看起来精确"的拍脑袋数字**（虽然方向对）

**我要求**：任何阈值必须给**"这个值对应什么可观测行为"**。例如：
- `<40%` ⇒ 域视图下最大可见组 ≤ 53 个点（133×0.4）⇒ **仍然可能毛球**
- **如果目标是"视口限制 ≤50 个点"**（phase3 §5.3 自己也写了 `默认视图可视图元数 ≤10`），**那阈值应该直接绑到"可视图元数"，而不是"占比"**

**⇒ 我建议把主指标换成**：`域视图下同时可见图元数 ≤ 10`（phase3 已有，但被"占比"抢了主角）。
**理由**：`≤10` 直接对应"用户一眼能看完"，`<40%` 只是它的一个间接代理。

### 7.3 task-86 指标设计的**结构性问题**（比单个指标更重要）

**问题：全部 6 个指标都是"状态量"，没有一个"变化量/使用量"。**

| 类型 | 例子 | task-86 有吗 |
|---|---|---|
| 状态量（当前长什么样）| 叶子率、平均度 | ✅ 6 个全是 |
| **变化量**（改了什么）| 域切换前后导航成功率差 | ❌ |
| **使用量**（被用了吗）| 图节点点击率、边利用率 | ❌ |

**⇒ 这是"测了动作、没测效果"的结构性表现。** 单个指标都能改好，但整体仍然测不到"这个设计成不成立"。

**我的补法**：每类主张至少配一个"使用量"指标（M-04/M-05/M-13/M-16）。

## 12. 一句话总结我的提案

> **这个设计成不成立，取决于「边有没有用」，而不取决于「边有多少、类型分得多细」。**
