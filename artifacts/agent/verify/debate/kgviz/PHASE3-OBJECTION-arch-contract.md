## 2. V2 可辨档数 —— **这是本场最该裁的**，我的异议直接否定 [B] 的 12–13 档

### 2.1 三方档数的**计量单位不同**（这是核心问题）

| 来源 | 数字 | **它实际是什么** | 证据 |
|---|---|---|---|
| **[C]** | 4 档 | **人眼可辨档数**（受 3px/20% 阈值约束） | `ev:file:artifacts/agent/verify/debate/kgviz/PROPOSAL-metrics-baseline.md#L98` |
| **[A]** | 5 档 | **离散半径档位数**（4/6/8/10/12） | `ev:file:artifacts/agent/verify/debate/kgviz/PROPOSAL-render-perf.md#L83-L88` |
| **[B]** | 12–13 档 | **映射函数输出后 distinct 半径值个数** | `ev:file:artifacts/agent/verify/debate/kgviz/PROPOSAL-todo-owner.md#L62` |

**[B] 原文（L62）**：「实测桶：degree 12 档、内容 13 档；最小值 5、最大 18（≈3.6× 直径，可辨）」

⇒ **[B] 的 12–13 不是「可辨档数」，是「连续函数 `r = 5 + 13*sqrt(t)` 分桶后的 distinct 值个数」**。
两者是不同量纲：**数学上能画出 12 种不同半径 ≠ 人能区分 12 档**。

### 2.2 用 [C] 的判据算 [B] 的方案 ⇒ **只有 4–5 档，不是 12–13**

我按 [C] 的判据 `相邻档半径差 ≥ max(3px, 20%×r)` 对各方方案复算：

| 方案 | 半径范围 | 绝对 3px 判据 | 相对 20% 判据 |
|---|---|---|---|
| 现状 | 6–9 | **2 档** | 3.2 档 |
| [C] 候选 | 6–15 | **4 档** | 6.0 档 |
| [A] | 4–12 | **3 档** | 7.0 档 |
| **[B]** | **5–18** | **5 档** | **8 档** |

⇒ **[B] 的 5–18px 在 [C] 判据下最多 5–8 档，与它声称的 12–13 档差 2.4×。**

**复现**：`python -c` 计算 `(rmax-rmin)//3+1` 与 `1+log(rmax/rmin)/log(1.2)`（见 §9 命令）。

### 2.3 更根本的问题：[C] 的判据**自身不自洽**

`max(3px, 20%×r)` 里两个条件在 5–18px 范围内**哪个起作用取决于 r**：
- r=5 时 `20%×r=1px` ⇒ 3px 主导
- r=18 时 `20%×r=3.6px` ⇒ 相对判据主导

⇒ **同一判据在不同半径下给出不同档数（5 vs 8），这不是"保守估计"，是判据未定。**

**我的裁定建议**：V2 **当前不可裁**。理由：
- 3px 与 4px 都是经验值（[C] 自承 `ev:file:...metrics-baseline.md#L89-L90`）；
- A/B 判读需真人（[C] 自承 `#L140` 标 S，本环境做不到）；
- **[B] 的 12–13 是对"可辨"的误用**，应作为 `unique_evidence` 但**不成立**。

**可执行的最小结论**：v0 **不承诺档数**，只承诺「**相邻可见档半径差 ≥ 3px 且总范围 ≥ 6px**」（即现状 6→9 不满足，需扩到至少 6→15）。档数由映射函数决定，**不作为验收判据**。

### 撤回条件
若有人给出**实测判读数据**（≥5 名用户 × ≥20 判读），证明真实阈值是 2px 或 4px ⇒ 本节全部撤回，按实测阈值重算。
**这是本场唯一能让 V2 可裁的证据，而我判定它当前不存在。**

## 3. V3 sizeScale 是否 v0 必须有 —— **我承认分位映射可以等价，撤回"必须"**

### 3.1 我 Phase 1 的主张与它的漏洞

我 Phase 1 说：「必须支持 `sizeScale: linear|sqrt|log`，否则长尾让多数节点不可见 ⇒ 契约可表达性问题」。

**[A] 用分位分桶绕开了它**：`ev:file:artifacts/agent/verify/debate/kgviz/PROPOSAL-render-perf.md#L83-L88`
```js
r = R_BY_BIN[bin(degree)]
```
**[B] 也用分位 + sqrt**：`ev:file:...PROPOSAL-todo-owner.md#L60-L62`
```js
p = clamp(rank_pct, 0.10, 0.90); t = (p-0.10)/0.80; r = 5 + 13*sqrt(t)
```

### 3.2 我的改判：**分位分桶确实等价于（甚至优于）sizeScale**

**等价性论证**：
- `sizeScale: log|x^0.5` 解决的是「长尾压缩」；
- **分位映射直接在秩空间上均匀分布** ⇒ 长尾被**结构性消除**，不需要任何 scale 参数；
- 且分位映射**自带**上下界（p10–p90）、**不依赖 max 的异常值**（[B] 的度数 max=25 会被 log 拉偏，分位不受影响）。

⇒ **我撤回「sizeScale 必须」**。但保留一条**弱主张**（见 §3.3）。

### 3.3 我保留的弱主张：分位映射**必须在契约上声明"它是相对的"**

**这是 A（契约）职责**：分位映射的半径**随图变化** —— 同一个 KP 在 133 节点图里和 1000 节点图里**大小不同**。
[A] 自己也意识到这点：`ev:file:...PROPOSAL-render-perf.md#L88`
> 数据依赖：分位阈值随图变化 ⇒ 同一节点在不同 KB 中大小不同。这是设计选择（相对重要性），必须在 tooltip 里显示 `degree=5（档 3/5）`，否则会被误读成绝对大小。

**我要求把它从"[A] 的建议"升级为【契约约束】**：
> 任何**相对量**（分位/归一化）驱动的视觉编码，**必须在可发现的 UI 处显示其绝对原值**，否则用户会把相对大小读成绝对属性。

**理由（非经验）**：`docs/design/kg-ontology-v0.md#L40` 已定 `reference` 是「**无断言跳转**」⇒ 图谱里**没有任何"重要性"语义**。分位大小会**凭空创造**一个"重要"语义，若不显示原值，就是**用一个相对量伪装成绝对属性**——与 KG 辩论反复批判的"看起来有实际没有"同类。

### 撤回条件
若有人证明「用户不会把相对大小读成绝对重要性」（需用户研究），本弱主张撤回。

## 4. V4 3D 大小怎么办 —— **我支持 [A]，反对 [B] 的 1.0–1.25**

| 方 | 主张 | 证据 |
|---|---|---|
| **[A]** | 3D 保持等大 + 度数用颜色 | `ev:file:...PROPOSAL-render-perf.md#L134-L136` 实测相机距离 1375–2447，**屏幕尺寸比 1.78×** |
| **[B]** | 3D size 动态范围收紧 1.0–1.25 + 雾 + legend | `ev:file:...PROPOSAL-todo-owner.md#L51` |

### 我的异议：**[B] 的 1.0–1.25 与 [A] 的 1.78× 透视混淆量级重叠 ⇒ 无法区分**

[A] 实测：同一 world 半径的**屏幕尺寸比就已有 1.78×**（纯透视造成）。
[B] 提议的 size 动态范围是 **1.0–1.25（=1.25×）**。

⇒ **信号（1.25×）小于噪声（1.78×）**。用户在 3D 里看到两个点大小差 1.3×，**无法判断**是"度数高"还是"离相机近"。

**这是可计算的，不是经验**：
```
信号/噪声 = (1.25 - 1.0) / (1.78 - 1.0) = 0.25 / 0.78 ≈ 0.32
⇒ 信噪比 < 1 ⇒ 该编码在 3D 里不可解释
```

⇒ **支持 [A]（3D 等大 + 颜色）**。若 [B] 坚持，**必须**给屏幕空间归一（`scale ∝ 距离`）把透视消掉 —— 但那等于放弃 3D 的深度线索，收益存疑。

### 撤回条件
若 [B] 给出屏幕空间归一后的实测（消除 1.78× 后信噪比 > 2），本异议撤回。

### 7.2 但 [C] 的 `node_radius_px` 有**契约缺陷**（我的核心职责）

[C] 的字段：`ev:file:...PROPOSAL-metrics-baseline.md#L172`
```
"node_radius_px": 9.0,  // 该节点当前渲染半径（验证大小编码是否影响点击决策）
```

**问题：`node_radius_px` 是【映射函数的输出】，不是数据。**
- 它依赖 `sizeMode` / `sizeRange` / 映射函数的具体实现；

- 记录它等于**把渲染实现细节固化进埋点契约**。

**建议替代**：记 `node_degree` + `size_mode` + `size_range`，**由分析侧用同一映射函数复算 radius**。
⇒ 这样历史数据在任何映射变更后**仍可比**（degree 是稳定量，映射是可复算的）。

### 7.3 `node_degree` 同理：若 degree 从引擎算（[A] 方案），埋点值也是前端派生量

但**degree 是稳定量**（只依赖 edges 拓扑，不依赖映射），所以记录它**可接受**。
⇒ **判据**：埋点只记**拓扑/事件事实**（degree、edge_id、zoom_k、graph_style），**不记映射产出**（radius_px）。

### 撤回条件

## 8. V8 毛球态判定是否零新增字段 —— **我维持零新增，但要求先统一分组口径**

我 Phase 1 说：毛球态是 `node.group` 的函数，零新增字段，但前端分组无后端字段。

**我现在的补充**：`node.group` **也不该进数据层**（与 §0.1 同一条判据：分组是渲染侧派生）。
但**毛球态阈值本身是相对量**（`edges/nodes > 4`），与 §3.3 的"相对量必须显示原值"同族。
