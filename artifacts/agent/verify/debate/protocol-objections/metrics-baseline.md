## 2. 【重点①】CONFLICT-1：B3 的边界 —— 我的立场

### 2.1 我的结论：**B3 只适用于「度量证据」，不可通用化。**

**理由（三条，都可检验）**：

#### 理由一：测量者的解读建立在**不可传递的口径知识**上

我 Phase 1 §1.3 写的原话是"token 基准的**解读权**和**测量权**必须同源——只有我知道这个数字背后的口径限制"。

这句话成立的前提是：**测量过程产生了局外人拿不到的隐含信息**。例如：
- "这次测量包含了冷启动，方案 B 缓存命中时其实更划算"
- "第 3 次运行出现了 GC 抖动，median 被拉高"
- "语料里有 12% 是公式，tokenizer 对公式的分词特别碎"

**这些信息只存在于测量现场**。别人可以质疑我的结论，但不能在我缺席时**替代我解读这个数字意味着什么**。

#### 理由二：架构判断的解读是**可传递的**——它的全部依据都在磁盘上

architect 的架构判断由什么构成？
- 读过的源码（`ev:file:<path>#L<n>`）
- 规范条款（`ev:spec:<spec>#<sec>`）
- 对比论证（谁都能重走一遍）

**这些材料的全部内容都在磁盘上、任何评审者都能独立复核**。
因此 architect 的结论**不依赖"只有他知道的东西"** —— 这与度量证据有本质区别。

**⇒ 通用化 B3 会让"评审"变成"要求原作者的许可"，这是评审的反面。**

#### 理由三：通用化会与人点出的失败模式③同构

如果每份结论的解读权都归提出者：
- 少数派可以主张"我的证据只有我能解读" ⇒ **任何反对都无法成立**
- 这恰恰是失败模式③（少数派握唯一证据却被压掉）的**镜像滥用版**

**⇒ 我的规则本来是为了保护少数派，通用化后反而会变成少数派的盾牌，让辩论无法收敛。**

### 2.2 我要求的 B3 改写文本

```markdown
- **B3 测量权与解读权同源（仅适用于度量证据）**：
  对 `ev:bench:<id>` 类证据，**测量者提交的"口径限制说明"是该证据的组成部分**，
  裁决引用该数字时必须同时呈现该说明；剥离说明的引用无效。
  **适用范围严格限于度量证据**，不推广到架构/规范/设计类判断——
  后者的依据全部可复核，任何评审者可独立解读。
  裁决者若认为某条口径限制不重要，须书面给出理由并进入 J2 的
  `unique_evidence_handled` 流程。 ← metrics-baseline R5（限度量）；`CONFLICT-1` 已裁决
```

**关键三要素**：
1. **范围限定词写进标题**（不是正文里补一句，防止被摘引时丢失）
2. **明确"限制说明是证据的组成部分"**（而非"证据之外的备注"）
3. **给裁决者留合法路径**（书面理由 + J2 流程），而不是"否决即违规"

### 2.3 你（Lead）问的「非度量结论的解读权归属未定」——

**我的回答：它不需要专门条款，因为 E1+J1 已经覆盖。**
- E1 要求每条结论带 `source_identity`
- J1 要求逐条对照证据

**⇒ 非度量结论的解读权归属 = 任何评审者**，凭 E1 的溯源即可复核。
**不需要新规则，只需要在 B3 里写清"不推广"这个否定性边界。**

**这也回答了你的顾虑**："如果通用化，architect 的架构判断也只能由 architect 解读，这会让评审失去意义" —— **完全同意，所以必须限定**。

## 3. 【重点②】B4：六类必须进正文 —— 我的立场

### 3.1 结论：**object。六类必须逐条写入协议正文。**

### 3.2 理由

合并稿 B4 现状：
```
- **B4 不认的"省 token"声明**（六类，详见 metrics-baseline §4.2），
  其中最关键：把工具调用开销藏进 system prompt 后只对比 per-call。
```

**这个写法有三个可被利用的漏洞**：

#### 漏洞一：「详见」指向一份未被冻结的文件
`metrics-baseline.md` 是我的提案，**协议冻结后它不在协议正文里**。
将来裁决者只读 `protocol-v1.md`（这很正常——协议正文才是裁决依据），
**他看到的是"六类（详见别处）"** ⇒ 无法据此判任何一类不认。

**⇒ "详见"= 六类在裁决时实际不存在。**

#### 漏洞二：只列"最关键"的那一类，会产生"其他五类不重要"的暗示
协议正文只点名了 (f)（system prompt 藏开销）。
**在裁决实践中，"正文点名了什么"就是"什么被重视"**。
其余五类（只报输入不报输出、只报单次不报分布、换口径对比、用压缩率代替绝对值、只测能跑通）会被视为**次要不认项**。

**而其中 (a)「只报输入不报输出」的实际危害可能比 (f) 更大**——输出 token 单价通常 3–5 倍，
只报输入是**最容易在无意中产生的偏差**（很多 logging 默认只记 prompt_tokens）。

#### 漏洞三：无编号 ⇒ 无法被 J2/J3 引用
协议里其他规则都有编号（E1-E5、B1-B5），可以写 `falsifiers: [B4.f]`。
**六类若无编号，裁决时无法精确指向"我这次主张违反了 (c) 换口径对比"**。

### 3.3 我要求的 B4 改写文本

```markdown
- **B4 不认的"省 token"声明（六类，以下列全部为判据，非举例）**：
  任何"省 token"主张，若属于下列任一形态，**不构成有效证据**：
  - **B4.a** 只报输入 token、不报输出：须齐报 `prompt` / `completion` / `total` 并给加权成本
  - **B4.b** 只报单次、不报分布：须报 ≥5 次的 median + min–max + 每次原始值（与 E5 联合生效）
  - **B4.c** 换口径对比：commit / 语料 / 任务集三者不全相同 ⇒ 不得相减，不得用于裁决
  - **B4.d** 用压缩率代替绝对 token：须同时给绝对值与压缩率
  - **B4.e** 只测"能否跑通"，不测"省不省"：须分离 `functional_pass` 与 `token_delta`
  - **B4.f** 把开销藏进 system prompt / tools schema 后只对比 per-call：
        须报**总账单**（system + schema + messages + completions）
  ← metrics-baseline §4.2（六类全文迁入，不再"详见"）
```

**为什么必须全文迁入而不接受"详见"**：
**协议是裁决依据，不是索引。** 一份需要跳转才能使用的协议，在压力下（时间紧、多人引用）必然退化为"只看正文"。

### 3.4 一个我必须坦白的观察

B4 被摘要化，**可能是合并时的正常压缩**（25 条里每条都只留一行）。
但**度量类的六类与别类不同**：它们每一条都是**独立的失效形态**，不是同一个原则的例证。
压缩后失去的不是细节，是**覆盖率**。

**⇒ 如果协议有总体长度限制，我接受 B4 用更短句式，但六类的「判据关键词」必须全部在正文。**

## 4. 【重点③】E4/E5 是否足以约束"看起来省了"的假象

### 4.1 E5 改写：合并稿的「或」必须改成强制二分

**合并稿现状**：
```
- **E5 不一致必须披露**：同一现象多次测量不一致时，禁止择一引用，必须报完整分布
  （或证明逐字节一致）。 ← metrics-baseline R4
```

**问题分析**：

我 Phase 1 §4.1 第 5 条原文是：
> **"要么逐字节一致，要么报完整分布"**，不是"必须一致否则作废"

以及 §2.4 R4 原文：
> 连跑 2 次若**除时间戳外不逐字节一致**，必须报告：两次的原始值、差异位置、是否已定位原因

**合并稿的「（或证明逐字节一致）」把两种义务写成了并列选项，且没有失效后果。**

**三个具体失效场景**（现在的写法无法处理）：

| 场景 | 现在的 E5 能否处理 |
|---|---|
| 两次不一致，且不报分布 | ❌ 只能判"未履行披露"，未明确该数据能否使用 |
| 两次不一致，报了分布，但**只引用有利的那次** | ✅ "禁止择一引用"覆盖了 |
| 两次一致，但**只在有利口径下一致**（换了语料） | ❌ 应归 B4.c，E5 管不到 |

**⇒ E5 缺的是「不一致且不披露 ⇒ 该数据不得用于裁决」这个后果。**

### 4.2 我要求的 E5 改写文本

```markdown
- **E5 不一致必须披露（二选一，无第三选项）**：
  同一现象多次测量，**必须满足二者之一**：
  - **(a) 除时间戳外逐字节一致**（机检 diff 通过），或
  - **(b) 报完整分布**：每次原始值 + median + min–max + 已知差异原因（或"未定位"）
  二者皆不满足 ⇒ **该数据不得用于裁决**（不是"建议补充"，是**不可用**）。
  **禁止择一引用**；**禁止把单次最好值表述为"实测值"**。
  特别地：token 类指标天然可能抖动（工具返回顺序影响上下文拼接），
  **因此 (b) 是常态路径，(a) 是理想路径**——但不得因"抖动正常"而跳过 (b)。
  ← metrics-baseline R4、§4.1-5
```

### 4.3 E4 必须补的第五条失效路径：跨口径不可相减

**合并稿 E4 现状**：
```
- **E4 可复现才有效**：主张"省 token / 省时 / 更快"必须有 `ev:bench:<id>`；
  评审者有权要求复现，**复现失败 = 证据作废**。
```

**E4 覆盖了什么**：单一数字能否重跑出来。
**E4 未覆盖什么**：**两个都能重跑的数字，能不能相减**。

**为什么这是必须补的**：
- 这是最隐蔽的形态：两个数字**各自都合规**（都有 `ev:bench`、都能复现、都有分布）
- 但 **commit / 语料 / 任务集不一致** ⇒ 相减无意义
- **E4 的"复现失败"永远不会触发**，因为**根本没有复现失败**

**这正是失败模式①（同源伪多数）在数据层的对应**：看起来两条证据，实际是两条不可比的证据。

### 4.4 我要求的 E4 改写文本

```markdown
- **E4 可复现才有效（含三条失效路径）**：
  主张"省 token / 省时 / 更快"必须有 `ev:bench:<id>`，且满足：
  - **E4.1** 评审者有权要求复现，**复现失败 ⇒ 证据作废**
  - **E4.2** `ev:bench:<id>` 必须自带完整溯源身份：
        commit(40位) + corpus_sha256 + script_sha256 + raw_artifact + artifact_sha256
        + 每次原始值 + env(OS/CPU/RAM/runtime)。缺项 ⇒ 证据等级降为 `unverified`，
        **不得用于裁决**。
  - **E4.3** 两个 `ev:bench` 相减（用于"省了多少"）**必须三者齐同**：
        commit / corpus_sha256 / 任务集。任一不同 ⇒ 只能表述为"跨口径参考，
        不作裁决"（与 B4.c 联合生效）。
  ← arch-contract R5、metrics-baseline §4.1、§4.2(c)
```

**为什么 E4.3 关键**：它把"看似两条证据实为不可比"从**口头提醒**变成**可机检条件**（三个 sha 比对）。

## 5. 我对 CONFLICT-1..4 的立场

### CONFLICT-1：度量规则是否通用化

**立场：仅度量。B3 必须限定范围。**

**完整理由见 §2。核心一句**：
> 度量者的解读建立在**不可传递的口径知识**上；架构判断的依据**全部可复核**。
> 通用化 B3 会让"评审"变成"要求原作者许可"，并与失败模式③的镜像滥用同构。

**保护谁**：整个辩论（评审的有效性）、少数派（避免 B3 被反过来当盾牌）
**伤害谁**（若通用化）：所有评审者、最终裁决质量

---

### CONFLICT-2：unknowns 的中立边界

**立场：我倾向「应知而未知」需扣分，但「应知」的判据必须可操作，否则该规则不可用。**

**我的具体提议（从度量视角）**：
`unknowns` 分两类处理：
- **`unknown_declared`（主动声明未知）**：合法交付物，**不扣分**（P4）
- **`unknown_should_have_known`（应知未知）**：扣分，**判据是**：
  该未知信息**在被引用的证据里已经出现**（例如：`ev:file:xxx#L42` 里明确写了缓存策略，提案却没提）

**为什么这个判据可操作**：它是**可机检的**——
把 `unknowns` 列表与被引用证据的文本做关键词/语义比对，能给出"应知"的候选。
这比"由裁决者凭感觉判应知"要硬得多。

**保护谁**：度量者（我若声明"未测跨环境 token"，不应被扣分——那确实是未知）；辩论质量（防止 unknowns 被滥用逃避责任）
**伤害谁**（若判据不可操作）：所有诚实申报 unknowns 的人（因为"应知"全凭裁决者主观）

---

### CONFLICT-3：P2「不得要求缺席证明」的边界

**立场：P2 应保留，但需补一条——「覆盖面清单的最低充分性」不由裁决者主观判，而由 F1 冻结的判据判。**

**理由**：
P2 说"以覆盖面清单 + 已知盲区声明评价"。但**谁判清单够不够**？如果由裁决者判，
则 P2 变成"提出者列个清单就算合规" ⇒ 可被滥用（CONFLICT-2 的同构问题）。

**我的提议**：
- F1 已冻结「可接受判据」
- **把"覆盖面清单的最低充分性"绑定到 F1 的判据上**：
  清单必须覆盖 F1 中列出的**每一个** concern；对未覆盖项必须显式说 `out_of_scope + 理由`
- 这样"够不够"变成**对照冻结判据的逐项检查**，而不是主观判断

**保护谁**：被要求列清单的一方（判据前置，不会事后加码）；辩论质量（防清单敷衍）

---

### CONFLICT-4：裁决合法性 vs 人的最终决策权

**立场：M1 与人的决策权不冲突，但**必须把我 Phase 1 §3.1/§3.2 的立场写进形式要件**。**

**我的立场（来自 Phase 1 §3）**：
- **人可以推翻可复核裁决**（组织事实）
- **但推翻时必须给理由 + falsifier**，且**该 dissent 必须被 J4 原样冻结**
- **特别地（我最在意的）**：**不得以"多数人认为该口径合理"推翻度量口径**

**为什么这条对我最重要**：
这是我 Phase 1 §3.1 唯一点名"不可接受"的裁决方式。
如果 CONFLICT-4 的裁决只说"人可推翻但需给理由"，**没有写"不得以票数推翻度量口径"**，
那么未来可能出现："5 个人认为你的语料选择不合理，所以你的基准无效"——**而语料是否合理是物理事实（是否密封、是否可复跑），不是票数问题**。

**我要求的 CONFLICT-4 补充**：
```
人推翻可复核裁决时，除给理由 + falsifier 外，还必须：
- dissent 原样进入 J4 冻结产物（不得摘要化）
- 若被推翻的是度量类结论（`ev:bench:*`），推翻理由必须包含
  "该口径在何处不密封/不可复跑"的具体判据，**不得以"多数认为"作为理由**
```

**保护谁**：度量者（防止我的物理事实被票数压过）
**伤害谁**（若不补）：任何提供硬证据的一方

## 6. 【新增建议 N1】共享假设必须先检验才可裁决

### 6.1 我要引用的现有规则（诚实说明：这是"新增建议"，不是从现有条款推导）

**我必须坦白的边界**：N1 **不能**从 E3 严格推导出来。
E3 只要求「登记 + 指派检验者」，**没有**要求「裁决前必须完成检验」。

**⇒ 所以 N1 是「新增建议」，按你的规则（"必须说明它从哪条现有规则推导出来，或标注新增建议"），我标注为新增建议。**

**但它有一个强论据**：E3 自己的最后一句是
> 「未检验的共享假设 ⇒ 该结论自动降级为"有条件成立"，**不得作裁决依据**」

**⇒ E3 已经包含了"未检验不得裁决"这个原则**，只是**没有把它应用到"架构辩论的前置假设"上**。

**因此 N1 的准确定性是**：**「E3 的既有原则在架构辩论前置假设上的显式应用」**，
不是全新规则。这是我能给出的最诚实的定位。

### 6.2 N1 要保护的假设

我 Phase 1 §5 点出的：

> **「MCP 化 / 全量移植 DSH 能力，一定会增加 token 开销（schema 描述、工具签名、上下文膨胀）」**

**为什么它必须被检验**：
1. 它**可能对，也可能错**（MCP 的结构化 schema 有时反而减少自由文本的冗余）
2. **如果所有人默认它对**，辩论会跳过实测直接进入"如何缓解"——**这正是失败模式②**
3. 更关键：**CONFLICT-1 的裁决可能建立在这个假设上**（你说得对）

**你说"CONFLICT-1 的裁决会建立在它上面"——我确认这个风险存在**：
如果 B3 通用化（CONFLICT-1 判"通用"），那度量者将无法在架构判断上提供 token 证据，
**辩论就在"未经检验的 token 假设"下进行架构决策**。这两件事是耦合的。

### 6.3 N1 建议文本

```markdown
- **N1（新增建议）架构辩论前置假设必须检验**：
  架构辩论开始前，必须对「本辩论依赖的、可能影响多方的未验证前提」做一次**显式检验**，
  至少在 CONFLICT 裁决前产出 `ev:bench:*` 或 `ev:spec:*`。
  当前已识别的必须检验项：
  - **A1「MCP 化一定会增加 token 开销」** —— 负责检验：度量方（我），
    判据：`ev:bench` 分离测「schema 开销」与「每次调用开销」，
    并含「零新增 schema」对照组（见 metrics-baseline §5）
  未完成检验 ⇒ 依赖 A1 的裁决只能标 `conditional`，不得终局。
  ← 新增建议；原则依据 E3 末句「未检验的共享假设不得作裁决依据」的显式应用
```

**保护谁**：整个架构辩论（避免在未检验前提上决策）、少数派（若他们反对 MCP 化，现在有了要求实测的正当路径）
**伤害谁**（若不加）：最终架构决策的正确性

### 6.4 我对 A1 的自我约束（重要）

**我必须声明**：我不会预设 A1 的方向。
