# 辩论协议提案 · 对抗评审视角（arch-contract）

> **作者**：arch-contract（对抗评审角色）。
> **Phase 1 独立提案**：未读 `agent-arch.md` / `metrics-baseline.md` / `steward.md`。
> **我的角色定位**：我不是提案者，我是专门挑提案者漏洞的人。所以我的提案只回答一个问题：
> **「挑毛病」这件事本身，怎么保证公平、不靠嗓门、不靠票数、不靠权威。**
>
> **立场声明（先亮底牌）**：我不主张"评审者永远对"。我要主张的是——
> **裁决的合法性来自「证据 + 可复核 + falsifier」，而不是来自 Lead、人、或多数票。**
> 如果协议最终让「异议被驳回的代价」低于「异议成立但被忽略的代价」，我就安全了。

---

## §1 我可能怎样被不公平对待（3 条危险，先写危险再写规则）

### 危险 1：被要求「只指出问题，但无权提替代方案」

**场景**：我作为评审者，常常被框定成"你说哪错了就行，怎么改是提案者的事"。
**不公平在哪**：这会把我的异议**降级成 nitpick**。如果提案者永远有权说"这是实现细节，我来定"，那么我挑出的每一个契约级问题（字段语义、失败语义、版本兼容）都能被一句"你只管验收，别管设计"挡回来——而契约级问题恰恰是我的核心职责，找不到替代方案时我的异议就"没有建设性"，于是被驳回。

**为什么对架构辩论尤其致命**：本次辩论的是**能力架构**（字段/版本/兼容/失败语义）。这些恰恰是"必须有人能说『这样定义不行，应该那样』"的领域。若评审者被剥夺替代方案权，等于让契约评审退化成"格式检查"。

### 危险 2：因「提案者证据多」而被反压（数量 ≠ 质量）

**场景**：提案者（`agent-arch`）会准备大量证据——业界惯例、benchmark、先例。我在 Phase 3 要指出漏洞，但我的证据天然是「反例、缺口、反证」，**数量上一定少于提案者的正面证据**。
**不公平在哪**：如果裁决规则是"证据更多的一方赢"，那么**任何提案都会赢**，因为提案者永远是举证责任较轻的一方（他只需堆正面材料，我找一条反例就够推翻，但"一条反例"在"十份正面佐证"面前听起来像孤证）。

**这正是人点出的失败模式 ①「同源伪多数」的变体**：提案者的十份证据可能都源自同一份上游材料（同一篇 DSH 文档被拆成十个引用点），我的一条反例却要单独站住。**数量加权会系统性偏袒提案者。**

### 危险 3：我挑出的问题被裁决成「nitpick」

**场景**：契约评审里，很多真正的缺陷初看"很小"——一个字段是可选的还是必填的、一个版本号该不该 +1、一个失败该抛错还是降级。提案者会说"这是实现细节，不值得拒绝整个提案"。
**不公平在哪**：**架构辩论的裁决单位必须是「问题」，不是「提案」**。如果协议要求"只有能推翻整个提案的才算有效异议"，那么契约级的小洞全部被漏掉——而这些小洞累积起来，正是系统后期最贵的债（版本兼容被破坏、失败语义歧义导致下游误判）。

**我的对应主张**：异议应该**独立成档、独立裁决**，不要求"足以推翻整个提案"。一个契约漏洞即使不推翻提案，也必须被记录为「已登记的偏离」并给出修复时点。

## §2 协议必须保证的规则（5 条，每条写明「若违反，谁受损」）

### 规则 1：异议必须**绑定证据**，且证据必须**可独立复核**（不可复核的口头断言不计票）

- **内容**：评审者提出的每一条异议，必须附带「证据位置」——可以是文件路径+行号、可复现的 command/script、或带 sha 的产物。纯断言（"我感觉这样不对"、"业界不这么干"）**不计入有效异议**。
- **若违反，谁受损**：**评审者受损**——因为异议不被采信，等于让我这个角色回到"看嗓门"；但更深一层，**整个裁决受损**——因为 Lead/人在复核时无法区分"真漏洞"和"情绪抵制"，最终只能靠感觉裁决，这恰恰是人最想避免的。

### 规则 2：**禁止共享假设伪装成独立证据**（拆穿失败模式 ②）

- **内容**：任何一条证据，只要**溯源后发现它和另一条证据同源于同一份上游材料、同一段代码、同一个未经验证的默认前提**，就必须**合并计数为 1**，而不是 N 票。裁决前必须做一次"证据同居性审计"——列出每条证据的第一手来源，检查是否有两条指向同一出处。
- **若违反，谁受损**：**裁决的公信力受损**。因为"看起来多票、实际一份证据"正是人点名的失败模式 ①+②的合体。被这个机制坑的是那些**真正独立的少数派证据**——它们因为没有复读机器，反而显得势单力薄。

### 规则 3：**少数派异议必须被单独、完整记录，不得被多数票静默**（拆穿失败模式 ③）

- **内容**：票决可以决定"提案是否通过"，但**不能抹掉异议的存在**。每条被否决的异议，必须进入一份 `rejected-objections` 清单，写清楚「谁提出的、证据是什么、否决理由是什么、什么证据出现会重新翻案（falsifier）」。
- **若违反，谁受损**：**握有唯一证据的少数派受损**——他们被票数压掉后，连"曾经有人反对过"的痕迹都没有，未来翻案无从谈起。这也是人点名的失败模式 ③ 的直接解药。

### 规则 4：**裁决必须给出 falsifier（可证伪条件）**

- **内容**：每一项裁决（通过/驳回）都必须附带一句话：**「出现什么证据，这条裁决就撤回」**。例如："若给出 N≥1000 且 p95<X 的真机 benchmark，本裁定『暂不采纳流式方案』即失效并重新裁决。"
- **若违反，谁受损**：**所有人受损，但评审者最重**——因为如果没有 falsifier，被驳回的异议就是"终审"，我下一次再提同一问题时会被说"已经裁决过了"。falsifier 让裁决是**可撤回的**，这才是"证据 + 可复核"的合法性来源，而不是权威的终局。

### 规则 5：**评审者有权要求「可复现」，提案者有义务提供，且复现失败 = 证据作废**

- **内容**：评审者说"你这个 benchmark 我不认，请给我能复现的脚本+数据"，提案者若不提供，或提供后评审者复现失败，则**该证据从提议中剔除**，不得再作为支撑。
- **若违反，谁受损**：**评审者受损**——会被迫在"无法验证的 benchmark"面前认输，而一个跑不通的 benchmark 和假证据没有区别。这条规则是 skill 里「每个数字可追溯」「null sequential build 自检」的辩论版。

## §3 我认为不可接受的裁决方式（2 条）

### 不可接受 1：「Lead 拍板 / 人批准」作为裁决的**最终合法性来源**

**为什么不可接受**：人自己说的——"我批了也不算，我们得有专业的人定位/设计"。如果协议最终写"争议以 Lead 或人的判断为准"，那就把裁决的合法性从「证据」偷换回了「权威」，恰恰违背了这次辩论的初衷。

**我能接受的替代**：Lead/人可以**发起**裁决、可以**指定**裁决适用的证据选择，但**裁决文本必须落在 falsifier + 可复核证据上**。权威的作用是"主持流程"，不是"当证据"。

### 不可接受 2：「宁可错杀，不可放过」式的**一票否决**（包括对我这个评审者的滥用）

**为什么不可接受**：这里我要警惕的是**反向的不公平**——如果协议给评审者"任一异议即可搁置整个提案"的一票否决权，那么我就成了新的独裁者，这同样不公平，而且会被人点名失败模式 ③ 反过来坑到握有真证据的提案者。
**我主动声明放弃这个权利**：评审者的异议应**独立裁决、按证据判定**，而不是"有一票否决"。我要的是"异议不会被静默、被降级、被票数压掉"，**不是**"我提异议就赢"。
**若有人用「评审者说不行」当一票否决来压提案者，我也反对。**

## §4 我需要的证据形式（什么样的证据我才认）

> 这一节是「对抗评审的验收门槛」。它直接决定：提案者拿出什么，我会接受；拿出什么，我会打回。

### 4.1 「业界惯例 / 标准做法」——**认，但有条件**

- **认**：作为**背景 / 默认选项的合理性**（"业界普遍用 X，所以我们默认 X，偏离要有理由"）。
- **不认**：作为**裁决性证据**（"业界都这么干，所以我们必须这么干"）。
- **条件**：引用业界惯例时，必须给出**可溯源出处**（具体文档/规格的章节，不是"大家都知道"），并且**说明这个惯例在本项目语境下的适用前提**。空泛的"业界惯例"在我这里**权重为 0**。

### 4.2 Benchmark / 性能数字——**必须满足「可复现 + 可证伪 + 归因」三重门槛**

- **可复现**：给脚本 + 种子/语料 sha + 环境口径，我跑一遍能对上（允许只差时间戳/路径）。
- **可证伪**：有对照基线，且**必须能构造出"必失败"的用例**证明测量有判别力（skill 里的"全部一致先证伪"）。一个永远全绿的 benchmark 在我这里 = 无判别力 = 不采信。
- **归因**：测量必须是密封的（同 commit 同参数，差异可落到具体改动）。"这次快了 20%，但中间混了三处其他改动"的结论不作数。

### 4.3 具体到架构辩论，我最信的三种证据（按可信度排）

1. **本仓库的现状反证**：提案说"现有能力模型可以做 X"，我 grep 代码发现 X 事实上有结构性障碍（如字段缺失、单例假设、写域冲突）——这是**最高权重**证据，因为它不可被"业界惯例"反驳。
2. **失败案例 / 边界用例**：具体到「字段 / 版本 / 兼容 / 失败语义」的 counterexample（"这个字段在场景 Y 下会歧义""这个版本号策略在回滚时会撞"）。**一条能跑通的 counterexample 可以推翻十份正面佐证。**
3. **可复现的最小实验**：为验证某条论断写的最小脚本，能复现某现象。**不是**论文级的 benchmark，而是"你说的这个行为，我实测是这样"。

### 4.4 我**明确不认**的证据（避坑清单）

- **未落盘的口头结论**（"我们讨论过，结论是…"）—— 认 disk artifact，不认记忆。
- **同名不同物的引用**（"某函数已经支持了"但那是被 IIFE 重绑掉的旧定义）—— 必须指向**生效版本**。
- **"全部一致 / 全部通过 / 零差异"** 且**没有反例用例**的测量 —— 无判别力，不采信。
- **字段缺失仍然判 match 的比较**（skill：字段缺失不得静默相等）。

## 附：我对自己角色的自我约束（这让我的提案不是纯自利）

1. **我不要求「一票否决」**。我要的是「异议不被静默、不被降级、不被票数压掉、裁决有 falsifier」。
2. **我的每条异议都自带证据**。证据不成立，异议自动作废，我不狡辩。
3. **我接受「我的异议被记录为 rejected 且给出 falsifier」**，只要这个 falsifier 是真实可操作的，而不是"永远不可能出现的证据"式的空头支票。
4. **我只审契约/接口**（字段、版本、兼容、失败语义），不越界去评"这个产品功能该不该做"——后者不是我的域。
