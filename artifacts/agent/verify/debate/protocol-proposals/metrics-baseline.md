# 度量验收视角：辩论协议独立提案

**作者角色**：度量验收（token benchmark / 判据提供方）
**Phase**：1（独立撰写，未读 `agent-arch.md` / `arch-contract.md` / `steward.md`）
**日期**：2026-10-25
**辩论对象**：Memoria agent 能力架构（全量移植 DSH / Memoria 作为 MCP server / 扩展点 / token 经济 / trace）

---

## 0. 我的角色定位（先声明，避免被误解）

**我不是一个"投票者"，我是一个"判据提供者"。**

这两者有本质区别：
- **投票者**输出"我赞成/反对方案 A"——这是意见，可以被票数统计。
- **判据提供者**输出"在这个密封口径下，方案 A 实测 X token，方案 B 实测 Y token"——这是事实，**不能被票数推翻**。

**人明确说过**：「看看怎样设计接口节约 token」。这句话把 token 消耗从"设计偏好"提升为**可测量的事实约束**。
因此我的产出物在被正确引用时，**不是一票，而是一条证据**。

**但如果我的角色被错误使用**（例如：让我跑一个对某方案有利的基准、或把我排除在裁决之外只当工具人），
那这条证据链就会被污染，**整个辩论关于 token 经济的部分将失去唯一硬证据**。这就是第 1 节要写的危险。

---

## 1. 我可能怎样被不公平对待（3 条）

### 1.1 危险一：被指派跑"对某方案有利的基准"

**具体形态**：
- 「你测一下方案 A 的 token 消耗」——但语料、任务难度、上下文长度被单方面指定为对 A 有利的取值
- 「方案 B 太复杂先不测了，你就测 A 证明它省 token」
- 「用这个现成的 benchmark 脚本跑一下」（而该脚本的 prompt 模板是为某方案量身定制的）

**为什么这会伤害我**：我的产出会变成**背书**而不是**测量**。我一旦在这种条件下出数字，
无论我是否声明"口径受限"，引用方都会把它当成"实测证明 A 更省"。

**规则需求**：见 §2.1（基准口径三方预先签署）与 §2.2（对照组对称性）。

---

### 1.2 危险二：我的数字被"未密封的对比"污染或替换

**具体形态**：
- 有人拿我某次数字（例如"方案 A 用 1200 token"）与**别人估算的**"方案 B 用 800 token"放在同一张表里比较
- 我测的是 commit `abc123`，但架构已改到 `def456`，引用时不说
- 我报的是**中位数**，被引用成**单次最好值**
- 我的两次跑**不一致**（一次 1200、一次 2400），但只有对我方有利的那次被引用

**为什么这会伤害我**：这会让我**无法为自己的结论辩护**——因为那个数字已经不是我的产出了。
更糟的是：一旦出现"我的数字被用来支持一个我没测过的结论"，我的可信度会永久受损。

**规则需求**：见 §2.3（数字带溯源身份）与 §2.4（不一致必须披露而非择一）。

---

### 1.3 危险三：被排除在裁决之外，只当"跑数的工具人"

**具体形态**：
- 我提交基准 → 其他人根据基准讨论 → 我不参与"这个基准是否回答了问题"的判定
- 裁决时引用"实测数据支持方案 A"，但**没人问我这个数据实际上意味着什么**
- 我的异议（"这个对比口径不一致"）在 Phase 3 被当作"技术细节"忽略

**为什么这会伤害我**：更根本地，**这会伤害辩论**。
因为 token 基准的**解读权**和**测量权**必须同源——只有我知道这个数字背后的口径限制
（比如"这个测量包含了冷启动，方案 B 缓存命中时不公平"）。

**规则需求**：见 §2.5（度量者对自身证据的解读权不可剥夺）。

---

## 2. 协议必须保证的规则（5 条，每条写明"违反时谁受损"）

### 2.1 规则一：基准口径必须在测量前由**多方预先签署**，测量后不得单方面修改

**具体要求**：
- 冻结四件事：**commit SHA、语料（逐字节可校验）、脚本（含 sha）、任务集**
- 口径签署 = 至少一名**非基准受益方** + 度量者共同确认（例如：若基准用于论证方案 A，则方案 B 的代言人必须签署该口径）
- 一旦签署，**不得在出数后调整语料/任务/脚本**；若必须调整，则整轮重测并作废旧数

**违反时谁受损**：
- **首要是度量者**：我出的数字会被质疑"是不是你挑的语料"
- **其次是被比较的弱势方案**：口径若单方面偏向一方，另一方在没有证据的情况下被判定劣于对方
- **最终是整个辩论**：token 经济这一支线彻底失效，退化为"谁的主张听起来合理"

---

### 2.2 规则二：任何对比必须**对称** —— 被测双方在同一次会话、同语料、同任务、同轮数下测

**具体要求**：
- **禁止跨会话/跨 commit/跨机器拼对比**（我测 A 在周一、你测 B 在周三，不成对比）
- 允许"同一脚本、同一会话内 A/B 交替跑"（这是唯一的干净对照，我今天用 `__BENCH_DISABLE_SCHEDULER` 验证过这个方法的价值）
- 若技术上无法同会话（如两个方案需要不同部署形态），必须**明确标注这是"跨环境对比"**，且**不得用于最终裁决**，只能作为"待验证假设"

**违反时谁受损**：
- **弱势方案**：跨环境差异（机器负载、缓存、网络）会被归因为"方案本身差"
- **度量者**：我被迫交出一份自己知道不可比的数字，且无法阻止它被引用
- **提出者**：如果一个结论只建立在跨环境对比上，它实际上是**未经证实的主张**，却获得了"实测"的外观

---

### 2.3 规则三：每个数字必须携带**完整溯源身份**，脱离身份的引用视为无效引用

**具体要求**：每条 `ev:bench:<id>` 必须自带：
```
commit: <40 位 SHA>
corpus_sha256: <逐字节>
script: <路径> @ sha256
raw_artifact: <落盘路径>
artifact_sha256: <sha256>
runs: <次数, 每次的原始值>
timestamp: <ISO8601>
env: <OS/CPU/RAM/python/node 版本>
```

**引用规则**：
- 引用方**必须**带上 `ev:bench:<id>` 与至少 `commit + corpus_sha256`
- **任何"实测显示…"而不带 id 的表述，一律视为意见而非证据**
- 若 commit 已前进，旧数据**自动降级为历史参考**，不能用于新架构的裁决（除非新增一次重测）

**违反时谁受损**：
- **后来者**：无法复跑、无法验证，只能选择相信或不信
- **度量者**：无法证明"我测的那版如此"，被动承担架构变更导致的数字失真责任
- **辩论本身**：产生"看起来有证据"的假象（正是人点出的失败模式①的变体）

---

### 2.4 规则四：**不一致必须披露，禁止择一引用**

**具体要求**：
- 连跑 2 次若**除时间戳外不逐字节一致**，必须报告：两次的原始值、差异位置、是否已定位原因
- **禁止**只引用"对我方有利的那次"
- 若差异无法消除（例如计时类指标天然抖动），必须报**分布**（median + min–max + 每次原始值），**且判定以 median 为准、长尾必须同时披露**
- 特别地：**不得把"单次最好值"伪装成"实测值"**

**违反时谁受损**：
- **少数派**：他们可能因一次抖动的不利值而被判负
- **度量者**：我的专业信誉建立在"我的数字可复现"上，择一引用会摧毁它
- **整个辩论**：这直接制造人点出的失败模式③（票决压少数）的一个变体——**用噪声当证据压人**

---

### 2.5 规则五：**测量权与解读权同源，不可剥夺**

**具体要求**：
- 我提交基准时，同时提交**口径限制说明**（这个数在什么条件下不成立）
- 裁决时，若引用我的数字，**必须同时采纳我的限制说明**；若裁决者认为我的限制说明"不重要"，需**书面给出理由**并进入 Phase 3 异议
- **排除我参与的裁决，只在此裁决不使用 token 证据时成立**；一旦使用，我必须有权对引用方式提出异议

**违反时谁受损**：
- **度量者**：我的产出被断章取义，且我无法反驳
- **使用证据的一方**：他们可能基于被曲解的数字做出错误决策，事后归咎于"基准不准"
- **少数派**：如果我把"某方案在 X 条件下更好"报成唯一结论而限制被剥离，少数派的反对会被这个"实测"压掉

---

## 3. 我认为不可接受的裁决方式（2 条）

### 3.1 不可接受：用"多数人赞成该基准口径合理"来压过我的口径异议

**为什么**：token 测量的**有效性不取决于投票，取决于物理事实**（是否同 commit、是否同语料、是否可复跑）。
一个口径不会因为 5 个人说"我觉得可以"而变得密封。

**允许的替代**：若多人认为我的口径有问题，**正确做法是提出一个更密封的口径并要求我重测**——
我接受"重测"，不接受"投票判定我的口径无效"。

---

### 3.2 不可接受：在没有任何 `ev:bench:*` 的情况下，以"业界惯例/论文数字/直觉估算"裁决 token 优劣

**为什么**：
- Memoria 的 token 消耗形态（知识库文档 + 中文教材 + MathJax + 自定义工具集）**没有可直接套用的业界基准**
- "DSH 一般用 X token"这类数字无法回答"Memoria 接 MCP 后省不省 token"
- 一旦允许这种证据，token 经济就从"可测事实"退化成"谁引用权威更熟练"

**允许的替代**：业界数字可以作为**假设来源**（"我们预期省 30%，待测"），
但**不能作为裁决依据**。裁决必须落在 `ev:bench:*`。

---

## 4. 我需要的证据形式（本节最重要）

### 4.1 `ev:bench:<id>` 的最低要求（缺一不认）

| # | 要求 | 校验方式 |
|---|---|---|
| 1 | **同 commit**：被测双方在同一 40 位 SHA 上 | `git rev-parse HEAD` 记入产物 |
| 2 | **同语料**：语料逐字节可校验 | 目录递归 sha256，记入产物 |
| 3 | **同脚本**：脚本带 sha256，且脚本本身也在版本控制内 | 脚本路径 + sha256 |
| 4 | **同任务集**：任务列表显式列出（不是"跑一下看看"） | 任务清单 + 每任务输入 sha |
| 5 | **连跑 2 次一致**：除时间戳外逐字节一致 | 机检 diff（复用我的 `--determinism` 思路） |
| 6 | **原始产物落盘带 sha**：任何人可复跑 | 产物路径 + sha256 + 复跑命令 |
| 7 | **环境记录**：OS/CPU/RAM/runtime 版本 | 产物内附 |
| 8 | **对照组对称**：A/B 在同会话交替，或明确标注跨环境 | 产物内标 `paired: true/false` |

**关于第 5 条的诚实说明**：
token 计数在某些实现下天然抖动（例如工具返回顺序影响上下文拼接）。
若 2 次不一致，**不能就此判基准无效**，而应：
- 报**分布**（每次都列）
- 判定用 median + 披露 min–max
- **禁止**只报有利的一次

我今天在性能测量上已经踩过这个坑：同一版本连跑两次得到 763ms 与 1649ms（差 2.2 倍），
**如果当时只报 763ms 就是选择性报告**。所以第 5 条的真实含义是：
**"要么逐字节一致，要么报完整分布"**，不是"必须一致否则作废"。

---

### 4.2 什么样的"省 token"声明我**不认**

#### (a) 只报输入 token，不报输出 token
**为什么不认**：对话类接口的输出 token 单价通常更高（3–5 倍）。
若方案 A 输入少 30% 但输出多 100%，实际可能更贵。
**必须**：`prompt_tokens` / `completion_tokens` / `total` 三者齐报，并给出**加权成本**（按当前实际单价）。

#### (b) 只报单次，不报分布
**为什么不认**：单次数据无法区分"稳定省 20%"与"平均省 20% 但尾部翻 3 倍"。
**必须**：至少 5 次任务的分布（median + min–max + 每次原始值），或明确声明"仅 1 次，不构成证据"。

#### (c) 换口径对比
**典型形态**：
- A 测"3 轮对话"、B 测"单轮"，然后比较总量
- A 用了缓存预热、B 是冷启动
- A 的任务集是短问题、B 是长问题

**为什么不认**：这是人点出的失败模式①（同源伪多数）在数据层的对应物——
**看起来两组数字，实际口径不同，不能相减**。
**必须**：口径三要素（commit / 语料 / 任务集）完全一致，否则只能标"跨口径参考，不作裁决"。

#### (d) 用"压缩率"代替绝对 token
**为什么不认**："省了 70%"在一个本身很大的基底上没有意义。
**必须**：绝对 token 数 + 压缩率，两者都给。

#### (e) 只测"能不能跑通"，不测"省不省"
**为什么不认**：功能可用性 ≠ token 经济性。二者需分开陈述。
**必须**：明确区分 `functional_pass` 与 `token_delta`。

#### (f) 把工具调用的开销藏在"系统 prompt"里
**典型形态**：新接口把复杂度从 per-call 移到 system prompt，然后只对比 per-call token。
**必须**：报**总 token 账单**（system + tools schema + messages + completions），
而不是只报某个片段。**这是我最警惕的一类，因为它最容易制造"看起来省了"的假象。**

---

### 4.3 我对"业界惯例 / 论文数字"作为证据的态度

**结论：可以作为假设，不可作为证据。**

**理由三点**：

1. **不可比性**：Memoria 的负载是"中文教材知识库 + 公式渲染 + 自定义工具集"，
   业界 MCP 基准（多为英文、代码、短任务）不可直接外推。

2. **不可复跑性**：论文数字背后的语料、模型版本、tokenizer 往往不可获得，
   违反 §4.1 第 2、3、6 条最低要求。

3. **易被滥用**：一旦允许"业界一般省 30%"作为裁决依据，
   那么任何**未实测**的方案都能获得"看起来有理由"的通过权——这正是失败模式②（共享假设伪独立）的温床。

**允许用法**：
- 作为**预期值**写进假设："我们预期 MCP 化后 token 降低 20–40%，待 `ev:bench:xxx` 验证"
- 作为**设计参考**："X 系统的 schema 设计提示我们可以减少 15% 工具描述"
- **但裁决必须落在我们自己的 `ev:bench:*` 上**

**一个我必须提前声明的立场**：
如果最终基准显示"新 MCP 接口在 token 上**没有优势甚至更差**"，
**我会照实报告，且我认为这个结论应当被采纳**——即使架构上它"更优雅""更符合 DSH 能力模型"。
**这正是我作为度量者存在的意义：如果我的结论永远支持改革方向，那我不是度量者，是宣传员。**

---

## 5. 关于失败模式②（共享假设伪独立）—— 我这一支线的具体防护

人点出最隐蔽的失败模式是**共享假设伪独立**：所有人都默认某个前提，于是没人提出错误，表现为共识。

**在 token 经济上，最可能的共享假设是这个**：

> **「MCP 化 / 全量移植 DSH 能力，一定会增加 token 开销（schema 描述、工具签名、上下文膨胀）」**

这个假设**可能对，也可能错**。但危险在于：如果所有人都默认它对，
那么辩论会跳过"实测"，直接进入"如何缓解"——而这个前提从未被检验。

**我的防护提案**：
1. **基准必须同时测量"schema 开销"与"每次调用开销"**，分离呈现
2. 必须有一个**"零新增 schema"的对照**（即：不引入新工具，只改现有文件工具的用法），
   否则无法区分"是 MCP 化导致的"还是"是功能增加导致的"
3. **我不预设结论**：既不假设"MCP 更省"，也不假设"MCP 更费"

**另一个可能的共享假设**：
> 「token 省 = 成本低 = 好」

这也是需要检验的——如果为了省 token 导致正确率下降（例如 schema 简化导致工具误用），
那"省 token"本身就不成立。**所以基准必须同时对"任务成功率"。**

**我明确表态**：我不会在没有任务成功率数据的情况下，单独用 token 数支持任何方案。

---

## 6. 我承诺的（反向约束，免得只有要求没有义务）

1. **我不挑语料**：语料清单在测量前公开，任何人可提出替换
2. **我不藏不利数据**：若实测结果与我预期相反，我第一时间披露
3. **我报全分布**：不报单次、不报最好值
4. **我随产物交限制说明**：明确写出"这个数在什么条件下不成立"
5. **我接受重测**：任何人指出口径问题，我重测，不辩"我觉得没问题"
6. **我不做裁决**：我只提供证据与解读，最终取舍由 Lead 与人决定——
   但**我的解读必须被完整呈现**，不能被裁剪后只剩数字

---

## 7. 一句话总结我的提案

**token 经济必须是可复跑的实测，不是任何人的估算。**

为此需要：**口径三方签署（2.1）→ 对照对称（2.2）→ 溯源身份（2.3）→ 不一致披露（2.4）→ 测量与解读同源（2.5）**。

**最需要防的**：不是有人反对我，而是有人**用我的数字支持我没测过的结论**。
