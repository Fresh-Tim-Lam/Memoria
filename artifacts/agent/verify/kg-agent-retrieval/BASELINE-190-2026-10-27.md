### 3.2 ⭐ 关键模式：**compaction 会让命中率骤降**

| compaction 后的事件 | 命中率 |

- **compaction 后骤降到 61–84%**（前缀被重写）
- **平均 94.17% 是两者的混合**

**⇒ 减少 compaction 次数 = 同时减少 (a) 上下文压力 (b) 缓存失效。这是一举两得的优化点。**

## 6. ⭐ 核心发现：工具结果的重复计费放大系数 = 10.94×

```
tool result 单次合计      : 108,995 token
因后续轮重发而额外付出    : 1,191,874 token
⇒ 放大系数                : 10.94×
```

### 6.1 为什么这是最重要的数字

**第 k 轮加入的工具结果，会在**后续每一轮**重复发送。**

- 一次 `grep` 产生 15,638 token
- 若它在第 4 轮产生，还有 15 轮要重发 ⇒ 真实成本 = **15,638 × 15 ≈ 234,570 token**
- 虽然重发部分大多命中缓存（单价 1/50），但**未命中的部分是 50 倍**

### 6.2 对 0.5.x 的直接含义

| 优化方向 | 单次省 | × 放大系数 | 真实收益 |
|---|---|---|---|
| 工具结果预算（单次上限）| 5,000 tok | 10.94× | **≈ 54,700 tok** |
| 图谱切片（每次少读 3 万）| 30,000 tok | 10.94× | **≈ 328,200 tok** |
| 提高缓存命中（5.8% 空间）| 250,606 × 5.8% | 1×（已计）| ≈ 14,535 tok |

**⇒ 工具结果体量的杠杆是"提高缓存命中"的 22 倍。**

## 7. 对 R8 指标设计的直接输入（我作为 D 方的核心贡献）

### 7.1 数据支持的指标优先级（推翻 Lead 的初步排序）

Lead 在 `ACCOUNT-2026-10-27.md` 里写：
> 「省 token 的收益上限是输入那 34% 里的一部分（约 28%），不是全部」

**我的数据支持这个结论，但进一步细化了"省哪里最有效"：**

| 优先级 | 指标 | 数据依据 |
|---|---|---|
| **P0** | **单次工具结果 token 上限** | grep 单次 15,638 tok（最大），read_document 单次 3,171；**放大 10.94×** |
| **P0** | **轮次数（一次问对）** | 19 轮中峰值轮调用 12 次工具；每多一轮 = 多一次全量 prompt |
| **P1** | **compaction 次数** | 8 次，每次命中率掉到 61–84% ⇒ 减少 compaction 同时省 token + 省缓存失效 |
| **P2** | **prompt tokens 总量** | 4,299,246（是结果，不是原因） |
| **不做** | **提高缓存命中率** | 已 94.17%，天花板 5.8%，杠杆最小 |

### 7.2 "轮次数比 prompt tokens 更值钱"的论证（Lead 要求我论证或证伪）

**Lead 的假设**：输出占 66%，所以轮次数（省输出）比 prompt tokens 更值钱。

**我的数据能证实的部分**：

```
completion 合计: 166,403 token
prompt 合计    : 4,299,246 token
⇒ completion/prompt = 3.87%
```

**但费用上输出占 66%**——因为**单价差 4–8 倍**（输出 4.00/8.00 元 vs 未命中 1.00/2.00 元）。

**⇒ Lead 的假设成立，但机制需要精确表述**：

> **不是「输出 token 多」（它只占 3.87%），而是「输出单价高 4–8 倍」。**
> **减少一次往返 = 省一次 complete 的输出 + 省一轮全量 prompt 的重发。**
> **⇒ 「轮次数」确实是最高杠杆的单一指标。**

**我不能证实的部分**：
- **无法从本次数据得出"少一轮能省多少"**——因为不知道"理想情况下需要几轮"
- **⇒ 需要 A/B 实验才能量化**（这正是 R8 要设计的）

### 7.3 我要否决的指标方案（Lead 要求至少 1 个）

#### ❌ 否决方案：「用总 prompt tokens 作为唯一优化指标」

**理由（三条，都有数据）**：

1. **总 prompt tokens 是"结果"，不是"原因"**
   - 4,299,246 里 **94.17% 是重复发送的缓存命中内容**
   - 压低总数最直接的方式是"减少轮次"——但那不属于该指标
   - **⇒ 该指标无法指导"该改哪里"**

2. **它会被"更好但更啰嗦的回答"反向激励**
   - 若优化后 agent 回答更详细（completion +50%），prompt 不变但**总费用上升**
   - **⇒ 单指标会导致"为了降 prompt 而牺牲答案质量"**

3. **它掩盖了真正的杠杆（放大系数）**
   - 单次工具结果 108,995 token 只占总量 2.5%
   - **但乘以放大系数 10.94× 后 = 1,191,874 token（27.7%）**
   - **⇒ 只看总数看不到"哪一次调用最贵"**

**替代方案**：用 **三元组** `(轮次数, 单次工具结果 max token, 答对率)`，不用单指标。

| **F3** | grep 单次最大 15,638 > read_document 单次最大 3,171 | 若另一会话中 read_document 单次 > 20,000 ⇒ 该结论是会话特例 |
| **F4** | 工具结果放大系数 10.94× | 若 compaction 后旧工具结果不再计费（被 shadow）⇒ 系数应更低，需重算 |
| **F5** | compaction 导致命中率掉到 61–84% | 若那几次低命中是别的原因（如新话题）⇒ 因果不成立 |
| **F6** | 轮次数比 prompt tokens 更值钱 | 若 A/B 显示"减少轮次"不降低成本（因输出单价已包含在单轮里）⇒ 需修正 |
