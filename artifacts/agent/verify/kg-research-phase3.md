### 1.1 取值与消费者

| 持久化 | `graph-settings.js:278` 存进 settings |

**⚠️ 修正阶段 2 的一处说法**：我阶段 2 说"只有 force 一个值"，**不准确**——有 `galaxy` 第二值。
但继续查后确认：**`galaxy` 是纯视觉变体，不是布局**：

### 1.2 加一个布局值的代价（关键接缝已定位）

**接缝是清晰的、低代价的**：
```
app.js:1295   state.graphLayout2d = new MemoriaGraphLayout2D(viewOpts);
app.js:1297   state.graphView2d  = new MemoriaGraphView2D({ layout: state.graphLayout2d, ... });
```
**布局是独立实例、注入视图** ⇒ 加新布局 = 在 `app.js:1295` 按 `graphStyle` 分派，**不改视图代码**。

**新布局必须实现的契约（视图只调这 10 个）**：
```
loadFromEngine(engine)      applyOptions(opts)        bounds2D()
getNode(id)                 nodes                     simLinks
setDragNode(id)             moveDragNode2D(...)       on(evt,fn) / off(evt,fn)
+ 内部 _ensureSimulationRunning()
```

### 1.3 硬约束：**零第三方依赖**

| 项 | 实测 |
|---|---|
| `graph-*.js` 模块数 / 总字节 | **15 个 / 192,357 B** |
| 第三方图库（d3/cytoscape/dagre/sigma/vis-network） | **0 命中** |

⇒ **所有图渲染是手写的**。**建议延续**：新布局也用纯 JS 手写（树布局算法本身简单），**不引入 d3/dagre**

## 2. 🔴 关键发现：现有"分组"对词典型库是失效的

### 2.1 现状机制

`graph-groups.js:83-101` `computeGraphGroups()` 用 **Union-Find 连通分量**分组：
```js
for (const l of links) uf.union(l.source, l.target);   // 只按"有没有边"合并
```
label 取 hub 节点名（`pickHubNode`）。
`graph-layout-2d.js:53` `initialPositionsForGroups()` 按组分 grid 摆位（`groupSpacing: 260`）。

### 2.2 实测：AAA_Vocab 上产出 1 个巨型组

| 指标 | 实测值 |
|---|---|
| 连通分量数 | **2** |
| **最大分量大小** | **132 / 133** |
| 其余分量 | 1 个孤立点 |

⇒ **现有分组在词典型库上等于没分组**（132 个点挤在一个"组"里，grid 摆位无从谈起）。
**这解释了为什么"分组"这个功能存在但用户感受不到。**

**对照多 KP 库**：行政法/ examples 的图结构健康（叶子 35%），连通分量会自然更分散，分组是有效的。
⇒ **同一个失效只发生在词典型库**，与阶段 2 的结论一致。

### 2.3 这意味着什么

> **"域概览"不是新增一个视图，而是"把分组依据从连通分量换成域"。**
> 工作量比想象的小（复用 `initialPositionsForGroups` + `groupSpacing`），
> 但**必须改 `computeGraphGroups` 的分组依据**（或新增一个 `groupMode` 参数）。

### 3.2 为什么建议树布局留 v1（这是我要给的"范围小但能做完"）

**理由（数据支持）**：
1. **多 KP 库**（行政法 contain 21、examples contain 28）：树**有意义**，但他们的图结构**本来就健康**（叶子 35%），
   毛球不是他们的主要痛点 ⇒ 树是"锦上添花"，不是"解痛"。
2. **词典型库**（人的原痛点所在）：contain 边 **0 条**（1 文件 1 KP），**树无骨架可依** ⇒ 树视图在这类库上是 133 个孤立点。
3. **域概览已能解决词典型库的毛球**（133 节点 → 6 个域节点），**树提供不了额外价值**。

⇒ **树布局的收益集中在"不是最痛的那类库"，且在最痛的库上无效** ⇒ 优先级低。

### 3.3 建议的 0.5 范围（最终）

## 12. 🔴 「分组」功能失效（本次阶段 3 的核心发现，单列一节）

### 12.1 事实

`graph-groups.js:83-101` `computeGraphGroups()` 用 **Union-Find 连通分量**分组（"有边就合并"）：

```js
for (const l of links) uf.union(l.source, l.target);   // 只按"有没有边"合并
```

**实测 AAA_Vocab（副本）**：

| 指标 | 值 |
|---|---|

| **最大分量大小** | **132 / 133（99.2%）** |
| 其余分量 | 1 个孤立点 |

⇒ **分组在词典型库上产出 1 个含 132 点的巨型组，分组等于没分。**

**同构问题**：这与 0.4.7 的两个已知问题同源——
- `文档资源附件出生即死`（功能在、路径断）
- `压缩从未被观测到`（机制在、未被触发）
- **`分组功能对词典型库失效`（组件在、算法产出废结果）** ← 本发现

### 12.3 修复方式（0.5 项 ① 的本质）

- 工作量小，但意义不同：**让一个"声称存在"的功能真的可用**

## 13. 「毛球态提示」设计（Lead D5 的额外要求，0.5 第 3 个小项）

### 13.1 目标

不改 `graphStyle` 默认行为（仍 `force`），但当图呈"毛球态"时给**可见的一次性提示**，
让"域概览"这个新能力**可被发现**（对齐"功能在但用户不知道"的教训）。

### 13.2 触发判定（纯数据，不主观）

| 条件 | 阈值 | 依据 |
|---|---|---|
| 最大分组占比 | **≥ 90%** | AAA_Vocab 实测 99.2% |
| 或 reference 占比 | **≥ 95%** | AAA_Vocab 实测 100% |
| （任一命中即触发） | | |

> 两个阈值都来自实测的 AAA_Vocab 边界（99.2% / 100%），留了余地避免误报。

### 13.3 文案 + 位置 + 交互

```
位置：图画布右下角（不遮挡图主体）
文案：「当前知识图谱较密集，可切换到「域概览」查看更清晰的结构」
交互：一个「切换」按钮 → graphStyle 切到 domain；一个「×」关闭（本次会话内不重复）
```

### 13.4 一次性语义

- **会话级一次性**：本会话内已提示过 ⇒ 不再弹（避免每次打开图都打扰）；
- 判定数据每次 build 后重新计算（分组占比可能随数据而变化）；
- 若用户已手动切到过 `domain` 一次 ⇒ 视为已发现，不再提示。

### 13.5 这一条是否为"装饰"

**不是**。理由：本轮反复出现的失败模式是"能力存在但用户不知道"（分组失效、压缩未观测）。
域概览若默认关闭且无任何引导，就会成为**下一个"出生即死"**。这条提示是**发现性兜底**，
与 D5(a)（默认 force）配合：**不改默认，但让新能力可被找到**。
