## 一、一句话结论

压缩之所以"从未被观测到"，根因不是 UI 缺样式，而是**渲染回放层把 `compaction` 事件静默丢弃**（`conversation_messages` 只有 4 个事件分支）。本任务：① 把该事件以 `role:"system"` **按原位置**投影出来（默认关闭，`reference.py` 引用投影逐字节不变）；② 用**与压缩判定同一个实现**（`history_chars(build_history(...))`）给出**字符预算**占用（分子分母都是字符，不与 token 混算）；③ 面板状态格显示「压缩预算 N%」+ 阈值提示 + **已压缩次数**，>80% 转红提示「该压缩还没压缩」。

## 三、根因与修法（关闭条件 3、4）

### 3.1 根因（上一实例查明，本次复核确认）

`conversation_messages()`（原 `history.py:510-553`）遍历事件时只认 4 类：
`USER_MESSAGE / LOOP_END(usage) / ASSISTANT_MESSAGE / TOOL_RESULT` ⇒ **`compaction` 落空**。
压缩摘要只进 `build_history()`（喂 LLM），而面板唯一会话通道 `agent_session_load` 走的就是这个渲染视图
⇒ **UI 永远拿不到压缩信号**。这比"UI 没显示"更准确，也是本任务存在的理由。

### 3.2 修法：**零行号漂移**的薄包装（重要决策）

`history.py:<行号>` 被 `docs/design/dsh-agent-port.md`、`docs/reference/agent-guide/10-*.md` 多处锚定
（如 `:520-523`/`:532`/`:545`）。首次实现就地改签名+docstring 导致 **+17 行，3 条文档锚点立刻失效**
（`test_doc_anchors` 亲测红过）。最终改为：

1. 原函数**整体只改名字**：`conversation_messages` → `_conversation_messages`（`history.py:510`，**行数不变**）；
2. 公开入口 `conversation_messages(kb_path, session_id, *, include_compaction=False)` **追加在文件末尾**（`history.py:724`）：
   - 默认：**原样返回 `_conversation_messages()` 的同一个对象** ⇒ "默认路径逐字节不变"由**结构**保证（不是靠分支写对）；
   - `include_compaction=True`：`_insert_compaction_rows()`（`history.py:693`）按 seq 把系统行**插到原位置**；
3. `__all__ += ["session_context_usage"]` 也在文件末尾（`history.py:663`）——插到上面常量区同样会推位。

**结果**（`git diff --unified=0`）：`history.py` 只有 2 个 hunk —— `@@ -510 +510 @@`（改名，1 行换 1 行）与 `@@ -640,0 +641,130 @@`（末尾追加）。**640 行以上零漂移**，既有文档锚点全部保持有效。

同理，`ui.py` 首版 docstring 扩写 +16 行 → `test_doc_anchors` 红 3 条（`agent_usage_stats` / `agent_session_delete` / `agent_session_rename`）。最终改为：方法体**0 行净增**（docstring 说明压进原有长行、返回处一行带上 `context_usage`），派生逻辑 `_agent_context_usage()` **追加在文件末尾**（`ui.py:2903`）。

### 3.3 压缩行内容（可回放证据）

`_compaction_record()`（`history.py:666`）输出：
`{role:"system", kind:"compaction", seq, covered(=被覆盖事件数), summary_chars, text(兜底)}`；
有效性判据与 `_compaction_plan()` **一致**（空 `shadowed`/空摘要 ⇒ 不投影，避免"回放看到压缩、摘要其实没生效"的假象）。
前端渲染成一条次要色系统行（`agent-panel.js:7233` `systemMessageEl`，不占用户/助手气泡）。

## 五、前端行为（关闭条件 2、3）

状态格（底部 `#status-agent`，即既有 token 用量格）：
- 可见文本 = `token 段 · 压缩预算 62% · 已压缩 2 次`（token 段原样保留，只追加）；
- 悬停明细 = 原有 token 明细 + 「压缩预算 62%（19.8k / 32k 字符）」+「阈值 80%（占字符预算；到点自动压缩早前对话）」+ 已压缩次数/说明 +（>阈值时）「占用已超过压缩阈值…fail-open，提问本身不受影响」；
- **>80%（严格 > `threshold_chars`）**：可见段变「压缩预算 81% · 该压缩还没压缩」且整格转红（`var(--error)`）；未超阈值还原颜色；
- **压缩后占比骤降如实显示**，不做平滑/掩盖；`compacted_times` 是"压缩发生过"的直接证据；
- **刷新时机 = 低频**：载入会话（RPC 响应）+ 每轮结束（复用 `agent_session_load`，无额外请求）⇒ 不轮询、不闪烁；语言切换时随既有 `renderStatusUsage` 重绘、自动换语言；
- 数据未知（旧会话/读盘失败/字段缺席或 `null`）⇒ 不显示预算段、不动 token 段（"未知"而非"0%"）；
- 系统行：压缩发生后**载入/切回该会话**即可回放看到一条「已压缩 N 条旧消息（摘要 M 字符）· 其后对话按摘要继续」（次要色、无气泡框、`data-msg-index` 与 messages 1:1）。

> 说明（如实）：系统行是**回放式**证据（重载后可见）；实时那一轮不会凭空插入一条 DOM 系统行，但**占用 % 与已压缩次数在同一轮结束时就已更新**（骤降可见）——这正是任务要求"可回放 + 已压缩次数"的组合。

## 八、未做 / 未取证 / 风险（如实）

1. **系统行非实时 DOM 插入**：压缩那一轮的实时面板不新增系统行，需重载/切回会话回放可见；占用%与次数在轮末即更新。（若要求实时，需在 `poll` 收尾做 DOM 手术，会破坏 `messages↔气泡 1:1` 纪律，本轮判断不值得。）
2. **未加 CSS 新的视觉规则**：系统行复用 `-agent-msg--assistant`（无框）+ 内联次要色；`app.css` 不在本任务写域，未改。（若设计要独立样式，需另行批准动 css。）
3. **`context_usage` 可为 `null`**：读盘异常时字段存在但为 `null`（前端按未知降级）。而非"整个键缺席"——两者前端都容忍，测试覆盖 `null`。
4. **`session_context_usage()` 读两遍会话文件**（`build_history` 一遍 + 数压缩事件一遍）：口径一致的代价；会话文件为百 KiB 级、每轮一次，实测无感。若将来要省，必须仍以 `history_chars(build_history())` 为唯一口径。
5. **未取证**：真实 Electron 面板里的人眼观感（颜色/截断）、真实长会话触发压缩的端到端截图。逻辑层已由 node 真源码单测 + 后端逐值断言覆盖。
6. **工作区里的非本任务改动**（提交时请勿计入）：`src/memoria/services/agent/ask_stream.py`（R4-3 呼出事件，2026-10-12 遗留）；`docs/reference/i18n-inventory.md` 是 `scan_ui_strings.py` **确定性重生成**；`docs/example/**` 为用户库 churn。
