### 3. 新增知识的“智能链接”：如何避免重复造节点？

这是你最有价值的问题：“怎么让它智能地帮我链接，决定是建新节点还是加入已有节点？”

这正好是 **RAG（检索增强生成）** 的用武之地。作为AI学者，你可以这样设计“维护场景”：

-   **写入拦截器（Hook）**：当你在 `新知识待整理/` 文件夹拖入一篇新论文的精炼文档时，触发一个脚本。
-   **语义指纹计算**：脚本调用本地嵌入模型（如 `BGE` 或 `text-embedding-3-small`），将新文档的“核心数学定义”和“符号集合”转化为向量。
-   **智能决策逻辑（建议代码逻辑）**：
    -   *阈值 > 0.9*：认为这是重复内容，**不建新节点**，而是将新文档作为“补充视角”挂载到已有节点下。
    -   *阈值 0.6 - 0.9*：认为是强关联，自动在 `extend` 或 `prerequisite` 中添加建议链接，并**弹出提醒**让你确认。
    -   *阈值 < 0.6*：确认为全新孤立节点，建议新建文件。

**关于“学习完忘记巩固了谁”**：这在图谱中叫**反向查询**。你不需要自己记，维护脚本每天自动生成一份 **“影响传播报告”** ——当你标记“已学习 梯度消失”时，报告自动提示：“注意，梯度消失 是 残差网络 和 批归一化 的**前置漏洞**，建议今日复习后者以巩固前者的理解。”

### 4. 两种关联的建模（强关联 vs 联想关联）

你的区分非常有洞见，这对应了图论中的**有向边**和**无向边**（或带权边）：

-   **强关联（学习先后/依赖）**：建模为 **有向边 (Directed Edge)**。`A -> B` 意味着你必须先懂A才能懂B。如果出现**环**（A依赖B，B依赖A），这是死锁。脚本应自动检测环并**高亮警告**，这时你必须引入“隐藏假设”或“外部基础”来破环。
-   **弱关联（方法论/思想类比）**：建模为 **无向边或虚线边**。在Mermaid图中画成 `A -.-> B`。这类边**不参与**“前置检测”，但参与“发散联想搜索”。当你在研究某个复杂公式卡住时，可以只查询“弱关联”边，寻找跨领域的类比（比如把梯度下降类比成下山，把注意力机制类比成数据库查询）。

**1. Markdown渲染时的链接识别**

当你渲染一个知识点的Markdown内容时，不能直接用常规的Markdown渲染器把 `[[目标]]` 转成 `<a href="...">`，而是需要自定义渲染逻辑：

```javascript
// 使用 marked.js 或自定义渲染器
function renderMarkdownWithLinks(content) {
    // 1. 先将 [[目标]] 转换为特殊的HTML标签
    const linkedContent = content.replace(
        /\[\[([^\]]+)\]\]/g, 
        (match, targetName) => {
            return `<span class="knowledge-link" data-target="${targetName}">${targetName}</span>`;
        }
    );
    
    // 2. 再交给marked渲染普通Markdown
    return marked.parse(linkedContent);
}
```

**2. 点击事件的监听与处理**

```javascript
// 在知识库浏览器的主容器上监听点击事件（事件委托）
document.getElementById('knowledge-viewer').addEventListener('click', function(e) {
    // 检查点击的元素是否是知识链接
    const linkElement = e.target.closest('.knowledge-link');
    if (!linkElement) return;
    
    // 提取目标知识点名称
    const targetName = linkElement.dataset.target;
    
    // 执行跳转逻辑
    navigateToKnowledge(targetName);
});

function navigateToKnowledge(targetName) {
    // 1. 检查知识库中是否存在该知识点（调用后端API）
    fetch(`/api/knowledge/${encodeURIComponent(targetName)}`)
        .then(response => {
            if (response.status === 404) {
                // 知识点不存在：提示用户创建
                showCreatePrompt(targetName);
                return;
            }
            return response.json();
        })
        .then(data => {
            // 2. 在知识库中添加/打开这个文件（概念上的"添加"）
            // 实际是在界面中新增一个内容面板或标签页
            addKnowledgeTab(targetName, data.content);
        });
}

function addKnowledgeTab(name, content) {
    // 在右侧或下方新增一个内容面板
    // 不是替换当前视图，而是追加
    const tabContainer = document.getElementById('tab-container');
    const newTab = document.createElement('div');
    newTab.className = 'knowledge-tab';
    newTab.innerHTML = `
        <div class="tab-header">
            <span>${name}</span>
            <button class="close-tab">×</button>
        </div>
        <div class="tab-content">
            ${renderMarkdownWithLinks(content)}
        </div>
    `;
    tabContainer.appendChild(newTab);
    
    // 同时记录到"已打开的知识点列表"
    addToOpenedList(name);
}
```

## 核心问题一：智能识别Markdown中的知识点

### 识别什么？

从一篇Markdown文档中，你需要识别以下几类“知识单元”：

| 类型 | 示例 | 处理方式 |
|---|---|---|
| **显式引用** | `[[注意力机制]]` | 直接提取为目标节点 |
| **术语/概念** | "Transformer架构中的自注意力" | 作为潜在节点候选 |
| **数学符号/公式** | `$\frac{\partial L}{\partial w}$` | 提取为公式节点，或关联到所属概念 |
| **人物/论文** | "Vaswani et al. (2017)" | 作为元数据节点 |
| **方法/算法** | "Adam优化器"、"梯度裁剪" | 作为技术节点 |
| **数据集** | "ImageNet"、"SQuAD" | 作为数据节点 |

### 如何识别？（技术实现）

```python
# 识别流程
class KnowledgeExtractor:
    def extract_from_markdown(self, filepath: str) -> dict:
        content = read_markdown(filepath)
        
        # 1. 结构化提取：frontmatter中的显式声明
        frontmatter = parse_frontmatter(content)  # 用户手动标注
        explicit_nodes = frontmatter.get('related', [])
        
        # 2. 正则提取：[[xxx]] 显式引用
        explicit_refs = re.findall(r'\[\[([^\]]+)\]\]', content)
        
        # 3. 实体识别：用NLP模型抽取未标注的术语
        # 选项A：本地轻量模型（如spaCy + 自定义NER）
        # 选项B：调用本地LLM（如Qwen/ChatGLM）做指令抽取
        # 选项C：用正则+词典匹配（高频学术术语库）
        implicit_entities = self.ner_model.extract(content)
        
        # 4. 去重与消歧
        all_candidates = set(explicit_nodes + explicit_refs + implicit_entities)
        
        # 5. 判定：哪些是"已有节点"，哪些是"新节点候选"
        existing = self.knowledge_graph.find_existing(all_candidates)
        new_candidates = all_candidates - existing
        
        return {
            'file': filepath,
            'explicit_links': explicit_refs,
            'implicit_entities': implicit_entities,
            'existing_nodes': existing,
            'new_node_candidates': new_candidates
        }
```

### 具体到“智能识别”的三种策略

#### 策略A：显式优先（用户手动标注）
用户在Markdown中用 `[[概念名]]` 显式标记。系统优先处理这些。
```markdown

---

残差网络解决了[[深度神经网络]]中的[[梯度消失]]问题。
```
- ✅ 最准确，用户完全控制
- ❌ 需要用户主动标注

#### 策略B：智能提取（LLM辅助）
用本地大模型读取Markdown，指令抽取知识点：


#### 策略C：混合模式（推荐）
1. 用户显式标注的 `[[xxx]]` → 最高优先级
2. 用户frontmatter中声明的 `related` → 次优先级
3. LLM抽取的候选 → 低优先级，作为“建议”呈现给用户确认

## 核心问题二：创建连接还是创建新节点？

这是决策逻辑问题。当系统识别出一个候选知识点时，需要决定：

```
候选知识点 C 被识别出来
        │
        ▼
   查询知识库：C 是否已存在？
        │
    ┌───┴───┐
    ▼       ▼
  存在     不存在
    │       │
    ▼       ▼
  关联到   创建新节点？
  现有节点    │
            ├── 是否与某个节点高度相似？
            │   └── 是 → 作为同义词/别名关联
            │   └── 否 → 创建独立节点
            │
            ├── 是否包含其他节点？
            │   └── 是 → 自动建立层级/包含关系
            │
            └── 是否需要用户确认？
                └── 是 → 弹出建议，让用户决定
```

### 决策逻辑的实现（伪代码）

```python
class LinkOrCreate:
    def decide(self, candidate: str, context: dict) -> Decision:
        # 1. 精确匹配
        exact_match = self.graph.find_exact(candidate)
        if exact_match:
            return Decision(action='link', target=exact_match, confidence=1.0)
        
        # 2. 模糊/语义匹配（向量相似度）
        similar_nodes = self.vector_store.search(candidate, top_k=3)
        if similar_nodes and similar_nodes[0].score > 0.85:
            return Decision(
                action='link_as_alias', 
                target=similar_nodes[0],
                confidence=0.85,
                note=f"是否将 '{candidate}' 作为 '{similar_nodes[0].name}' 的别名？"
            )
        
        # 3. 是否可分解为已有概念的组合？
        components = self.decompose_concept(candidate)
        if components:
            # e.g., "多头注意力" = "多" + "头" + "注意力"
            # 建议创建新节点，并自动连接 components
            return Decision(
                action='create_with_relations',
                components=components,
                confidence=0.7,
                note="建议创建新节点，并自动关联到其组成部分"
            )
        
        # 4. 默认：创建孤立节点，等待用户完善
        return Decision(
            action='create_isolated',
            confidence=0.3,
            note="未找到匹配，建议创建新节点，请手动标注关系"
        )
```

```yaml
---
# ===== 必填字段 =====
id: "ddpg"                    # 唯一标识符（小写、连字符分隔，用于URL/跳转）
title: "深度确定性策略梯度"    # 显示名称
aliases:                      # 别名列表（搜索时命中）
  - "DDPG"
  - "Deep Deterministic Policy Gradient"

# ===== 关系字段（强关联） =====
prerequisites:                # 前置知识（必须先学）
  - "mdp"
  - "policy-gradient"
extensions:                   # 扩展/后续应用
  - "td3"
  - "sac"

# ===== 关系字段（弱关联） =====
analogies:                    # 方法论类比
  - "dqnn"                    # 与DQN的类比
  - "pid-controller"          # 与控制论的类比

# ===== 元数据 =====
created: "2026-06-28"
updated: "2026-06-28"
tags: 
  - "强化学习"
  - "连续控制"
  - "深度强化学习"
status: "draft"               # draft | reviewed | mature
---
```

### 关键设计原则

1. **`id`是唯一真理**：所有内部链接使用`[[id]]`，而不是`[[标题]]`。这解决了重名问题。
2. **`title`和`aliases`是搜索的入口**：用户搜索“DDPG”时，编译器查的是`id`和`aliases`字段，而不是遍历全文。
3. **关系字段是图谱的边**：编译器读取这些字段，直接构建节点间的有向边。

## 第二步：编译器的工作流程

当用户在`data/nodes/`目录下新增、修改、删除`.md`文件时，编译器需要执行以下流程：

```
┌─────────────────────────────────────────────────────────────────────┐
│                     Memoria 编译器执行流程                          │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  Step 1: 扫描文件系统                                               │
│  ├── 遍历 data/nodes/ 下所有 .md 文件                              │
│  └── 与上次编译的清单对比，识别新增/修改/删除的文件                  │
│                                                                     │
│  Step 2: 解析每个 .md 文件                                         │
│  ├── 提取 Frontmatter (yaml) 作为结构化元数据                       │
│  ├── 提取正文内容 (Markdown) 作为全文检索素材                       │
│  └── 提取正文中的 [[id]] 引用，归入 "正文引用列表"                  │
│                                                                     │
│  Step 3: 构建知识节点 (Knowledge Node)                              │
│  ├── 将 Frontmatter 中的 id, title, aliases 存入 nodes 表          │
│  ├── 将 prerequisites, extensions, analogies 存入 relations 表     │
│  └── 【关键】正文中的 [[id]] 引用 → 存入 citations 表              │
│      （这个表专门存“正文中提到的其他知识点”，区别于关系字段）        │
│                                                                     │
│  Step 4: 验证与完整性检查                                           │
│  ├── 检查所有引用的 id 是否都存在                                   │
│  ├── 检查是否存在循环依赖（A依赖B，B依赖A）                         │
│  └── 生成警告报告，输出到 memoria_warnings.log                      │
│                                                                     │
│  Step 5: 构建索引                                                   │
│  ├── 创建 id → 文件路径 的哈希映射（O(1)查找）                     │
│  ├── 创建 别名 → id 的哈希映射                                     │
│  ├── 构建全文索引（用于模糊搜索）                                   │
│  └── 构建图谱数据（nodes + edges，供可视化渲染）                    │
│                                                                     │
│  Step 6: 输出产物                                                   │
│  ├── memoria.db (SQLite 数据库)                                    │
│  ├── memoria.graph.json (D3.js 可用的图谱数据)                     │
│  └── memoria.index.json (轻量索引，用于快速查找)                    │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

## 第三步：解决“文本搜索陷阱”——三张表的设计

这是你指出的核心陷阱。普通搜索之所以会导向“引用了该知识点的文件”，是因为**没有区分“节点本身”和“节点被提及”**。

Memoria使用三张表来彻底解决这个问题：

### 表1：`nodes`（知识节点表）
| 字段 | 说明 | 示例 |
|---|---|---|
| `id` | 唯一标识（主键） | `ddpg` |
| `title` | 显示名称 | `深度确定性策略梯度` |
| `file_path` | 源文件路径 | `data/nodes/ddpg.md` |
| `frontmatter` | 完整元数据（JSON） | `{"prerequisites": ["mdp"]}` |

### 表2：`relations`（关系表——强/弱关联）
| 字段 | 说明 | 示例 |
|---|---|---|
| `source_id` | 源节点 | `ddpg` |
| `target_id` | 目标节点 | `mdp` |
| `relation_type` | 关系类型 | `prerequisite` / `extension` / `analogy` |

### 表3：`citations`（引用表——正文中提到的）
| 字段 | 说明 | 示例 |
|---|---|---|
| `source_id` | 提及其他节点的节点 | `ddpg` |
| `target_id` | 被提及的节点 | `policy-gradient` |
| `context` | 上下文片段 | `DDPG基于...` |

### 搜索逻辑的变革

当用户搜索`DDPG`时：

```sql
-- 旧方法（会命中所有提到DDPG的文件）
SELECT * FROM files WHERE content LIKE '%DDPG%';

-- 新方法（精准命中知识点节点）
SELECT * FROM nodes 
WHERE id = 'ddpg' 
   OR title = 'DDPG' 
   OR aliases LIKE '%DDPG%';
```

**结果**：用户只会被导向`ddpg.md`这个知识点的主页，而不是所有提到DDPG的文件。

**反过来**：如果用户想查看“哪些文件提到了DDPG”，可以查询`citations`表，看到`ddpg`被哪些节点引用过。

## 第四步：第二阶段的HTML导入扩展

你的规划非常合理——先支持Markdown，再扩展HTML。这体现了**自底向上、渐进增强**的设计思路。

### HTML导入的挑战

HTML文档（如从网页保存的论文、博客）通常**缺乏结构化Frontmatter**，而且包含大量无关的导航栏、广告等噪音。

### 扩展方案：HTML→Markdown转换器 + 智能解析

```python
class HTMLImporter:
    def import_html(self, html_path: str) -> dict:
        # 1. 清洗HTML（移除导航、广告等）
        clean_html = self.clean_html(html_path)
        
        # 2. 提取核心内容
        content = self.extract_main_content(clean_html)
        
        # 3. 转换为Markdown（用html2text等库）
        markdown_content = html2text.convert(content)
        
        # 4. 智能提取知识点特征
        # - 从标题提取title
        # - 从关键词/标签提取tags
        # - 从引用文献提取related
        frontmatter = self.extract_frontmatter_from_content(markdown_content)
        
        # 5. 生成标准.md文件，写入data/nodes/
        self.save_as_markdown(frontmatter, markdown_content)
```

**注意**：HTML导入不能完全自动化，编译器的职责是：
- 生成一个**高质量的候选.md文件**
- 在UI中展示预览，让用户确认/修改Frontmatter
- 用户确认后，才正式纳入知识库

## 第五步：用户添加新文档的两种模式

| 模式 | 触发方式 | 编译器行为 |
|---|---|---|
| **自动解析模式** | 用户把`.md`文件放入`data/nodes/`，编译器检测到变化 | 自动解析Frontmatter，自动提取`[[id]]`引用，自动更新索引 |
| **引导配置模式** | 用户在Memoria界面点击"新建知识点" | 弹出表单：填写ID、标题、别名、前置知识等。提交后生成标准`.md`模板文件 |

**两者的关系**：
- 自动解析模式适合**批量导入/迁移**已有文档。
- 引导配置模式适合**日常新增**，确保结构化信息的完整性和规范性。
