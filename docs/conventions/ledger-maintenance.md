# 台账维护规范（待办 / 门禁 / 作业登记）

> **用途**：定义 `docs/todo.md`（待办与阶段门禁总表）与 `docs/design/maintenance-jobs.md §5`（维护作业登记表）的**登记、状态语义、收口判据、对账与归档规则**，使台账始终"代码是什么就写什么"，不因缺判据而长期虚开。
> **目标读者**：项目负责人（复核与拍板）；`registrar`（本台账的写者）；任何登记/修订台账条目的 Agent 与人。
> **关联文档**：[meta-rules.md](./meta-rules.md)（规范书写元规则）、[docs-management.md](./docs-management.md)（文档登记与修订记录）、[AGENTS.md](../../AGENTS.md)（单一事实源表与 Agent 职责）、[../design/maintenance-jobs.md](../design/maintenance-jobs.md)（作业登记表）、[../guides/collaboration.md](../guides/collaboration.md)（存疑即停、待评审问题须答复）。
> **状态**：生效中，2026-09-14（首次建立，同日完成首轮对账）；2026-09-16 增补规则 8（上下文预算与已收口条目的清理）。

---

## 0. 为什么需要本规范（问题陈述）

2026-09-14 首轮对账（三路只读核验，`src/**` 逐条取证）发现台账存在三类失真：

1. **已收口但仍开放**：11 条（如 C01/C05/C07/L02/S01/E05/E12/I01/E9/i18n④/E3-durable-flush），代码与产物早已闭环。
2. **描述与代码不符**：7 条（如 C02/C03/C06/C08/L01/E02），其中 C08、L01 的"智能推荐"在代码里是 `disabled` 占位，E02 的表格编辑按钮**无事件绑定**。
3. **内部自相矛盾**：同一文件不同章节状态不一致（§0 与 §7/§8、§12 与 §14 G4 段、`maintenance-jobs.md` §4 与 §5）。

**根因**：把四类性质不同的东西混在同一列状态里——「真开放」「代码完成但验收未闭环」「待评审」「已收口」。其中"代码完成待验收"占比最大，于是表看起来永远开着，读者逐渐不再信任它。

---

## 规则 1：台账是单一事实源，写者唯一

**触发条件**：新增、修改、删除任何台账条目时。

**约束对象**：`registrar`（写者）；其它 Agent 只读。

**规则内容**：
1. 台账的单一事实源只有两处：`docs/todo.md`（待办 + 阶段门禁 + 归档）与 `docs/design/maintenance-jobs.md §5`（维护作业登记）。二者在 [AGENTS.md §1](../../AGENTS.md) 的单一事实源表中登记。
2. 其它文档（设计稿、规范、README）**不得**再维护一份待办状态副本；如需引用，只引用台账条目 ID。
3. 台账变更属于 `registrar` 的权限域；`builder`/`verifier` 只提交证据与建议。

**可验证性**：全仓 grep 状态标记（`⏳`/`🔄`/`💡`/`🔴`），若在 `docs/todo.md` 与 `maintenance-jobs.md §5` 之外出现"任务状态表"，即违反。

**违反后果**：出现并行事实源 → 停止登记，先合并回单一事实源。

---

## 规则 2：状态标记 + 四类分区（不得混装）

**触发条件**：登记新条目或修订既有条目状态时。

**约束对象**：`registrar`。

**规则内容**：

沿用 `docs/todo.md` 头部既有六标记，语义固定为：

| 标记 | 含义 |
|---|---|
| ✅ | **已收口**：有证据锚（见规则 3、4），且不再需要后续动作 |
| 🔄 | **进行中**：已开工，部分达成 |
| ⏳ | **待做**：未开工 |
| 💡 | **方向性**：需求未规格化，无法直接开工 |
| 🔴 | **Bug**：已知缺陷 |
| ⬇️ | **最低优先级** |

在此之上，**每条必须额外归入下列四类之一**，四类不得混装于同一状态列：

| 类别 | 判定 | 允许的标记 |
|---|---|---|
| **K1 真开放** | 未开工或部分开工，后续动作在开发侧 | ⏳ / 🔄 / 💡 / 🔴 |
| **K2 代码完成·验收未闭环** | 代码/产物已齐备，缺真机验收或落盘验收证据 | 🔄（必须注明"验收未闭环"） |
| **K3 待评审** | 设计稿/方案未拍板，动作在评审侧 | ⏳（必须注明"待评审"） |
| **K4 已收口** | 见规则 4 的收口判据 | ✅（必须带证据锚） |

**可验证性**：抽取任意 10 条，检查其状态列是否可无歧义地映射到 K1–K4；"代码已完成但标 ⏳"或"待验收标 ✅"即为违反。

**标注形式**：类别以**行内标注**为准（如 `✅（K4）`、`🔄（K2 验收未闭环）`、`⏳（K3 待评审）`），**不新增表格列**，避免大范围结构变动。

**存量过渡**：本规范生效前登记的条目，由对账分批补齐类别标注；未标注者暂视为 K1，遇对账时补标。

**违反后果**：该条目视为未登记，退回重登。

## 规则 3：证据锚必填（状态变更的前置条件）

**触发条件**：任何条目的状态发生变化（尤其 → ✅）时。

**约束对象**：`registrar`（不得自行编造）；证据由 `verifier` 或执行者提供。

**规则内容**：状态列或紧随其后的括注中，必须给出**可复核的证据锚**，形式限于：

| 证据类型 | 合法形式 |
|---|---|
| 实现证据 | `文件路径:行号`（如 `app.js:11021`、`services/executor.py:31-68`） |
| 产物证据 | 产物路径（如 `scripts/benchmark/maintenance/results/g4-gate-summary-2026-09-09.json`） |
| 评审证据 | 设计文档中"已评审锁定"的状态行 + 决策记录章节 |
| 验收证据 | `[真机]` 项须有落盘记录（`results/**` 或 `artifacts/_audit/**` 的 json/md） |

**禁止**：以"口头确认""对话中说过""应该做了"作为证据；无证据时状态只能停留在 🔄/⏳ 并注明"无落盘证据"。

**可验证性**：抽查证据锚指向的文件/行号是否存在且内容相符。

**违反后果**：无证据的 ✅ 一律回退为 🔄，并在对账报告中记为失真项。

---

## 规则 4：收口判据（什么时候可以标 ✅）

**触发条件**：准备把条目状态改为 ✅ 时。

**约束对象**：`registrar`；由项目负责人复核拍板。

**规则内容**：按条目性质分别满足：

| 条目性质 | 收口判据 |
|---|---|
| 实现类（功能/机制已落地） | 有实现证据锚；涉及读写的另需 `validate_kb` errors=0 或等价断言 |
| 行为类（交互/性能/UI） | 实现证据锚 **+** 验收证据（`[真机]` 必须落盘）；性能类另需 A/B 对照（依 [../design/maintenance-benchmark.md](../design/maintenance-benchmark.md)） |
| 评审类（设计/方案） | 设计文档状态 = 已评审锁定，且其"决策记录/打开问题"章节已逐项拍板 |
| 边界类（确认不做的） | 明确写出"不做 + 理由 + 替代路径"，状态记 ❌ 或 ⏳ 并注明范围 |

**门槛纪律**：K2（代码完成待验收）在拿到落盘验收证据前**不得**升为 ✅；K3（待评审）在拍板前不得视为已决策。

**可验证性**：检查 ✅ 条目能否在 3 步内（状态 → 证据锚 → 文件/产物）自证。

**违反后果**：该 ✅ 撤销，条目退回 K2/K3，并在对账报告中列明。

---

## 规则 5：收口动作（改状态 + 记归档，不物理搬行）

**触发条件**：条目满足规则 4 并通过复核时。

**约束对象**：`registrar`。

**规则内容**：
1. 就地改状态为 ✅，并**补证据锚**（规则 3）。
2. 同时在 `docs/todo.md §10 已完成归档` 新增/追加对应批次的汇总条目（含 ID + 证据锚），使"何时收口、凭什么收口"可追溯。
3. **默认不物理移动原行**（保留 ID 位置与检索性）；仅当某分区**整体收口**时，才将该分区整段移入 §10 并在原处留一行指针。→ **已收口条目改按规则 8 出表**（规则 8 生效后，本条只适用于未收口条目）。
4. 被证伪的条目（描述与代码不符）**不得静默删除**：改描述或改状态，并在对账报告中记录原因。

**可验证性**：抽查任一 ✅ 条目，在 §10 能查到同 ID 的收口批次记录。

**违反后果**：归档缺失 → 该收口视为未完成。

---

## 规则 6：定期对账（台账与现实比对）

**触发条件**：① 每次发布里程碑；② 每月底；③ 用户显式要求；④ 发现"表与代码不符"个案时。

**约束对象**：`registrar` 执行；`verifier` 可独立复核。

**规则内容**：
1. **只读核验**：逐条对 `src/**`、`scripts/benchmark/maintenance/results/**`、`artifacts/**` 取证；**禁止**在对账阶段改代码。
2. **分类产出**：对账报告须给出五类清单 —— ① 已收口但仍开放；② 描述与代码不符；③ 代码完成·验收未闭环；④ 真开放；⑤ 无法判定（❓，须写明缺什么信息）。
3. **产物落点**：`artifacts/_audit/<date>-ledger-reconcile.md`（与既有 `artifacts/_audit/summary.md` 同处）。
4. **处置**：按报告修订台账；修订本身记入 `docs-management.md §4.2` 修订记录。
5. **对账"无法判定"项**：须写明所需信息与责任人，不得留空。

**可验证性**：报告的 ①②类清单是否都能在本次台账修订中找到对应改动。

**违反后果**：台账与报告不一致 → 对账视为未完成。

---

## 规则 7：禁止事项

**触发条件**：登记或修订台账时。

**约束对象**：`registrar`（及任何代办者）。

**规则内容**：以下行为禁止 ——

1. 无证据的 ✅（见规则 3）。
2. 只加不删/只加不收：条目闭口后不更新状态。
3. 混装类别：把"代码完成待验收"写成 ⏳、把"待评审"当作"已决策"。
4. 描述与现状不符：功能描述停留在**设计意图**而非**代码现实**（首轮对账的 7 条均属此类）。
5. 同一事实在两处登记（规则 1）。
6. 把"待真机验收"长期滞留而无验收计划日期。
7. 删除条目以"清除噪音"而不留归档与理由（**已按规则 8 归档的 ✅ 条目不在此列**）。

**可验证性**：抽查最近 20 次台账改动，是否均满足规则 2–6。

**违反后果**：由项目负责人裁定回退，并在对账报告中登记。

## 规则 8：上下文预算与已收口条目的清理

**触发条件**：① 每次台账写入后；② 发布里程碑；③ 用户显式要求清理；④ 体积超预算。

**约束对象**：`registrar`。

**规则内容**：

1. **体积预算**：`docs/todo.md` ≤ **36 KB**、`docs/design/maintenance-jobs.md §5` ≤ 8 KB。台账是每次会话都要被读入的上下文，超限即触发清理。（2026-09-16 首次清理后 `docs/todo.md` 为 32.4 KB。）

2. **台账只写"现状 + 下一步 + 证据锚"，禁写开发流水账**。以下一律不属于台账，属 CHANGELOG / 提交记录：
   - 多轮对话摘要、"2026-09-03 已迁移 A，2026-09-04 又迁移 B…"式的过程追述；
   - "①②③④ 已完成"式的进度罗列、逐文件的迁移清单、逐键的 i18n 键名枚举；
   - 已被后续提交覆盖的中间态描述。

3. **压缩不得丢事实**：条目被压缩后，其中唯一需要长期可追溯的信息应**转移到对应文档**再删——规范进 `docs/conventions/**`、设计进 `docs/design/**`、版本级变更进 [version.md](./version.md) §7 CHANGELOG。**禁止**让某事实只存在于被删掉的台账叙述里。

4. **已收口（K4 / ✅）条目出表**：
   - 单条收口 → 从活动分区删除该行，并把 ID 追加到 §10 的**当日批次行**；
   - 分区整段收口 → 整段删除，§10 记一行并注明分区名；
   - 出表的合法性来自"已在 §10 归档 + git 历史可查（`git log -S <ID>`）"，**不视为**规则 7.7 的"无归档删除"。

5. **归档行格式**（一行一批次，禁止逐条长叙述）：

   ```
   | <日期> | <ID 列表> | <一行汇总> | <证据锚：commit / 文档 / 产物路径> |
   ```

6. **准入与保护**：只有满足规则 4 收口判据的条目才能出表进 §10。**K2（代码完成·验收未闭环）与 K3（待评审）不得因"看起来做完了"被清掉** —— 它们是台账存在的主要理由。

7. **可追溯性下限**：清理后仍须能回答"这个 ID 在哪收口、凭什么收口"，靠 §10 的 ID 列表 + 证据锚 + `git log -S`。

**可验证性**：清理前后各抽取**全部未收口 ID**（⏳/🔄/💡/🔴/⬇️）做集合比对，必须逐条保留、无遗漏；抽查任一被删 ✅ 的 ID，在 §10 或 `git log -S` 中可查到；`wc -c docs/todo.md` 在预算内。

**违反后果**：误删未收口条目 → 立即从 git 历史恢复并在对账报告登记；体积超预算且未清理 → 本次清理视为未完成。
