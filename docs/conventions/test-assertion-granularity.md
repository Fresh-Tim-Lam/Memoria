## 0. 一句话结论

> **这不是"少数几处写坏了"，而是一种遍布 24 个文件、约 560 处的系统性测试风格。**
> 它的价值是真实的（钉住易碎业务契约），**不能一刀切删掉**；
> 但它**押错了粒度** —— 多数断言押在"整行 / 含变量名的字面量"上，而不是"最小可辨识契约点"。
> ⇒ 该修的不是"删断言"，是**加一条可执行的粒度判据 + 一个机检**，让新断言默认押对粒度、
> 旧断言在**变红时**能一眼看出"这是合法重构该同步改"还是"这是真回归"。

## 2. 根因诊断（比 Lead 说的一层更深）

Lead 的定性：**断言绑实现 ⇒ 合法重构被挡；断言绑意图 ⇒ 长期有效**。这个方向对，但我要补一层：

**"绑实现"和"绑意图"之间，还有一档叫"绑契约点"。**

区分三类断言：

| 类别 | 例子 | 是否该保留 | 出问题的机制 |
|---|---|---|---|
| **A. 绑意图/行为**（运行期） | `assert load_ui_settings()["last_kb_path"] == "/old"` | ✅ 该保留 | 几乎不出问题 |
| **B. 绑契约点**（源码里一个**稳定符号**） | `assert "_previewCacheDrop" in js` | ✅ 该保留（见 §4） | 符号改名才红，合理 |
| **C. 绑实现词面**（源码里**整行 + 变量名 + 无关后缀**） | `assert 'syncLog("syncToDisk: 保存成功"); _previewCacheDrop(savePath);' in js` | ⚠️ 该**收窄** | `syncLog` 文案变、`savePath` 改名都红——而这些都**不是**被测契约本身 |

**task-164 撞红的正是 C 类**：
- `syncLog("syncToDisk: 保存成功")` 里的 `syncLog(...)` 是**日志调用**，不是被测契约；
- `savePath`（原 `currentPath`）是**变量名**，合法重构改它就是该红？——不该，因为契约是
  "写盘成功 ⇒ 缓存失效"，不是"必须用某个叫 `savePath` 的变量"。

⇒ **根因不是"碰了源码"，是"断言串进了与契约无关的词面"。**

## 3. 判据（四条，Lead 已批准；主体不含阈值，阈值见 §3.5 实测结论）

> 形式对齐 org.md §2.6 的 B 条款。Lead 已批 B-1/2/3，并**追加 B-4**（机制性根治）。

### B-test-literal-1 源码字面量断言的**粒度上限**

> **凡以"源码 `in` 字符串"形式断言实现，必须断【最小可辨识契约点】，不得断整行 / 函数体全文。**

- **最小可辨识契约点** = 一个**稳定符号**（函数名 / 关键方法调用 / 关键字面量常量名），
  **≤2 个符号**，且**不含与契约无关的前后缀**（不含日志文案、不含局部变量名、不含同行的其它语句）。
- 反例（判违规）：
  - `assert 'syncLog("syncToDisk: 保存成功"); _previewCacheDrop(savePath);' in js` —— 押了
    `syncLog` 文案 + `savePath` 变量名 + 两语句并排，应改成 `assert "_previewCacheDrop(" in js`。
  - `assert 'meta = { hits: 0, lastOpenAt: Date.now(), loadMs: 0, agingStamp: _previewEvicts }' in src`
    —— **5 个符号**，实测真实命中（`test_preview_cache_policy.py:251`）。

### B-test-literal-2 「断整行 / 全文」的豁免要**显式注明**

> **若确有理由断整行/全文（防删除某段无法用符号表达的逻辑），必须在断言同行注释里
> 写明确切理由 + "此断言会因重构而红，届时请同步更新而非删除"**，否则按 B-test-literal-1 论处。

### B-test-literal-3 改源码时，同步改其结构守卫属**义务**

> **改 `src/**` 中任一被结构守卫引用的符号（函数名/变量名/常量名），必须**同一次提交**里
> 同步更新受影响的守卫。**

### B-test-literal-4 ★ **守卫本身必须能被机检发现"是否失效"**（Lead 追加，机制性根治）

> **若守卫引用的符号在 `src/` 里已不存在（被重命名/删除），机检必须报 `FAIL`。**

- **为什么这条最重要**：B-3 说的"漏改"如果只能靠人检查，就永远不会被发现。
  B-4 把"维护滞后"从**人的记性**转成**机器可见的信号** ——
  这也是"不靠人记得同步，靠机检发现守卫指的东西没了"的唯一落地方式。
- 与今晚 `prompt_drift` / `VERSION-NOTE-PUBLISHED` 同一条思路。
- **落地**：`scripts/agent/test_guard_check.py` 的 FAIL 级检查。

### 3.5 阈值：实测结论（**不是先想出来的，是跑出来的**）

Lead 微调了顺序：先定判据主体（不含数值）→ 跑机检拿分布 → 再回填阈值。以下是实测结果。

**全仓实测（404 条源码字面量断言，24 文件）**：

| 判据 | 命中 | 评价 |
|---|---|---|
| 长度 ≥40 字符 | **224 条（55%）** | ❌ **严重误伤** |
| 长度 ≥100 字符 | 13 条 | ⚠️ 仍误伤 |
| **符号数 > 2** | **6 条** | ✅ **精准** |

**决定性反例（同一份数据里同时存在）**：

| 例子 | 长度 / 符号数 | 长度判据 | 符号判据 |
|---|---|---|---|
| `if (window.MathJax?.typesetPromise) { ... }` | **331 字符 / 1 符号** | ❌ 误伤（它是合理的"函数存在"守卫） | ✅ 放过 |
| `return { line: line, col: off + 1, lineStart: off === 0 };` | **58 字符 / 4 符号** | ❌ 放过（太短不报） | ✅ 抓住 |

⇒ **长度是错的代理指标，符号数才是对的。**
**长度降级为"辅助信号"**（只用于报告排序、帮人定位），**不单独判违规**。
阈值 `MAX_CONTRACT_SYMBOLS = 2` 直接来自 B-test-literal-1 的原文，不是拍的。

**符号数分布**（224 条超长里）：0 符号 74 条 / 1 符号 120 条 / 2 符号 24 条 / 3 符号 3 条 / 4 符号 2 条 / 5 符号 1 条。

|---|---|---|
| `test_display_preload.py` | 每类失效触发点都调用 `_previewCacheDrop` | **保留意图**，但把整行断言**收窄为符号断言** |

| `test_agent_panel_token.py` | 大量 UI 结构（函数定义、类名、i18n 键） | **大部分保留**（它们钉的就是"这段代码必须存在"，见下） |
| `test_display_fonts.py` | 字体默认值 + 函数结构 | **保留**（钉的是稳定公开接口） |

### 一个必须说清的区分：**"防删除"是合法诉求，不该被错杀**

`test_agent_panel_token.py` 里 `assert "function wrapTurn(rec, msgEl)" in src` 这类**断"函数必须存在"**，
钉的其实是"**这个入口不能删**"，因为删了会导致其它模块静默坏。
这是**合理的契约点**（函数名 = 稳定契约），**不该**被"改成行为证据"——行为证据很可能是
"打开面板看到气泡"，那既不精确也难写。

⇒ **B-test-literal-1 的"≤2 个符号"上限，天然覆盖了这类**：`"function wrapTurn"` 是 2 符号，
合法；而 `'const baseMessageElForIndex = messageEl;'`（含变量赋值细节）就超了，应改成
`assert "messageEl" in src`。

## 5. 机检（已实现：`scripts/agent/test_guard_check.py`）

### 5.1 两级判据（Lead 批准：**WARN 不是 FAIL**，但 FAIL 级另有其用）

| 检查 | 级别 | 依据 | 实测（全仓 404 条断言） |
|---|---|---|---|
| **符号已在 `src/` 不存在** | **FAIL** | B-test-literal-4 | **0 条**（当前无失效守卫） |
| **符号数 > 2** | **WARN** | B-test-literal-1 | **6 条** |
| 长度 ≥100 字符 | 辅助信号（仅排序） | — | 13 条 |

### 5.2 为什么 WARN 不是 FAIL（Lead 采纳我的理由）

若把"符号数超标"直接 FAIL，会一次打出大量仓促改动 ——
**"为过门禁而改断言" 会破坏这些守卫原本守住的东西**。
WARN + 豁免注释的组合，让它**长期逐步收窄**，而不是一刀切。

**但"符号失效"必须是 FAIL**：那条不是"风格问题"，是**守卫已经测不到任何东西了**（它永远绿）。

### 5.3 是否进 `team_audit`：**建议先独立，不进门禁链**

Lead 倾向后者，我同意，理由：
- 判据刚立，**WARN 分布还可能调**（阈值/符号提取规则都在实测中改过两次）；
- 若立刻进 `team_audit`，按 org.md §2.6 **B3-c**，它必须同时进 `STEWARD_STANDARDS`，
  否则"门禁判据本身没人审"——而它还没稳定到值得被审；
- **先独立跑（`--strict` 供清债），稳定后再接**。

### 5.4 自检（证红/证绿）

```
[OK] 符号失效 ⇒ FAIL (broken=1)
[OK] 符号数超标 ⇒ WARN (over_symbol=1)
[OK] 合法守卫不误报
== SELF-TEST: PASS ==
```

## 7. 关于"危险动作"清单（Lead 附带要求）

Lead 说 render-perf 在共享工作区 `git checkout -- app.js` 约 90 秒，差点丢掉 sync-mapper 的未提交改动。
这条应进"危险动作清单"。我评估：**该录，且应该是最高优先级的一类**（比"断言粒度"更直接地造成"丢别人的工作"）。

建议条款（供 org.md 或 lead-dispatch-rules.md 采纳）：

```
禁止对他人可见工作区的文件执行 git checkout -- <file> / git reset --hard。
对照实验（pre/post、A/B）一律用 git worktree 或复制到 %TEMP% 的独立副本。
理由：工作区是共享的；checkout/reset 会丢弃他人未提交改动，且无分支历史可回滚。
```

> 这条我**建议直接采纳**（不需要等"评估"），因为它和"断言粒度"正交，且风险等级更高。

## 9. 结论（更新）

**立项已批准，四条判据已定稿，机检已实现并跑出全仓分布。**

三个关键实测结论（都推翻了初版假设）：
1. **长度不是好判据，符号数才是**（331 字符 1 符号 vs 58 字符 4 符号）；
2. **当前 FAIL=0** —— 没有真正失效的守卫，问题不是"守卫坏了"而是"粒度粗"；
3. **与 prompt_drift 不冗余**（交集 5%）。

**真正要改的是粒度**（整行 → 最小可辨识契约点），不是**形式**（源码断言 → 行为断言）。
若只因两个测试红就"把大量源码断言改成行为证据"，会**误杀合理的防删除守卫**，
且"行为证据"在 UI 层往往既不精确又难写。
