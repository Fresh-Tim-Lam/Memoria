# 基准度量协议 · C9「性能预算」口径契约

> 状态：**生效中**（2026-10-19）　｜　协议版本：`1`
> 适用范围：`scripts/benchmark/surface/` 下所有**性能类**读数（当前 = 契约 C9）
> 权威实现：`scripts/benchmark/surface/cdp.mjs` 的 `describeSamples` / `describeRuns` / `runC9Measurement` / `evaluateC9`
> 离线复核：`scripts/benchmark/surface/analyze_c9.py`
> 变更约束：本文件是**方法论契约**。改阈值/改口径 = 改契约 ⇒ 必须在本文件 §11 记一行，并同步 `cdp.mjs` 的 `C9_DEFAULTS` 与 `analyze_c9.py` 的 `NOISE_DEFAULTS`（两处必须逐字一致）。

---

## 1. 这份文档要解决什么

### 1.1 触发问题

8 次 run（同 commit `f4ea83d8`）的 C9 中位数在 **14.0 → 26.2 ms** 之间摆动（1.87×），
而契约预算是 **≤ 16 ms**。若把摆动当噪声，则「26.2 是 14.0 的 1.87 倍」既可能什么都不是，也可能是一次真回归 —— **判据无法给出结论**。
battlemap 因此把「修度量（A0）」排在任何重构之前。

### 1.2 关键结论（先给答案）

用 11 份历史 raw 逐键序列做静态反推（`analyze_c9.py`，过程见 `artifacts/agent/verify/metrics-agent-report.md`）得到：

| 观测 | 事实 | 含义 |
|---|---|---|
| **run 内趋势** | 11/11 次 run 的「后半段均速 / 前半段均速」落在 **0.89–1.09** | run 内**没有**随时间漂移 ⇒ **不是**随机抖动 |
| **run 间差异** | 高/低两组相差 **~1.7×**，且**与 commit 一一对应** | 是**两个可复现的档位**（同一 run 内非常稳定） |
| **离群键** | 每次 run 的「最大 3 键 / 其余键」稳定在 **1.08–1.74** | 存在**固定的批量排队污染** |
| **首键** | 第 1 键恒为 **3.1–4.5 ms**，与其余键的形态完全不同 | 首键测的是另一条路径（冷路径/游标首次落位），**不是稳态** |
| **内部噪声门** | 11 次 run 中 **10 次各自都过** IQR/p95/spread 门 | ⇒ **单次 run 内部是稳定的**；档位差异**不能**用噪声门解释掉 |

► **对 15.8 vs 26.2 的回答（这是本次最重要的一句）**：
**不是同一分布的合理波动。** 两次 run 各自都通过全部内部噪声门（15.8 侧 IQR/median 0.100、spread 0.065；
26.2 侧 0.076 / 0.081），且差异 1.65× 远大于任何一次 run 的内部离散度 ⇒
它落在**运行间**变异的量级上，而这部分变异**只可能**来自环境/commit；本次数据把环境与 commit **混在一起**，故
**单凭「噪声」或「回归」都不能下结论**——正确表述是「**跨运行档位差异，需按 §6.5 的跨 run 复核判定**」。

⇒ **旧度量的三重缺陷**，按影响大小排列：

1. **批量口径（主因）**：`typeText('z'.repeat(30))` 一次性把 30 个键塞进同一事件循环队列 ⇒
   每个键的「keydown→落真源」都含**排在它后面的键**的排队时间。实测「顶 3 / 其余」稳定 > 1，
   且随键数增长会**系统性放大**——所以一次性连发测的从来不是「单键交互时延」。
2. **无 warmup**：第 1 键恒为 3.1–4.5 ms 的异常形态被混进样本（30 键里占 1 个，≈3% 权重，虽小但方向不可控）。
3. **单轮 + 判 single value**：只有一个 median，没有轮间重复 ⇒ **无法把「run 间档位差异」与「run 内测量误差」分开**，
   这正是 1.87× 摆动看起来像噪声的原因。

> 结论：**旧数据不能用来判绿/红，也不能用来断言"是噪声"或"是回归"**。修复的方向不是"多跑几次取平均"，而是**换口径 + 加跨 run 复核层**（§6.5）。

## 2. 铁律（任何施工 agent 都必须遵守）

| # | 铁律 | 违反后果 |
|---|---|---|
| **R1** | **不得一次性连发**：一次按键 = 一个采样单元。按下 → 等这一键在真源侧落定 → 再按下一键。 | 测出来的是批量排队时延，数值随键数线性放大。 |
| **R2** | **必须 warmup** 并**丢弃**：正式采样前打 N 个键，全部不入统计。 | 冷启动/首帧/JIT 混入样本。 |
| **R3** | **必须多轮**：R 轮，每轮各自取 median，再对「轮 median」取中位数（multilevel median-of-medians）。 | 单值判据不可判（本次问题的直接成因）。 |
| **R4** | **判绿/红之前先判噪声**：键间 IQR/median、键间 p95/median、轮间相对极差任一超阈值 ⇒ **inconclusive**。 | 把测量失败误报成"回归"或"通过"。 |
| **R5** | **inconclusive 是度量状态，不是性能状态**。报告/对话**不得**把它表述为「通过」「达标」「失败」「退化」。 | 污染台账与门禁（§6.3）。 |
| **R6** | 报读数时 **n / R / warmup / min / median / p95 / max / IQR / 离散度 / 输入通道** 必须**同时**给出。 | 数字不可复现、不可比较（README「口径边界 2」）。 |
| **R7** | **不得用 `min` 冒充单键成本**。（重复采样同一函数的最小值**只抬高不降低** ⇒ 系统性放松预算。） |
| **R8** | **不得在 `insertText` 内部**插入计时/采样代码（会把自己算进被测对象）。采样只能放"到达前"与"返回后"。 |
| **R9** | 性能读数**必须绑定文档规模**（行数）与**运行环境**；跨档位/跨机器不可直接比较。 |
| **R10** | 改阈值或改口径 = **改契约**：须在 §11 记录，并同步三处实现（`cdp.mjs` C9_DEFAULTS、`analyze_c9.py` NOISE_DEFAULTS、本文件）。 |

## 3. 采样：逐键独立（对应旧缺陷 ①）

### 3.1 受信任输入不变

打字**必须**继续走 CDP `Input.dispatchKeyEvent`（`keyDown` 带 `text` + `keyUp`），
使 Blink 编辑管线产生**真实**的 `keydown` / `beforeinput`（true trusted event）。
**禁止** `el.value=`、`dispatchEvent(new Event(...))`、`execCommand('insertText')` 作为被测输入
（后者仅可用于"对照实验"，且必须在读数里标注为非受信任）。

> **逐键 ≠ 换成非受信任输入**。本次修复只改「发多少键、之间隔多久」，**不改输入通道**。
> 具体的可复现性边界见 §7。

### 3.2 单键协议

```
for each key:
  1. 记 seq0 = perfSeq()                 // 页面侧单调插入计数
  2. typeText('z')                       // keyDown(text)+keyUp
  3. 轮询 perfSeq() 直到 > seq0          // ★只观测，不驱动 ⇒ 不把轮询延迟混进样本
     超时 settleTimeoutMs ⇒ 记 settleTimeouts++，该键不计入样本
  4. 取该键的延迟值（§4）；相邻键之间不插入任何额外 sleep
```

**为什么要「等落定再按下一键」**：这样每个键的排队时间恒为 0，
「keydown→落真源」才真正只包含**这一键**的开销。若不等，就退回旧实现的批量口径。

### 3.3 采样不落在被测区间内

页面侧 `installPerf()` 包裹 `MemoriaEditSync.insertText` 记录时延；`perfSeq()` 只读一个计数器。
**任何**计时/采样代码都不得放进 `insertText` **之内**（R8）——否则测的是"带观测器的实现"。

## 4. 度量定义（对应旧缺陷 ①的量化部分）

### 4.1 旧度量及其代理偏差

旧实现取 `fromKeyMs = t(insertText 返回) − t(keydown)`。
在**同一任务**内这条是真的；但在**跨任务流水**下（渲染/布局/GC 与按键并行）它不是本键独占的时间。
历史数据给出了直接证据：键的显示自由结束时间差 ≈ **3.1–4.5 ms**（= 首键值），
而单键值落在 **13–30 ms** ⇒ **远超**用自由时间解释的份额 ⇒ 是**排队**，不是"多给了时间"。

### 4.2 主口径：`appendMs`（逐键百分位估计）

记事件日志中该键为第 k 个（k 从 0 起），`A_k` = 第 k 键的 keydown 时刻，`E_k` = 第 k 键 `insertText` 返回时刻，`A_0 = T_install`。
实测表明 `A_0 < E_0 ≤ A_1 < E_1 ≤ …`（单调、流水、被测量在窗内非自由完成）。

- 若 `A_k > A_{k-1}`（本键的 keydown 落在**前一键落定之后** ⇒ 两端都可观测），则
  `E_k − A_k` **就是**本键独占耗时（**干净真值**）。
- 若 `A_k ≤ A_{k-1}`（跨任务流水，keydown 被吞进前一键的处理窗口）⇒ 真值不可直接观测，取本会话的**百分位估计**。

**实现（确定性、单调）**：

```
appendMs_k = (1 − q) · (E_k − A_{k-1}),      q = 0.30
D_k        = E_k − A_{k-1}                    // 共享主线程上的连续占用
```

**无偏性论证**：`D_k` 是"这段被测量在共享主线程上实际占用"的连续时间戳证据，占用只能来自有限个被测量（即这些按键）。
故若 `D_k` 的 q 分位为 `d`，则**至少有 (1−q) 比例的键**满足「这一键 ≤ d」。
因此 `quantile(D, q)` 是**单键稳态成本的上界估计**（`percentile(D,q) ≤ percentile(T, 1−q)`）；取 `q = 0.30` 使上界收紧到"约 70% 的键都满足"的强度。

**为什么取固定百分位、而不是「取最小值」**（R7）：重复采样同一函数时 `min` 只随样本量**单调不增前先增**——
因为 `D_k ≥ T_k` 恒成立，取 min 只会向**上**偏，判据随之变**松**。固定百分位在**任意按键数**下口径一致。

> 已知残余：`appendMs` 略**高**（比真值，含 ≤30% 的流水段）。方向明确（保守：更容易判红、更难得绿），故可作为预算判据。
> 关键词：它必须是由 `E−A_{k-1}` 定义的估计量，**不得**换成"取最小"或"取平均后随便扣掉一段"。

### 4.3 对照口径（只用于诊断，**不用于判定**）

`fromKeyMs` 照旧报出（事件循环代理），另报其 `perKeyMin` 作为**上界**参考。
两者方向**相反**（append 偏高、fromKey 偏高更多），二者夹住真值；**判定一律用 `appendMs`**，避免挑口径。

### 4.4 为什么不用 PerformanceObserver / CDP Tracing

- `PerformanceObserver` 看不到「按键 → 真源」的边界（它给的是任务级时长，不是业务语义）；
- CDP Tracing 的时钟与页面 `performance.now()` 不同源，跨源相减会引入不可控偏差；
- 且两者都会**在事件循环上加观测开销**，直接污染被测量。

本协议的估计量**只用页面内同一个 `performance.now()` 时钟**，且采样点只在被测区间之外 ⇒ 零观测开销。

## 5. Warmup 与多轮

### 5.1 warmup（对应旧缺陷 ②）

| 项 | 默认 | 说明 |
|---|---|---|
| `warmupKeys` | **5** | 正式采样前打 5 个键，**全部丢弃**。作用：渲染路径/JIT/首帧/游标首次落位就位。 |

warmup 键**单独记录**在 `counts.warmupSamples`（仅诊断用，**永不进入统计**）。
> 依据：历史数据里首键恒为 3.1–4.5 ms（形态与其余键完全不同），说明"前几次按键"确实走不同的路径。

### 5.2 多轮（对应旧缺陷 ③）

| 项 | 默认 | 说明 |
|---|---|---|
| `rounds` (R) | **5** | 轮数 |
| `keysPerRound` | **10** | 每轮键数 |
| 正式样本量 `n` | **R × keysPerRound = 50** | 每轮连续采样，轮间不重载页面、不切视图 |

**聚合**：`perKey` 对**全部 50 键**求分位（主口径的 perKey 统计）；
`rounds[]` 先算每轮 median，再取「**轮 median 的中位数**」——即 **median-of-medians**。
判据只投在 `median-of-medians` 上（§6.1）。

> 为什么不直接把 50 个键池化取中位？池化会把"某一轮整体变慢"稀释掉；
> 分层（先轮内取中位、再轮间取中位）对**轮级扰动**（如某轮被后台任务打扰）更稳健，且能**直接给出轮间离散度**（§6.2 用它做噪声门）。

## 6. 离散度与判据（对应旧缺陷 ④）

### 6.1 决策序（**先噪声、后预算**）

```
1. 取 primary.perKey  (全部正式键的 appendMs 分布)
   取 primary.rounds  (轮 median 序列)
2. 噪声门：任一条超阈值 ⇒ decision = "gray"(inconclusive)   ← 到此为止
3. 预算判：median-of-medians ≤ budgetMs ? "green" : "red"
```

**顺序不可交换**：先判预算等于"在噪声里挑一个数当结论"，正是旧判据失效的原因。

### 6.2 阈值（`evaluateC9` / `analyze_c9.py` 的 `NOISE_DEFAULTS`）

| 指标 | 定义 | 阈值 | 拦住什么 |
|---|---|---|---|
| `iqrOverMedian` | 键间 `IQR / median` | **≤ 0.25** | 键间离散过大（测量不稳定） |
| `p95OverMedian` | 键间 `p95 / median` | **≤ 1.60** | 少数离群键（GC/后台任务/单次抢占） |
| `roundSpread` | `(max − min) / median`（**轮 median 序列**） | **≤ 0.20** | 轮间不稳定（环境在漂） |
| `minLiveKeys` | 正式键数 `n` | **≥ 20** | 样本不足（不可推断） |
| `deadKeys` | 未落真源/超时的键 | **= 0** | 采样中断（样本有洞） |

**为什么 `roundSpread` 用相对极差而不是 IQR**：R 只有 5，IQR 在 5 点上无统计意义；相对极差与 R、量级都无关，可跨会话比较。

**为什么 p95/median 是必要的**：`iqrOverMedian` 对**少数**离群键不敏感（25%/75% 分位都不动），
而本问题里恰恰存在"顶 3 键"型的少量污染（历史数据 1.08–1.74）。两者互补，缺一不可。

**为什么**用 `p95/median` **而不是** `max/median`（重要）：`max` 分辨不了「少量低幅污染」与「单个孤立离群」——
一次 GC 就能把 `max/median` 顶到与"3 个 26 ms 污染键"同一量级；
而 `p95` 对 3/50 = 6% 的污染**看得见**（`p95/median` 从 1.09 升到 1.50），对 1 个 GC 则**看不见**（这是**期望**行为：
孤立 GC 不属于「键盘→真源」的稳态成本，不该把结论判红）。
反过来，**低幅污染（如 26 vs 14）本身可能不构成度量失效**——它反映真实的排队/热路径差异，
此时判据仍应正常判绿/红，而不是一律 gray。阈值 `1.60` 正是按这个尺度定的（见 §6.2 校准依据）。

**阈值校准依据**（合成实验，见 `metrics-agent-report.md` §4A.3）：
| 情形 | `p95/median` | 判定 |
|---|---|---|
| 干净（±12% 抖动） | 1.09 | green（正确） |
| +3 键 26 ms（≈1.9× 基线的**低幅**污染） | 1.50 | green（污染真实存在但**不足以**判度量失效） |
| +3 键 34 ms（≈2.4× 基线的**高幅**污染） | 1.78 | **gray**（拦下） |
| +1 个 60 ms GC | 1.09 | green（孤立离群被 p95 吸收，符合预期） |

### 6.3 三态语义（R5）

| `decision` | `status` | 含义 | 允许的表述 | 禁止的表述 |
|---|---|---|---|---|
| `green` | `pass` | 低噪声 ∧ 达标 | 「达标（n=50, R=5, median-of-medians=x ms）」 | — |
| `red` | `fail` | 低噪声 ∧ 超标 | 「超标 x ms > 16 ms」 | — |
| `gray` | `inconclusive` | **度量无效** | 「**不确定**：噪声超阈值（原因…），本次读数不作绿/红」 | 「通过」「达标」「失败」「退化」「回退」 |

`gray` 的处置：**重测**（同机、同档位、关掉后台负载），不是"改阈值让它变绿"。

### 6.5 跨 run 比较（A/B、回归检测、门禁必用）

§6.2 的噪声门只回答「**这一次测量本身可信吗**」。它**不**回答「这次比上次慢了，是噪声还是回归」。
这两件事必须分开，否则会出现两种错判：

| 错判 | 表现 | 防护 |
|---|---|---|
| **把真实回归说成噪声** | 单次 run 26.2 ms，被一句"测量有 ±60% 噪声"打发 | §6.5 **跨 run 复核**（本协议强制） |
| **把噪声说成回归** | 单次 run 偶发被后台任务打扰，直接判红并触发返工 | §6.2 噪声门（高频离群已被 p95/median 拦住） |

**跨 run 复核规则**（A/B、改善类改动、门禁收口**必须**执行）：

1. **配对**：A、B 两版各跑 **≥3 次**（不同进程、交替顺序 A/B/A/B/A/B，减少时间漂移混淆）。
2. **单 run 有效性**：任一次 run 自身 `decision=gray` ⇒ 该次作废重测（不进比较）。
3. **点估计**：每版取自身「各 run 的 median-of-medians」的**中位数** `M_A`、`M_B`。
4. **判定**：
   - 两版**中位的中位**之比 `max/min ≥ 1.15` **且** 两版各自的 run 间相对极差都 `< 1.15` ⇒ **可判为真实差异**；
   - 否则 ⇒ **不可判**（差异小于可分辨尺度），**不得**写「回归」或「改善」。
5. **本仓实测校准**（历史 11 份 raw，见报告 §2.4）：同一档位的多次 run 之间比值落在 **≈1.09 以内**；
   跨档位（真实代码差异）为 **1.65–1.89×**。故 `1.15` 是保守阈值——**宁可不判，不误判**。

> 反例（不得再犯）：拿「8 次 run 的中位数摆动 1.87×」当"测量噪声"的依据 ——
> 那 8 次恰恰**分摊在两个不同档位**上（见 §1.2「run 间差异与 commit 一一对应」），
> 把它读成噪声，等于**把真实差异算进了噪声预算**，从而把判据阈值人为撑大。

### 6.6 口径自校验：干净键对账（`cleanKeys`）

若某次会话里出现「本键 `keydown` 落在**前一键落定之后**」的键（记 `d = A_k − E_{k−1} ≥ 0`），则这一键
**独占主线程**，`fromKeyMs` 给出的就是**真值**（单键独立成本，无任何代理偏差）。这类键称**干净键**。

实现上恒有 `appendMs = 0.70·(E_k − A_{k−1}) ≤ fromKeyMs`，故对干净键：

```
fromKeyMs / appendMs = 1 / 0.70 = 1.429        ← 结构恒等式
```

**用途**：`cleanKeys.n > 0` 时，`evaluateC9` 会核对 `cleanMedian / appendMedian` 是否落在 `[1.05, 2.20]`。
这**不是**精度检查（1.429 是恒等式），而是**口径完整性检查**：它能抓住
「重复计时」「键跨越多次 GC」「`arriveT` 未复位导致跨键累计」这类结构性错误。

**能自报真值作为下界**：以干净键的 median 作为 `lowerBoundMs` 报出。
`appendMs` 是上界估计、干净键给真值 ⇒ 二者夹住真实单键成本。

**注意（反直觉但重要）**：CDP 每次 `Runtime.evaluate` 往返都会占用主线程，若在按键之外多抓快照，
会把键间隙撑大从而**人为制造**干净键。因此本协议要求：**采样窗口内除 `measureSeq` 轮询外，不做任何额外页内调用**。

### 6.4 预算来源

`budgetMs = 16`，来自 `docs/design/view-surface-contract.md` §3.3「性能预算」与 §5 C9。
**本协议不改预算**（那是契约的事）；本协议只保证「预算判在哪个统计量上」以及「什么时候**不允许**判」。
阈值集中为**一个** `budgetMs` 常量，禁止在不同文档里出现第二个预算数字。

## 7. 可复现性边界（**必须如实声明**）

| # | 边界 | 影响 | 处置 |
|---|---|---|---|
| B1 | **输入是 CDP 合成的受信任事件，不是物理键盘**——`isTrusted === true`，但事件间隔由本协议决定，不受 OS 输入时序影响 | 这是**优点**（可复现）；但**不能**据此推断真实人手速下的表现 | 报告里写「输入通道：CDP keyDown+keyUp」，不写「真实键盘」 |
| B2 | **逐键轮询引入了 ≤2 ms 的轮间间隔**，且间隔内页面可空转 | 与"连续快速敲键"略有差异 | 间隔**恒定**（sleep 2ms 轮询）⇒ 是稳定偏置，不是随机噪声；且被测量的 `D_k = E_k − A_{k-1}` 定义在**页内时钟**上，与轮询节拍解耦 |
| B3 | `appendMs` 是**上界估计**（偏高 ≤30%） | 判红更严、判绿更难 | 方向固定 ⇒ 可作判据（§4.2）；如需更紧，只能上真 tracing（代价：跨时钟） |
| B4 | `headless=new` + `--disable-gpu` | 与真机有 GPU 合成差异 | README 已声明；跨环境数字**不可**直接比较 |
| B5 | 单机单档位（`scale-5k.md`） | 不能外推到 10k 档 | 引用时必须带行数与档位 |

> **如果将来发现"CDP 逐键"确实无法代表目标场景**（例如需要物理键盘），**不得**硬改口径，
> 而应按 §10 的最小改法（多次 run 取中位的中位）作为**过渡**，并把口径变更记进 §11。

## 8. 报告契约（R6）

任何 C9 读数，**以下字段必须同时出现**（缺一样即视为不可复现）：

```
n, R, warmup,                  // 样本量 / 轮数 / 预热数
min, median, p95, max,         // perKey 分布（主口径 appendMs）
IQR, iqrOverMedian, p95OverMedian,
roundSpread,                   // 轮间相对极差
cleanKeys.n, lowerBoundMs,     // 干净键数 + 单键成本下界（真值，§6.6）
budgetMs, decision,            // 预算与三态结论
docLines, inputChannel,        // 文档规模 + 输入通道
```

**必填的反例**（历史报告犯过）：
- 「median 17.5 ms」——没有 n/R/warmup/离散度 ⇒ 不可复现；
- 「max 46.7 ≤ ?」——把 max 当判据（旧实现用 `max ≤ 16`）⇒ 一次 GC 就红，与性能无关。

机器可读形态见 §9 的 `evidence.measurement` / `evidence.verdict`。

## 10. 迁移（v1 → v2）

| 项 | v1（旧） | v2（本协议） |
|---|---|---|
| 输入 | `typeText('z'.repeat(30))` 一次性连发 | 逐键：按 1 键 → 等落定 → 再按 |
| warmup | 无 | 5 键丢弃 |
| 轮数 | 1（单批） | 5 轮 × 10 键 |
| 主统计量 | `max`（`run_probe.py` 判 `max ≤ 16`） | `median-of-medians(appendMs)` |
| 判据 | `max ≤ 16`（一次 GC 即红）；报告称「预算 ≤16」= 口径漂移 | `median ≤ 16` ∧ 噪声全达标，否则 inconclusive |
| 离散度 | 无 | IQR/median、p95/median、roundSpread |
| 结论 | 二值（绿/红），噪声下不可判 | 三态（green / red / **gray**） |
| raw schema | `surface-probe-raw/1` | `surface-probe-raw/2` |

**旧 raw（v1）的处置**：`run_probe.py` 遇到缺 `evidence.measurement` 的 C9 证据时
⇒ **一律 `inconclusive`**，并在读数里写明「v1 批量口径，不可判」，**绝不**回退到 `max ≤ 16`。

**过渡期最小改法**（若暂时无法跑 v2 探针，例如只有物理键盘环境）：
同一 commit、同机、同档位**连跑 ≥5 次**，对「每次 run 的 median」取**中位的中位**并给出轮间相对极差；
此时 `R = 5, keysPerRound = 30, warmup = 0`，**必须在报告里标注 `warmup=0` 且口径为 v1 批量**，结论至多 `inconclusive`。
