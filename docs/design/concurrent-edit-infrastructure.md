# 人机并发编辑基础设施（Human × Agent Co-editing）

> **状态**：设计稿（2026-10-21），尚未开工
> **触发**：用户提问「memoria agent 和用户同时编辑一个文件的场景，需要什么基础设施」
> **关系**：依赖阶段 2 的 `BlockIndex` / `EditCore`（P4）；本文档定义 P4 之后的能力边界

---

## 0. 一句话结论

**Memoria 已经有 60% 的并发基础设施（乐观并发 + 冲突拒写 + 强制覆盖备份），缺的是最关键的 40%——
「提案化」与「块级合并」。而这 40% 依赖 P4 EditCore 的增量编辑能力。**

## 2. 四种并发模型对比

| 模型 | 体验 | 人的劳动保障 | 自动化程度 | 实现成本 |
|---|---|---|---|---|
| **① 直接写 + 冲突检测**（现状） | agent 直接改盘，人保存时才发现冲突 | ❌ 可能白写 | 高 | 最低（已有） |
| **② 提案化**（推荐主路径） | agent 出块级 diff，人在编辑器逐条接受 | ✅ 人始终掌控 | 中 | 高（依赖 P4） |
| **③ 全自动 + 可撤销** | agent 直接改，一键回滚 | ⚠️ 事后可救 | 最高 | 中（已有 backup） |
| **④ 硬锁** | 一方独占 | ✅ | 低 | 低但**会死锁** |

**推荐**：**② 为主 + ③ 作为"信任模式"选项**。理由：
- MemorIA 定位是"本地优先的知识库"，**用户对库的掌控感 > 自动化流畅度**
- 硬锁（④）明确排除：agent 进程可能崩溃、人可能忘关窗口 ⇒ 死锁不可避免

---

## 3. 四层基础设施（按依赖顺序）

### A. 编辑 lease（不依赖 P4，可先做）

**问题**：现在 `stale_write` 是**写时检测**。人写了几百字，agent 提交，人一保存发现白写。

**设计**：

```
人打开文件 → 前端声明 lease（POST /editing/lease {relPath, ttlMs}）
                    ↓
             服务端记录 {relPath: {holder:'ui', expiresAt, heartbeat}}
                    ↓
agent 要写同文件 → 检查 lease
   ├─ 有活跃 lease → 不写；转为「提案」或排队等人释放
   └─ 无 lease    → 正常写（仍带 version 校验）
```

**关键约束**：
1. **lease 必须在服务端**——agent 是独立进程，不能只靠前端
2. **必须自动过期**（心跳 + TTL，例如 60s 心跳 / 180s TTL），否则人关窗口后 agent 永久受阻
3. **advisory（建议性）而非硬锁**——agent 可以在用户忽略 lease 时仍提议，但**不得静默写**
4. **lease 不替代版本校验**——两者叠加，lease 防"白写"，version 防"覆盖别人的改动"

**不做的**：不做"强制抢占"（人可随时忽略 lease，那时候走 ② 提案或 ③ 撤销）。

### B. 块级 patch 提案（**依赖 P4**）

**核心**：agent 不该"整文件覆盖"，而该出**块级 diff**。

```jsonc
{
  "baseVersion": "sha256:abc...",     // agent 读到的版本
  "patches": [
    {
      "blockId": "K17",                // BlockIndex 的块身份
      "srcLineStart": 42, "srcLineEnd": 55,
      "newText": "...",                // 替换该块
      "rationale": "统一术语"
    }
  ],
  "rationale": "本次共 3 处改动..."
}
```

**前端呈现**：编辑器里对应块显示为「建议改动」（diff 高亮 + 接受/拒绝按钮），**人不点接受就不写盘**。

**为什么块级**：
- `BlockIndex` 已提供块身份与行区间（阶段 1 交付）
- 块级 patch 天然可**逐条接受**，粒度合适
- 整文件 patch 会让人无法判断"到底改了什么"

### C. 双向编辑事件流（**依赖 P4**）

```
人编辑 → onPatched({changedIds}) → 通知 agent（"这几块刚被改了"）
agent 写 → 推送到前端 → 编辑器增量更新（不整篇重载，不丢光标）
```

**阶段 2 已准备好一半**：`onPatched({changedIds})` 是精确的（P1 的 `_pendingChanged:Set`，42 个测试覆盖）。

### D. 块级三方合并（**依赖 A+B+C**，最后做）

```
base:   [A][B][C]
human:  [A'][B][C]     ← 只改 A
agent:  [A][B][C']     ← 只改 C
merged: [A'][B][C']    ← 无冲突，自动合并
```

**同一块**改动才需要人工裁决。这也是块身份的最大价值——**它让"合并"有可判定的单位**。

---

## 4. 推荐的推进顺序

| 阶段 | 内容 | 依赖 | 风险 |
|---|---|---|---|
| **A** | 编辑 lease（服务端，心跳+TTL） | 无 | 低 |
| **B** | 块级 patch 提案 + 前端 diff 接受 | **P4 EditCore** | 高（改编辑路径） |
| **C** | 双向事件流 | **P4 EditCore** | 中 |
| **D** | 块级三方合并 | A+B+C | 高 |

**注意**：B/C/D 都卡在 P4。所以在 P4 之前，**唯一能独立推进的是 A**。

---

## 5. 对 P4 的接口要求（本文档对 P4 的约束）

**P4 EditCore 必须暴露块级增量应用接口**，否则 B/C/D 全部无法实现：

```js
// 必须支持「按块 id 增量应用」，而不是只能整篇 setText
applyBlockPatches(patches: Array<{blockId, srcLineStart, srcLineEnd, newText}>): void
// 用于 agent 写入后的增量更新（不丢光标、不整篇重渲）
```

**验收**：P4 报告中必须有"用 `applyBlockPatches` 改 3 个块后，光标位置不变、其余块 DOM 未重建"的证据。

---

## 6. 已确认的设计裁决（留给后续实现）

| # | 裁决 | 理由 |
|---|---|---|
| R1 | **不实现硬锁** | agent 崩溃 / 人忘关窗口 ⇒ 死锁不可避免 |
| R2 | **lease 在服务端，不在前端** | agent 是独立进程 |
| R3 | **lease 不替代版本校验** | 两者职责不同：lease 防白写，version 防覆盖 |
| R4 | **默认走提案化，不走直接写** | 用户掌控感 > 自动化流畅度 |
| R5 | **patch 必须块级，不得整文件** | 整文件 patch 让人无法判断改了什么 |
| R6 | **合并只在块级做** | 块身份是可判定单位；行级合并会产生无意义的冲突 |

## 7. 未解决的开放问题

1. **lease 的持有者模型**：同一用户开两个窗口，是共享 lease 还是各自独立？（倾向：**按"用户+文件"而非"窗口+文件"**，避免自己和自己冲突）
2. **agent 的"编辑中"感知粒度**：只看 lease，还是也要看"最近 N 分钟内有过 onPatched"？
3. **提案的过期策略**：agent 出的提案基于旧版本，人改过之后提案该自动失效还是重申？（倾向：**标记为"基线已过期，需重新生成"**）
4. **多 agent 并发**：当前 Team 模式下多个 teammate 可能同时改同一文件——**是否需要 agent 之间的 lease**？（倾向：是的，且应复用同一套 lease 机制）
5. **审计口径**：人接受的 agent 提案，审计记录归谁？（倾向：**双记录**——人接受动作 + agent 提案来源）
