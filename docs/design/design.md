## 1. 数据模型

### 1.1 现状梳理（供参考）

**当前 frontmatter 结构**（以 `examples/ddpg.md` 为例）：
```yaml
id: ddpg
title: Deep Deterministic Policy Gradient
provides:                             # 信号A：结构化知识点声明
  - id: ddpg                          #   {id, title, anchor}
    title: Deep Deterministic Policy Gradient
    anchor: ddpg-intro                #   支持文件内锚点定位
prerequisite: [policy-gradient, q-learning]  # 前置依赖
extend: [td3]                         # 扩展关系
tags: [actor-critic, policy-gradient, reinforcement-learning]  # 主题标签
```

**当前 `[:anchor:xxx]` 语法**：正文写 `## 标题 [:anchor:ddpg-intro]`，C++ parser 提取行号存入 index.json 的 anchors 数组，链接 `[[id#anchor]]` 跳转时定位到该行。

**当前向量权重**（embeddings.py 通过重复实现）：
| 信号 | 来源 | 权重 |
|---|---|---|
| provides（A） | frontmatter | 高（重复2次） |
| tags（C） | frontmatter | 高（重复2次） |
| user_added | .build/user_config.json | 高（重复2次） |
| jieba_terms（D） | jieba 正文提取 | 中（1次） |
| cited_ids（B） | 正文 `[[id]]` | 极低（1次） |

### 1.2 已确认的决策

| 项 | 决策 | 说明 |
|---|---|---|
| **最小单元** | **知识点（concept），不是文件** | 一个文件包含多个知识点，每个知识点有独立 id。文件只是"容器" |
| provides + tags 合并 | **合并为 `concepts`** | 有 id=知识点（可被 `[[id]]` 跳转），无 id=tag（纯主题标签） |
| title 字段 | **不保留** | 用核心 concept（权重最高的）的 name 作为展示名 |
| 文件 id | **废弃** | 只有知识点 id，文件用文件名标识。frontmatter 不再有 `id` 字段 |
| anchor 机制 | **废弃** | 每个知识点有独立 id，`[[知识点id]]` 直接跳转，不需要 anchor 定位 |
| 向量编码粒度 | **混合（文件级初筛 + 知识点级精排）** | 文件级向量用于初筛，知识点级向量用于精排到具体知识点 |
| 跳转定位 | **标题匹配** | 跳转按知识点 id 查找；定位正文时用 concept 信息匹配标题。id 不出现在正文中（链接不显示 id，标题也不显示 id） |
| jieba_terms | **移出数据模型** | 分词是搜索内核的实现细节，不是数据模型字段 |
| 路由表位置 | **放 frontmatter** | 严格限制 frontmatter 写在 md 开头，不担心污染 |
| prerequisite/extend | **统一为 edges** | 以知识点为最小单元，不存在"文件级"说法，所有关系都是知识点级 |
| user_config 覆盖层 | **废弃** | 数据源统一在 frontmatter |
| concepts 的角色 | **辅助搜索内核定位 id** | concepts 的 name/weight 帮助搜索内核更好地匹配到正确的知识点 id，但 id 本身不显示在正文中 |

### 1.3 新数据模型

**核心变化**：最小单元从"文件"变为"知识点"。一个文件包含多个知识点，每个知识点有全局唯一 id。文件无 id，用文件名标识。

**frontmatter**（用户配置，直接改 md，严格写在开头）：
```yaml
description: "DDPG是一种连续动作空间的actor-critic强化学习算法"
concepts:                             # 知识点 + tag 统一管理
  - id: ddpg                          # 有 id = 知识点（可被 [[ddpg]] 跳转）
    name: Deep Deterministic Policy Gradient
    weight: 1.0                       # 核心知识点，权重最高，用作展示名
  - id: ddpg-actor                    # 另一个知识点
    name: Actor Network
    weight: 0.7
  - name: actor-critic                # 无 id = tag（纯主题标签，不可跳转）
    weight: 0.5
  - name: policy-gradient
    weight: 0.5
edges:                                # 所有关系统一为 edges（知识点级）
  - type: reference                   # 正文引用（对应 [[文本]]）
    text: "策略梯度"
    targets: ["policy-gradient", "ddpg"]
  - type: prerequisite                # 前置依赖（知识点级）
    targets: ["q-learning"]
  - type: extend                      # 扩展关系（知识点级）
    targets: ["td3"]
```

> 注：
> - 无 title 字段。展示名 = concepts 中 weight 最高的 name。
> - 无文件 id 字段。文件用文件名标识。
> - 无 anchor 字段。知识点 id 全局唯一，`[[id]]` 直接跳转。
> - id 不出现在正文中。链接 `[[策略梯度]]` 显示文本，不显示 id。标题也不含 id。
> - concepts 的 name/weight 辅助搜索内核匹配到正确的知识点 id。

**待选 tag（下栏）**：存 `.build/pending_concepts.json`（工作区状态，不进 frontmatter）

### 1.4 向量编码（混合方案）

**两级向量**：

| 级别 | 粒度 | 用途 | 编码输入 |
|---|---|---|---|
| 文件级 | 一个文件一个向量 | 初筛，快速找到 top-N 相关文件 | description + 所有 concepts 的 name |
| 知识点级 | 每个知识点一个向量 | 精排，从 top-N 文件中定位具体知识点 | concept 的 name + 该知识点相关的正文片段 |

**搜索流程**：
1. 用户输入查询
2. 用文件级向量初筛，找到 top-N 相关文件
3. 在 top-N 文件内，用知识点级向量精排，定位到具体知识点 id
4. 返回知识点 id 列表

### 1.5 向量输入确认

| 向量级别 | 编码输入 | 说明 |
|---|---|---|
| 文件级 | description + 所有 concepts 的 name | 初筛用 |
| 知识点级 | concept 的 name + 该知识点相关的正文片段 | 精排用 |

> description 已在文件级向量（H3 决策隐含确认）。

### 1.6 cited_texts 提取（已定）

**F1 提取进向量**：正文 `[[文本]]` 的文本喂给文件级向量模型（低权重）。
- edges.text 是路由数据（用于跳转匹配）
- 向量输入是语义搜索输入（用于相似度计算）
- 两者不同，[[文本]] 既进 edges.text（路由），也进文件级向量（语义）

## 2. 链接模型

### 2.1 设计原则
- **最小单元是知识点**：每个知识点有全局唯一 id，`[[知识点id]]` 直接跳转。文件只是"容器"。
- **正文 `[[]]` 标注链接位置**：`[[]]` 内是文本，不是 id。文本通过 edges 中 type=reference 的条目关联到知识点 id。
- **关系统一为 edges**：正文引用、前置依赖、扩展关系都是"边"的不同类型，统一用 `edges` 字段管理。
- **同一文本 = 同一跳转**：同一个文本（同文件内）匹配同一个 reference 边。

### 2.2 数据结构

frontmatter 的 `edges` 字段管理所有关系：

```yaml
edges:
  - type: reference                   # 正文引用（对应 [[文本]]）
    text: "策略梯度"                   # 正文 [[]] 内的文本
    targets: ["policy-gradient", "ddpg"]  # 目标知识点 id 列表（支持多目标）
  - type: reference
    text: "DDPG"
    targets: ["ddpg"]
  - type: prerequisite                # 前置依赖（知识点级，无 text）
    targets: ["q-learning"]
  - type: extend                      # 扩展关系（知识点级，无 text）
    targets: ["td3"]
```

正文：
```markdown
根据[[策略梯度]]配比，参考[[DDPG]]实现。
```

### 2.3 边类型与字段

**边的字段**（最终设计）：
- `type`：边类型
- `text`：仅 reference 有，正文 `[[]]` 内的文本
- `targets`：目标知识点 id 列表（**无序集合**，跳转顺序由运行时 LinkTargetQueue 决定）
- **无 source 字段**：源隐式 = 文件本身（边存在哪个文件的 frontmatter，源就是哪个文件）
- **无 id 字段**：边用元组标识，reference 用 `(type, text)`，其他用 `(type, targets)`

**边的方向**：是边类型的语义属性，不是独立字段
- reference：文件 → 目标（正文引用）
- prerequisite：文件 → 目标（文件依赖目标）
- extend：文件 → 目标（文件扩展目标）
- analogy：文件 ↔ 目标（类比，可视为双向）

| 类型 | 有 text | 方向 | 说明 |
|---|---|---|---|
| reference | 是 | 文件→目标 | 正文 `[[文本]]` 引用 |
| prerequisite | 否 | 文件→目标 | 前置依赖 |
| extend | 否 | 文件→目标 | 扩展关系 |
| analogy | 否 | 文件↔目标 | 类比关系 |

### 2.4 三种链接状态（针对 reference 边）

| 状态 | 条件 | 行为 |
|---|---|---|
| 实链接（单目标） | reference 边存在且 ≥1 个目标 | 左键直接跳转 |
| 实链接（多目标） | reference 边存在且有多个目标 | 左键弹窗多选 |
| 虚链接 | 正文有 `[[文本]]` 但无对应 reference 边 | 左键提示"虚链接"，可呼出编辑窗口定向 |

### 2.5 虚链接的成因

- **成因 A**：用户在正文新写了一个 `[[新文本]]`，edges 中还没有该 text 的 reference 边
- **成因 B**：~~edges 条目的目标 id 被删除/改名~~ —— 用户不会直接修改 edges，此情况暂不讨论

> 注：目标 id 失效（如目标知识点被删/改 id）属于 §9 报错机制的范畴。

### 2.6 知识点 id 的全局唯一性

每个知识点 id 必须全库唯一。冲突处理采用 **C3 两者结合**：
- builder 构建时检测冲突，报错页面提示用户改名
- 报错前若用户点跳转，用冗余文件机制兜底（弹窗选哪个文件的知识点）

**后续开发计划**（纳入路线图）：知识点原子级操作
- **删除**：删除某知识点 id，清理全库 edges 中引用它的目标
- **转移**：把知识点从一个文件迁移到另一个文件（id 不变，文件归属变）
- **合并**：两个同义知识点 id 合并为一个，全库 edges 目标联动

### 2.8 边字段设计（已定）

- **无 source 字段**：边存在哪个文件的 frontmatter，源就是哪个文件。方向是类型语义属性，不是字段。
- **无 id 字段**：边用元组标识。reference 用 `(type, text)`，其他用 `(type, targets)`。
- **targets 无序**：edges.targets 是候选目标集合。跳转顺序由运行时 LinkTargetQueue 决定（用户多选顺序 → 排队 → 第一个跳转，其余入顶栏队列；取消后按队首出列）。
- **同一 text 多次出现**：一条边（text 是 key），正文多处 `[[策略梯度]]` 共享同一条 reference 边。

### 2.7 知识点跳转定位

`[[知识点id]]` 跳转时的定位机制：
1. 系统查 frontmatter 找到该 id 所在的 concept 和文件
2. builder 构建索引时，为每个知识点 id 建立映射：id → 正文位置（通过 concept 的 name 匹配标题位置）
3. 跳转时查此映射，滚动到对应位置

**关键约束**：
- id 不出现在正文中（链接 `[[策略梯度]]` 显示文本，不显示 id；标题也不含 id）
- concept 的 name 用于辅助定位（builder 用 name 匹配标题找位置）
- 如果 name 匹配不到标题，跳转到文件开头

## 3. 左键跳转交互

1. 读取 `[[]]` 内文本
2. 查 edges 中 type=reference 且 text 匹配的边
3. **无匹配边**：视为虚链接，提示并可呼出编辑窗口定向
4. **1 个目标**：直接跳转到该知识点 id 所在文件
5. **多个目标**：呼出弹窗允许用户多选
   - 第一个选中的作为跳转目标
   - 其余选中的加入顶栏文件列表（用**队列数据结构**管理此操作，支持中段移除与重排，复用现有 `LinkTargetQueue`）

## 4. 配置窗口 UI

### 4.1 入口
- **顶栏"配置"按钮**：与"构建索引""打开目录"并列。点击打开配置窗口（模态）。

### 4.2 整体布局
- **左侧**：文件资源列表（类似旧审核页面的文件列表），可点击切换配置对象；带"当前文件"按钮快速定位
- **右侧**：配置内容区，纵向三栏

### 4.3 右侧三栏

```
┌─────────────────────────────┐
│ 顶栏：description           │  ← 文件描述（无 id 字段）
├─────────────────────────────┤
│ 上栏：已应用 concepts       │  ← 当前文件生效的 concepts（知识点+tag）
│  [concept1] [concept2]      │
│  [多选] [删除] [下移]       │
├─────────────────────────────┤
│ 下栏：待选 concepts（灰色） │  ← 系统推荐 + 用户手动创建的待选
│  [concept3] [concept4]      │
│  [输入框创建] [解析按钮]    │
│  [多选] [删除] [上移]       │
└─────────────────────────────┘
```

### 4.4 concepts 操作语义

- **下栏 = 待选**，不是"推荐"——因为用户也可以在下栏**手动创建**待选项
- **多选删除 = 彻底删除**（从当前文件的 concept 集合移除）
- **上移 / 下移 = 上下栏调整操作**（上移=采纳到上栏；下移=从上栏撤回到下栏待选）
- **操作流程**：在某一栏多选 → 点"删除"或"上移/下移"

### 4.5 链接编辑入口（双入口）

**入口 1：右键链接 → 下拉菜单 → "编辑此链接"**
- 在正文对链接右键，下拉菜单含"编辑此链接"选项
- 呼出对该链接的编辑面板（针对单个链接）

**入口 2：配置窗口子面板 → 文件资源树选文件 → 通览所有链接**
- 配置窗口内有"链接"子面板
- 选择文件后，列出该文件所有 edges（reference/prerequisite/extend/analogy）
- 点击某条 edge 展开编辑

### 4.6 解析按钮
点击"解析"调用搜索内核，内核内部用 jieba 等手段从正文提取候选，增量合并到下栏待选，不覆盖用户已添加/已应用的项。

## 5. id 修改的联动

文件 id 已废弃，只有知识点 id 需要联动。

### 5.1 知识点 id 修改
- 链接存的是文本，不是知识点 id；知识点 id 修改不影响正文 `[[]]` 文本
- 但 edges 中作为目标的 id 需要全库更新：当某知识点 id 改为 newId 时，扫描所有文件的 edges，把指向 oldId 的目标改为 newId
- builder 的 id → 正文位置映射也要更新
- 复用现有 `replaceLinkIdPreservingText` 的设计哲学：id 隐式，渲染文本不变

## 6. 搜索匹配内核

本系统多处使用搜索匹配（链接编辑、虚链定向、配置窗口加 concept、加链接、文件列表过滤），应封装为统一内核。

**jieba 归入搜索内核**：jieba 分词是搜索内核的实现手段，不是数据模型字段。搜索内核内部用 jieba 提取候选，但结果不作为独立数据模型字段暴露。

### 6.1 封装层级：L2 前后端都封装

**后端封装**：聚合向量相似 + jieba 分词 + 模糊字面匹配，统一原子接口
```python
search(query, scope, limit) -> [{id, name, file, score, source}]
# scope: "file" | "concept" | "all"
# source: "vector" | "jieba" | "fuzzy"（命中来源，便于前端归一化展示）
```

**前端封装**：统一调用入口 + 防抖 + 本地缓存 + 结果归一化 + 多选状态管理

**解耦目的**：后续完善内核（如换 embedding 模型、加分词词典、加同义词扩展）时，不用牵一发而动全身，前后端契约稳定。

## 9. 文件安全与鲁棒性 → 检查功能的报错机制

> 议题：什么行为会导致系统错误？比如用户在外部编辑器删除了 md 某个 `[[]]` 标记。

### 9.1 定位
文件安全问题归入**检查功能的报错机制**，不混入编辑窗口流程。
- 用户点击"检查"（或启动时自动扫描）
- 报错页面列出所有异常项
- 每项可选"修复跳转"或"删除跳转"

### 9.2 待识别的异常类型（草案）

| 异常类型 | 描述 | 修复选项 |
|---|---|---|
| 孤立路由条目 | 路由表有该文本，但正文 `[[]]` 中已无此文本 | 删除该路由条目 |
| 失效目标 | 路由表目标 id 对应的文件不存在（被删/改 id） | 重新定向到其他 id，或删除该目标 |
| 正文虚链 | 正文有 `[[文本]]`，路由表无该文本条目 | 在报错页提示，引导用户去编辑窗口定向 |

### 9.3 待定
- 检查触发时机：仅手动触发 / 启动时自动 / 保存时自动
- 报错页面 UI：列表形式？每项一行带"修复/删除"按钮？
- "修复跳转"的交互：呼出搜索内核让用户选新目标？
