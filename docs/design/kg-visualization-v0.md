## 0. 设计目标与明确的"不做"

### v0 要解决的用户问题（按优先级）

```
Q1 图上"哪个节点更重要"看不出来 —— 现状所有节点半径恒为 6px
Q2 每次打开布局都大变 —— 现状随机初始化 + alpha=1
Q3 134 个标签全画、无避让 —— 标签淹没图形本身
```

### v0 明确不做（每一条都有裁决理由）

```
✗ 3D 里用大小编码重要性  → D-KGV-04：透视 1.78×，叠加人范围最坏表观 3.92×，信号 < 噪声
✗ 内容体量作为 size 模式 → D-KGV-05：node 无 chars 字段；行数判据被 D-KG-07 禁用
✗ 跨会话位置持久化        → D-KGV-07：v1 候选，需先做实验
✗ 12–13 档 / 5 档 / 4 档 → D-KGV-01：均超出人给定范围，物理上不成立
✗ 埋点 node_radius_px     → D-KGV-08：映射产出不是数据，改映射后历史值不可比
✗ labelHover 逐事件埋点   → D-KGV-08：per-frame 写入是性能反模式
```

## 1. 节点大小（D-KGV-01/02/03 已被 D-KGV-13 取代）

### 1.1 范围（人裁决，最高效力）

```
视觉尺寸 = 基准 × [75%, 165%]（线性：半径/直径等比）
基准     = 现状 nodeRadius 常量（当前 6.0px）
⇒ 半径 4.50 ~ 9.90px，跨度 5.40px（直径 9.00 ~ 19.80px）
```

⚠️ **未决（U-KGV-2）**：用户把 `nodeRadius` 设置调到非 6 时（可调范围 4–12），
75%~165% 是随基准缩放，还是仍以 6.0px 为基准？v0 实现按**随基准缩放**，
但此点在 v0 验收时须记录实际行为。

### 1.2 连续变化（人裁决 D-KGV-13，**取代原"3 档"**）

```
★ 节点尺寸【不设挡位】，在 4.50 ~ 9.90px 之间【连续变化】
```

**这条裁决消解了整个 V2 争议**：V2（可辨档数 3/4/5/12–13）建在"人眼能区分几档"这个
**无法实测**的问题上（三方全是经验值，`metrics-baseline` 承认"当前不可判定"并设计了 3 小时判读实验）。
连续映射下**不存在"档"** ⇒ 该问题整体消失：不需要档数、不需要 tiePolicy、不需要判读实验。

**两端可辨性（不需要"单档可辨"）**：
```
直径比 9.90/4.50 = 2.20×；面积比 = 4.84×
⇒ 最大/最小节点差异显著，但【任意相邻节点之间的差异不需要可辨】
   —— 这正是连续设计的目的：不应该有"档"的断层感
```

**反锯齿偏移**：渲染层对所有半径有 **+1.0px 常量溢出**（`ev:bench:kgviz-v2-discriminability`）。
差分类判据不受影响（常量差分抵消），但**绝对直径断言必须加上该偏移**，否则系统性偏 1px。

### 1.3 映射契约（连续，无阈值数组）

```jsonc
{
  "kind": "continuous",              // 冻结：连续映射，不是 quantile 分桶
  "t": "percentile-rank",            // t(d) ∈ [0,1] 单调不减；默认连续分位
  "relative": true,                  // 必须同时在 UI 显示 degree 绝对原值
  "radiusRange": { "min": 4.50, "max": 9.90 }   // 由 基准×[0.75,1.65] 派生
}
// 公式：radius(d) = R_MIN + (R_MAX - R_MIN) · t(d)
// 注意：thresholds / tiePolicy 字段【已删除】—— 连续映射下不存在档与档边界
```

**t(d) 的三个候选与 v0 选择**：

| 方案 | 定义 | 优点 | 代价 |
|---|---|---|---|
| **A 连续分位（v0 默认）** | `t = percentile_rank(degree)` | 人口在半径轴均匀分布，结构性消除长尾，最厚节点仍可达 R_MAX | 半径依赖语料人口 ⇒ 同 degree 跨库半径不同 |
| B 线性归一 | `t = (d-d_min)/(d_max-d_min)` | 半径直接反映绝对差 | 受长尾支配（少数超大 degree 把其余压到极小） |
| C 平方根归一 | `t = sqrt(t_B)` | 折中 | 仍受 d_max 异常值影响 |

**v0 取 A（口径已修正，见下）**：Phase 3 已论证分位在结构上消除长尾、自带上下界
（`arch-contract` 因此撤回「sizeScale 必须」）。连续分位与"分桶分位"的唯一区别是**没有档边界**。

### ⚠️ D-KGV-14 · t(d) 的口径修正（实现时发现的设计缺陷）

> 本文件最初写 `t = percentile-rank`（纯 ECDF）。实现时发现**纯 ECDF 有算术缺陷**：
> 设 degree 分布为 `[1,1,1,2,3]`，ECDF 给出 `t(1)=0.6 / t(2)=0.8 / t(3)=1.0`
> ⇒ **最小值的 t=0.6 而不是 0**（因为 min 本身有并列，占 3/5）⇒ **永远到不了 R_MIN**，
> T-size-4 的范围验收必然失败。

**修正后的口径（v0 冻结）**：
```
t(d) = rank_of_distinct_degree(d) / (n_distinct_degree - 1)
  · 末尾 distinct degree ⇒ t = 1 ⇒ radius = 9.90
  · 首个 distinct degree ⇒ t = 0 ⇒ radius = 4.50
  · 同 degree ⇒ 同半径（并列正确共享半径）
  · 无档位、无取整、无平台
```
**为什么这仍然符合"连续变化"**：连续的本意是「每个不同的 degree 得到各自的半径，端点都取到」，
不是「按 ECDF 累积概率分布」。修正后两端都可达、无平台、单调不减 —— 这才是可验收的连续。

实现位置：`graph-engine.js` 的 `MemoriaGraphSizing`（函数名 `percentileRankT` 是历史命名，
语义已是 distinct-degree 归一化 rank ⇒ 后续小改时重命名为 `normalizedRankT`）。

A 的代价（同 degree 跨库半径不同）由 **tooltip 显示 degree 原值** 兜住；
⇒ **验收必须用同一语料**（见 §7 三元组与 §8 T-census）。

### 1.4 tie（并列）：**已不需要策略**

```
连续映射下：同 degree ⇒ 同半径 —— 这是【正确行为】（相同数据应得到相同视觉结果）
⇒ 原 D-KGV-02 的 tiePolicy 条款【删除】
⇒ 副作用如实记录：并列多的语料会出现大片同半径节点
   这是真实数据结构，不是缺陷；但验收必须报告"distinct 半径数 vs distinct degree 数"
```

### 1.5 必须显示绝对原值（否则凭空创造语义）

本体已定 `reference` 是**无断言跳转** ⇒ 图谱本身没有"重要性"语义。
用分位大小会把"排名"读成"重要" ⇒ **节点 tooltip 必须显示 degree 原值**。

## 2. 3D 视图（D-KGV-04）

```
v0：3D 节点【等大】；重要性/度数用【颜色】编码，不用大小
```

依据：透视造成屏幕尺寸比 **1.78×**（相机距离 1374.88–2447.01，fov 50）；
叠加人给定 2.2× 范围 ⇒ 最坏表观比 **3.92×**；信噪比 ≈ 0.32（信号 < 噪声）。

**成本澄清**：3D 不做大小的理由**不是性能** —— galaxy 已用共享 `SphereGeometry` + `mesh.scale`，
逐节点半径 0 额外几何、0 额外 draw calls。拒绝理由是**语义不可解释**（深度与重要性通道重叠）。

**falsifier**：若 3D 深度判读任务正确率 ≥80% 且归一组显著优于等大组 ⇒ 可撤回。

### D-KGV-16 · 3D 光晕（galaxy halo）也必须等大

```
发现：节点 mesh 已 scale=1（等大），但 galaxy 的 halo（装饰性发光）仍随 degree 变
⇒ 光晕是【表观的尺寸线索】⇒ 若随 degree 变，等于绕过"3D 不做大小编码"的裁决
⇒ 裁决：3D 光晕半径【不随 degree 变化】（统一值，或仅随 zoom 变化）
```

**理由**：D-KGV-04 的裁决依据是"3D 里尺寸通道不可解释（透视 1.78× 混淆）"。
如果 mesh 等大但光晕随度数变大，用户在 3D 里**仍然看到"度数大的看起来更大"** ⇒
该裁决被装饰层绕过。判据必须是【用户在 3D 里是否感知到尺寸差异】，而不是 `mesh.scale === 1`。

## 3. 标签（D-KGV-06）

### 3.1 优先级：可读性前置成立，性能前置不成立

```
✅ 保留：134 个标签无条件全画、无避让 ⇒ 标签淹没大小差 ⇒ 标签必须先做 LOD/避让
✗ 撤回：「标签是 size 的性能前置」
   实测：134 节点下标签开销仅 0.4→0.5–0.6ms（20–33%），占 60fps 预算 3–4%
   "75%" 只在合成 N=3000 时成立
```

### 3.2 v0 取值

```
· 标签避让（碰撞检测 + 优先级：度数高 > 度数低）
· 密度阈值以上隐藏次要标签（悬停显示）
· 不做：逐帧重算布局（会与 §4 的稳定性冲突）
```

## 4. 布局稳定性（D-KGV-07）

### 4.1 v0 承诺（零存储成本）

```
① 确定性种子：同一语料 + 同一种子 ⇒ 每次打开节点坐标【字节级一致】
② 会话内保位：hover / zoom / select 不触发全局 reheat
③ 新节点锚点生长：增量加入的节点在已有邻居附近生长，不重排全局
```

**实测依据**（`ev:obj:D` 真机 5 次）：reset 平均位移 mean **185.6–219.2px**（中位 199.4），
p90 ≈ **398px**，**92.5–97.8% 节点移动** ⇒ 现状确实是"每次都大变"。

### 4.2 v1 候选（不在 v0）

```
跨会话位置持久化。前提实验：重开定位指标 ≤1.5× 首次（C 的 V-07）
⇒ v1 若要做，必须先证明"空间记忆"是真实用户行为，而非推理
```

## 7. 语料身份（D-KGV-12，**必须遵守**）

```
语料身份 = 三元组 ( HEAD sha, manifest_sha256, 测量时间 )
冻结值：HEAD d9341bd1（dirty=true）/ manifest_sha256 a6866c46cab71c43… / 2026-10-26
规模：294 文件（158 md + 136 yaml）；节点 134 / 边 404
build 状态：post_build=true（.memoria/build 产物存在）
```

### 三条硬约束

```
① 禁止再用单一"语料 sha"（旧值 051deb78 无法对应任何可复现状态）
② 该语料【不可从 git 复现】：
   git archive HEAD docs/example ⇒ 61 节点 / 154 边
   当前工作区 AAA_Vocab         ⇒ 134 节点 / 404 边
   方案 1（构造可复现语料）实测不可行（需重建 73 sidecar + 24 md = 重新造数据）
   ⇒ manifest_sha256 是唯一身份；一旦工作区改变，该 manifest 永久失效且无法回滚
③ 判"语料是否一致"看 manifest_sha256，不看 artifact_sha256（后者含时间戳）
```

### 新增事实（修正既有表述）

```
158 个语料 md 中只有 134 个产生 KP，24 个不产生
（Writing 课程笔记 / plan / prompts / reading / question-bank，其中 L9-Part1Summary.md 为 0 字节）
⇒ 「1 文件 1 KP」应表述为：「134 个 KP 文件各占一个 md，另有 24 个无 KP 的库内 md」
```

### build 副作用（残差 A）

```
kb_build 是【破坏性迁移】：kb_build.py#L293-298 strip hints 后 open(full,"w") 写回源 md；
#L312 写回 sidecar。同一副本：build 前 collector 404 边 → build 后 454 边
⇒ 任何边/degree 测量【必须记录 build 状态（pre/post + build sha）】
```

## 8. 验收（可测）

| 项 | 判据 | 失败处理 |
|---|---|---|
| **T-size-1** | 最大 degree vs 最小 degree 节点，用户判断"哪个更大" ⇒ ≥90%（唯一需真人项） | <80% ⇒ 范围不足，需扩大 range |
| **T-size-2** | 单调性（机检）：radius 随 degree 单调不减，无反转 | 有反转 ⇒ 映射实现错误 |
| **T-size-3** | ★连续性（机检）：distinct 半径数 == distinct degree 数（差 ≤ tie 数）；且【无平台】——"相邻 rank 半径差 <0.01px"的连续段占比 ≤5% | 出现平台 ⇒ 说明偷偷分了桶 |
| **T-size-4** | 范围（机检）：运行期 min/max radius 落在 [4.50, 9.90] ± 反锯齿 +1.0px 内 | 越界 ⇒ 范围派生错误 |
| **T-label** | 标签避让后，随机 20 节点中用户读出 ≥16 个标签（80%） | 未达标 ⇒ 加强避让 |
| **T-depth** | 3D：两个深度不同但同 degree 的节点，用户判断"哪个更重要" ⇒ 若 ≥80% 判对 ⇒ 说明用户在把深度误读为重要性 ⇒ 强化"3D 不用大小" | — |
| **T-double** | 【澄清后】检查两视觉通道是否编码**不同变量**或**方向相反**；同变量冗余编码（颜色与大小都编码 degree 且方向一致）⇒ **不视为冲突**（强化而非矛盾） | 有真冲突 ⇒ 二选一 |
| **T-stable** | 同一语料打开两次，确定性种子下节点坐标【字节级一致】 | 不一致 ⇒ 种子未生效 |
| **T-census** | 节点/边数 = 134/404（按 manifest_sha256 校验） | 偏差 ⇒ 失败并报 U-C2 |

**T-size-1 / T-label / T-depth 需要真人参与**（U-KGV-5）⇒ 发布前是否必须完成，待人与 Lead 确认。
**T-size-2/3/4 与 T-census 全部可机检** ⇒ 每次构建都应跑（防"偷偷分桶"）。

> **D-KGV-15（T-double 澄清）**：galaxy 风格同时用颜色与大小编码 degree ⇒
> 这是**同变量冗余编码**，判定为**允许**（冗余强化 ≠ 冲突）。
> 真正的冲突是：颜色编码 A 变量、大小编码 B 变量，或两者方向相反。
> T-double 的实现应检查后者，不应对前者报错。

> ★ **T-size-3 是"连续 vs 分桶"的直接证据**：若实现里其实偷偷按档位取整，
> distinct 半径数会远小于 distinct degree 数，且出现"平台"（大段相邻 rank 半径完全相同）。
> 这是本次连续化裁决唯一需要新增的机检 —— 不用它，"连续"就只是文档上的说法。
