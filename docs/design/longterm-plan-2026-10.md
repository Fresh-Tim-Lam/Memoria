### W0 中期结论（2026-10-22）

**E25 前置调查已完成，结论与裁决**：

- **既有文档图片资产链只吃本地路径**：`image-tools.js:67 startInsertImage` → `select_image_file`（对话框）→ `import_image(local_path)`（`ui.py:857` → `document.py:879`，落 `<kb>/.memoria/images/`，MD5 去重 + registry）→ `insertSourceLine("![alt](<rel>)")`。
- WebView2 剪贴板给的是 `File`/`Blob`，**没有真实路径**；无任何 RPC 接受"图片字节 → `.memoria/images/`"。
- 唯一"字节→落盘"既有 RPC 是 `agent_attach_image`，但它**明确落 `.memoria/agent/attachments/` 且不进图片注册表**（设计上避免被未使用图片清理误伤）⇒ 属对话附件链，**不能复用**。

**裁决：方案 A** —— 放宽写入范围到 `ui.py` / `document.py`，把 `DocumentService.import_image(local_path)` 重构为：

```
_import_image_bytes(name, data)     # 核心：落盘 + MD5 去重 + registry
import_image(local_path)            # 读文件后调核心（保持既有调用方不变）
import_image_base64(name, b64)      # 解码后调核心（新增，供剪贴板用）
```

**硬约束**：① 禁止在新 RPC 里重写落盘/去重/注册表逻辑（那是"第二条链"的开端）；② 保留 MD5 去重命中返回既有路径、registry 登记、相对路径插入、未使用图片清理语义；③ 大小上限 ≤20MB + 非法 base64/扩展名明确拒绝，前端必须显示失败而非假装成功。

**明确否决**：方案 B（复用 `agent_attach_image` 落 attachments 再插 `![]()`）—— 会造成两类图片资产混住 + 绕过注册表；方案 C（不修）—— 用户要求修。

**前端要求**：只在确有图片时 `preventDefault`（纯文本粘贴路径完全不动）；多图按序插入、单张失败不影响其它；插入后光标落到插入点之后；走既有 undo 栈（Ctrl+Z 可撤销）。

### W4.3 第 30 轮：L03「公式也可作为链接被点击」结论**已复核**（结论：属实，且短期不建议实现）

**待复核的原声明**（`docs/todo.md` L03）："解析器视 `[[…]]` 为纯文本、公式为独立原子节点"。

**代码复核（2026-10-23）**：
- `parser.js:222-238`：`[[id|display]]` → `AST.wikiLink(id, display)`，其中 **`display` 是原始字符串**
  （`inner.slice(pipeIdx+1)`），**不走 `parseInline`** ⇒ 加粗/颜色/公式等行内标记在 display 内**一律按纯文本**
- `surface/render-core.js`：wikilink 渲染成 `-wikilink` `<a>`，内容为文本
- 行内公式是**原子 inline**（`contenteditable="false"`，见 render-core 注释），可编辑性依赖该原子性

**⇒ 原声明属实。** 实现"公式作为可点击链接"需要：
1. `wikiLink.display` 改走 `parseInline`（改动小，但会**改变存量文档中 display 的渲染语义** —— 以前 `**x**` 是字面量）
2. 再把公式节点包进 `<a>` ⇒ **破坏"公式是原子 inline"的假设**，影响 `mapper.domToAst` 的节点↔源码映射与编辑落点
3. 还需要处理可访问性（`<a>` 内 `<mjx-container>` 的点击/焦点）与 MathJax 重新排版的交互

**判定**：**不实现（wontfix-by-design）**，理由：
- 收益低（极少有人需要"公式当链接文字"）
- 风险高（改 display 语义会静默改变存量渲染；破坏公式原子性会影响编辑映射）
- 若用户确需，更安全的替代是**在链接旁并列公式**（`[[id]] $公式$`），而非嵌套

**⇒ L03 从"未实现待做"改为"已复核：不实现（记录理由与替代方案）"**，请 todo owner 按此收口。

### W0 第 3 轮观察：E28 的**语义冲突**必须先裁决（现实现自相矛盾）

**这是设计层面的二选一，必须明确后再改**：

| 方案 | 行为 | 代价 |
|---|---|---|
| **A（当前实现）** | `>` / `> ` 视为**字面段落**（用户内容），空引用块不可表示 | 用户敲 `>`+空格能正常输入（修好 E28）；但**存量文档里作为"空引用分隔行"的 `> ` 会从引用块变成普通段落**，渲染变化 |

| **C（折中）** | 解析保持 B，但**输入路径特殊处理**：编辑态下用户刚敲入的 `> ` 不即时当引用块，等用户继续输入非空白字符或失焦时才提交为引用块 | 兼容存量 + 修好输入；代价是输入路径要加状态，复杂度上升 |

**我的倾向：C** —— 因为 A 会静默改变存量文档的渲染（`> ` 空行从引用块变段落），而这类"看起来没变其实变了"的改动最危险；
但 C 需要确认 `EditSync` 是否已有"延迟提交"的位置可用，否则复杂度不可控。

**下一步**：先量化 A 的影响面 —— **统计仓库/KB 里以 `> ` 开头的行有多少**（尤其"整行只有 `>` 或 `> `"的行）。
若存量里几乎没有"空引用行"，A 的风险可接受、直接选 A；若很多，走 C。

**量化结果（2026-10-22）**：`artifacts\_kbwork_perf_edu` + `docs` 共 **137 个 md**，
其中**整行只有 `>` 或 `> ` 的行 = 20 行**，其它引用行 = 1,029 行。

⇒ **方案 A 会让这 20 行从"空引用块"变成"普通段落里的字面 `>` 字符"**（屏幕上真的显示一个 `>` 符号），
视觉上像 markdown 坏了。**因此方案 A 不可接受。**

**新增方案 F（我倾向，成本最低）**：**解析语义不变**（`> ` 仍是空引用块，即方案 B），
把问题定性为**呈现问题**而非法解析问题 —— 空引用行在预览里高度为 0，用户敲空格"看不到任何变化"。
修法：给空引用行一个可见行高（`min-height: 1lh` 或最小 padding），使空格/光标有可见落点。
- 优点：**不改解析语义**（20 行存量渲染不变）、不改输入路径、无存量风险
- 需先验证：真实场景里用户敲的到底是"空引用行里补空格"还是"普通段落里打 `>`"，
  两者修法不同（前者=F，后者=需另议）
- **验证方法**：真机在预览里复现，记录输入前后的 source 与 block 类型变化

**裁决待定项**：A / B / C / F 四选一，需先有真机复现证据（第 4 轮做）。
