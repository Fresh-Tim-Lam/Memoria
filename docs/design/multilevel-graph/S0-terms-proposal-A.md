## 0. 总立场（12 项的共同前提）

1. **图谱是"视图"，不是"数据转储"**：底层 KG（KP + edges + links）是唯一事实源；"多层次/多维度"是**取景层**（视图模型）的属性，不回写数据（U-4/U-5/U-26/U-27）。
2. **语义是断言层的属性**，不是名字/几何/渲染现象（U-1；v0.2 §2.3：`contain_kind=structural` "不承诺整体-部分"）。
3. **最小粒度=知识点（KP）**：层次的形式化落在"KP 集合的嵌套划分"，最深层的块必须是单 KP（U-28）。
4. **2D/3D 是同一渲染契约的两个后端**，不拆设计线（U-33）。
5. **"边存无/类型"是视图相对语义**：同一对节点在不同层/维/上下文可以"显示边/不显示边/显示不同类型"；**视图里没有 ≠ 数据里没有**（U-27/U-17）。
6. 本提案的**定义是"建议裁决"**：需按章程逐项裁决、并集、异议后冻结；未冻结前不得作为实现依据。

## 1. S0-1「语义」

**定义（一句话）**：图谱语境下，"语义"指一条关系**承载可判定的断言**（有谓词、有真值条件、可被消费者当作推理前提），而不是"名字看起来像"、"几何上包含"或"渲染出来了"。

**形式化**：令边 `e=(P, a, b)`，P 为谓词，`Dom(P)×Dom(P)→{真, 假, 未定}`。e 是语义边当且仅当：
- **T1 可命名**：P 可被写出（如 `contain(整体,部分)`、`extend(A,B)`），不是"相关性/相似性"占位词；
- **T2 可真假判定**：存在正文/证据使 P(a,b) 可判真/假（可构造反例），而不是仅由渲染/几何决定；
- **T3 决策绑定**：存在消费者（人/agent）决策 Δ，使 e 的加入可改变结论（可作前提）；
- **T4 非偶然**：e 不因布局、缩放、取景或数据投影偶然产生。

**分类（建议裁决的操作口径）**：
```
semantic      ：T1∧T2∧T3∧T4；v1 允许 = contain_kind=semantic（v0.3 curate_contain，带 assertion_source+curated_by/at）
                 或作者断言型 edge（provenance_state=asserted，谓词可命名）
structural    ：仅 T4 + 几何/层级证据（如 contain_kind=structural）：结构事实，非语义断言
navigation    ：reference（无断言跳转）；co-citation/相似/邻接等派生相似（按 G3 规则不物化为语义）
```
**反例**：
- ✗ "A 的 range 包含 B 的 range" ⇒ 只是结构包含；当作整体-部分语义是 v0.2 明确禁止的读法（v0.2 §2.3）。
- ✗ `reference` 边（无断言跳转）因为"有边且被点击"就算语义（ontology §2.1：reference **不进语义边集**）。
- ✗ 两个 KP 在同一文件/同一标题下、或布局上靠近 ⇒ 语义（属于结构/布局偶然性）。

**边界用例**：
- `extend` 边：有方向但谓词弱；**只有带作者证据（asserted）才计入 semantic**，否则按 navigation/投影处理（本项目假设；S1/S4 细化）。
- 同一对节点同时有 structural contain 与 semantic contain：它们是**同一关系的两种断言状态**，不是两条语义边；视图按 `contain_kind` 择一显示（见 S0-6/S0-12）。
- 8 条已知退化 contain（同名/OCR）不得作为语义证据（G2/G4 冻结名单，B 级）。

**U 映射**：U-1（语义）、U-2（双层价值）、U-10（语义关联）、U-13/U-14（按语义划分）、U-15（语义边挂接）、U-17（防跨图语义污染）、U-27（边存无/类型）。

**建议裁决**：采纳上述定义与 T1–T4 判据；**"语义"一词只用于断言层**，不得用于命名结构包含、布局邻近或渲染现象；产品/agent 消费必须显式区分 semantic / structural / navigation 三类。

**证据等级**：A（U-1/U-17 原话；ontology §2.1、v0.2 §2.3 明文）+ **本项目假设**（T3 决策绑定作为操作性判据的严格程度）。

## 2. S0-2 层次（level）与最小粒度

**定义（一句话）**：层次是**同一知识库上 KP 集合的嵌套划分**；第 ℓ 层的"显示节点"是划分块，最深层（最细层）的块是单个知识点。

**形式化**：设知识库的 KP 集合 `K` 有限。
```
层 ℓ ∈ {0,1,…,L}；划分 Π_ℓ 是 K 的不交非空子集族，⋃Π_ℓ = K
显示节点集 V_ℓ = Π_ℓ（每个块一个节点）
嵌套（细化）：Π_{ℓ+1} ⪯ Π_ℓ，即 ∀B'∈Π_{ℓ+1}, ∃B∈Π_ℓ: B'⊆B
最小粒度层：Π_L = {{k} | k ∈ K}（所有块都是单 KP）
深入一层：块 B∈Π_ℓ → 查看它在 Π_{ℓ+1} 中的细化块集合
全展开：Π_L（所有 KP 可见）
```
**反例**：
- ✗ 一个"节点"不对应 K 的任何子集（如"一次搜索命中的若干 KP 集合"）⇒ 它不是层节点，而是**维度/取景产物**（S0-3/S0-6）。
- ✗ 句子/段落/概念作为 KP 之下的新层 ⇒ v1 不允许（U-28：最小粒度=KP 毋庸置疑；更深层只保留位置，由 S1/S10 研讨）。
- ✗ 层间不嵌套（同一层既有整文件簇又有若干散 KP，同时声称"进入下一层"却不细化）⇒ 非法层。

**边界用例**：
- 某层划分允许大小为 1 的块（KP 直接显示）；这是合法划分，但**默认视图不得整体退化为全展开**（U-5/U-26；默认层应尽量有聚合，具体视觉/算法属 S2/S3）。
- KP 身份用 `kp_id`（非名字）：同名不同 id 的 KP 必须作为不同块元素（G4 E-IDEA-010）。
- 深于 KP 的层次：v1 只登记"开放槽位"，不实现、不进入视图模型（U-25/U-28）。

**U 映射**：U-4（多层次）、U-5（非全展开）、U-6（代表子图节点）、U-8（层次维度）、U-26（默认替代/全展开开关）、U-28（最小粒度）、U-29（agent 设计 KP）。

**建议裁决**：采纳"嵌套划分"形式化；`L` 由算法/数据决定但**最深层固定为单 KP 层**；"更深层"（句/概念）作为**开放槽位**登记，不在 v1 实现；层的划分必须可复算、可回溯来源（S2/S6 细化存储与缓存，S0 只要求可复算/可解释）。

**证据等级**：A（U-4/U-5/U-8/U-28 原话）+ **本项目假设**（用"划分"而非"缩放级别"来形式化层次；需 S1/S2 复核）。

## 3. S0-3 维度（dimension）

**定义（一句话）**：维度是在**同一层次**上改变"取哪些节点/边、沿什么关系扩展、扩展几步"的取景规则；它不是粒度本身，也不是视觉风格。

**形式化**：
```
维度 D = (id, scope_fn, edge_sources, direction, default_hops, termination, priority, status)
视图坐标 = (ℓ, D, focus f, 预算 B)
View = Select(Π_ℓ, D, f, B)          # 同一数据源，不同取景函数
已指定维度（本场建议）：
  H = hierarchy      ：高层用 Π_ℓ 的块节点 + 结构边（contain structural）
  A = association    ：在当前视图上按语义边挂接一跳/有限跳（U-10/U-11/U-15）
开放槽位：其他维度（时间/引用链/前置依赖…）只登记 {id, 定义草案, 边源, 默认跳数, 终止条件, 状态=reserved, owner, U-ref}
"全展开"不是维度，是模式开关（S0-8）
```
**开放槽位登记规则（U-25）**：`status=reserved` 的维度**不得出现在视图模型/产品代码**；转 `specified` 必须经 S1 章程 + Lead 裁决 +（若涉契约）人批；每槽位必须写"若实现，边源/跳数/终止"三要素，否则登记无效。

**反例**：
- ✗ 把 `graphStyle`（force/galaxy）当维度：那是**视觉风格**，不改变取景集合（现有代码 A 级证据）。
- ✗ 把"按文件分组/搜索过滤"直接叫维度：除非按上表登记并说明边源与终止条件。
- ✗ 未经登记私加"时间维度"并进入产品（违反 U-25 的"先留槽位"）。

**边界用例**：
- 层次与关联的组合顺序：**层次先定基座（Π_ℓ），关联只做增量挂接**（本项目假设；顺序/可交换性由 S1 验证）；不得反向用关联结果重定义层次。
- 关联维度在最小层（KP 层）：允许——此时基座已是单 KP，关联挂接一跳（S0-5）。
- 同一视图引用两个关联维度：v1 只允许一个关联维度生效（优先级表由 S1 定），避免预算叠加不可解释。

**U 映射**：U-8（层次维度）、U-9（其他维度）、U-10（关联维度）、U-11（跳数）、U-12（更多维度）、U-25（开放槽位）、U-30（关联维度定义）。

**建议裁决**：采纳"维度=取景规则"定义；v1 只指定 `H` 与 `A` 两个维度 + 开放槽位注册表；留槽 = 文本登记，不实现；全展开是模式而非维度。

**证据等级**：A（U-8..U-12/U-25/U-30 原话；graph-settings/graphStyle 事实）+ **本项目假设**（组合顺序、单关联维度限制）。

## 4. S0-4 簇 / 代表连通子图

**定义（一句话）**：簇是 KP 集合上一个**语义内聚、与外部只有零星桥接**的子集，用作粗层显示的代表节点；它不是严格连通分量（不要求内部连通，也不要求外部无边）。

**形式化**：设 `C⊆K`，`E_sem` 为语义边集（S0-1），`E(C,K\C)` 为跨边界边。
```
内聚：μ(C) = 语义内边数 / 可能对数（或等价归一化内聚度）≥ τ_coh
桥：β(C) = |E(C,K\C)| / (|E(C)| + |E(C,K\C)|) ≤ τ_bridge（或桥数 ≤ b）
簇 = μ(C)≥τ_coh ∧ β(C)≤τ_bridge
严格连通分量 = C 内部连通 ∧ E(C,K\C)=∅（要求比簇强，U-13 明确不采用）
代表节点 r(C)：视图节点 kind=cluster，覆盖成员 C；视觉大小 ∝ 规模/质量；点击 = 深入一层
```
**反例**：
- ✗ 把整库弱连通分量当"一个簇"（一个巨型毛球，U-3/U-13 反例）。
- ✗ 按文件夹/标题层级直接当簇：那是**结构分组**，不是语义内聚（U-1/U-13/U-14）。
- ✗ 用 8 条退化 contain（同名/OCR）当内聚证据（G2/G4 已知坏数据）。
- ✗ 用 `graph-groups.js` 的并查集闭包结果直接当新簇：现有分组接近**连通分量**，与"内聚+零星桥"定义不同（现有代码 A 级）。

**边界用例**：
- 单成员簇 = 一个 KP：**在粗层允许作为"不聚合"的退化块**，但不得当作"代表子图"（语义上应直接显示 KP 节点；视觉由 S3）。
- 簇的桥可以等于 0（此时它同时是连通分量）；但**定义不要求** 0。
- 一个 KP 属于多个关联簇：允许（S0-7），但**同一层的划分必须互斥**（否则层不成立，S0-2）。

**U 映射**：U-6（代表子图节点）、U-7（点击深入）、U-13（非严格连通子图）、U-14（按语义划分小群）、U-15（一跳挂接）、U-19（点簇节点）、U-21/U-31（多归属）。

**建议裁决**：采纳定义与"簇≠严格连通分量"的区别；v1 每层簇族必须构成**该层划分**（互斥完备，S0-2），跨维度/关联的**重叠簇**归 S0-7 多归属处理；簇只用语义边（排除退化边）计算；阈值/算法由 S2 定，S0 只定"可采纳性判据"。代表节点是**视图节点**，不是新 KP（不回写 `knowledge_points`）。

**证据等级**：A（U-6/U-7/U-13/U-14/U-19 原话；`graph-groups.js` 现有并查集闭包代码）+ B（8 退化边：`artifacts/.../G4`、`contain-evidence.json`）+ **本项目假设**（"每层簇族=划分、重叠归多归属"）。

## 5. S0-5 一跳挂接

**定义（一句话）**："一跳"= 从当前视图节点出发，沿**当前维度允许的语义边**经过**恰好一条边**到达的节点及其边；不继续展开该节点背后的邻域。

**形式化**：当前视图 `V`，焦点集 `F⊆V`，维度 `D` 允许边集 `E_sem(D)`，方向 `dir(D)`。
```
attach₁(V,F,D) = {(u,v,e) | u∈F, e∈E_sem(D)∩E_selected, e 连接 u→v（按 dir），v∉V}
跳数 = 边步数；depth=1
禁止闭包：不得把 (v,w)∈E_sem(D) 自动加入同一视图（那是第 2 跳）
跨维度：不自动计跳；每个维度独立跳数计数，切换维度即重置（显式用户动作）
"背后"边界：只渲染端点 v 与边 e；v 所在其他子图/簇的内部成员不渲染（U-17）
```
**反例**：
- ✗ 展示 2 跳邻居（U-18 明确限制理由：污染语义/体验）。
- ✗ 把结构 contain 边当关联维度一跳（除非该维度显式声明包含结构边；默认关联维度只走语义边）。
- ✗ 把已在视图内的节点重复算作"挂接"（它不是新节点；按去重规则合并）。

**边界用例**：
- 同一对节点多条不同类型边（reference/extend / structural/semantic contain）：**仍算一跳**；显示类型由维度与 S0-6 类型映射决定。
- 一跳节点 v 属于另一个簇/层：只显示 v（bridge singleton）并提供"进入其所在子图"入口，不显示 v 的内部成员/边（U-17/U-21）。
- 一跳节点是簇代表节点：点击进入子图（U-7/U-19）；是 KP：点击跳到编辑器对应位置（U-20，旧行为保留）。

**U 映射**：U-10、U-11、U-15、U-17、U-18、U-19、U-20、U-21、U-22。

**建议裁决**：采纳"恰好一条边、不闭包、跨维度显式重置"的计法；关联维度默认只走语义边（`semantic` 或作者断言型），结构边仅作层次维度/导航背景；"背后图不带入"用视图模型硬约束（一跳端点不展开其邻域），机制在 S4 细化。

**证据等级**：A（U-11/U-15/U-17/U-18/U-19/U-20 原话）+ **本项目假设**（"仅语义边、跨维重置"的具体口径，待 S1/S4 裁决）。

## 6. S0-6 选择性渲染 + 边「存无/类型」

**定义（一句话）**：渲染集合由（层, 维度, 焦点, 预算, 语义条件）计算得出；**边是否被渲染、显示为何种类型，是视图相对的语义**，不等于底层数据里的"有边/无边"。

**形式化**：
```
View = Select(Π_ℓ, D, f, B) → ViewModel
边 e 被渲染 ⇔ e∈E_selected ∧ endpoints∈V_selected ∧ type_allowed(D) ∧ e 满足该视图的断言条件
视图边状态（建议最小枚举）：
  full            ：完整渲染（当前视图内）
  bridge_only     ：只作为跨簇/跨层桥边渲染，不带背后子图
  folded          ：折叠进簇（不显示，但计数/提示可显示）
  hidden_by_level ：低于当前层粒度而未显示
  hidden_by_dim   ：当前维度不含该边类型
  hidden_by_budget：跳数/数量预算截断
  unknown         ：未计算/不可判定
类型映射 τ_view(e)：显示类型 = (base type, contain_kind, basis)；
  structural contain ≠ semantic contain；reference 不得显示为 contain/extend。
数据缺席 vs 视图缺席：视图缺席只说明"本视图未选"，不得推出"数据里无关系"。
```
**反例**：
- ✗ 旧行为"payload 里每条边都渲染"（`graph-engine.js:179-180` `loadPayload` 直接把 `payload.edges` 全部 `expandLinks`）——违反 U-16/U-27。
- ✗ 视图中没有 A→B 的边 ⇒ 断言"A 与 B 无关系"（把视图缺席当数据缺席）。
- ✗ 把 `contain_kind=structural` 渲染成"整体-部分"语义（v0.2 §2.3 禁止）。
- ✗ 全展开时改变类型口径（同一份数据两种读法）。

**边界用例**：
- 全展开模式（U-26 开关）：显示全部数据边，但**类型映射与语义条件不变**（structural 仍显示 structural）；"有无"仍按数据。
- 多类型边：按维度优先级择一显示 + 徽标/计数提示其他类型（具体视觉 S3/S4）。
- 预算截断：被截断的边必须可解释（`hidden_by_budget`），不得静默丢弃。

**U 映射**：U-3、U-16、U-17、U-26、U-27、U-18（预算理由）。

**建议裁决**：采纳 ViewModel 的边状态枚举与类型映射规则；**禁止**"数据有边就渲染"进入默认视图；全展开是显式模式，但必须复用同一类型映射与状态语义；视图模型必须携带缺席原因（至少区分"未选/折叠/预算"），S4 细化枚举与算法。

**证据等级**：A（U-16/U-17/U-26/U-27 原话；`graph-engine.js:179-181` 全量渲染事实）+ **本项目假设**（状态枚举的具体取值；S4 可调整）。

## 7. S0-7 多归属

**定义（一句话）**："属于"是**成员关系**（KP 与簇/层/视图类别的归属）；"视图出现"只是当前渲染集合里的可见性——成员不蕴含出现，出现也不蕴含成员。

**形式化**：
```
成员关系 M ⊆ K × Cluster × Role（持久或可复算，须有来源 provenance：author/algorithm/agent）
视图出现 A(view) ⊆ K（由 Select 产生，含 reason ∈ {member, one_hop, bridge, focus}）
M ⇏ A；A ⇏ M
同一层：π_ℓ 是函数 K→Π_ℓ（每个 KP 恰属一个块）——这是"层内单归属"
跨层：同一 KP 在每一层各属一个块（嵌套包含关系，不冲突）
跨维度/关联：同一 KP 可属多个关联簇（多归属）；S0 不设上限，S2/S6 决定上限与存储
```
**反例**：
- ✗ 把"当前渲染出来了"当作成员关系写回数据（循环定义）。
- ✗ 把一跳出现的节点登记为簇成员（出现≠成员）。
- ✗ 认为 KP 只属于它的 sidecar 文件（文件是存储容器，不是语义归属；U-21 明确跨子图/层/维度多归属）。

**边界用例**：
- 同一 KP 在粗层属簇 C，在细层属单 KP 块：两者都是成员关系，不冲突（不同层）。
- 同一 KP 同时属两个关联簇：允许；视图需记录"从哪个入口来"（U-22 的返回路径依据，S5 细化）。
- 成员关系可计算不持久化（如 S2 聚类结果缓存），但必须可复算、可解释；若持久化，须标 provenance（S6 决定）。

**U 映射**：U-21、U-22、U-31、U-19/U-20（点节点行为）。

**建议裁决**：采纳"成员关系 vs 视图出现"二分；层内单归属、跨层嵌套、跨维度多归属；S0 不设上限；视图模型必须给节点标 origin（member/one_hop/bridge）以支撑导航与返回；持久化与上限留 S2/S6。

**证据等级**：A（U-21/U-31 原话；现有实现无成员概念，`graph-engine.js` 只用 KP 节点）+ **本项目假设**（层内单归属/跨层嵌套的组合规则）。

## 8. S0-8 默认视图 vs 全展开

**定义（一句话）**：默认入口是**层次视图**（非全展开，节点可为簇/代表节点）；全展开是同一数据源上开关后的**兼容视图**（所有 KP + 所有数据边，旧行为）；二者不是两条产品主线（U-26 解读约束）。

**形式化**：
```
数据源 S = collect_graph_data(kb)（唯一事实源）
默认视图 D0 = View(Π_0, A, focus=root, budget=B0)     # 节点可为 cluster，显示为选择性子图
全展开   F  = View(Π_L, D_full, edges=all_data_edges) # 所有 KP；但类型映射与语义规则同 D0
模式枚举 {default, full_expand}；同 ViewModel schema
切换：保持当前 KP 焦点；无法保持（焦点在折叠簇内）⇒ 映射到包含它的最近块/根，并提示
```
**反例**：
- ✗ 双入口（默认全展开 + 另做一套多层视图）= 违反 U-26"彻底替代"。
- ✗ 默认视图仍渲染全部数据边（假多层）。
- ✗ 全展开用另一套边类型/语义规则（两个世界）。
- ✗ 切换模式静默丢失当前位置。

**边界用例**：
- 当前层已到最小层（KP 层）：默认视图在**该焦点范围**内等价于全展开（收敛），不算双主线。
- 全展开下的规模问题：U-32 明确"规模不是问题，关键在后端检索算法"；S8/S9 定指标，S0 不设阈值。
- 模式开关是**用户显式动作**，不是 agent 默认切换；状态进入导航历史（S5）。

**U 映射**：U-5、U-26、U-32、U-33（同一接口）、U-3（体验）。

**建议裁决**：采纳单数据源 + 两种模式 + 同一 ViewModel；默认入口**替代**旧全展开（U-26），全展开只作为显式开关的兼容路径；两者共享类型映射与语义条件；切换规则（焦点保持/映射/提示）由 S5 细化。

**证据等级**：A（U-26/U-32 原话；当前默认全量渲染事实 `app.js:1842-1861` + `graph-engine.js:179-181`）+ **本项目假设**（切换焦点映射规则）。

## 9. S0-9 渲染接口边界

**定义（一句话）**：渲染接口 = **视图模型**（纯数据输入）+ **渲染后端**（2D/3D 实现同一接口）+ **事件回传**（稳定 id 的最小事件集）；后端不得直接读 KB/sidecar。

**形式化（最小契约，建议）**：
```
ViewModel（输入）:
  { view_id, mode: default|full_expand, level, dimension, focus,
    breadcrumb: [{kind, id, label}],
    nodes: [{id, kind: kp|cluster|bridge, label, member_count?, expandable, state}],
    edges: [{id, source, target, type, contain_kind?, state, label_key}],
    capabilities: {can_expand, can_toggle_full, can_navigate_back} }
Renderer（后端实现，2D/3D 同签名）:
  mount(root, viewModel) → instance
  update(viewModel, {transition?})
  destroy()
  on(event, handler)
Event（回传，稳定 id、最小集）:
  nodeClick      {node_id, kind}
  clusterExpand  {node_id, level?}           # 进入子图（U-7）
  edgeClick      {edge_id}
  breadcrumbClick{level, id}
  modeToggle     {mode}
  navigateBack   {}
约束：事件只带 id/枚举，不带正文/用户输入（沿用 D-KG-07 隐私边界）；
      渲染后端不得调用 get_graph_data / 读 sidecar；所有取景计算在视图模型构建层。
```
**反例**：
- ✗ 2D/3D 各自定义数据结构或事件字段（实测不一致：2D `nodeClick` 带 `edge_id`，3D 不带——`graph-view-2d.js:544-547` vs `graph-view-3d.js:1043`）。
- ✗ 渲染后端直接 `call("get_graph_data")` / 读文件拿数据。
- ✗ 事件回传整个节点对象/DOM 引用（不可跨后端、不可复现）。
- ✗ 2D、3D 各开一条设计线/两套 UX（U-33 明确禁止）。

**边界用例**：
- 后端能力差异（3D 可能有额外能力）：用 `capabilities` 声明，不改变 ViewModel/事件契约；不允许"3D 专有事件"绕过契约。
- 折叠进簇的边（S0-6 `folded`）：不产生 edgeClick；若要支持"查看折叠计数"，作为节点事件/提示（S3 细化）。
- 全展开模式：同一 ViewModel schema，`mode=full_expand`。

**U 映射**：U-6、U-7、U-19、U-26、U-33（+ U-3 体验、U-35 工程图）。

**建议裁决**：采纳单一 ViewModel + 最小事件契约；2D/3D 仅是后端实现，不得拆设计线；渲染器**禁止数据获取**（只吃 ViewModel）；事件只传稳定 id。S3 定视觉/节点 token，S4 定取景算法，S5 定状态机，S6 定数据契约。

**证据等级**：A（U-33 原话；现有 2D/3D 代码共存与事件不一致，file:line 可核）+ **本项目假设**（ViewModel/事件字段的最小集——由本场建议、S3/S6 可扩展但不得减少）。

## 10. S0-10 agent 的角色边界

**定义（一句话）**：agent 在**设计知识点**层是主导；在**决定语义**层是可写入但受证据约束的参与者（不得自动推断 semantic）；在**决定取景**层是检索/取景算法的设计与执行者，但不进入渲染/视觉实现。

**形式化（三层边界）**：
```
L_kp   （KP 设计：产生/边界/命名/粒度/去重/多归属）  ：agent 主导 + 人监督审计（S10 细化，U-29）
L_sem  （边语义：semantic contain / 断言）          ：agent 可经 curate_contain 写入，但必须
                                                      assertion_source + curated_by/curated_at（v0.3）
                                                      ；structural 由系统派生，agent 不得手造
L_view （取景：层次/维度/预算→ViewModel）           ：agent 可设计/执行检索与取景（S9，U-32），
                                                      可提议 ViewModel 参数；不得实现渲染器/DOM/视觉
人      ：KP 政策审批、semantic 抽查/撤销、产品决策
系统    ：structural contain 派生、类型归一化、机检（schema/G6）
```
**反例**：
- ✗ agent 把几何 contain 当 semantic 自动标注（v0.2/v0.3 明确禁止"程序自动推断 semantic"）。
- ✗ agent 直接操作渲染/布局/视觉（越层）。
- ✗ agent 把"取景结果"反过来当语义证据（循环）。
- ✗ agent 拆/并 KP 无审计（L_kp 越界，S10 会定义审计）。

**边界用例**：
- agent 提议 KP 修改：先提案、后落库（S10 定义人监督/回滚）。
- agent 提议 semantic curation：带锚点与审计身份；人可抽查/撤销（v0.3 规则）。
- agent 提议的 ViewModel 参数（如关联维度跳数）只能作为输入；最终视图由取景算法生成，渲染后端只执行。

**U 映射**：U-2（双价值）、U-29（agent 设计 KP）、U-32（后端检索）、U-35（工程图/角色）。

**建议裁决**：采纳三层边界；S0 只冻结**边界**，机制留 S9（取景算法）/S10（KP 设计）/S7（agent 消费）；明确：semantic 不得由程序/agent 无证据推断；渲染器不属 agent 写域。

**证据等级**：A（U-29/U-32 原话；v0.3 §2.3 规则 1、`dec-20261102-5f71d1da`；ontology §1"agent 侧从不读边"）+ **本项目假设**（三层权责的边界划分细节）。

## 12. S0-12 术语映射（新 ↔ 现有产品术语）

**定义（一句话）**：术语映射是**新术语到现有产品术语/字段/代码行为的显式函数**，每个映射必须标"等价/扩展/冲突"之一，冲突必须给兼容/迁移/回滚。

**形式化**：`τ: NewTerms → ExistingTerms ∪ {∅}`，关系 `rel ∈ {same, extends, conflicts, none}`；约束：
- `rel=same`：语义完全等价（可直接映射，如 `contain_kind=structural` ↔ 结构包含）；
- `rel=extends`：新术语在旧字段上有增义（如 ViewModel extends `get_graph_data` payload），旧数据可缺省/降级；
- `rel=conflicts`：新语义与旧行为不可同时成立（如"数据有边就渲染" vs 选择性渲染；`graph-groups` vs 新簇），**必须**给兼容/迁移/回滚与红线；
- `rel=none`：新概念无现有对应（如维度、代表节点），须在 S6 定存储/接口。

**U 映射**：U-1/U-10（语义）、U-16/U-27（渲染与边存无）、U-20（KP→编辑器）、U-21（多归属）、U-26（默认/全展开）、U-28（KP 粒度）、U-33（渲染接口）。

**建议裁决**：采纳下表映射与 5 条术语冲突红线（§S0-12 兼容段的①–⑤）；`rel=conflicts` 的项必须在 S1–S6 之一给出落地方案，否则 S0 冻结稿保留"待解冲突"标记，不得静默按旧口径实现。

> 下表给出一一映射；冲突处标红并给兼容/回滚。

| 新术语 | 现有产品术语/字段/代码 | 关系 | 冲突/注意 |
|---|---|---|---|
| 语义（semantic edge） | `edges[]` 的 `type`/`contain_kind`/`provenance_state`/`assertion_source` | 语义=断言层分类；`reference` 不算语义边 | `edge` 这个名字在旧文档里=语义关系，但数据里含 reference（非语义）⇒ 消费者必须过滤（ontology §2.1） |
| 结构包含 | `contain_kind=structural`（v0.2） | 结构事实、非语义 | 不得显示成"整体-部分" |
| 语义包含 | `contain_kind=semantic` + v0.3 curation 字段 | 语义断言 | 缺证据即降级 structural（fail-safe） |
| 层次（level） | 无现有产品术语；旧"全展开"是最深层 | 新概念；默认视图替代全展开（U-26） | 旧渲染无层概念，视图模型需新增 |
| 维度 | 无现有产品术语；`graphStyle`（force/galaxy）≠维度 | 新概念 | 视觉风格不得与维度混用 |
| 簇（cluster） | `graph-groups.js` 的 groups（并查集闭包） | 现有 groups≈连通分量，新簇=内聚+零星桥 | **不能直接复用**；旧分组仅作 UI 页签/毛球判断 |
| 代表节点 | 无；现有节点都是 KP | 新节点 kind=cluster | 现渲染/点击假设 `node.kp_id` 存在（`app.js:1661-1677`）⇒ 需区分 kind |
| 一跳挂接 | 旧"ego-only / 0.5 范围"（D-KG-09） | 相关但新语义：预算/维度/防背后图 | 旧 ego 是 0.5 临时范围，不是维度 |
| 选择性渲染 | 旧行为=payload 全部边渲染（`graph-engine.js:179-180`） | 新=Select 后渲染 | 旧"数据有边就画"假设必须废弃（U-27） |
| 视图模型（ViewModel） | `get_graph_data` 返回的 `{nodes,edges,groups,graph_audit}` | 新 ViewModel 是渲染层输入，扩展 level/dimension/state | 现有 payload 无层/维/缺席原因 |
| 渲染后端 | `graph-view-2d.js` / `graph-view-3d.js` + `graph-engine.js` + layouts | 2D/3D 是同一接口的实现 | 事件字段已不一致（2D 有 edge_id、3D 无）；需统一 |
| 成员关系 | 无现有边类型；KP 归属文件（sidecar）是存储 | 新概念（S2/S6 定义） | 文件归属≠语义成员；成员需 provenance |
| 多归属 | 现 KP 只在所属文件的 `knowledge_points[]` | 新：跨层/维/簇多成员 | 存储模型需 S6 设计 |
| 全展开 | 旧默认（force 全量视图） | 新=开关后的兼容模式 | 旧默认入口将被替代（U-26） |
| 语义确认（curation） | `contain_kind` + v0.3 `curated_by/curated_at` +（规划）`curate_contain` | 兼容；新流程入口 | 需审计与证据（S0-1/S0-10） |
| 视图出现（appearance） | 旧=payload 内所有节点都渲染 | 新=Select 结果 + reason | 出现≠成员（S0-7） |

**反例（术语映射误用）**：
- ✗ 把 `graphStyle=galaxy` 说成"关联维度"（视觉风格≠取景维度）。
- ✗ 把 `graph-groups` 的分组结果直接叫"簇"（并查集闭包≈连通分量，不是内聚+零星桥）。
- ✗ 沿用旧 `nodeClick` 逻辑对簇节点调用 `jumpToTarget({file,kp_id})`（簇节点没有 single `kp_id`，需先行展开或映射到代表 KP，规则留 S5）。
- ✗ 把 `get_graph_data` payload 原样当 ViewModel 交给 2D/3D（缺 level/dimension/edge-state，且渲染器仍会直读数据）。

**边界用例**：
- 旧数据无 `contain_kind`：映射表按 structural（fail-safe）；无 `curated_by/at` 的 semantic 不应存在（schema/collector fail-closed）。
- `reference` 边在旧数据中占比高：映射为 navigation，不得因"在 `edges[]` 里"就归语义。
- 同一 KP 同时在 `knowledge_points[]`（存储归属）与多个视图成员关系：前者是 sidecar 结构，后者是视图/分析概念，二者不是同一层事实（S0-7）。

**兼容/迁移/回滚（预注册判据 3）**：
- **数据层**：v1 不要求改 sidecar 数据；新增内容（簇/成员/视图状态）若持久化，必须走 S6 契约并保持旧数据可读（缺字段 fail-safe）。
- **渲染层**：默认入口替换是**行为变化**，全展开开关保留旧视图作为兼容路径；回滚 = 关闭新视图默认入口、恢复 `loadGraphData` 旧路径（文本/配置级回滚，无数据迁移）。
- **术语冲突红线**：① 不得把 `graphStyle` 叫维度；② 不得把 `graph-groups` 当新簇；③ 不得把 reference 当语义边；④ 不得把视图缺席当数据缺席；⑤ 不得把 structural contain 显示为整体-部分。

**证据等级**：A（ontology/schema/现有代码 file:line；U-25/U-26/U-27/U-33）+ **本项目假设**（新术语的最终命名若与 SE 专家/复核方冲突，按章程并集裁决）。

## 14. 预注册：最可能争议点（供 Lead 并集/异议）

1. **层次是否必须"每层都用划分"**（本提案：是）。反方可能主张"层=缩放尺度、允许同一层混合粒度/自由节点"（更灵活但不可形式化、难保嵌套）。若采纳反方，需要另给形式化定义，否则 U-28 的"最小粒度"无法落地。
2. **簇是否必须构成划分（互斥）**（本提案：层内是；重叠归 S0-7 多归属）。反方可能主张"簇天然重叠、不要求划分"；这会与 S0-2 的层形式化冲突（需把层降级为"非划分的覆盖族"）。
3. **全展开是否必须复用同一类型映射/语义条件**（本提案：是）。反方可能主张"全展开是旧兼容视图，可以保留旧口径"；这会导致同一数据两种语义读法（违反 U-1/U-27 的一致性），但兼容成本更低。

> 另有次级争议：S0-1 的 T3"决策绑定"是否过强（可能把很多弱语义边排到 navigation）；S0-9 的 ViewModel 重构成本是否值得（旧渲染直接吃 payload）。按章程逐项裁决，不做静默合并。
