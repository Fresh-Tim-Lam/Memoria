# 性能改善阶段（0.4.5 前置）— 计划与判据

> 状态：**立项 2026-10-22**。目标版本 **0.4.5**。
> 前置：P6 显示子系统重构已完成（0.4.4 已发布，legacy 渲染器删除）。
> 本文件是**判据的单一事实源**；测量协议细节见 `docs/design/perf-ops-contract.md`、`docs/design/realapp-measurement-protocol.md`。

---

## 1. 为什么现在做、以及为什么要先修度量

**已知事实**（`artifacts/agent/verify/incremental-waste-report.md`，实测）：

| 项 | 耗时 | 占打开路径 |
|---|---|---|
| **MathJax `typeset`** | **758.8 ms** | **73%** |
| `renderMermaid` | 193.4 ms | 19% |
| `render` | 62.3 ms | 6% |
| 全量扫描（`postProcessWikilinks` + `bindPreviewLinks`）| **< 2 ms** | 0.2% |

**⇒ 打开大文档慢 = MathJax + mermaid，不是块级后处理。**

**但**：0.4.4 发布说明里我们如实写了「P1/P2/P3 三项工作量计数与重构前逐字节相同 = 无性能改善」。
原因是**没做过同口径的前后对比**，而不是"没有优化空间"。

**度量必须先于优化**，因为本项目已实测到 6 类验证缺陷（见发布说明），
其中「机器上另有一个打包版 Memoria.exe 抢 CPU」直接让一次时延测量失效。

## 2. 三条痛点的当前定性

| 编号 | 痛点 | 现状判断 | 优先级 |
|---|---|---|---|
| **P1** | 打开大文档慢 | **主战场**：typeset 758.8ms + mermaid 193.4ms | 🔴 高 |
| **P3** | 切页签慢 / 切回来重算 | 疑似同类（切回可能重新 parse/render/typeset），**需实测确认** | 🟠 中高 |
| **P2** | 打字卡顿 | 既有读数 **median 7.1ms / p95 7.6ms**（16ms 预算内） | 🟢 低 |

## 3. 候选优化方向（研究阶段，先估收益再动手）

### A. MathJax 延迟排版（视野优先）—— 主攻
**思路**：DOM 结构照旧全量渲染（**不改块身份、不动布局**），只把 `typeset` 按**可见性**排序/延迟：
1. 首屏可见公式**优先** typeset → 首屏可交互时间大幅下降
2. 视口外公式在 `requestIdleCallback`/滚动时补
3. 保留原公式文本节点直到被 typeset（避免布局跳动需处理占位尺寸）

**预期收益**：首屏时间 ≈ typeset × (可见公式占比)。若首屏 15% 公式 ⇒ 理论 **−85% 首屏 typeset 开销**。
**风险**：滚动到未排版区域时的"逐步出现"观感；需占位高度策略避免抖动。

### B. 公式结果缓存（跨渲染/跨打开复用）
**思路**：以 `(latex, displayMode, 主题)` 为键缓存 `mjx-container` 的 DOM 片段，命中则直接插入。
**预期收益**：同一文档重复打开、切页签回来、同 KB 高频公式（教材大量重复）命中率可能很高。
**风险**：MathJax 内部 id 唯一性（需重新分配 id）；缓存体积。

### C. mermaid 延迟渲染 + 缓存
**思路**：同 A/B 策略（视口优先 + `(code, theme)` 缓存 SVG）。
**预期收益**：193.4ms 里可压掉大部分。
**风险**：mermaid 布局依赖容器宽度 ⇒ 缓存需带宽度键。

### D. 切页签避免重算（P3）
**思路**：先实测切回时到底重做了什么（parse? render? typeset?）。若是 typeset 重跑 ⇒ A/B 同样受益。
**风险**：需先有测量，不能猜。

## 4. 判据（硬性，不可事后改口径）

### 4.1 基线身份
一次基线 = **数据 sha + 工具 sha + 配置隔离状态 + 机器并发状态**，四者缺一无效。

### 4.2 噪声门
- 每操作 **≥15 轮**（非 5 轮；5 轮曾把噪声误判成 1.178× 退化）
- 报 **P50 / P95 / max + sd**
- **判有效需：均值差 > 2×sd**，否则判"未见差异"
- 测量期间**不得有其它 Memoria 实例在跑**（硬要求；本机曾出现打包版占 80% CPU）

### 4.3 改善必须同时满足
1. **同口径**前后对比（不许 headless vs realapp 混比）
2. **A 类工作量计数不劣化**（确定性计数器）
3. **交互与渲染等价不回退**：12 剧本 12/12 + 渲染等价（块级签名 + A1–A11 + astCount/domCount）
4. 报**绝对目标达成度**：
   - 首开（教材级，2850 公式）：目标 **≤ 400ms**（现在 ~995–1025ms）
   - 切页签：目标 **≤ 150ms**
   - 打字：保持 **p95 ≤ 16ms**（不回退即可）

### 4.4 禁止的"改善"手段
- 减少功能（延迟加载可以，**丢弃内容不行**）
- 改测量口径 / 换机器 / 换脚本后不与基线同工具 sha 对比
- 把"没有变慢"写成"变快"

## 4.5 体验预算（人 2026-10-22 拍板）

> 人原话：「提高渲染速度和体验，需要权衡哪些不渲染哪些预渲染；**我能接受的各种交互延迟不超过 0.1 秒**」

### 逐操作预算（硬指标）

| 交互 | 预算 | 口径 |
|---|---|---|
| **打开文档 → 首屏可读** | **≤ 100 ms** | openFile → 首屏块可见且公式已排版 |
| **切页签 → 可读** | **≤ 100 ms** | activateTab → 目标文档首屏可读 |
| **点击跳转 → 目标可见** | **≤ 100 ms** | 已有基线：P50 68–75 ms（**已达标，不得回退**）|
| **滚动 → 新内容可读** | **≤ 100 ms / 屏** | 滚动进入视口 → 该屏内容排版完成 |
| **打字 → 光标处更新** | **p95 ≤ 16 ms** | 已有实测 p95 7.6 ms（**已达标，不得回退**）|

### 由此推导出的核心约束

`typeset` 全量 758.8 ms（540 公式，约 **1.4 ms/公式**）。
真实教材 `08_第8章` 有 **2,850 公式** ⇒ 全量 typeset 线性外推 **≈ 4 秒**。

**⇒ 若「打开 ≤100ms」，同步路径上能排版的公式数上限 ≈ 100ms ÷ 1.4ms ≈ 70 个**
（还要扣掉 parse/render 的时间，实际更少）。

**结论：100ms 预算下，「全量同步 typeset」在数学上不可能。必须分级。**

## 4.6 三级渲染策略（技术方案骨架）

> 人已明确接受"权衡哪些不渲染 / 哪些预渲染"。下面把"哪些"定义成可执行规则。

| 级别 | 范围 | 时机 | 预算 | 失败表现 |
|---|---|---|---|---|
| **T0 同步必渲染** | **首屏可见块**（视口 + 0 屏）及其内部公式 | 打开时同步 | 计入 100ms | 超预算 ⇒ 打开变慢 |
| **T1 预渲染** | **下一屏 ±1 屏** | `requestIdleCallback` / 首屏完成后的空闲帧 | 不计入首屏，但必须**在用户滚到之前完成** | 用户快速滚动会看到未排版内容 |
| **T2 延迟渲染** | 更远区域 | 进入视口前 1 屏时触发 | — | 快速拖动滚动条可能看到文本态公式 |

### T1 窗口大小必须**自适应**
- 若单块排版慢（大块公式多）⇒ 窗口缩小到 1 屏
- 若单块排版快 ⇒ 窗口扩大到 2–3 屏
- **判据：T1 的提前量必须 ≥ 用户典型滚动速度 × 排版耗时**

### 抖动的处置（人未要求零抖动，但必须有界）
- **占位高度用保守估计**（宁可占大，避免内容上跳）
- **允许的抖动：只向下推移，且单次 ≤ 1 行高**
- **搜索/跳转命中**：目标块**立即提到 T0**（不能被延迟）

### 必须保留的功能（不许为性能删）
- 公式编号（`tags:"ams"`）正确性
- mermaid 图完整渲染
- 搜索/跳转/知识点高亮
- 渲染等价（块级签名 + A1–A11 + astCount/domCount）

## 4.7 验收口径变更（相对 §4.3）

§4.3 原目标「首开 ≤400ms」**按新规格收紧为 ≤100ms**。
但**验收要分开看**：

| 指标 | 目标 | 说明 |
|---|---|---|
| **首屏可读** | **≤ 100 ms** | 人的体验预算，主判据 |
| **全量完成** | 记录但**不作门禁** | 全量 typeset 4s 是本质成本，靠 T1/T2 掩盖体感 |
| 切页签可读 | ≤ 100 ms | 同上 |
| 打字 p95 | ≤ 16 ms | 不回退 |
| 跳转 P50 | ≤ 100 ms | 不得回退 |

**⚠️ 这意味着"全量完成时间"不再是验收项** —— 只有"用户感知到的可读时间"是。
这是人拍板的体验取舍，必须写进发布说明，避免后续被误读为"性能没提升"。

## 4.8 交互序列约束（人 2026-10-22 补充）

> 人原话：「**而且跳转之后，用户可能滚动滚条，进行编辑等操作**」

⇒ **分级不能按"文档从上到下"设计，必须支持"任意位置进入 + 连续操作"。**

### 1. 跳转后立刻滚动（跳转邻域优先）

跳转命中位置 **≠ 文档首屏**。若跳转后仍按"从文档头开始预排"，用户跳到第 300 行后往下滚，看到的是未排版内容。

**规则**：
- 跳转后 **T1 预渲染窗口必须以跳转目标为中心**（前 1 屏 + 后 2–3 屏，按下滚方向加权）
- **不得**因为"文档头部还没排完"而推迟跳转邻域
- 跳转目标块**及其邻域**在 `highlightPreviewRange` 之前提升到 T0（`app.js:11578`）

### 2. 拖动滚动条（快速跨越大量内容）

拖动滚动条 = 每秒跨越几十屏，若每屏都触发排版 ⇒ **任务风暴 + 抖动**。

**规则**：
- **拖动过程中不做 typeset**，只做占位高度维护（避免滚动位置跳动）
- **滚动停止后**（debounce ≤ 50ms）对**当前视口**立即提升 T0，随后恢复 T1 预排
- 拖动经过的区域**不预排**（用户没停下来看）
- **可选优化**：拖动时用"文档序 + 块高"直接算目标块（若有块高索引）

### 3. 跳转后编辑（关键：编辑安全性）

用户在**未排版块**上编辑时，必须保证：

| 要求 | 说明 |
|---|---|
| **不丢内容** | 块重渲后公式文本必须完整（不得因为"未排版"而丢公式）|
| **该块公式立即排版** | 编辑所在块重渲时，其公式**同步** typeset（提升 T0）|
| **已排版块不得回退** | 编辑块 A 不得让块 B 的公式退回文本态 |
| **光标/行映射正确** | `data--block-index` / `srcLine` 必须保持（现有块级嵌入已保证，需回归验证）|
| **undo 正确** | 撤销后公式与文本一致 |
| **pending 集合正确更新** | 重渲块产生的新公式节点要进 pending；旧节点移除 |

### 4. 打字预算与公式的冲突（必须实测并定论）

打字预算是 **p95 ≤ 16ms**，但若编辑块含多个公式：
`20 个公式 × 1.4ms/公式 = 28ms > 16ms` ⇒ **单次按键可能超预算**。

**必须在 S1 实测**：在公式密集块中输入 1 个字符的端到端耗时。
**若超 16ms，有两种处理，需人拍板**：
- (a) 该块公式**延迟到 idle 再排**（按键快，但公式短暂显示文本态）
- (b) 同步排（公式即时正确，但按键超 16ms）

### 5. 连续操作不得累积

`跳转 → 滚动 → 编辑` 连续发生时的要求：
- 前一批 typeset 任务必须被**正确作废**（已有 token 作废机制 F4）
- 不得出现"排完一遍又重排一遍"（同一块重复 typeset）
- 不得因为作废而**永久漏排**（作废后必须重新入队）
- **A 类工作量计数**在"跳转+滚动+编辑"序列中不得爆炸（用于检出任务风暴）

### 6. 新增验收项（本阶段）

| 场景 | 判据 |
|---|---|
| 跳转 → 立刻下滚 1 屏 | 新屏 ≤100ms 可读 |
| 跳转 → 拖动滚动条到文档 80% 处 → 松手 | 视口 ≤100ms 可读 |
| 跳转 → 在目标块输入 1 字符 | 见 §4.8.4（16ms 或人拍板的替代口径）|
| 跳转 → 编辑 → undo | 公式与文本一致，无重复/丢失 |
| 上述序列重复 5 次 | 无任务风暴（A 类计数线性，非指数） |

## 7. S0/S1 实测结论（2026-10-22，全部真机）

### 7.1 已修复（已入库）

| 编号 | 问题 | 修复 | 实测收益 |
|---|---|---|---|
| **F1** | **公式在"预览视图下打开"时全部不渲染**（`oldsymbol` → autoload 404 → 整个 typesetPromise reject，被 `.catch` 吞掉）| `[+]` 只留真实存在的扩展 + `macros: { boldsymbol: ["\\mathbf{#1}",1] }` | mjx **0 → 2850**（打开即渲染）|
| **B1** | `stampBlockLines` 内每块 `body.split("\n")` ⇒ **O(n²)** | split 提到循环外 | JS **721ms → 0.8ms**；打开 **−22%**；最大冻结 **−30%** |
| **A** | `renderDocument` 逐次 `appendChild`（4001 次）| DocumentFragment 一次挂载 | **无显著增益**（噪声内），仅代码更干净 |

### 7.2 关键事实（推翻了立项时的假设）

| 假设 | 实测 | 结论 |
|---|---|---|
| typeset 758.8ms 是打开慢的主因 | 真实教材上 typeset **仅 149ms** | ❌ 不是主因 |
| A1（eager 分批 + 让出）能消除冻结 | 全量 1.7s → **5.7s**，冻结仍有 2 次 2.3s | ❌ 方案否决 |
| renderEditor（1.7 万节点）是大头 | 实测 **28–37ms**（`display:none` 跳过 layout，只剩 DOM parse）| ❌ 不是主因 |
| `_tagInlineMathContainers` 1241ms（CPU profile self time）| 消融后**无改善** | ⚠️ profile 归因误导 |
| contentEditable 触发大规模 style recalc | 消融后**无改善** | ⚠️ 不是主因 |

### 7.3 打开 08 章（2850 公式）的真实现状

| 指标 | 值 |
|---|---|
| 打开 → 块全部出现（热轮）| **2.85 – 3.1 s**（B1 前 3.7 – 4.0 s）|
| 最大帧间隔 | **1.7 – 1.9 s**（B1 前 2.5 – 2.8 s）|
| 浏览器 `RecalcStyleDuration` | **1.85 s** |
| 浏览器 `LayoutDuration` | **1.03 s** |
| 已归因的 JS 段（RPC 109ms + renderEditor 32ms + tabs/kpList ≈0）| **≈146 ms** |
| **未归因** | **≈1.2 s** |

**⇒ 打开 08 章的成本主要是浏览器侧样式重算 + 布局（建 4001 块 + 2850 行内公式 + 19 张 mermaid 的 DOM 树），不是某个 JS 函数的算法问题。**

### 7.4 结论与下一步

1. **微优化已到边际**：已修的两处（F1、B1）是能找到的最后两个"低垂果实"。
2. **要再降一个数量级，必须做结构性改造**：
   - **惰性块物化**：只建首屏块，其余在接近视口时追加（同时解决 layout 与 typeset 的 eager 成本）
   - **mermaid 延迟渲染**：08 章 19 张图渲染 ≈750ms，首屏 0 张
   - 这两项属 0.4.6，**不在 0.4.5 范围**（P6 之后不宜立即再做一次架构改动）
3. **0.4.5 的性能口径（诚实）**：
   - 已修复"公式不显示"的发布级 bug
   - 打开 08 章最大冻结 **2.5s → 1.7–1.9s（−30%）**，块出现 **−22%**
   - **不宣称"打开快了一个数量级"** —— 数量级改善需要 0.4.6 的惰性物化
