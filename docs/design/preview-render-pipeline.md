## 0. 一句话

**先把两个被混在一起的问题分开**：① **当前文档的渲染**（`#preview` 里的活 DOM 参与布局/绘制）—— 这是"切大文档慢"的来源；② **缓存里的渲染产物**（池条目的 `DocumentFragment`，**不在文档里**、只吃堆）—— 这是"想多缓存几个"的内存压力。四条线的优先级：**L1 刷新分档**（成本最低、且能立刻修掉一个真问题）→ **L5 预加载挑法** → **L2 离屏跳过** → **L3 缓存形态（须先实测）** → **L4 增量渲染**（治本、大工程）。

## 1. 现状事实（全部带行号，可复核）

### 1.1 池的存储形态与估算口径

- 池 = `app.js` 末尾的预览 DOM 缓存：`Map<relPath, {frag, map, ast, version, fp, scrollTop, bytes, prerendered}>`（`app.js:12961`）。
  条目的 `frag` 是**整棵渲染好的活 DOM**（`DocumentFragment`），切走时**移动节点**搬进去、切回时**移动节点**搬回来（`app.js:13063`、`app.js:13123`）——注释明确这是为了"已挂的事件监听与已排版好的 MathJax/Mermaid 产物一并保留"（`app.js:12939-12941`）。
- 占用只有**估算**：`_estimatePreviewBytes = nodes*120 + chars*2`（`app.js:13001-13014`），设置页那句"估算占用约 N MB"用的就是它（`display-settings.js::preloadFootprintNote`）。**没有实测堆占用**。
- 条目还挂着 `ast`（解析树）与 `map`（行号映射）——**AST 是常驻的第二份数据**，JS 对象开销通常是同名文本的 3–5 倍。

### 1.2 两个 `content-visibility` 管不着的地方（先排除一个常见误解）

`DocumentFragment` 里的节点**本来就不参与布局与绘制** ⇒ 对**缓存池**用 `content-visibility` **没有收益**。它只对**当前打开的文档**有效：3983 行全在 `#preview` 里，浏览器为整篇算样式、布局、绘制，而用户一次只看一屏。

### 1.3 刷新的既有阶梯与失效点

- **入口**：`#btn-refresh`（`index.html:77`，绑定 `app.js:12363-12368`）= **硬刷四连** `refreshFiles → loadLinkTargets → loadGraphData → openFile(cur,{skipNav:true})`；`#btn-build`（`app.js:12369` → `buildKb`）在四连之外还**写 sidecar + 改写 md + 写 build/*.json**。
- **事实上已有 A–J 十档**（只是没抽象）：A `refreshFiles`（只重扫，`app.js:645`）/ B `openFile`（单文档，`app.js:1413`）/ C `loadLinkTargets`（`app.js:402`）/ D `loadGraphData`（`app.js:1078`）/ E `refreshKbPendingSummary`（`app.js:503`）/ F `sync_manifest`（写清单）/ G `sync_pending`（写 pending）/ H `repair_path_cascade`（写盘）/ I `validate_kb`（只读审计）/ J `build_kb`（全库重写）。
- **缓存失效点共 14 处**，按触发源分布：本地编辑（`app.js:160`）、写盘成功（`app.js:137`）、视图模式变更（`app.js:1628`）、关页签（`app.js:1326`）、换库/关库/文件集合变化（`app.js:516/608/651` → `_previewCacheClear`）、语言/主题（`app.js:13302/13303` → `_previewCachePurge`），以及 6 处池自身一致性机制（版本/指纹失配、stash 重登记、预渲染失败、评分淘汰、入场闸拒收）。
- **🔴 本轮找到的真问题**：agent 一轮对话结束时 `refreshAfterTurn`（`agent-panel.js:4521-4548`）**无条件**调 `app.refreshFiles()`，而 `refreshFiles` 里有 `_previewCacheClear()`（`app.js:651`）⇒ **整库缓存被清空**。也就是说：刚缓存好的大章节，agent 随便回一句就没了。它其实**已经算好了** `turnWroteSomething`（`agent-panel.js:4513-4519`，判本回合有没有写过库），却没拿它来分档。

### 1.4 编辑时的重渲路径（**整篇**，带防抖）

```
editor 'input' (app.js:7062)
  ├─ scheduleRenderSync()  防抖 RENDER_DEBOUNCE_MS = 80ms (app.js:66, 112-119)

        ├─ _previewCacheDrop(currentPath); _previewDomKey = null; _preloadStop("edit")   (app.js:160)

```
- **没有分块/增量**：`options.incremental` 这个参数存在，但只用于"不重写 loading 占位 / 不尝试缓存恢复"（`app.js:1893-1911`），**仍是整篇**。
- 忙时排队（`_renderPending`，`app.js:1884-1891`）与"命中缓存就整棵搬回"（`app.js:1894`）是现有的两条收敛手段，但**编辑中的文档永远命中不了缓存**（`markDirty` 每次都 `_previewCacheDrop`）。
- 解析器**已经有块结构**（`ast.blocks[]` + `data--block-index` + `stampBlockLines`）—— 这一点很重要：**增量的天然单位已经存在**。

- 候选 = `openTabs` 里**按数组顺序**第一个"非当前、未缓存、未试过"的页签（`app.js:13188-13197`）；配额 `preloadMaxTabs`（默认 8），行数闸 `preloadMaxLines`（默认 4000），缓存行数闸 `previewCacheMaxLines`（默认 8000）。

## 2. 调研结论（外部成熟方案，带出处）

| 方案 | 做法 | 可借鉴的数字 |
|---|---|---|
| **Typewright**（[SPEC.md](http://raw.githubusercontent.com/lprhodes/typewright/HEAD/SPEC.md)） | **块级增量**：只有与改动区间重叠的块重扫（+ 小范围前后看顾，处理跨块合并/拆分如空行分段、围栏开合）；未变块**保留节点**、只做**位置重映射**；并明确两条原则 —— "**字符串是真源**，渲染是非破坏性叠加"、"**视口界定工作量**" | 50 KB 文档：中段编辑 **~1.6×**、末尾追加 **~8.6×** 快于全量重解析；另有阈值触发的虚拟化让 1 MB 文档仍可编辑 |
| **Incremark**（[why-incremark](https://www.incremark.com/guide/why-incremark.html)、[comparison](https://www.incremark.com/guide/comparison.html)） | 流式**增量解析**：稳定块缓存，只解析新增 ⇒ `O(n)` 而非全量重解析的 `O(n²)`；边界感知（代码块/列表等嵌套结构） | 916 行文档：**87.7 ms** vs 全量方案 1441 ms（**16.4×**）；文档越大优势越大 |
| **虚拟化 / 窗口化**（[virtualization-and-windowing](https://sujeet.pro/articles/virtualization-and-windowing)） | 四条路径：定高虚拟化 / 变高虚拟化 / **DOM 回收** / **CSS `content-visibility: auto`**。CSS 路径的取舍被写得很直白：**保 DOM、跳过离屏布局与绘制，代价是不省内存**（仍可被"页内查找/锚点"命中） | 长内容分节 + `content-visibility: auto` 的首屏渲染提升常见数倍（[数据与配方](https://webperfclinic.com/article/css-content-visibility-rendering-performance-guide)，必配 `contain-intrinsic-size` 防 CLS） |
| **CSS containment**（[contain 2026](https://webperfclinic.com/article/css-containment-layout-paint-size-2026)） | `contain: layout paint`（=`content`）让"块内的改动"不外溢 ⇒ 单块重排不惊动整篇 | 是增量渲染的**前置条件**（没有它，改一个块仍可能整篇 layout） |
| **活 DOM vs 序列化字符串的内存量级** | 活 DOM 每节点约 100–200 B（Blink 的 Element/Text 对象 + 属性表，DevTools 的[分离 DOM 与堆快照](https://learn.microsoft.com/zh-cn/microsoft-edge/devtools/memory-problems/heap-snapshots)是官方口径）；序列化 HTML 平均每节点 20–40 B | ⇒ **约 3–6 倍**。仓库自己的估算 `nodes*120 + chars*2`（`app.js:13013`）正落在"活 DOM"这一档 |

**一句话总结**：**增量渲染**（Typewright / Incremark）与**离屏跳过**（`content-visibility`）都有成熟做法且与 Memoria 的"字符串为真源 + 有块结构"前提一致；"换字符串省内存"方向正确但有明确的代价清单（见 §3.3）。

## 3. 设计（四条线 + 一条已确认的小修）

### 3.1 L1 刷新分档：soft / medium / hard（**建议先做**）

把已有的 A–J 阶梯**命名成三档**，并给三个触发点固定映射（全部复用现有函数，**不新造机制**）：

| 档 | 语义 | 动作（组合现有函数） | 用在 |
|---|---|---|---|
| **soft 软刷** | 只作废**派生视图**，不动当前文档 | `_previewCachePurge()`（他页签条目）+ `refreshKbPendingSummary()` + `loadGraphData()` | **agent 对话结束但本回合没写库**、切换侧栏页签后的轻同步 |
| **medium 中刷** | 当前文档作废重开 + 文件集合重扫 | soft + `refreshFiles()` + `openFile(cur,{skipNav:true})`（仅当它在被写清单里） | **写面 apply 成功**、agent 写库后的对话结束 |
| **hard 硬刷** | 整库重扫 + 链接表 + 图谱（± `validate` / `build`） | `#btn-refresh` 现有四连（`app.js:12363-12368`），可选挂 `validate_kb` / `build_kb` | **用户手动**（`#btn-refresh` / `#btn-build`） |

**本轮同时修掉 §1.3 那处真问题**：`refreshAfterTurn` 按 `turnWroteSomething` 分档 —— 没写库走 soft（**不再清空整库缓存**），写过库走 medium。验收：单测钉"未写库的一轮之后，池里条目数不变"。

### 3.2 L2 当前文档的离屏跳过（低成本、收益大）

> **⚠️ 本节已被 2026-09-24 的真机读数判死，落地后当日删除**（`app.css` 那两行 `content-visibility: auto` /
> `contain-intrinsic-size` 已撤）。两原因：① **搬不动**那 ~1.45 s —— `paint` 只从 1833 → 1788 ms，因为它只让
> 浏览器**跳过**屏幕外的活，30 万节点仍全在 DOM 里；② 与被取代它的 **§3.7 窗口化**冲突：被 `content-visibility`
> 跳过的块 `offsetHeight` 返回的是**估值**，而窗口化正靠量真高让滚动条越用越准。以下原文保留作历史。

给 `#preview` 的块级元素加 `content-visibility: auto` + `contain-intrinsic-size: auto <估算高度>`，并给块加 `contain: layout paint`。要点：
- **必须配 `contain-intrinsic-size`**，否则滚动时高度回填会跳版（CLS）；
- 只对**大文档**启用（阈值可复用"性能"面板的行数门槛，或新加一个开关）；
- 对**编辑模式**要谨慎：`contentEditable` 区域被 `content-visibility: auto` 跳过时，光标定位/选区映射可能出问题 ⇒ 建议**仅预览/只读视图启用**，编辑视图先不动（这条要在实现时验证）。
- 与 L4 的关系：`contain: layout paint` 是 L4 的前置条件，两者一起做。

### 3.3 L3 缓存形态：`dom`（现状）↔ `html`（序列化字符串）—— **先实测再定默认**

- **能省的**：按 §2 的量级，活 DOM → HTML 字符串约 **3–6 倍**缩减；AST 是否也跟着换成"按需重解析"是第二个可省项（当前 AST 常驻）。
- **代价（四条，必须逐条量）**：① 恢复要 `innerHTML` 解析一次（不再是"移动节点"）；② 事件监听全丢，要重绑（`bindPreviewLinks` 靠 `data--bound` 去重、`postProcessWikilinks` 幂等 ⇒ 可重绑，但 `attachImageLightbox` 等要逐条确认）；③ **MathJax（CHTML）/ Mermaid（SVG）产物能否活过序列化** —— 理论上都是真标签、不必重排，**但必须实测**（可能带 `document` 引用或 assistive 隐藏节点）；④ 成本搬家：序列化是切走时的 O(n) 遍历，可能把卡顿从"切回"挪到"切走"。
- **实测口径（定默认值前必须给数字）**：同一台机器、同一个第 8 章，量三组 —— `dom` 与 `html` 两种形态下 ① 池内 8 个条目的**堆占用**（DevTools 堆快照）；② **切回耗时**（`previewCacheScores().lastSwitchMs`）；③ 恢复后**功能完整性**（链接可点、图片灯箱、公式/图形仍在）。
- **① 已可现场量（2026-09-24 追加，不必等完整实测）**：设置 →「显示」→「性能」→「刷新读数」新增一行 **池占用（实测节点数）**：
  `N 条 / M 节点 / 文本 K 字符 ⇒ 估值 X MB（按 120 B/节点）· 活 DOM 区间 L · 若改存序列化 HTML 约 H；另含常驻 AST B 块`。
  其中**节点数是遍历缓存子树数出来的真数**（`_previewPoolFootprint()` 走 `entry.frag`），两档区间由 `MemoriaPreviewPolicy.estimateBand()` 按每节点 **100–200 B（活 DOM）/ 20–40 B（序列化）** 给出（出处见 §2）。
  ⇒ **"静态化能省多少内存"这一半可以当场回答**；**剩下两半**（切回耗时回升多少、MathJax/Mermaid 产物能否活过序列化 = 功能完整性）仍须 K3 实测。
  另：读数还报 `entry.ast` 的**常驻块数** —— AST 现在随条目常驻（恢复时不必重解析），改存 HTML 时**这项正好可以一并放掉**（要么按需重解析、要么连它也序列化），是第二笔可省项。
- **预期结论（待验证）**：如果 ③ 成立且 ② 的回升可接受（例如 < 100 ms），则大文档用 `html`、小文档用 `dom`（**按条目的 `bytes` 与实测恢复成本自适应**）——这也正好能塞进 AG64 那套评分里（多一项"形态"的决策）。
- **⚠️ 上面这条"预期结论"已被 2026-09-24 的真机读数否掉一半**：**省内存成立**，但**恢复耗时不会因换形态而下降**（命中已是"移动节点"；`innerHTML` 反而要重新解析一次）。详见下一节。
- **🔴 2026-09-24 真机实测判定（AG68，人给的读数）** —— 这一组数**否掉了"静态化能提速"**，并把靶子挪到了别处：

  | 读数 | 值 | 含义 |
  |---|---|---|
  | 池内条目 | **2 条 / 506,239 节点 / 文本 461,156 字符** | **每章约 25 万节点**（≈59 节点/行 —— MathJax CHTML 每公式几十~上百层 span） |
  | 池占用 | 估值 **58.8 MB**（区间 49.2–97.4 MB） | 只有 2 条、`累计淘汰 0 次` ⇒ **当前根本不在内存瓶颈上** |
  | 序列化 HTML 估算 | **10.5–20.2 MB** | 每条约省 **20–40 MB**；8 条填满约省 160–300 MB ⇒ **省内存成立** |
  | **最近一次切页签** | **360 ms（走了缓存搬回）** | **关键**：命中已跳过 markdown 解析与 MathJax 重排**还要 360 ms** |

  **推论**：那 360 ms 不可能是"取节点"的钱（命中走 `appendChild(fragment)` = 移动节点），只能是**挂进可见文档之后的 O(n) 收尾**（两轮全量扫描 `postProcessWikilinks` / `bindPreviewLinks`、同步 mermaid、写 `scrollTop` 触发的**强制同步布局**）。而**换序列化字符串也要重造同样 25 万节点、再跑同样那几轮扫描 ⇒ 省不了这 360 ms**。
  ⇒ **结论：`dom → html` 只买"内存"这一半，不买速度**；且当前池未满，这一半也还不急。
  **靶子按性价比重排**：① 先量清 360 ms 花在哪（**已落地**：`_beginSwitchTiming` / `_markSwitch` 分段计时 + 读数行「切页签分段」，见 §1 的现状事实与设置面板 §2.24）→ ② 查"预渲染为什么一次都没命中"（读数 `0/8 · 0%（0 中/10 未中）`）→ ③ **减少节点数**（公式渲染形态：CHTML 深层树 → SVG / 公式级固化 ⇒ 内存与耗时一起降）→ ④ L2 离屏跳过 → ⑤ 缓存形态静态化（最后）。
  **两个读数的读法（避免误判）**：`预渲染配额 0/8` 里的 `_preloadDone` **在改门槛时会被有意清零**（AG65：清 `_preloadTried` 让放宽后的章节重新有机会）⇒ `0/8` 不等于"没跑过"；而 `命中率 0%（0 中/10 未中）` 才是真信号，它当前可由"只开了两三个页签、且都已缓存 ⇒ 没有候选"解释（加上模型样本 42 < 50 还没热）。

### 3.4 L4 增量渲染（治本，大工程）

**目标**：编辑时只重跑**脏块**（`O(edited block)`），而不是整篇。要动四处（缺一不可）：

1. **脏块识别**：`collectEditorBody()` 已经有逐行结果 ⇒ 与上一版做**行级 diff**，映射到 `ast.blocks[]` 的块区间；边界处按 Typewright 的经验**多看顾前后各一块**（空行分段、围栏开合、列表紧/松会跨块改语义）。
2. **只重渲脏块**：`P.parse` 支持按块区间解析（现有 parser 是整篇入口，需要加一个入口或接受"从第 N 块到第 M 块"的切片）；渲染只替换对应的 DOM 子树。
3. **行号映射的偏移重映射**：`_blockLineMap` 全量重建 ⇒ 改成"脏块重算 + 其后块的偏移增量"（**这行号是跳转 / KP 锚点 / 选区映射的依赖，最容易出错的一步**）。
4. **`stampBlockLines` 只对脏块重打** + contentEditable/非编辑标记的增量补做。

**编辑模式的三个复杂点（你最担心的地方，单列）**：① **光标与选区**：块被替换后要把光标位置按"块内偏移"搬过去（跨块编辑时还要处理块合并/拆分）；② **编辑中的块不做复用**（脏块永远重渲，不管它多大）；③ **与写盘的次序**：现在 `markDirty` 会 `_previewCacheDrop(currentPath)`（`app.js:160`）⇒ 编辑中的文档不缓存，这条在增量下应保留（否则缓存与正文会分叉）。

**收益预估（据 §2 外推，非实测）**：第 8 章（3983 行 / 567 块级公式）现在每次停手 80 ms 就整篇重渲；增量后单块编辑应落在**数十毫秒**量级。**开工前先测基线**（用现成的 `_lastSwitch.ms` 口径扩一个"编辑重渲耗时"读数）。

### 3.5 L5 预测式预加载：从启发式到**马尔可夫链**（人 2026-09-24 追加的想法）

> 人：「我们捕捉用户在当前文件进行的跳转行为，跟踪以**文件**为粒度……基于**马尔可夫链**的，也是当年 Google 的核心，他用更好的算法记录了节点相连的权重，智能地追踪了足迹」。
> **史实更正**（不影响判断）：PageRank 是 Google **搜索**的核心（1998，在**网页图**上做马尔可夫链的稳态分布），不是 Chrome 浏览器的核心。但抓的**机制**准确 —— "在图上按跳转权重做随机游走、用稳态分布衡量重要性"，正是马尔可夫链 + **带重启的随机游走**（personalized PageRank，PPR）那一族。**采纳**。

**两步走**（避免一次上大件）：

- **K1'a 启发式（先上，2 小时级）**：`收益 = T̂(loadMs) × 未来被切的概率`，概率项由"目录相邻 ±1 章最高、最近打开过次之、同目录再次之"构成；配额按收益降序（而不是"页签栏最靠前的 N 个"）。只改 `_nextPreloadCandidate()`（`app.js:13188-13197`）+ 一个开关。

> ① **预渲染只在「文件打开之后」做**（预览 / 源码 / 分栏**任一都算**）—— `_preloadDocumentOpen()` 拦在**调度与执行两个入口**（`_preloadSchedule` / `_preloadTick`）；理由：打开过程中抢 CPU 会拖慢你正要看的这一份，而没有打开任何文件时更不该预渲染。
> ② **切换当前文件后，把投机的预渲染产物与「新的候选集」比对并删除**（避免滞留）—— `_preloadPruneStale()` 挂在 `renderPreview` 收尾、且**先清后排**；保留集 = **打开着的页签 ∪ 仍被预测的文件**；**人真正打开过的条目**（`_previewCacheStash` 写的是 `prerendered: false`）**一律不碰**（那是第一层的正经缓存）；清掉的条数进 `previewCacheScores().stalePruned` + 面板读数。
> ③ 随之**必须**放开的一条（否则 ② 无事可做、第二层也只是重排页签）：**预测目标可以不是打开的页签** —— `_preloadPool()` 的来源二 = 预测里收益最高的 `PRELOAD_PREDICT_MAX = 2` 个文件，`_preloadOne` 的守卫也从"必须是打开的页签"放宽为 `_preloadStillWanted()`（**页签或仍被预测**）。"提前渲染你还没打开的那一章"正是 ② 要清的滞留来源。

#### 模型（K1'b）

**节点** = 库内文件（库内相对路径）；**边** = **用户发起**的跨文件跳转；**权重** = 带**时间衰减**的计数。

1. **记录一次跳转** `a → b`（时刻 `t`）——对 `a` 那一行先**惰性衰减**再 `+1`（次数不衰减就会让早年的习惯永久统治）：
   ```
   row_a(b) ← row_a(b) · 2^(−(t − touched_a)/τ)     τ = 半衰期（默认 14 天，可配）
   row_a(b) ← row_a(b) + 1
   visits(b) += 1;  lastSeen(b) = t
   ```
   行内**按度截断**（degree ≤ 64，丢最小项）⇒ 稀疏、上限可控。
2. **预测（当前文件 `c`）** —— **带重启的随机游走**，截断 K 步（就是 PPR 的幂迭代近似）：
   ```
   q₀ = e_c
   q_{k+1} = α · e_c + (1 − α) · q_k · P        α = 重启概率（默认 0.35，可配）；K = 3（可配）
   S(next) ∝ q_K(next) + μ · π(next)            μ = 先验权重（默认 0.15）；π = 全局 PageRank 稳态分布
   ```
   **为什么不是"一阶 argmax"**：预渲染想知道的是"**接下来几跳内谁最可能被打开**"（soon-reachable），不是"下一步的精确最大"。`α` 越大越偏"只看一步"，越小越看"远处的可达性"；`K` 步截断给的就是这个视野。
   **为什么要 `π` 先验**：新文件、或"从 `c` 出发根本走不到"的文件，在 `q` 里是 0；全局稳态 `π` 兜住这类冷启动（它正是 PageRank 最原始的那个用途）。`π` **懒算**（模型载入时、或每 N 次跳转跑一次幂迭代；图小，毫秒级）。
3. **与成本相乘**（承接 AG64 的 `T̂`）：
   ```
   收益(next) = S(next) · T̂(loadMs(next)) · (1 − 已在池 / 已打开)
   配额按收益降序分配
   ```
   **注意区分两个决策**（别混）：**预渲染**看"**未来会不会被打开**"（用 `S`）；**淘汰**看"**留着值不值**"（用 AG64 的 `score`）。两者都乘 `T̂`，但概率项不同 —— 一个文件可以"值得留"却"不值得现在预渲染"。
4. **冷启动与回退**：`c` 无出边 / 模型为空 / 全库样本 < 50 次 ⇒ `q` 退化为 `e_c`，只剩 `π` + 目录相邻 + `openTabs` 顺序 ⇒ **就是 K1'a 的启发式**。开关默认开、可关，可一键清空。

#### 反污染（**这条最关键**）

模型必须只学**人的**足迹，否则学的是自己的尾巴（自激回路）：

| 计入 | **不计** |
|---|---|
| 切页签（点页签栏 / 快捷键）、`[[wikilink]]` 点击跳转、文件树点击、搜索/大纲跳转、前进后退 | ① `openFile(..., {skipNav: true})` 的**编程式重开**（`#btn-refresh` 四连与写面同步 `syncAfterWrite` 都走它）；② **预渲染自身**的 `load_document`；③ agent 侧写面重开 |

- 记录点放在 `openFile` 的**用户入口**（`skipNav` 为假的那条），**不要**放在缓存/预渲染里。
- **同文件内的锚点/大纲跳转不计跨文件边**（只算该文件的活跃度）。

#### 落点与生命周期

- **`<kb>/.memoria/cache/nav-graph.json`** —— 明确是**可再生缓存**（对齐 `AGENTS.md §1`：`.memoria/cache/**` 不作为事实源、不进 manifest/sidecar、不被 `validate_kb` 审计）。
- 上限：节点 ≤ 5000、边 ≤ 20000、单文件 ≤ 512 KB；超限按 `visits` 截断。**换库不跨库共享**（路径命名空间不同）；**换主题/语言不影响**（与内容无关）。
- 「性能」面板加：开关 + 「清空导航模型」按钮 + 读数（模型节点/边数、**预渲染命中率**）——复用 AG65 那个现场读数块。
- **隐私**：只有路径与计数、只在本机、一键可清。

#### 评测（敢上模型的前提，也是它比"黑盒模型"强的地方）

- **埋点先行**：K1'a 阶段**只记录跳转序列**（不改预测）⇒ 攒出真实回放集。
- **离线回放**（hold-out：每个会话最后 20% 的跳转作测试集）：
  | 编号 | 预测器 |
  |---|---|
  | A | 页签顺序（**现状**） |
  | B | 目录相邻（上一章/下一章） |
  | C | 一阶马尔可夫 `argmax P1` |
  | **候选** | 截断 PPR（`α` / `K` 扫参） |
  指标：**top-1 / top-3 命中率** + **命中时的平均收益**（省下的 `T̂(loadMs)`）。
- **线上**：把"预渲染过的页签后来真的被打开的比例"放进面板读数。

### 3.6 KP 层：把预测建在**知识点图**上（人 2026-09-24 追加）

> 人：「知识库天然的最小单位节点是**知识点**，我觉得我们可以利用这个基础设施，尽管**文件还是最小的渲染单位**」。
> **采纳**。这条把 §3.5 里那张"网页图"从**行为边**扩到了**结构边** —— 而**结构边库里本来就有**（零采集成本），正是 PageRank 当年拿到的那份"链接图"。

**两层图，各司其职**

| 层 | 节点 | 边 | 用途 |
|---|---|---|---|
| **KP 层**（**预测在此**） | `(file, kp_id)` —— 库内既有标识（`apply.py:101`、`ask.py:133` 都用这个键） | ① **结构边（已有）**：sidecar 里 KP 间的 `links` 与图谱边（`graph/edge_derivation.py` 推导，产物 `.memoria/build/graph.json`；`link_audit.py` 已在 KP 粒度审计）② **行为边（新增）**：用户实际跳转 | 预测"下一个可能被读的**知识点**" |
| **文件层**（**渲染在此**） | 库内相对路径 | 用户跨文件跳转 + 目录相邻 | 决定"预渲染哪一份**文件**" —— **渲染的最小单位仍是文件** |

**为什么这是明显升级**：结构边是**编辑时就写下、随内容演进的语义关系**（`[[链接]]` / sidecar `links[]`）⇒ **不需要任何用户历史就有先验**（冷启动、新库、新章节立刻可用）；行为边只在它之上做**个性化** —— PPR 的重启点从"当前文件"细化到"当前正在读的 **KP**"。

**合成（结构先验 + 行为证据，按样本量收缩平滑）**

```
P(kp' | kp) ∝  counts(kp → kp')   +   κ · w_struct(kp → kp')        κ = 平滑强度（可配）
                 ↑ 行为边（时间衰减，§3.5）  ↑ 结构边（权重：显式边 > 同文件内 / 同章 > 同目录）
q_{k+1} = α · e_{kp} + (1 − α) · q_k · P                             # 重启点 = **当前 KP**
```
`κ` 让"没数据时偏向结构、数据多了逐渐偏向真实行为"（等价于贝叶斯收缩）⇒ 冷启动不会空转。

**投影回文件层（关键，不能省）**：渲染单位是文件，一个文件可能命中多个 KP，而预渲染的成本是**整份文件**：
```
S_file(f) = Σ_{kp ∈ f} S(kp)                # 也可取 max（放大"有一个超热 KP"）；求和更稳
收益(f)    = S_file(f) · T̂(loadMs(f))        # 成本项用**文件**的实测加载耗时（AG64 的画像）
```
⇒ **一份 4000 行的大文件只命中一个弱 KP，很可能仍不值得预渲染**；小文件命中强 KP 则立刻值得。这与 §3.5 那条"**预渲染**看未来会不会被打开、**淘汰**看留着值不值"是同一套纪律。
**KP→文件 的映射不用新建**：`kp_index.collect_kp_targets` 已有（`ids` / `file_stems` / `(文件, kp_id)` 对，见 `graph/edge_derivation.py:231` 的注）。

**KP 粒度还白送两个信号**（都在库里，不需采集）：

1. **未读 / 待复习优先**：KP 有 sidecar 状态与 `pending` 机制，且本仓已有 FSRS 复习线 ⇒ **复习队列本身就是"用户接下来最可能打开的 KP 集合"**，可作为一档很强的先验（可配）。对记忆类应用这是天然需求：**先把该复习的那批预渲染好**。
2. **KP 级活跃度**：同文件内的锚点跳转按 §3.5 不计"跨文件边"，但在 KP 层它就是一条**同文件边** ⇒ 能表达"这个文件里被反复读的是哪几个 KP"，进而参与 `S_file` 的加权。

**成本与风险（如实）**

- **零成本的部分**：结构边（已有）、KP→文件 映射（已有索引）、KP 粒度审计（`link_audit.py` 已在做）。
- **要新增的部分**：① 行为边的记录（`from_kp → to_kp` 计数；比文件级只多"当前 KP 在哪"这一个字段）；② KP 层 PPR —— **图规模 = KP 数，比文件数大 1–2 个数量级** ⇒ 必须**稀疏 + 截断 K 步**（不能全量迭代到收敛；必要时只保留 `q_k` 前 64 个候选再展开）。
- **KP id 会改名**：本仓已有**全库级联重命名** `rename_kp_id()` → `kp_rename.rename_kp_in_kb()`（带 `dry_run`，op `rename_kp`）⇒ 行为边**可选地**跟着重映射；更省的做法是**容忍陈旧**（失配的边走 §3.5 的时间衰减自然淘汰 —— 它本来就是**可再生缓存**）。
- **边界（写清楚）**：**渲染的最小单位仍是文件** ⇒ KP 层的红利**全在"预测质量与冷启动"**上；要真正"只渲染到某个 KP 的块"，得等 §3.4 的**增量渲染**到位（那时才谈得上"预渲染到第 N 块"）。

1. **只服务"新一次加载"**：新增 `pendingLoad`（模块启动即 `true`；`_previewCacheStash()` 切走时 `markLoad()` 重新置位；`attach()` **消费一次即清**）⇒ **同文档重渲染（编辑同步 / 切视图模式 / 刷新）一律不接管**，直接走 `_restorePlainPosition()` 那条老路（整篇真 DOM、按源码行定位、**零估值零补偿** ⇒ 不漂）。读数判据：出现 `attach✗ same-doc` 就是"编辑走了老逻辑"（**这正是预期**）。
2. **过渡终点 = 交还控制权**（**仅普通换文件**；⚠️ **跳转进入不排**，见下一段）：接管后 `TRANSITION_MS = 1200 ms` 到点把整篇**分帧分块物化**（`requestAnimationFrame`，**24 槽/帧**）⇒ 物化完 `_unbind()` + `st = null` + 恢复位置 ⇒ 之后滚动/编辑全是老逻辑。**为什么必须分帧**：整篇**一次性**物化 = 5879 次 `replaceChild` = **一个超长任务** ⇒ 真机表现就是「**直接卡死**」；24 槽/帧把长任务切成 ~245 帧（每帧只有几十微秒的 DOM 操作），且**编辑先到即中止**（`const s2 = st; if (!s2) return;`）。

**⚠️ "换文件 = 一次加载"必须与"能否暂存"解耦（2026-09-25，AG95；第二份真机日志定案）**：那份日志里**一条 `attach?` 都没有**（窗口化**整场没生效**），而 `attach✗ same-doc` 却打在**明确的换文件**上（`教材/04 → 教材/08`、`教材/09`、`教材/11`，调用栈 `_previewCacheRestore → renderPreview → setViewMode → openFile → activateTab`）⇒ `pendingLoad` 恒为 `false`。**根因**：`pendingLoad` 只由 `_previewCacheStash()` 里的 `markLoad()` 置位，而那个函数有 **8 条早退**（`!state.doc` / `_dirty` / 无 `preview_body` / 源码视图 / `_previewDomKey` 失配 / 行数超上限 / 预览空…）—— 在"大文档 + 频繁编辑"下它几乎总是早退 ⇒ **下一份文件永远被当成"同文档重渲染"** ⇒ 180–284 KB 的文档整篇进 DOM（30 万节点 + 整篇 MathJax/mermaid + 每次编辑整篇重渲）= 人说的「连滚轮都滚不动」。**修法**：`openFile` 里 `state.currentPath !== relPath` 即调 `markLoad()`（**换文件就是一次加载，与"能不能暂存"无关**）。同一轮另修两处"窗口化一旦真生效就会露出来"的落点问题：① `keepPosition()` 对**任何加载**（`pendingLoad`）都不采"旧 DOM 的视口行" —— 否则换文件会把**上一篇的行号**当锚点、新文件直接落在中段；② `anchored`（= `claimScroll()` 的判据）**只在真有锚点时**为真（跳转目标 / 缓存条目锚点），冷加载保持 `false` ⇒ `_restoreTabScroll()` 的**页签像素**兜底仍能写进来（入口 ① 在"未命中缓存"时的唯一来源）。

**⚠️ 逃生门 + 两个"卡住"死结 + 诊断一律走 error 级（2026-09-25，AG96）**：人：「**这么久都没办法解决，现在还出现卡在一个预览窗口的无法滚出的**」。这一轮不再只加读数：

1. **逃生门 —— 设置「性能 → 窗口化渲染」（默认开）**：关掉 ⇒ 预览立刻退回**整篇渲染 + 原生滚动**（老路径）；控制台亦可即时切 `MemoriaPreviewWindow.setEnabled(false)`。**窗口化只该是性能优化，关掉不许改变正确性**（`willTakeOver()` 在关闭时也返回 `false` —— 否则"整篇 mermaid"会被跳过而没人替它渲染）。落点：`winEnabled`（初始值直接读 `-display-settings`，因为本模块可能晚于"设置通告"加载）+ `attach` 的 `_skip("disabled")` 闸门 + `setPreviewCachePolicy` 里转发 + 设置面板新勾选行（与算法侧 `DEFAULTS` 同源，有跨文件钉子）。
2. **`s.moving` 死锁（"卡在一窗里出不去"的现成解释）**：`_move()` 收尾调 `_afterMaterialize()`（补 mermaid / 链接 / 排版），**它一抛异常，`s.moving` 就永远是 `true`** ⇒ `_cover()` 从此直接 `return false` ⇒ **窗口再也不跟随滚动** ⇒ 画面看着就是"卡在这一窗里"。⇒ `try/ catch(_skip("materialize")) / finally(s.moving = false)`。
3. **诊断一律走 error 级**（`_err`）：两份真机日志里 `attach✗`（error 级）**一条不漏**，而 `attach?` / `move`（log 级）**一条都没有** ⇒ 从此"必须看见"的三样都走 error：`attach⇢ #N load=? jump=? on=?`（证明 `attach` 到底被调用没）、`render ⇢ entry/✗ source-mode/✗ already-rendering/✗ token 顶掉`（`renderPreview` 的每个早退点）、`wheel@document inPane=? target=<…>`（capture 阶段问一次"滚轮落在谁身上" —— `inPane=0` 就是事件被别的东西吃了）。

**⚠️ 跳转进入（入口 ③）：窗口化照旧，但「不排过渡物化」（2026-09-25，AG94；修正 AG93）**：人反馈「**跳转之后就卡死，滚不动**」后，AG93 曾按"跳转路径反复出问题"把跳转改成**完全不窗口化** —— 真机日志立刻否掉它：`attach✗ jump` 之后整篇 4000 块全在 DOM 里，**跳转后 4.7 s 一个事件都没有、随后 11 s 空白**（30 万节点绘制 + 整篇 MathJax + 整篇 mermaid 全回到流水线上）⇒ 人：「**连滚轮都滚不动**」。**窗口化真正不能丢的，正是"DOM 里只有一窗"这一条**，而真正要拿掉的是**过渡终点的整篇物化**（5879 次 `replaceChild` = 「跳转之后编辑直接卡死」那一刀）—— 人要的是"**在包含定位点的窗口里播放定位**"。

| # | 位置 | 要求 | 漏了会怎样 |
|---|---|---|---|
| ① | `openFile` | 凡**跳转意图**（`kpId` / `errorHighlight` / `lineHint`；`restoreScroll` 的页签切换**不算**）即 `jumpArrival()` —— **没有解析出目标行也要打** | ③ 的 `keepPosition()` 会把**上一个文件**的视口行当成目标行 |
| ② | `jumpArrival()` | 只置 `jumpIn`（**不再**跳过窗口化）；`markLoad()` 会清它（跳转若因当前是**源码视图**而没走到 `attach`，标记滞留 ⇒ 下一次正常换文件被"上一个文件的目标行"顶掉） | 要么整篇进 DOM（AG93 的坑），要么下一次换文件落错位置 |

**诊断（三样，全进控制台）**：`render slow <总ms> · 解析 … 建DOM … 打行号 … mermaid … MathJax起 …`（流水线 ≥ 250 ms 即打，回答"哪一段吃掉时间"）；`wheel(idle) top= max= vh= nodes=`（**未接管时**第一次滚轮 ⇒ 事件到了没 / 窗格能不能滚 / DOM 里有多少节点）；`scroll(idle) top=`（未接管时真滚到了 ⇒ 原生滚动是通的，卡的是我们自己的重活）；`plain-restore L… → top=… 实到=… max=…`（跳转落点自证：被夹到 0 说明那一刻内容还没有高度）。

**⚠️ 与 MathJax 的顺序（2026-09-24 真机读数跟进，AG73）**：**队列要排在 `attach` 之后、且挪到两帧之后**。原顺序（冷渲染在 `renderPreview` 中段排、命中在恢复末尾紧接着排）会让 MathJax 在**窗口化生效之前**就开始 ⇒ 它把**整篇 22 万节点**都排一遍（真机 ≈1.8 s 主线程重活），既挡住第一帧、又把下一次切换拖住（`_mathPending` 链式等待：读数里 `mathjax` 打点 == `render` 累计就是它在等这条链）。改法：两条路径都用双 `rAF` 把 `queuePreviewMathTypeset()` 推到"窗口已定、第一帧已画"之后 ⇒ 它只排**窗口内**那点公式（实测窗口一帧 22 ms）。代价是公式"晚一拍"变渲染态 —— 与 `app.js:1963` 原注释同一取舍。

**⚠️ 与"预渲染排队"的取消缺口（2026-09-24 真机读数跟进，AG74）**：`_preloadSchedule()` 的"先等两帧"是用 **`rAF`** 排的，而 `cancelIdleCallback` **取消不了已经排进 rAF 的那一步** ⇒ 切页签时 `_preloadStop()` 把 `_preloadIdle` 置 null 后，那个 `arm` 仍会被 rAF 调到、照样登记一次空闲回调 ⇒ 切完之后又冒出一次**整篇预渲染**（≈1 s 主线程长任务）。真机证据：脚本侧已降到 **314 ms**（上一轮 MathJax 那刀生效），但 **`frame1` 迟至 1504 ms**、`画面 1810 ms`，且用户报告**这期间滚轮与输入全冻**。修法：`arm` 首行自检 `_preloadIdle !== -1`（被取消 ⇒ 直接退出）。

**⚠️ 跳转优先于"恢复上次位置" + 窗口化调试读数（2026-09-24 AG76）**：人实测「跳转还是一开始先渲染文件的最开头……而且文件没有打开过的话，跳转位置是错的，仍然无法滚动，**要调试日志**」。**① 跳转被顶掉的根因**：AG75 把目标行写成"**仅在没有缓存锚点时**生效"（`(!a && pendingLine)`）⇒ **文件看过一次**（命中缓存 ⇒ `a` 存在）时目标行被旧位置顶掉，于是又变成"先渲旧位置、卡一会、再跳过去"。改法：`pendingLine` **无条件优先**（`(_jumpIdx >= 0) ? _jumpIdx : (a.i …)`），且跳转时 `off = 0`（落到目标块**块首** —— 人：「从该窗口的开头播放定位」）。**② 调试读数（人明确要）**：窗口模块加**有界环形日志（最近 8 条）+ 计时器**，经 `stats()` → `previewCacheScores().win` → 设置「性能」底部**两行**：
   - 计数行：`滚轮 N 次 · 滚动 N 次 · 兜底 N 次 · 窗口 from–to/slots（真身 shown）· scrollTop top/max · 锚点行 line→命中 jump`；
   - 日志行：最近 8 条 `attach` / `anchorLine` / `move` / `wheel`。
   **判据表**（一眼定位，不再靠猜）：`wheel` 不涨 ⇒ 滚轮事件**没到预览区**（被谁拦了 / 指针不在预览区）；`wheel` 涨而 `scrolls` 不涨 ⇒ 事件到了**窗格没滚**（`fallback` > 0 就是我们补的那一下）；两者都涨而画面不动 ⇒ **窗口没跟随**（看 `move` 轨迹）；`max` 为 0 ⇒ **窗格根本不可滚**（占位块高度没生效）；跳转看 `anchorLine`（目标行）与 `jump`（命中下标；-1 = 没找到 ⇒ 落回旧位置/文档头）。**③ 顺带加了滚轮兜底**：`wheel` 事件到了但那一回合窗格没动 ⇒ 我们自己滚一次（`deltaMode` 按行/页折算；平滑滚动时跳过，避免与浏览器打架）—— 它既让滚轮**当下可用**，也把"原生滚动生效没"变成可读的数（`兜底` 计数）。

**⚠️ 切视图模式要**保住位置**（2026-09-24，AG82）**：`setViewMode()` 切模式会**重渲染预览**（`renderEditor()` + `await renderPreview()`）⇒ 那次收尾走的是**冷渲染**那条 `attach(preview, {})`，**锚点是文档头** ⇒ 预览先回开头，随后才量"顶部对应哪一行"⇒ 量到的已是第一行 ⇒ 人看到"**位置漂移或回到文件开头**"。改法：在 `renderEditor(state.doc)` **之前**调 `MemoriaPreviewWindow.keepPosition()` —— 它用 `captureAnchor()` 取"视口顶部那一块的源码行"记进 `pendingLine`，`attach` 随即以它定锚（`pendingLine` 用完即清 ⇒ 只影响这一次渲染；换文件走 `openFile`，不经过这里）。

**⚠️ 槽位表必须按"块元素"摊，不能按 `#preview` 的直接子节点（2026-09-24 实测踩到，AG80）**：渲染器把整篇包在**一个** `<div class="-preview-content">` 里（`renderer.js:52`）⇒ **`#preview` 永远只有 1 个子节点** ⇒ 按直接子节点摊就只摊出 1 个槽、被 `MIN_SLOTS` 挡下（真机日志：`attach✗ slots<120 1`，这解释了"窗口化一次都没生效"）。改法：槽位表 = `preview.querySelectorAll(".-src-block[data--block-index]")`（文档序）；换窗/回搬一律**走每个槽自己的父节点**（`node.parentNode.replaceChild(…)`）；"是否已物化"的判据 = **`node.parentNode` 是否存在**（与容器包在哪儿无关）。（编辑模式那次早退只是把同一个分支换了个名字 —— 两条都是"窗口化从没生效"的原因。）

**落点**：`app.js` 末尾整块 `(function memoriaPreviewWindow(){…})()`（**零行漂移**；它拿不到主 IIFE 的闭包 ⇒
只经 `window.MemoriaApp.pvPostWikilinks` / `pvBindLinks` 两个**幂等函数引用**就地补链接）+ `app.css` 末尾
`.-pv-spacer`；六个挂钩点全部是**同行追加**（`attach` 两处 / `detach` 与 `captureAnchor` 各一处 /

### 3.8 **回退之后的结论**：限制在哪、下一步做什么（2026-09-25，AG97）

**① 为什么 K4a 反复失败（全部有真机日志，不是推测）**：窗口化不是"一个算法"，而是**一整套虚拟滚动引擎**，每件都必须自己写对，且它们互相耦合：

| 子系统 | 我们踩到的真机现象 |
|---|---|
| 窗口跟随 | `move 2872-2911` / `2872-2912` 交替 ⇒ **自转**（`_cover` 重入 + 无迟滞）；边界上"卡住"；`s.moving` 一旦被异常留在 true ⇒ **窗口再也不跟随**（"卡在一窗里出不去"） |
| 高度账本 | 未测量的块只能估高 ⇒ 滚动条长度与"跳到第 N 行"的像素口径必须**始终自洽**，一旦真高回填就要补偿 `scrollTop`（手工版 scroll anchoring）⇒ 这是"画面往上飘"的来源 |
| 定位 | 跳转要先"物化目标块"再量；缓存锚点会顶掉跳转目标（"文件没打开过时跳转位置是错的"） |
| 接管时机 | 只在"加载那一趟"接管（否则编辑时搬窗 ⇒ 光标乱跳）；但"是不是加载"这个标记本身要可靠（曾因暂存早退而整场失效） |
| 收尾 | 过渡终点的整篇物化 = 5879 次 `replaceChild` = **一个超长任务**（真机"直接卡死"）；改成 24 槽/帧也只是把卡顿摊开 |
| 与其它重活的关系 | 窗口化把"整篇 MathJax / 整篇 mermaid"从流水线上**换走了**，一旦窗口化因任何原因没接管，**那两步就全回来了**（真机：跳转后 4.7 s 无事件、随后 11 s 空白）⇒ 成败被放大 |

**② 限制（limitation）到底是什么**：
- 预览是 `contenteditable` 的**整篇 DOM**，而编辑同步是"**每键整篇重渲**"（`preview.innerHTML="" + appendChild`）。
  这两条合起来形成一个死结：
  - 只要"**每键整篇重渲**"不变，**DOM 规模**就是帧成本的唯一决定因素（30 万节点 ⇒ paint ~1.8 s）⇒ 你会一直想减少 DOM；
  - 而任何"**减少 DOM**"的机制（窗口化 / C-V / 静态化）都必须**同时**处理光标、选区、IME、行号定位、块内偏移 —— 又要和"整篇重渲"抢 DOM 所有权。
- 更直接的一条：**"减少 DOM"是在给"整篇重渲"打补丁**。真正该动的是**重渲本身**。

**③ 参考实现（要研究的候选，不是结论）**：
- **只读虚拟列表**（成熟、可直接借鉴算法）：`react-window` / `virtua` / `Clusterize.js` 这一系 —— 共同点是"**只有一维列表、没有编辑**"，所以它们能把"占位高度 + 窗口跟随"写成几百行。
- **可编辑场景**（与我们同构，值得逐个读它们的 view 层）：ProseMirror、CodeMirror 6、Lexical —— 共同点是"**框架拥有 DOM**，按**块/行**做协调，绝不整篇重建；光标/选区/IME 由框架统一管"。
  ⇒ **我们的 `data--block-index` + 槽位表已经是这条路的雏形**，缺的是"块级增量重渲"。
- 另一个方向（编辑器行业的老答案）：**把"每键整篇重渲"换成"只重渲改动块"**（稳定块身份 + 只替换那一块的 DOM + 位置按块身份保），DOM 规模自然下来 ⇒ 窗口化就不必存在。

**④ 下一步（架构层，等拍板；不要再用补丁推进 K4a）**：
1. **块级增量重渲** —— ✅ **第一刀已落地（2026-09-25，AG98）**：预览区编辑的**五条提交路**（结构性编辑 `commitRange` / 回车 `splitParagraph` / 边界插空行 / 图片块 / 撤销重做）原来都走"改完源码 → `renderPreview()` 整篇重渲"，现全部改走 `paintPreviewAfterSourceEdit()`：**全量解析（很便宜，30–90 ms）+ 公共前后缀差分 ⇒ 只重建真正变了的那几个块**（`R.renderBlock` + **重编块下标** + `stampBlockLines` + 只对新块排 MathJax / 补 wikilink / 按需渲 mermaid），任一步不满足不变量 ⇒ 退回整篇（老路径）。**注意它不需要窗口化**，而且方向与窗口化相反：**DOM 规模不再随每次编辑被重建**。钉子 `tests/test_preview_block_commit.py`（含"普通输入那条好路不许被改动"）。**未取证**：真机手感（回车是否不再闪/卡）。
2. 若要再看虚拟化：**先决定"谁拥有 DOM"**（框架 or 手写），再决定窗口化是否作为它的附属品重建 —— 不要在半所有权状态下再走一遍 K4a；
