---

## 0. 一句话

把「**谁在打字那一刻写 DOM**」还给浏览器，把「**位置↔像素**」交给一张高度账本，最后才谈窗口 —— 窗口化是这两件的**附属品**，不是先行件。

| 期 | 内容 | 需要窗口化吗 | 治什么 |
|---|---|---|---|
| **K5a** | 输入所有权反转 + 块内 DOM 复用 + 热路径去 O(文档) | **不需要** | 「打字不是当帧出现」 |
| **K5b** | 高度账本（估算先行 + 实测回填 + 前缀和增量） | **不需要** | 「跳转/切模式落点漂」 |
| **K5c** | 视口化（CM6 式 `viewport`） | 是（它的正题） | 「大文档滚动/冷渲染」 |

> **⚠️ 施工顺序已被 §1.9 ③ 修订** —— 不再按"收益大小"排，而是**按"与既有交互的交叉面"排**：
> `A0 取数 → A3 低风险项 → K5b 账本 + 块稳定 id → A2 块内复用 + 三层/冻结规则 → A1 所有权反转 → 单向流 + reconciler(R16) → K5c 视口化`
> 开工前置（三层所有权 + 冻结规则 + 交互探针契约测试）见 **R17**。

## 1. 三个口径先对齐

### 1.1 「预览—源码对称」对称在哪、不对称在哪（评审问题 ①）

**对称的是结果**（两侧内容互为镜像）：源码改 → 预览同步；预览改 → 源码同步。这一点现在的实现就是这样，不动。

**不对称的是"打字那一刻谁写 DOM"**：

| | 源码区（`.-line-content`） | 预览区（`.-src-block` 内的 inline） |
|---|---|---|
| DOM 形态 | **纯文本行**（一行一个元素，没有 inline 结构） | **结构化**（段落/标题/列表/`<strong>`/`<code>`/MathJax 容器） |
| 我们现在怎么做 | **从不 `preventDefault`** —— 浏览器原生敲，我们只在 `input` 上（80 ms 防抖）重读文本 | **`preventDefault`** 一切，路由到 AST 管线自己改 DOM |
| 为什么不同 | 原生编辑**破坏不了**它的结构（它没有结构） | 原生编辑**会破坏**结构：把 `<strong>` 删一半、跨块删除、把块拆开 |

⇒ 「对称」的正确读法是：**预览侧向源码侧看齐（能不拦就不拦），但只在"拦不拦都不破坏结构"的范围内**。那个范围恰好是：

- ✅ **`insertText`**（纯插入，插在哪就是光标处）—— **反转**（本方案 A1）
- ❌ **`deleteContentBackward` / `deleteContentForward`** —— 可能跨块合并 / 拆块，读回要处理块合并语义 ⇒ **继续拦**
- ❌ **`insertParagraph`** —— 结构性（拆段），**继续拦**
- ❌ **`insertCompositionText`** —— 规范规定**不可取消**（Chrome 实测 `e.cancelable === false`）；而且我们现在**本来就放行**，只在 `compositionend` 提交

> 结论（R12）：**只反转 `insertText`**。理由不是"复杂度低"，而是**只有它在"对称"与"不破坏结构"之间同时成立**。
> 附带收益：反转后，**预览区与源码区的打字口径一致**（都是原生先写、我们后同步）—— 这才是你说的对称。

### 1.2 块内复用：方案 ① vs ② 的**算法时间复杂度**（评审问题 ②）

> 人澄清：「我说的复杂度是**算法时间复杂度**不是实现难度」⇒ 本节按复杂度重写（原先答的是"实现量"，那是次要判据）。

先定义：`n` = 该块内 inline 节点数，`m` = 该块的 markdown 字符数（≈ 文本长度），`d` = 本次改动碰到的字符数（打字时 `d = 1`），`N` = 全篇字符数。

| 成本项 | ① 同类型块只改文本节点 | ② inline 文本级 diff（利用"模型已知改动"） |
|---|---|---|
| 结构判定 | **Θ(n)** —— 要比对新旧 inline 序列（读两边） | **Θ(d)** —— 改动是本模块自己算出来的，**不需要判定**（Lexical 那条口径："它知道自己改了什么"） |
| DOM 写入 | Θ(n) → **加"值没变就不写"守卫后降到 Θ(d)** | Θ(d) —— 只写变化的那几个文本节点 |
| 本块 markdown 生成 | **Θ(m)** —— 两边共同的**下界**（`G.generateBlock(block)`，源码面板要用它） | 同 |
| **块内小计** | Θ(n + m) → 加守卫后 **Θ(d + m)** | **Θ(d + m)** |
| 外层（两者都要付） | **Θ(N)**：`spliceBlockSource()` 每键整篇 `split`/`join`（`app.js:7699-7708`） | 同 |

**答案**：**② 的算法时间复杂度严格更低一阶** —— ① 的判定是 Θ(块大小)，② 是 Θ(改动量)。

**但它在本仓当前形态下不构成瓶颈，三条理由**：

1. **有共同下界 Θ(m)**：每次按键都要 `G.generateBlock(block)` 出本块 markdown（源码面板要用）⇒ 块内阶数差只决定**下界之上还剩多少**，不影响下界本身。
2. **① 加一句守卫就抹平写入项**：`if (node.nodeValue !== v) node.nodeValue = v;` ⇒ ① 的写入量也掉到 Θ(d)，只剩"判定是 Θ(n) 次**读**"（读 `nodeValue` 比写便宜约一个量级）。**加上这一句之后，① 与 ② 同阶。**
3. **更外层还挂着 Θ(N)**：`spliceBlockSource()` 每键 `state.doc.body.split("\n")` + `join("\n")` 是 **Θ(全篇)**（§2 A3 的靶子）。**Θ(N) 没拿掉之前，块内 Θ(n) 与 Θ(d) 的差不是瓶颈。**

⇒ **选 ① 的理由不是"实现简单"，而是"在 Θ(N) 还挂着的时候，先付 ② 的复杂度不划算"。**
⇒ **什么时候改选 ②**：A0 的读数若显示"**重渲块**"那一段才是大头（而不是"锚点 / 源码 / 脏标记"），说明 Θ(N) 已不是瓶颈、块内项浮上来 ⇒ 那时改 ②（再往下甚至要动"增量 markdown 生成"，因为 Θ(m) 是硬下界）。

> **实现量**（① ~40 行 / ② ~200+ 行）是**次要判据**，不构成决策依据 —— 上面那张表才是答案。

### 1.3 什么是「高度账本」（评审问题 ③）

**定义**：一张表，**每块一行** —— `{blockIndex, srcStart, srcEnd, estHeight, realHeight?}`。
`estHeight` 由**块类型 + 文本长度**估算（CM6 `HeightOracle.heightForLine()` 的思路）；实测后写 `realHeight` 并**只重算失效点之后的前缀和**（Monaco `CustomLine.prefixSum` 的朴素做法）。

**它解决三件事**：

1. **总高** ⇒ 滚动条长度（不用把整篇挂进 DOM 也能有正确的滚动范围）；
2. **位置 ↔ 像素双向换算** ⇒ 跳转落点 / `scrollIntoView` / `_getViewTopSrcLine` / `_restoreCurrentViewScroll`；
3. **高度变化后补 `scrollTop`**（滚动锚定）⇒ 这是"上下飘"的正解。

**为什么现在必需**：MathJax 排版与懒加载图片都是**后到**的 ⇒ 你量到的高度**不是最终高度**（AG104 那次"二次校准"就是在给这个打补丁）。
**"持久化"的含义**：把实测高度存盘（`<kb>/.memoria/cache/**`，`AGENTS.md §1` 的"可再生缓存"），下次打开同一文档不必重新量、不跳动。
> **2026-09-28 人审：「可以有」** ⇒ 本节的**高度账本（K5b）方向确认**，R14 先按"内存 only"做。

### 1.4 三方数据：源码区 / 预览区 / AST —— **谁是「共同真源」**（评审问题 ④）

> 人问：「那你两边（源码-预览）共同的数据结构是不是 AST」—— **不是**。共同的真源是**正文文本**；**AST 是预览侧的派生输入**（外加"预览编辑"时的中间表示）。

| 层 | 是什么（代码事实） | 谁写它 | 谁读它 |
|---|---|---|---|
| **① 磁盘 `.md`** | 最终事实 | `syncToDisk()` 把 `state.doc.body` 写下去 | 后端 |
| **② 内存正文**（← **共同真源**） | `state.doc.body`（字符串）+ `state.doc.lines`（按行数组） | 两侧编辑最后都落到这里 | 源码面板 `renderEditor()` **直接按 `lines` 渲染**（`app.js:1606`）；预览渲染时 `P.parse(body)`（`app.js:1932`） |
| **③ AST** | `_doc` = `P.parse()` 的产物（`blocks[]`）。**不在 `state.doc` 里** —— 它是 app.js 的模块级变量（`app.js:7647`），预览缓存条目里另存一份（`app.js:13217` 的 `entry.ast`） | 由 ② 解析而来；**预览侧编辑时**先改 AST，再用 `G.generateBlock()` 反向生成 markdown 写回 ② | 预览渲染 `R.render(_doc)`；映射器 `M.setDoc(_doc)`（DOM ↔ AST 双向换算） |

**两个要点**：

1. **源码面板根本不碰 AST** —— 它就是一堆纯文本行（`.-line-content`），每行的 `textContent` 就是那一行 markdown；行号也只是行号。
2. **两侧发起编辑时的先后顺序是**反的**：

| 谁发起 | 顺序 |
|---|---|
| **源码侧**（在 `.-line-content` 里敲） | 浏览器原生改那一行 → 我们收集全文 → **重新整篇 `P.parse` 出 AST** → 重渲预览 ⇒ **文本先，AST 后** |
| **预览侧**（在 `.-src-block` 里敲） | 先改 AST → `G.generateBlock()` 生成该块 markdown → 写回 `state.doc.lines/body` → 同步源码面板 ⇒ **AST 先，文本后** |

⇒ 两条路「谁先谁后」**相反**，而**落点只有一个**（② 内存正文）。§2.0 里那个「DOM 领先」的窗口，本质上是**在这唯一的落点上又插了一小段延迟** —— 这就是 A1 那份 flush 清单必须存在的原因。

### 1.5 决策记录：**为什么不把 AST 提为「共同真源」**（评审问题 ⑤）

> 人问：「为什么不用 ast 作为底层，这样似乎更双向」。
> **结论：真源留文本（保真），AST 升级为「带稳定块身份的索引」（双向更稳）。**三条理由：

**理由 1：`parse` 不是双射 —— 来回一趟会改掉原文，而「文本保真」是第一原则。**
代码证据（`js/source-gen.js`）：无序列表**一律生成 `- `**（第 77 行）、表格分隔行**一律 `| --- |`**（第 83 行）、围栏固定 ```。所以 `parse → generate` 会把用户写的 `*` / `+` 列表记号、表格对齐（`|:---|` / `|---:|`）、空格排布**改掉**。
今天的设计**已经在规避这件事**：整篇保留原文（`state.doc.body` 就是用户原文，`renderEditor()` 逐行原样渲染），**只有你真正编辑过的那一块**才经历一次 round-trip（`commit()` 里的 `G.generateBlock(block)`）。
⇒ AST 一旦成为真源，**打开 / 保存就要整篇 round-trip** ——「我没动过的文件，打开一下就变了样」，对本地 Markdown 文件 IDE 不可接受。
> **可自测**：随便找个文件，在预览里改一个字，然后 diff —— 被编辑那一块里的列表记号 / 表格对齐可能就变了，其余块不变。

**理由 2：「更双向」这件事，今天**已经在用 AST 做了**。**
源码 ↔ 预览的光标 / 选区 / 跳转位置换算走的就是 `MemoriaMapper`（`astToDom` / `domToAst`），而 §1.4 已说明两侧编辑都经过 AST。**缺的不是「把 AST 提为真源」。**

**理由 3：把 AST 提为真源，会引入两件大工程 ——「不可预测的改块范围」与「增量 parse」。**
源码侧现在是**自由文本编辑**，用户可以打出任何半成品（半个围栏 ```、`**粗` 没闭合、表格写到一半）。文本 diff 是**局部且可预测**的；而「一个字符引起的**块级**变化范围」**不可预测**（`#` 让段落变标题、一个反引号让后面一大段变代码块、一个 `|` 让上下行变表格）。
⇒ 源码侧一旦走 AST，就必须做**增量 parse + 局部重写**（ProseMirror / CM6 那个量级的东西）；现在之所以「整篇 parse 30–90 ms 就够」，正因为它只是**读**、不是真源 —— 半成品也能解析，下一拍重来。

**所以「更双向」应该落在这里（折中方案）**：

| 不做什么 | 做什么 |
|---|---|
| ❌ 不把 AST 提为真源（会丢文本保真 + 引入增量 parse） | ✅ **真源留文本**（`state.doc.body` / `lines`：保真、可 diff） |
| ❌ 不按 `_doc.blocks[i]` 的**数组下标**做长期引用 | ✅ 给块**稳定 id**，让**预览缓存 / 锚点 / 落点 / 块内复用**都按 id 引用 |

> **为什么必须换成 id**：**下标会随编辑整体位移**（§3.8 早记过「锚点由源码行改块下标 + 块内偏移」）。而 K5b 的高度账本天然就是「按块身份」的表 —— 两者要一起做；它同时是 **K5a-A2「块内 DOM 复用」能成立的前提**。

### 1.6 业界对标：这是**主路**，不是我们独创（2026-09-28 联网核对）

> 人问：「你觉得这样好吗，联网搜索一下有没有类似做法」。**结论：站得住 —— 我们正好在业界主路上，只是此前选错了实现。**

**① 业界把 Markdown 编辑器明确分成两派，并且早就给「模型真源派」贴了 lossy 标签**：

| 派 | 代表 | 真源 | 格式保真 |
|---|---|---|---|
| **文本真源派** | Obsidian Live Preview（CM6 + decoration/widget）、`@plannotator/atomic-editor`、`@latentic/live-markdown`、`edodo-write` | Markdown 字符串本身 | **byte-for-byte**（"value in / onChange out 是同一个 markdown 串"） |
| **模型真源派** | ProseMirror / Tiptap / Lexical / MDXEditor | 自定义 AST | 被公开标注为 **Lossy (serializer)** |

- `@latentic/live-markdown` 的对比表直接写着：Source of truth = **Custom AST** ⇒ Round-trip fidelity = **Lossy**；Source of truth = **Markdown string** ⇒ **Byte-for-byte**。
- Obsidian 官方帮助与第三方架构资料一致：Live Preview = **CM6 的 decoration/widget**，"Markdown source 作为 CM6 的 document 保留，只把语法标记藏起来"；`atomic-editor` 的 README 一句话总结 —— *"Raw markdown is the source of truth. Every decoration is view-only."*
- `edodo-write` 的架构文档：*"The contentEditable surface is **the view**; **Markdown is the state**; parse/serialize is the reconciler"* —— 它连 undo 存的都是 **Markdown 快照**，并有 `tests/roundtrip.test.ts` 守着。
- 另有独立架构研究（cyberbaser）把这件事称作 **"lossless round-trip 是基石"**，并专门写了 "Why WYSIWYG corrupts OFM"（为什么富文本模型真源会破坏 Obsidian 风味 markdown）。

⇒ 所以「AST 当真源」不是没人做过 —— **做过的人都被标成 lossy**；而「文本真源」才是面向 `.md` 文件产品的主流答案（也正是 §1.5 的结论）。

**② 如果真要以树为真源，那它必须是 CST（带 trivia），不是 AST —— 三方编译器级先例**：

| 项目 | 原话 / 做法 |
|---|---|
| **Roslyn**（C#） | 语法树 "**hold all the source information in full fidelity**"，"can produce the **exact text** that they were parsed from"，含空白 / 注释 / 预处理指令（`SyntaxTrivia`） |
| **LibCST**（Python） | *"**Like a JPEG, the Abstract Syntax Tree is lossy**"* —— 丢注释、丢换行类型（`\n` / `\r\n`）、丢参数间空格 ⇒ 它专门做了 "a lossless CST that looks and feels like an AST" |
| **js-hcl2**（TS 设计文档） | *"**No existing JS parser retains trivia**… We need a concrete syntax tree designed specifically for faithful re-printing, so we build it ourselves"* |

⇒ 我们现在的 `P.parse` 就是**有损 AST**（没有 trivia）⇒ 提为真源必然改文件。要提也得先造 CST —— 那是另一个量级的工程。

**③ 两条**独立印证**了我们的具体决定**（不是一个人拍的）：

- **「块要用稳定 id，不能用下标」**：Tiptap 3.30 的 decorations 文档原话 —— widget **key 必须用「你自己的稳定 id」，不能用 position 或 list index，否则组件会 remount 并丢掉状态**。（正是 §1.5 折中方案右边那半。）
- **「每键只重扫变化的块」**：同一份文档给了 `update: 'changedRanges'` + `createInRange()` —— *"only rescans the blocks that actually changed… the difference between scanning the whole thing on every keystroke and scanning one paragraph"*。
- **「大文件要靠只渲染视口」**：CM6 系（latentic / atomic-editor）都把"1 MB 文档秒开、60 fps"归功于 **CM6 只渲染视口**，而把 ProseMirror / Tiptap 归为 **slow（DOM-per-node）** —— **我们现在的 DOM 视图就是那一档** ⇒ 支持 K5c 的方向。

**④ 但要如实说一条：我们的形态与它们都不完全一样。**
它们是**单栏**（本行即预览，live preview）；我们是**双栏**（源码栏 + 预览栏）。"文本真源"在双栏里更自然（源码栏本来就是文本），但**"预览栏要能直接编辑"这一点，业界没有现成对应物**。所以我们的架构本质是 **「文本真源 + 两套可编辑视图」** —— 这块没有直接可抄的，只能把 K5a / K5b / K5c 自己走对。

**⑤ 一条被纠正的推论（人 2026-09-28）**：我原本把「要不要砍掉双栏」记成了候选（R16）—— 人指出：**「双栏本质上只是把背后的同步展示出来了，问题不在双栏本身」**。这是对的：

- **双栏不制造同步，它只是把同步*外化***。单栏（Obsidian）里同一份「文本 ↔ 视图」同步照样存在，只是**看不见**；砍成单栏不会让同步变少，只会让它**不可观测**。
- 反过来说，双栏是个**验证装置**：改一处、另一处应立刻一致 —— 「AST 落后 DOM」「顺序反了」这类问题在双栏里是**肉眼可见**的，单栏里只能靠猜。
- ⇒ 所以 R16 **不是**性能或正确性的出路；真正的问题被这句话抬了一层：**「同步」本身没有被显式建模**（见 §1.7）。

### 1.7 同步才是本体：两条相反的补丁路径 → 单向数据流 + 一个 reconciler（2026-09-28）

> 由 §1.6 ⑤ 那句「**双栏只是把背后的同步展示出来了，问题不在双栏本身**」往下推一层。

**今天的事实**（§1.4 第 2 点）：两个编辑方向各有一套**方向相反**的补丁逻辑 ——

- **源码侧编辑**：改那一行文本 → 收集全文 → **整篇 `P.parse` 出 AST** → 重渲预览
- **预览侧编辑**：**改 AST** → `generateBlock()` 出 markdown → 写回文本 → 同步源码面板

⇒ 「同步」这件事**没有被写在任何一个地方**，而是**散成两条路径 + 一堆约定**。近期三类问题都是这个结构的直接后果：

| 现象 | 结构性原因 |
|---|---|
| 切模式位置漂移（AG105，且是回归） | 锚点 / 滚动位置的采集时机**散在两处**（重渲前 vs 重渲后）—— 删掉一个挂钩就回归 |
| 「先源码、后预览」（AG103 / AG105） | 两条路径的**先后顺序不一致**，预览侧又被推迟 180 ms ⇒ 差距被放大到肉眼可见 |
| flush 清单（§2.0 A1） | DOM 领先之后，「谁先读谁要先落定」**是个纯约定**，漏一处就静默错位 |

**方向：把「同步」做成一等公民 —— 单向数据流 + 一个 reconciler**
（业界对应物：`edodo-write` 的 *"parse/serialize **is the reconciler**"*、Lexical 的 `Reconciler`、CM6 的 `changedRanges`）

```
        ┌────────── 唯一真源：正文文本 ──────────┐
输入侧   源码栏（采集文本变更）      预览栏（采集文本变更）
                 │                            │
                 └─────────┬──────────────────┘
                           ▼
                  [ 一次变更（operation） ]
                           ▼
                  [   reconciler   ]
                   ├─ 文本 → AST（parse / 局部 reparse）
                   ├─ AST  → 预览 DOM（按块 diff，K5a-A2）
                   └─ 文本 → 源码面板（按行 diff，K5a-A3）
                           ▼
            两个视图都是「订阅者」：只读渲染 + 采集输入
```

**四个要点**：

1. **唯一入口**：无论编辑发生在哪一栏，都归一成「**对真源（文本）的一次变更**」—— 不再有「预览侧先改 AST 再回写文本」这条反向路径。
2. **单向传播**：真源 → 派生（AST / 两套 DOM）由**同一个 reconciler** 更新；两栏之间**不再互相 patch**。
3. **于是「双栏」从问题变成性质**：同步只在一个地方发生 ⇒ 两栏看到的永远是同一个结果、**同帧一致**（§1.6 ⑤ 那个「验证装置」就从"能发现问题"升级为"结构上不会出问题"）。
4. **与 K5a 不冲突、互补**：K5a-A1 管的是「**什么时候**把 DOM 让给浏览器」（性能），reconciler 管的是「**谁来更新、按什么顺序**」（正确性）。

**代价（如实）**：这是**视图层重写**量级 —— 现在「预览侧编辑」是直接改 AST 再回写；改成单向流之后，**预览栏的每次编辑也必须先变成一次"文本变更"**（即预览栏要能算出"我这次编辑对应文本的哪一段"）。所以它应排在 **K5a（性能）→ K5b（账本）之后**，并且**可能重定义 K5c 的靶子**（视口化会被"reconciler 的按块更新"吸收掉一部分）。

**据此划三条线**：

- **线 1 · K5 直接管的**：#1（K5a-A1 所有权反转）、#2/#3/#4 的**出口重渲方式**（K5a-A2 块内复用）、#8（K5b 账本）、以及"重渲的粒度"（§1.7 的 reconciler）。
- **线 2 · K5 必须不破坏的（回归红线）**：#3 与 #4 —— 它们的 `textarea`/`input` 是**预览 DOM 里的原生元素**，块级复用与视口化**绝不能把正在编辑的那个搬走或换掉**（会丢内容 / 丢焦点）；#7 块级复用后必须**重绑**；#10 撤销快照语义不能被"DOM 领先"打破（flush 清单就是干这个的）。
- **线 3 · K5 明确不管的**：#5 lightbox 交互细节、#12 拖拽到对话栏、#13 源码编辑器 drop、#6/#14/#15/#16。**唯一例外是 #16**：视口化会让原生 `Ctrl+F` 失效 —— 这是 **K5c 必须显式处理的一项**（自带 find，或接受"只搜已渲染块"；CM6 就是自带 find panel）。

**两条结构性结论**（"边界"的价值在这里）：

**A. 预览区有 3 套编辑管线，只有第 1 套走 AST。**
① 行内文本 → AST 管线；② 块编辑（代码/公式/表格/mermaid/图片）→ **直接按 `srcStart/srcEnd` 拼 markdown 行写回（旁路 AST）**；③ 图片 caption → 直接改 DOM、退出时回写。
⇒ 所以 §1.7 说的"两条相反的补丁路径"**其实是三条以上**。单向流 + reconciler 要统一的是**这些全部** —— 这正是"牵涉内容有点多"的准确来源。

**B. "跨视图注入 DOM"在这个仓里已经欠过一次债。**
#9 的假光标往**源码行里**注入 `.-sync-cursor`，逼得 `collectEditorBody()` 每次都要专门剔除它（`app.js:86`，注释里记着历史 bug：`"aaa"` → `"a|aa"`、`"<details>"` → `"<details>|"`）。
⇒ **K5c 视口化必然要往预览里放"非内容 DOM"（占位块 / 窗口边界）**，同一类债会再来一遍。**所以现在就立一条 K5c 约束：窗口化的 DOM 必须在"内容之外"** —— 不落在 `.-src-block` 之内，不被 `collectEditorBody()` / `stampBlockLines()` / `domToAst()` 看见。

### 1.9 穿插的根源与对策：把「16×N 交叉」压成「1×N」（2026-09-28）

> 人：「**然后各种复杂的接口穿插还要顾渲染方式优化的问题**」。
> 这是本仓的真实困难：**要优化的那层 DOM，正好是那 16 类交互共用的领土**。

**① 根源：`#preview` 是一块"没有所有权边界"的共享领土。**
现在同时往它上面写东西的至少有：内容渲染（`R.render`）、块级复用（`reRenderBlock`）、缓存搬回（整棵子树）、装饰注入（KP band / `.-sync-cursor` / flash）、临时交互（块编辑的 `textarea` / caption）、只读增强（lightbox）。
**没有任何一条规则说"谁能动谁"** ⇒ 每次优化都得逐个交互去问"会不会撞"⇒ 就变成 16×N 的交叉。

**② 对策一：给 `#preview` 划三层所有权 + 一条冻结规则。**

| 层 | 谁拥有 | 谁能动它 | 例子 |
|---|---|---|---|
| **内容层** | **reconciler / 块级提交** | 只有拥有者；且必须遵守下面的冻结规则 | `.-src-block` × N、块内 inline / 公式 / 图片 |
| **装饰层** | 各功能自己 | 只能**叠加在内容层之外**，且**按块身份定位**（不按像素） | KP 高亮 band、`.-sync-cursor`、flash |
| **临时交互层** | 交互自己，**期间该块冻结** | 内容层在冻结期间**不得动这个块** | 块编辑的 `textarea`/`input`、caption、lightbox overlay |

**冻结规则（一处定义，三处受用）**：reconciler / 块级提交 / 视口化在动手之前，对每个候选块问一次 ——

```
isBlockFrozen(blockId) := 正在块编辑
                        || 正在 caption 编辑
                        || 组合中且光标在此块
                        || 非折叠选区跨过此块
```

命中 ⇒ **跳过**（不重建、不摘除、不搬走）。

> 这条把「16 类交互 × N 个优化」压成「**1 条规则 × N 个优化**」—— 是本仓把渲染优化继续做下去的唯一现实路径。
> 它同时服务 K5a-A2（块内复用）、K5b（锚点 / 落点）、K5c（视口化）。

**③ 对策二：按「与既有交互的交叉面」排序，而不是按「收益大小」排序。**
两次历史事故都源于"动了共享机制、没补既有消费者"：

- **AG97** 回退窗口化时删掉挂钩 ⇒ **AG82 的 `keepPosition()` 一起没了 ⇒ 切模式漂移回归**（AG105 才补）；
- **AG103** 为"当帧"把重渲推迟 180 ms ⇒ **打破了"预览在前、源码在后"**（AG105 才补）。

⇒ **每次优化必须配一张"这次动了哪个共享机制、有哪些既有消费者"的回归清单** —— 清单就是 §1.8 那张表的列。

由此得到**修订后的顺序**（相比 §0 的「K5a → K5b → K5c」，把"低交叉面"的提到前面）：

| 步 | 动作 | 交叉面 | 为什么在这个位置 |
|---|---|---|---|
| 0 | **A0 取数** | **零** | 只加读数，不改行为 |
| 1 | **A3 的低风险项**：关掉 `logCursorContext` 白工；（是否动 `spliceBlockSource` 由读数决定） | **零** | 不改 DOM 语义 |
| 2 | **K5b 账本 + 块稳定 id** | 仅 #8 | 不碰 DOM 归属，却立下"块身份"这条地基 |
| 3 | **A2 块内复用 + ② 的三层与冻结规则** | #3 / #4 / #7 / #8 | **必须先有冻结规则**，否则一改就撞 |
| 4 | **A1 所有权反转** | #1/#2/#3/#4/#10/#11 + flush 清单 | 最想要的手感，但得等第 0 步读数与第 3 步冻结规则到位 |
| 5 | **单向流 + reconciler（R16）** | 全部 | 视图层重写量级 |
| 6 | **K5c 视口化** | 全部 + #16 | 所有权变化最大，**最后做** |

> ⚠️ **本表已被 §1.11 末表取代**（接口化之后：**探针 + legacy 基线 → 按红项做 `NewSurface` → 每步 C 全绿且已绿不回退**）。本表**保留**，作为"按**交叉面**而非收益排序"这条原则的原始记录 —— 该原则在 §1.11 的顺序里**仍然成立**（红项内部仍按交叉面小者优先）。

**④ 对策三：把「契约测试」升格为 K5 的门禁。**
现在的 `pytest` 多数是**静态断言**（"源码里有没有某个字符串"，例如 `assert "reRenderBlock(...)" not in js`）—— 它在重构面前**几乎没有保护力**：改个函数名就全废，而真正的行为回归（点了链接没反应、双击图片不弹编辑、band 错位、`textarea` 被搬走）**一条都测不出来**。
⇒ 需要的是**行为契约**：*"任何一次块级重渲 / 复用 / 视口移动之后，块内既有交互仍可用"* —— 即渲染完跑一遍**交互探针**（点 wikilink / 双击图片 / 查 band 位置 / 查 `textarea` 还在不在）。
仓库已有 `docs/example/rich-content-test/_harness.py`（`AGENTS.md` 里的 **L4 交互**验证）—— **把它升格为 K5 每一步的门禁**，这是唯一守得住"接口穿插"的东西。

### 1.10 换一条路：**接口化 + 从 0 重做 + 探针语料库**（2026-09-28，人提议；待拍板）

> 人：「**在原来的地方改动牵涉东西很多，要不我们把这个接口化，然后按照需求专门从 0 开始做，一一把接口对齐，这样压力测试和准确性测试也方便，另外我们得创一个临时知识库专门测试这一点**」

**为什么这条路对**（接 §1.8 / §1.9）：就地改的代价已经在 §1.9 说清 —— 要在**共享领土**上一边优化一边避开 16 类交互，每次改动都是 16×N。接口化把这件事**反转**：新实现**只对一个窄接口负责**，"避开既有交互"就从"每次都要想"变成"**接口上根本没有这些通路**"。
它还顺手解决两件事：**可测**（接口即测试面）与**可回退**（老实现还在）。

**这条提议同时改写了 K5 的性质**：K5a / K5b / K5c 从"对旧代码打的补丁"变成 **`NewSurface` 的需求规格** —— 旧代码只在 `LegacySurface` 里当参照。

#### 范围（人 2026-09-28 定）：**整个「显示子系统」**

> 人：「**整个显示区域涉及的接口，所有有关显示的**」。比原草案（只包预览视图引擎）**大一圈** —— 双栏 + 视图模式 + 两栏之间的位置同步，**全部进接口**。

**纳入**：

| 块 | 现有哪些（代码） | 在接口里的形态 |
|---|---|---|
| 视图模式与布局 | `setViewMode`（source / split / preview） | `setMode(mode)` |
| 源码面板 | `renderEditor` / `patchEditorLines` / `collectEditorBody` / 假光标 / 行号 | **引擎内部** |
| 预览面板 | 渲染 / 编辑 / 装饰 / 块编辑 / caption | **引擎内部** |
| 两栏位置同步与落点 | `_getViewTopSrcLine` / `_scrollToSrcLine` / `_saveCurrentViewScroll` / `_restoreCurrentViewScroll` / `highlightPreviewRange` | `setScrollAnchor` / `getScrollAnchor` / `revealRange` |
| 只读增强 | lightbox / wikilink 激活 / hover | 引擎内部（纯视图） |
| **当前文档的渲染缓存与预渲染** | `_previewCacheStash` / `_previewCacheRestore` / 预渲染调度 | 引擎内部 —— **它决定"显示"的时序，必须一起进** |

**排除（连同理由，需人确认）**：

| 排除 | 理由 |
|---|---|
| **知识图谱**（2D/3D、`sim-core` / `graph-*.js`） | **独立渲染器 + 独立数据**（节点 / 边），与"文本真源"不耦合 |
| 检查 / 配置 / KP 弹窗 | 表单，不是文档显示 |
| ~~对话栏的助手气泡 markdown~~ | **人 2026-09-28 修正：不排除** —— 它**也用 memoria 语法、也能点击跳转**，只是**不需要编辑** ⇒ 改为**只消费「渲染内核」**，见下方 **A′** |

#### A′. 两层拆分（因对话栏气泡的共性而修正）

> 人 2026-09-28：「对话栏助手气泡**使用的也是 memoria 语法，并且还能点击跳转**，有一点共性，但是**不需要考虑编辑**，也有不同」。
> ⇒ 接口**拆成两层**（比"排除气泡"更准，也更省）：

```
【渲染内核（只读）】  文本 → 块 DOM + wikilink / KP 可激活
   ├─ 消费者 A：预览栏（可编辑）
   └─ 消费者 B：对话栏助手气泡（只读、流式）      ← 只消费内核，不消费外壳

【可编辑外壳（预览栏专用）】 applyEdit / 冻结规则 / 光标 / IME / undo
```

**三个好处**：

1. 气泡与预览**共用同一套「memoria 语法 → DOM」**，消掉"两种渲染器渲染同一种语法"的既有重复；
2. 气泡是**只读消费者** ⇒ 它是渲染内核的**天然一致性测试**（同一份文本，两边渲染出的 DOM 可逐字比对）；
3. §1.7 单向流里「文本 → DOM」那一步**就是**渲染内核；**气泡只是另一个订阅者** —— 与 §1.7 的图完全同构。

**如实（真实差异，必须进接口）**：气泡是**流式**的（边生成边追加），预览是**整篇 + 可编辑** ⇒ 内核要同时提供「**增量追加**」与「**整篇重建**」两个入口。

#### A. 接口草案（宿主 ↔ 视图引擎）

原则：**一条内容变更入口 + 一条文本变更出口 + 若干回调/查询**（这就是 §1.7 的单向流被接口化）。

```js
// 宿主（app.js）与视图引擎之间的唯一契约（草案）
interface PreviewSurface {
  // ── 生命周期 ──
  mount(container, host)                       // host = 下面的回调集
  setText(text, cause)                         // 打开 / 换文件 / 外部重载
  destroy()

  // ── 输入：宿主 → 引擎（宿主不直接改 DOM）──
  applyEdit(op)                                // op = "对真源文本的一次变更"（§1.7 的唯一入口）
  undo(); redo()
  revealRange(startLine, endLine, opts)        // 跳转落点（账本在引擎内部）
  setScrollAnchor(anchor); getScrollAnchor()   // 切模式 / 换文件
  getSrcRangeForSelection()                    // 选区 → 源坐标

  // ── 输出：引擎 → 宿主（引擎不写磁盘、不碰后端）──
  host.onTextChange(text, cause)               // ★ 唯一的"真源更新"出口
  host.onCursorChange(srcRange)                // 源码侧假光标
  host.onLinkActivate(target)                  // 点了 wikilink / KP
  host.onRevealRequest(kind, payload)          // 请宿主做（开文件 / 滚源码）
  host.onMeasure(stats)                        // 读数：耗时 / 节点数 / 窗口区间
}
```

> **接口已定稿到独立文档**：[view-surface-contract.md](view-surface-contract.md)（两层接口 + 双插头协议 + 时序契约 F1–F8 + 冻结规则 + **契约测试 C1–C12** + 不承诺清单）。**本文只保留动机与范围；接口细节以契约文档为准。**

**注意它顺手消灭了什么**：缓存池、预测器、块编辑的 `textarea`、caption、lightbox **都不在接口里** —— 它们要么变成引擎内部实现（块编辑/caption），要么退回宿主（缓存池/预测器/lightbox 是**文件级/只读**的事，与视图引擎无关）。

## 2. K5a：让「输入」**先出现在屏幕上**，再慢慢同步

> 这一节原先写得太压缩（人：「我看不懂 2」）⇒ 重写为 **先讲机制、再讲改法**。**读 A1 之前请先看 §2.0。**

### 2.0 心智模型：浏览器里「打字」的四个站

```
① 按键
② beforeinput 事件   ← 浏览器问一句："我要往光标处写/删点东西，有人反对吗？"
③ 浏览器写 DOM       ← 没人反对（没有 preventDefault）就写；写完喊一声 input 事件
④ 任务结束 ⇒ 浏览器 style/layout/paint   ← ★ 画面在这一刻才更新
```

> **「有人」是谁？—— 不是别人，就是我们自己。** 具体说，是 `edit-handler.js` 里挂在预览区上的那个 `beforeinput` 监听器（`bindBeforeInput`）。**反对的方式 = 在这个监听器里调 `e.preventDefault()`。** 浏览器没有别的"人"可以反对。

**一句话结论：字符什么时候出现在屏幕上，只由两件事决定 —— 第 ③ 站是谁做的、以及第 ④ 站之前主线程有没有被我们占住。**

**今天我们的做法（在 ② 站举手反对）**：我们在 `beforeinput` 里调 `e.preventDefault()`，等于告诉浏览器「别写，我自己来」。于是第 ③ 站变成**我们的 AST 管线**：算 markdown → 改源码面板 → 重渲这一块 → 恢复光标，**全做完任务才结束**，浏览器这才画。
⇒ 用户看到字的时刻 = **我们干完的时刻**。
> 最近两轮（AG101 / AG103）只是把这套活儿**变便宜**（整篇重渲 → 只重渲一块；整篇重建源码面板 → 只改那几行），但**顺序没变**：还是「我们干完 → 才画」。所以只要这套活儿还有几毫秒、或者某处又变重，用户就还是「等一会才有反应」。

**今天我们对不同按键的态度（这就是「什么情况下会反对」）**：

| 你按了什么 | 我们今天的做法 | 结果 |
|---|---|---|
| 普通字符（`a` / `#` / 数字…）→ `insertText` | **反对**（拦下来自己改） | 字要等我们干完才出现 ← **本方案唯一要动的那一条** |
| 回车 → `insertParagraph` | **反对**（自己拆段） | 同上，而且它会**改结构** ⇒ **不动** |
| 退格 / 删除 → `deleteContent*` | **反对**（自己合并 / 删除） | 同上，可能跨块 ⇒ **不动** |
| **中文输入法打字过程中** → `insertCompositionText` | **反对不了** —— 规范规定它的 `beforeinput` 是 `cancelable = false`；我们本来也不拦（监听器早退） | **字是浏览器原生写的、当帧可见**；只有"落字"那一刻（`compositionend`）我们才同步 |
| 粘贴 / 其它 | 不拦（监听器直接早退） | 浏览器原生处理 |

> 由此得到两个事实，正好解释之前的现象：
> ① **中文输入法打字时，字本来就是「当帧出现」的** —— 我们实测到的"慢"不是因为字没出现，而是**我们在这期间干了别的**（AG103 那次 180 ms 后的"渲染态归一"，很可能正好落在你下一次组合中间，把组合打断了）。
> ② **当初为什么要反对**：预览区是**结构化 DOM**，浏览器原生编辑会破坏结构（把 `<strong>` 删一半、跨块删除、把块拆开）⇒ 我们自己改才能保证 AST 与 DOM 一致。而 `insertText` 是唯一一条「**原生改了也不会破坏结构**」的路 —— 所以只有它值得交还。

**改后的做法（在 ② 站不反对）**：让浏览器自己写（第 ③ 站归它），它写完任务就结束、**这一帧就把字画出来**；我们**等画面出来之后**再去更新 AST 与源码面板。

```
今天：  [ 我们的全套同步 …………………………………… ] → 画   ⇒ 字出现在「我们干完」之后
改后：  [ 浏览器写 DOM ] → 画（★字已可见） → [ 我们的同步 ] ⇒ 字当帧出现，同步落在画之后
```

**为什么偏偏要 `rAF` 里再套一个 `setTimeout(0)`**（这是本节最容易看不懂的地方）：
- `requestAnimationFrame`（`rAF`）的回调跑在**「这一帧开始、但还没画」**的位置 ⇒ 在里面干活，照样挡着绘制；
- `setTimeout(0)` 的回调是**下一个任务**，而浏览器的渲染步骤**发生在两个任务之间** ⇒ 在 `rAF` 里排一个 `setTimeout(0)`，那个回调就**必然在这一帧画完之后**才跑。
⇒ 这就是「画完再同步」的标准写法，不是随手写的两跳。

**代价（必须说清）**：这样一来，**DOM 会领先 AST 一小会儿**（从「浏览器写完」到「我们同步完」之间）。任何在这段窗口里**读 AST / 读源码**的代码都会读到旧的 ⇒ 所以那些入口要先「把待办落定」（`flushPendingSync()`）。**A1 里那份「flush 清单」就是这条前提的必然代价，不是设计癖好。**

**一个类比**：
> 今天的做法像 —— 前台每收一笔钱都先**打电话回总部报账**，总部记完账回一句「可以了」，收银员才敢把钱放进抽屉：顾客看见「钱进抽屉」永远晚于总部记账。
> 改后的做法像 —— **先把钱放进抽屉**（顾客当场看见），总部那边**稍后再对账**。

### A0（**第一步，必须先做**）：先给这条链装个秒表，别猜

**为什么**：我知道「哪些代码每次按键都在跑」（§3.9 ⑤ 那张表，7 笔，都带行号，可复核），但**完全不知道每一笔各占多少毫秒**。在这种情况下动手优化，就是「猜哪段慢改哪段」—— 正是要避免的「堆积错误」。

**怎么做**：现在 `commit()` 里已经有一行 `[EDIT] 按键提交 Xms`（`app.js:8188`，只在超过 20 ms 时才打印），但它只有一个总数。把它拆成 5 段：

```

### A1（**核心**）：把 `insertText` 的「否决权」交还浏览器

**要说清的三件事**：

1. **只改一条路**：`inputType === "insertText"` —— 也就是**普通的字符输入**（敲 `a`、中文选词后落字）。**回车（`insertParagraph`）、退格 / 删除（`deleteContent*`）、输入法组合中的半成品（`insertCompositionText`）都不动** —— 理由见 §1.1（它们要么会改结构、要么本来就不可取消）。
2. **改法**：在这一支里**不再举手反对**（不 `preventDefault`），让浏览器把字写进 DOM；我们只把「插入点」记下来，再排一个「等这一帧画完之后再同步」的待办。
3. **现有的 AST 管线一行不改** —— 待办到点后走的还是原来的 `insertText()`；只是它这次拿到的 DOM **已经是浏览器写好的**，所以多传一个 `nativeDone=true`（它早已存在于 `commit()` 的第三个参数里，见 AG105）。

**代码（第一处：`edit-handler.js` 的 `beforeinput`，只动 `insertText` 这一支）**：

```js
if (inputType === "insertText") {
  if (!e.data) return;
  // ① 记下"插入点"的 AST 坐标（此刻 DOM 还没变，锚点最准）
  if (!EH.dockAfter) syncFromSelection("beforeinput");
  // ② 锚点不合法（光标不在可编辑块上 / 停在不可编辑块边界）⇒ 退回老路（拦 + 自己改）
  if (!EH.cursorAST || EH.dockAfter) { e.preventDefault(); EditSync.insertText(e.data); return; }
  // ③ 不 preventDefault ⇒ 浏览器原生插入（当帧可见）；我们只排队，等画完再同步
  EditSync.acceptNativeInsert(e.data, EH.cursorAST);
  return;
}
```

**代码（第二处：`app.js` 的 `MemoriaEditSync` 新增「排队 + 到点同步」）**：

```js
var _pendingNative = null, _nativeAfterPaint = 0;
function acceptNativeInsert(text, anchor) {           // 只排队，不当刻改 AST
  if (!_pendingNative) _pendingNative = { text: "", anchor: cloneCursor(anchor) };
  _pendingNative.text += text;                        // 一拍内连敲多次 ⇒ 合并成一次
  if (_nativeAfterPaint) return;
  _nativeAfterPaint = requestAnimationFrame(function () {          // ① rAF 在"绘制前"跑
    _nativeAfterPaint = setTimeout(flushPendingSync, 0);           // ② setTimeout 在"这一帧画完之后"跑
  });
}
function flushPendingSync() {                          // ★ flush 清单里的每个入口都要先调它
  if (_nativeAfterPaint) { cancelAnimationFrame(_nativeAfterPaint); clearTimeout(_nativeAfterPaint); _nativeAfterPaint = 0; }
  var p = _pendingNative; if (!p) return;
  _pendingNative = null;
  var EH = window.MemoriaEditHandler;
  if (EH) EH.cursorAST = p.anchor;                     // 用"拍前"记下的锚点
  insertText(p.text, true /*forceGroup*/, true /*nativeDone*/);
}
```

**把两个时序并排看**（`任务` = 浏览器的一段同步执行；`帧` = 一次 style / layout / paint）：

```
【今天】一条任务里干完所有事，然后才画
 任务  beforeinput → 我们 preventDefault → 算 markdown → 改源码面板 → 重渲这一块 → 恢复光标
 ├─ 任务结束
 └─ 画 ★   ← 字在这一刻才出现（= 我们干完的时刻）

【改后】浏览器先画，我们画之后才同步
 任务  beforeinput → 我们记锚点、不 preventDefault → 浏览器写 DOM → input 事件
 ├─ 任务结束
 ├─ 画 ★   ← 字在这一刻出现（浏览器自己写的，我们没挡）
 ├─ 帧开始 → rAF 回调（只排一个 setTimeout，此刻还不干活）
 └─ 任务  setTimeout(0) → flushPendingSync() → 更新 AST + 源码面板 + 脏标记
```

**四条必须同时成立的护栏**（缺一条就出问题）：

1. **输入法组合期间一律不排队**。中文输入法在组合期间，DOM 里放的是「半成品 / 候选」—— 这时动 DOM 会把组合打断（候选词消失、字要重打）。
   `beforeinput` 在组合期间本来就早退（既有逻辑）；`flushPendingSync()` 也要在 `_composing` 为真时**把待办交给 `compositionend` 处理**，自己不跑。
2. **「打字把段落变成标题」不享受延迟**。打 `# ` 会把段落转成标题：这时 DOM 是段落、AST 是标题，两边对不上。
   ⇒ `insertText()` 里比对 `block.type` 前后是否变化，**变了就当刻重渲**（走 `nativeDone=false`），不走那 180 ms 的延迟。
3. **原生路不要再动选区**。浏览器已经把光标放对了；我们若再 `sel.removeAllRanges()+addRange()`，反而会打断下一次输入法组合。
   ⇒ `nativeDone=true` 时 `commit()` 只更新 `EH.cursorAST`，不设 Range。
4. **flush 清单**：因为「DOM 领先 AST」，下面这些入口**执行前必须先 `flushPendingSync()`**（漏一处 = 读到旧的 AST ⇒ 编辑错位）：
   - `MemoriaEditSync` 的**每个**出口：`insertText` / `insertParagraph` / `backspace` / `deleteForward` / `deleteSelection` / `commitRange` / `applySnapshot`(undo/redo) / `commitSelection` / `revertBlock` / `flushRepaint`
   - `getEditContext()`（所有编辑的公共前置）
   - `markDirty()` 之前（写盘读的是 `state.doc.body`）
   - `setViewMode()` / `openFile()` / `activateTab()`（切模式 / 换文件会 `collectEditorBody()` + 整篇重渲）
   - `_previewCacheStash()` / `_previewCacheRestore()`（缓存里存的必须是已同步的 DOM）
   - `scheduleEditorRangesResolve()` 的定时器回调（它 `collectEditorBody()` 后发给后端）
   - `beforeinput` 的非 insertText 分支（backspace / enter / delete：它们要基于最新 AST 算）
   - `bindComposition` 的 `compositionstart`（组合开始前要把待办落定）
   - `selectionchange` / `mouseup`（光标移动 ⇒ 锚点语义变了）
   - `keydown` 的 Ctrl+Z / Ctrl+Y（undo / redo 前）
   → **对策**：`flushPendingSync()` 做成**幂等 + 极便宜**（没待办时一个 `if` 就返回），然后**逐个入口加**；再写一个开发期自检 —— `getEditContext()` 里若发现还有待办没落定，直接 `console.error("漏 flush")`。**把「漏掉清单」变成一条看得见的报错，而不是静默错位**（这是这套改法里唯一真实的风险点）。

**验收**：真机「打字当帧出现」＝**是**（预览区直输 ASCII 与中文 IME 各一次）；`ada⏎啊SD…` 行首退格仍正确；`pytest` 不掉。
**回滚**：`localStorage["-native-typing"]="0"` ⇒ `acceptNativeInsert` 直接转 `insertText(text, false, false)`（= 回到 AG105 的行为）。

### A2：重渲一块时**只改文字，不拆不建**

**现状**：`reRenderBlock()` 调 `R.renderRange()` —— 它把这一块的 DOM **整个拆掉重建**（连同块里的公式容器一起）。在浏览器里这是一次「结构性改动」：要重算布局、重绘，而且**光标所在的那个文本节点也被换掉了**。

**改成**：在重建之前先判断一句 —— **结构没变、只是文字变了吗？**

- **判据**：块类型相同 **且** 块内 inline 子节点的类型序列相同（`text` / `bold` / `italic` / `code` / `link` / `wikilink` / …，公式容器视为「同类」）。
- **成立** ⇒ 走快路：**只把变化的那几个文本节点的内容改掉**（`nodeValue` / 必要的属性），**不新建元素、不替换元素**，公式子树也原样保留。
- **不成立**（类型或结构变了）⇒ 退回现在的整块替换。
- 加一句「**值没变就不写**」的守卫（`if (node.nodeValue !== v)`）—— 这样实际写入量就与改动量成正比（见 §1.2 的复杂度对照）。

> 类比：抽屉里有一叠卡片，现在只有一张变了 —— 以前是**把整叠倒出来重摆**，现在是**只换那一张**。

**收益**：DOM 元素替换数从「整块」降到 **0** ⇒ 不再触发该块的 reflow / paint 级联，也不会把光标所在的文本节点换掉。
**验收**：`pytest` 新增钉子（同构 ⇒ 元素引用不变；异构 ⇒ 元素被替换）。
**风险**：判据写松了会把「该重建的」判成「同构」⇒ 视图与 AST 分叉。**对策**：判据只允许「文本内容差异」，**任何结构差异一律整块重建**（保守优先）。

### A3：按 A0 的秒表读数，去掉「每次按键都要付的全文级开销」

**先解释这一类问题**：文档正文在内存里有两种形态 —— 一个字符串 `state.doc.body`，和一个按行切好的数组 `state.doc.lines`。现在每敲一个键，`spliceBlockSource()` 都要先把**整篇**字符串 `split("\n")` 切成数组、把改动那几行拼进去、再 `join("\n")` 拼回字符串。5900 行的文档就是**每键一次全文规模的拆装**。
> 这跟「只想改一行，却把整个文件重排版」是同一类浪费。

**三个候选（从 A0 的读数里挑真正贵的那 1–2 笔做，不要一次全做）**：

| 候选 | 改法 | 注意 |
|---|---|---|
| `spliceBlockSource()`（`app.js:7699`） | `state.doc.lines` **原地 `splice`**（不重建数组）；`state.doc.body` 改成**惰性重建** | ⚠️ **undo 快照**存的是 `state.doc.body`（`recordUndo`）—— 若 `lines` 改成原地 splice，快照就不能再握数组引用；body 仍需在**推快照时**重建一次（`join`）。**所以这一笔的净收益 = 省掉「split + concat + 数组分配」，只保留 join**，是否值得看 A0 读数 |
| `logCursorContext()`（`edit-handler.js:522`） | 加开关**默认关**（`localStorage["-ctx-debug"]`）；或改成「只在锚点不合法时打」 | 它每次按键都做 `document.querySelector('.-src-block[data--block-index="N"]')`（**全篇属性选择器扫描**）+ TreeWalker + 块文本拼接 + 两条日志字符串拼接 —— **纯白工**，是 7 笔里最没道理的一笔 |
| `restoreCursor()`（`app.js:7743`） | 原生路只更新 `EH.cursorAST`（见 A1 护栏 3）；非原生路保留 | 顺带去掉「每键 `sel.removeAllRanges()+addRange()`」这个 IME 风险点 |

**验收**：A0 那五段读数里，被改的那一段显著下降；总时长 ≤ 8 ms。

## 3. K5b：高度账本（**不需要窗口化也吃一半收益**）

**新建** `src/memoria/ui/static/app/js/block-metrics.js`（**纯函数**，可 `node` 直跑断言）：

```js
// 账本 = 每块一行；estHeight 是估算，realHeight 是实测（可缺）
{ blockIndex, srcStart, srcEnd, estHeight, realHeight? }
```

- `estimate(block)`：按块类型给基线（heading 1–6 / paragraph / list / code / table / math_block / mermaid / blank）+ 文本长度折算（`HeightOracle.heightForLine()` 的思路）；
- `prefixSums(ledger)`：前缀和（块 → 文档内 top）；`invalidate(fromIndex)` 只重算失效点之后；
- `atHeight(y)` / `atSrcLine(line)` / `topOf(blockIndex)`：**位置 ↔ 像素双向**；
- `applyMeasured(index, height)`：回填实测 + 只重算其后前缀和 + **返回该块 top 的变化量**（交给调用方补 `scrollTop`）。

**接线（先只换"落点"，不动 DOM 所有权）**：

| 现有函数 | 现在怎么做 | 改成 |
|---|---|---|
| `_getViewTopSrcLine(mode)`（`app.js:1690`） | 从容器 top 起 **逐块 `getBoundingClientRect` 探** | 查账本 `atHeight(scrollTop)` |
| `_scrollToSrcLine(mode, line)`（`app.js:1717`） | 找到目标块再 `getBoundingClientRect` 差值 | `scrollTop = ledger.topOf(block) - 容器偏移` |
| `_restoreCurrentViewScroll()` | 按源码行定位（同款逐块探） | 同上 |
| **`_reanchorJumpScroll()`（AG104）** | 事后 ~350 ms / ~1.4 s **再对准两次** | **可以撤掉** —— 落点由账本保证；账本在实测回填时**补 `scrollTop`** |

**落点**：内存 only（R14 推荐）；持久化到 `<kb>/.memoria/cache/**` 是可选项（`AGENTS.md §1` 的"可再生缓存"）。
**验收**：5900 行文档上跳转 / 切模式落点**不漂**（判定口径：跳完读"首屏第一块的 `data--src-line`"应命中目标行 ±1）；`block-metrics.js` 有 node 单测（估算/实测自洽 + 前缀和失效点重算正确）。

## 4. K5c：视口化（窗口化的正确形态）

**前置条件（硬门槛）**：K5a + K5b 都已落地并取证。**未成立不许开工**（K4a 就是在缺配套件的情况下一路翻车的）。

在 K5b 的账本之上，把"窗口"做成 CM6 式 `viewport`：

| 件 | 规则 |
|---|---|
| **视口** | `viewport = 可见区 ± Margin`，**必须包住可见区** |
| **迟滞** | `viewportIsAppropriate()` 式：可见区**快撞到窗口边缘**、或窗口比需要的大出 2×Margin，才重算；`bias` 让缓冲带**朝滚动方向倾斜** |
| **窗口移动** | **只处理两端进出的块**（Monaco `ViewLayerRenderer`），**不重建整窗** |
| **滚动锚定** | 顶部锚点块 + 文档内 top，**每轮统一补偿一次** `scrollTop`；滚到底不补 |
| **定位** | **先查账本**（`getViewport(bias, scrollTarget)`），**禁止"先物化再量"** |
| **光标/选区** | composition 与光标所在块**永不摘走**；主选区不在窗口内 ⇒ **为其额外建单行窗口** |
| **禁止** | **不做"过渡终点整篇物化"**（CM6 只有 `printing` 才关窗口化） |

**"谁拥有 DOM"**：K5a 已经答了 —— **模型拥有结构、浏览器拥有当帧输入**（与 CM6 同构）。这是开工前必须先写在文档里的那一句（§3.8 ④-2 要求的）。
**验收（三条同时成立，缺一不算）**：真机 **滚动流畅 + 编辑不卡 + 跳转准**；**且设置里能一键关掉回到整篇渲染，关掉不改变正确性**（AG96 逃生门口径）。
**默认值**：先**默认关**，人肉开关跑一周无事故再切默认开。

### R3a.4 三种卡型渲染（归 `RenderCore` 侧 · 只读）

**结论：新增一个极小的 `review-card` 渲染器**（挂在既有 `window.MemoriaMarkdownPreview` 面或并列新模块），**正文 markdown 复用既有管线**，仅 `cloze` 挖空需自定义分词。

- **既有渲染入口（取证）**：`window.MemoriaMarkdownPreview` IIFE（`markdown-preview.js:5`），导出 `renderHtml` / `renderToElement` / `normalizeBody` / `parseInlineTokens` 等（`markdown-preview.js:1879-1894`）。卡面 `front` / `back` 先经此管线渲染（复用公式、高亮、链接），**不另写 markdown 解析**。
- **各卡型**：

| type | 正面 | 背面 | 渲染 |
|---|---|---|---|
| `basic` | `front` | `back` | 正面 → 翻面 → 背面 |
| `cloze` | `front` 中 `{{c1::…}}`（可多段 `{{c2::…}}`）替换为**占位**（下划线/空框），其余照常 | 显示答案：占位处填回 `…` 原文 | 需一个**挖空分词器**：按 `/\{\{c\d+::(.*?)\}\}/g` 切，非挖空段走 `renderHtml` |
| `reverse` | `back` | `front` | 方向由卡定义**互换**（渲染同 basic，仅取值互换） |

- **挖空标记事实源**：`kb.py:4244-4245`（`_review_cloze_re`，注释「`{{c1::…}}`，序号可多个」）、`:4275-4276`（cloze 卡 `front` **必须**含 `{{c1::…}}`）⇒ 分词器正则与后端校验**同源**。
- **只读纪律**：渲染不产生任何写，符合 `RenderCore` 语义（本文 §1.10 A′ / [view-surface-contract.md](view-surface-contract.md)）。

### R3a.5 数据流、失败与重试

```
进入模态
  └─(1) RPC 调 review_due_list（取一次全量） ⇒ 整段 JSON（每张含 card_id + 卡面 front/back/type 等 + FSRS 状态）
        └─(2) 建本地队列 queue = [...cards]
             └─(3) 逐张消费：翻面 → 评分
                  └─(4) 每评分调一次 review_grade(card_id, grade)（幂等）
                        ├─成功：出队，M+1，渲染下一张
                        └─失败：见下「失败与重试」
  └─(5) 退出：汇总（完成 M / 未评 K）
```

- **一次全量**：仅进入时调 1 次 `review_due_list`，避免「每张一次请求」（正面回应本提案约束）。
- **每评分一次 `review_grade`**：幂等键 = `card_id + 评审日`（`kb.py:4732`），同日同卡重复评分不叠加。
- **失败与重试（提案，待定 D）**：评分调用失败 → **不静默丢弃**：① 该卡**留在队列**并标记「未评」，**队尾重试**一次；② 仍失败则**跳过并在结束页计入「未评 K」**（不伪造完成）；③ 审批被拒/超时/无应答 → toast 提示，**不推进进度**（后端 fail-closed，见 `kb.py:4643-4644`）。
  - **待定 D**：重试次数（建议 1 次）与「失败卡是否插队尾」。

### R3a.6 进度与结束态

- **顶部**：「今日到期 N / 已完成 M」——N 来自 `review_due_list` 返回数量（`kb.py:4493` 的 `len(due)`），M 为本地成功 `review_grade` 计数。
- **结束页两文案**：
  - **全部清完**（`N == M`）：「今日复习完成 ✓」。
  - **还剩 K 张未评**（`K = N - M > 0`）：「今日已评 M 张，还剩 K 张未评」。**须明示**：「**未评的明天照样到期**」—— 未评分不改 `progress.json` 状态，次日仍 `due`（由 `fsrs.py due` 决定，`fsrs.py:351-375`）。

### R3a-2.1 失败边界实测（真实读数）

被测命令统一形如 `python <KB>/.memoria/agent/fsrs.py <cmd> --kb <KB> --date <D>`（即 `review_grade` 内部所走的**同一条** CLI）。

| 场景 | 是否可复现 | 原始报错 / 输出 | 对 `progress.json` 的影响 | 分类 |
|---|---|---|---|---|
| 评"当前不在到期"的卡（`due --date` 不含它） | 是 | 无错误，exit 0：`{"status":"ok",...,"due":"2026-01-08","reps":2,...,"idempotent":false}` | **改写**：c1 `due` 2026-01-04→2026-01-08、`reps` 1→2、`stability` 3.173→5.869142，新增 1 条 log | 非失败（`grade` **不看** `due`） |
| `card_id` 不存在（拼错 `c999`） | 是 | 无错误，exit 0：`{"status":"ok","card_id":"c999",...,"reps":1,...,"idempotent":false}` | **新增**幻影卡 c999 状态 + log 条目（无存在性校验） | 非失败（但为隐患） |
| `progress.json` 只读（`attrib +R`） | 是 | exit 1：`{"status":"error","error":"[WinError 5] 拒绝访问。: '…progress.json.<rand>.tmp' -> '…progress.json'"}` | **不变**（`os.replace` 失败即回滚；无 `.tmp` 遗留） | **暂时性** |
| 同日同卡第 2 次、**同分**（3→3） | 是 | 无错误，exit 0，`"idempotent":true` | 不变（`due`/`reps`/`log` 长度均不动） | 非失败（幂等） |
| 同日同卡第 2 次、**不同分**（3→1） | 是 | 无错误，exit 0，`idempotent:true` 且回 `"grade":3`（**第一次的分**） | 不变 | 非失败（幂等，首分胜出） |
| `cards.json` 半坏（删某条 `card_id`）→ 跑 `grade` | 是 | 无错误，exit 0（`grade` **不读** `cards.json`），正常改写 c1 | 正常改写（c1 `due`→2026-03-24、`reps`→3） | 非失败（见下一行） |
| `cards.json` 半坏 → 跑 `due` | 是 | exit 1：`{"status":"error","error":"cards.json 结构非法：以下条目缺 \"card_id\"（须为 str）：1"}` | 不变 | **不可评**（结构性：整队列 fail-closed 并列出坏下标） |
| 被禁用卡（`disabled:true`） | 未在 fsrs 层复现 | 判定在**工具层**：`review.grade: 卡片 <id> 已被禁用…`（`kb.py:4507-4508`）；fsrs **不读** `disabled` | 不变 | **不可评**（跳过、不重试） |

> **关键结论**：**"不在到期里"的卡不会被拒** —— `fsrs.py grade` 只做 `(card_id, review_date)` 幂等判断，**从不**校验 `due`。至于 `card_id` 存在性：**已于 `1bbe6036` 修正** —— 工具层 `_review_grade_precheck` + `fsrs.py op_grade` **双层 fail-closed**，拼错/不存在的 `card_id` 一律拒绝（不再静默新建幻影卡；上方 §R3a-2.1 中该读数为**修复前**行为）。因此队列/UI **仍应**用 `review_due_list` 的结果界定"可评集合"，但其坏 id 已由 `grade` 兜底拒绝。

其余两类实测条件：
- **暂时性**：见"只读"行；"找不到 Python 解释器"由 `_review_run_fsrs`（`kb.py:4333-4337`）归为同类。
- **结果不明**：`grade` 的 subprocess `timeout=60`（`kb.py:4346`）或进程被杀时，可能"已写盘但未返回"；临时库**未能稳定造出**该条件（见 R3a-2.6 说明）。
- **审批被拒**：五把 `review_*` 工具 `read_only=False` ⇒ 分发前过审批门（`kb.py:4640-4644`）；审批被拒时工具体**根本不被调用** ⇒ 算"未评"，**不是失败**。

### R3a-2.2 `review_grade` 的队列处理策略（待定 D 的定案）

| 失败分类 | 处理 | 依据 |
|---|---|---|
| **不可评**（卡不存在 / 被禁） | **跳过并记下，不重试** | 重试也不会成功。被禁由工具层拒绝；卡不存在现由工具层 + fsrs 层 fail-closed 拒绝（`1bbe6036`）⇒ **仍建议在队列构建时用 `review_due_list` 的 id 集合过滤** |
| **暂时性**（写不进去 / 解释器不可用） | **队尾重试一次** | 多为例外而非永久错；只读实测 exit 1、`progress.json` 未变，重试有意义 |
| **结果不明**（超时 / 中断） | **也重试**（安全） | 评分按 `(card_id, review_date)` **幂等**：实测同日同卡连评不叠加（见下） |
| 最终仍未评 | **退出时汇总列出**，提示"未评的明天照样到期" | 与 `review.donePartial` 文案一致（R3a.9） |

**幂等复验（"结果不明可安全重试"的实证）**：临时库对 c3 连做三次**同日**评分——
1. `grade 3 @2026-02-01` ⇒ `due=2026-02-04, stability=3.173, reps=1`，`log` 长度 3→4；
2. 再 `grade 3 @2026-02-01` ⇒ `idempotent:true`，`due` / `stability` / `reps` 与 `log` 长度**全不变**；
3. `grade 1 @2026-02-01`（**不同分**）⇒ 仍 `idempotent:true` 且回 `"grade":3`，状态**全不变**。

⇒ 同一 `(card, day)` 无论重试几次、分是否变化，`progress.json` 只落**第一条**；"结果不明"重试**不会**把评分算两遍。**注意**：该幂等只在**同一天**成立，跨天重试 = 次日新评（这不是重试，是新的一天）。

### R3a-2.3 设计红线：**不做乐观更新**（写死）

- 界面**以工具返回为准**：只有 `review_grade` 返回成功，才把该卡计为"已评"并前移进度。
- **未返回成功即显示「未评」**，**绝不**先把卡面翻到下一张、也不先把计数 +1（**不做乐观更新**）。
- 依据 R3a-2.1：`grade` 可能 exit 0 却写进"不该评的卡"（无 `due` / 存在性校验），也可能 exit 1；界面若自行假设成功，会与 `progress.json` 真相不一致。

    - **证据（实测，2026-10-12 · 提交 `bf854d9b`）**：**审批拒绝不写**（`file_exists_after_reject` 为 `false`）；**允许写入**（给出**含 `kind` 为 `feedback` 的新行原文**）；**非法参数五种全部拒绝且文件一字未变**（缺 `feedback` / 缺 `card_id` / 卡不存在 / `verdict` 越枚举 / `score` 非数）；**读出闭环三种过滤**（`kind` / `verdict` / `card_id`）均正确；**向后兼容**（手工造无 `kind` 的旧记录 ⇒ `kind` 为 `answer` 命中、`kind` 为 `feedback` 命中零）并有**反向验证**（把缺省改错 ⇒ 命中零，恢复 ⇒ 命中一）；**端到端**有反馈的卡显示上次反馈与得分、无反馈的卡不显示、console 错误与 uncaught 均为 `0`。`pytest 1433 → 1440 passed`（新增七条钉子）；`i18n_selftest` 12 行全 PASS；`node --check` 静默。

## 附 R4-3：悬浮卡形态（可被 agent 呼出 / 可撤回 · 方案待拍板）（**权威汇总见 `docs/design/review-cards-handoff.md`**；本节为产出时的历史记录）

> **性质**：**纯方案、未施工**（本节只追加设计，**未改任何 `src/**`**）。人原文（逐字）：「本身复习卡片就是可以智能体呼出的一张矩形卡片，而不是一个手动点击进入的面板，当然用户可以手动点击面板进入 agent 设置好的卡片，以防没有及时回复 agent，悬浮卡片撤回不显示」。
> **拆四条**：① 主形态 = **悬浮矩形卡**（agent 可**呼出**）；② 已交付**模态面板退为手动兜底入口**（agent 没及时回时可自己点进去看「agent 设好的卡」）；③ **悬浮卡可撤回 ⇒ 不显示**；④ 卡是「**agent 设置好的**」（呼出哪张、何时呼出由 agent 定）。
> **一句话边界**：**v1 只支持「作业进行中」呼出**（复用现有 250ms 轮询）；**作业结束之后**的呼出/撤回想生效，须 **v2** 新增「面板打开时的低频空闲心跳」。

### 2. 呼出与撤回的通道（核心 · 已取证）

**既有事实（逐条取证）**：

- **agent → UI 没有推送，只有轮询**：前端 `agent_ask_poll` 每 **250ms** 一次（`agent-panel.js:113` `POLL_INTERVAL_MS = 250`；循环 `:1192`；发请求 `:1210`），提交后被 `poll()` 启动（`:1184`）。
- **轮询只在「一次作业进行中」**：只有 `agent_ask_start`（`ui.py:1194` → `ask_stream.py:286` `start`）成功拿到 `job_id` 后才有轮询；作业结束（`done`/`error`）即 `job=null` 退出循环（`agent-panel.js:1238-1246`）。**全仓没有"无作业时仍轮询"的空闲心跳**。
- **agent 工具只在作业线程内执行**：`ask()` 在工作线程里跑（`ask_stream.py:345` `self._pool.submit(self._run, job)`，`:348` `_run` → `ask()`）⇒ **作业一结束，agent 不再执行任何工具**。
- **单飞**：同时只允许一个 ask 作业（`ask_stream.py:324-331` 返回 `busy`）；作业对象**纯内存态**（`ask_stream.py:280` `self._jobs`），保留最近 `KEEP=8`（`:275`），重启即丢。
- **可复用的「轮询载荷捎带」范式**（无需新通道）：`agent-question.js:296-311` 包一层 `MemoriaApp.call`、只认 `agent_ask_poll`，从响应读 `pending_questions`；`plan-confirm.js:617-629` 同款；`approval_bridge.py:14` 同为 250ms 轮询。**呼出/撤回可照此在 `agent_ask_poll` 载荷里追加 `pending_summons`**（只增不改）。

**结论 —— 「agent 在作业结束后主动呼出」能不能做到？**

- **能（作业进行中）**：只要在**一次 ask 作业进行中** agent 调呼出工具 ⇒ 呼出信号随下一次 `agent_ask_poll` 载荷带回（**低成本、零新通道**）。
- **不能（v1 · 作业结束后）**：① agent 已停（无执行上下文）；② 前端也停了轮询（无投递通道）。**两端俱缺** ⇒ **v1 只支持「作业进行中」呼出**。
- **v2 需要什么**：「面板/floating 存在时的**低频空闲心跳**」——面板打开期间以低频（建议 **5–10s**）空轮询一个只读端点，用于①投递「作业近尾声时排队的呼出」、②让**撤回**在作业结束后仍能生效。**成本（如实）**：静默期常态占「一次/若干秒」的本地 RPC 往返（进程内调用，远低于出网开销，但非零）、可能的渲染/日志噪声；耗电在本机进程中很小，但"总是开着面板"会有微量常驻开销。**更根本的限制**：空闲心跳只解决**通道**，**不产生 agent 决策**——真正"作业结束后 agent 主动想呼出"还需**定时/后台 agent 运行（不属本节范围，列 v2+）**。

**撤回（revoke）回传与及时性**：

- **信号路径与呼出对称**：agent 调 `review_revoke()` ⇒ 置「待撤回」标记 ⇒ 前端**下一次轮询**读到 ⇒ 清除悬浮卡。
- **及时性量级**：作业进行中 = **≤ 1 个轮询间隔（250ms）+ 一次本地 RPC 往返（毫秒级）**；作业结束后 = **无通道**（须 v2 空闲心跳，≈ 5–10s）。
- **用户还没看 / 已看到分别怎么处理**：
  - **未交互**（卡在"未作答"态）⇒ **立即移除、不显示**（落地"撤回不显示"）；落一条审计（见下）。
  - **已交互**（已聚焦 / 已开始作答但未提交）⇒ 建议**不移除正在作答的卡**（生抽走会挫败且可能丢输入），改为提示「agent 已撤回，本次作答仍会记录」。**此条为建议、待定（§7）**。
  - **已提交**（已写 `attempts.jsonl`）⇒ 撤回无意义、忽略（作答流水 append-only、不撤销）。

**呼出/撤回要不要落记录？**

- **建议：落「审计/遥测」事件，但绝不写 `attempts.jsonl`**。
- **理由**：`attempts.jsonl` 的语义 = **用户作答流水**（一行 = 一次作答，读端计数/统计；现存 `kind` 只有缺省 `answer` 与 `feedback` 两种，见条目 12）；呼出/撤回是 **agent 行为、非用户作答**，混入会污染 `total`/统计并使读端 `kind` 模型更脆。**v1 建议**：呼出/撤回作为**内存态计数 + 可选一行日志**（易失），**不做持久审计**；若将来要持久审计，须按 §5 走「登记事实源」（**别塞进 `attempts.jsonl`**）。

### 3. agent 侧能力与骚扰控制

**建议新增两个 agent 工具**（命名/参数待定，见 §7）：

| 工具 | 参数 | 语义 | 建议审批档 |
|---|---|---|---|
| `review_summon` | `card_id`（可选；缺省 = 从**今日到期**里挑一张） | 请求 UI **呼出该卡**悬浮显示（**不写库**，只产生 UI 交互） | **免审批**（`read_only=True`，同 `review_attempts_list`，`kb.py:5117-5120`/`5151`）——它**不写任何文件**；若改为过审批（`read_only=False`，同 `review_feedback_add` `kb.py:5354`/`5389`）则变成"先弹确认卡再呼出"，**反噬"agent 主动呼出"的初衷** |
| `review_revoke` | 无（撤回当前被呼出的那张） | 请求 UI **撤回**悬浮卡 | **免审批**（同上，不写库） |

> **如实**：以上 `read_only` 只是**建议**；审批档最终由人与 `approvals.py` 策略决定（`kb.py:2854-2860` 记录过"设计稿与实现的一处偏差"，此处不预判）。

**骚扰风险与控制（给出推荐）**：

- 风险：agent 反复呼出会烦人，甚至打断写作/阅读。
- 手段（建议一起上）：
  1. **全局开关**（用户可关；关闭后 `review_summon` 直接 no-op / 结构化拒绝）——加在既有 agent 设置区（先例：`#agent-net-toggle` 复选框 + `.-agent-net` 标签，`index.html:346-347`，位于 `#agent-settings` `index.html:329`）。
  2. **一次性只允许一张**（单卡槽；新呼出**替换**旧的，不排队）。
  3. **冷却**：同一 `card_id` 呼出后 **≥ 5 分钟**不得重复；全局相邻呼出 **≥ 30 秒**（数值待定）。
  4. **用户「收起/忽略」后短暂 snooze**（如 30 分钟内不再呼出该卡）。
- **推荐组合**：**默认开** + **单卡槽** + **上线即带 2/3/4 三道限流**；默认值最终由人拍板（§7）。

**允许呼出「任意卡」还是「只允许今日到期」？**

- **建议：v1 只允许呼出「今日到期」的卡**。理由：呼出是**打断式**交互，只有到期卡才值得打断；允许任意卡会让 agent 变成"随机抽卡打扰"，且与既有"复习 = 今日到期"口径不一致（`review_due_list` 内部走 fsrs.py `due`，`ui.py:2259`）。若确要"预习/自选"，作为**用户显式请求**下的例外，而非默认能力。

### 5. 与「事实源」的关系

- **建议：待呼出队列做成「内存态、不落盘」** ⇒ **不是新事实源**，**无需**改 `AGENTS.md §1`。承载点建议挂在既有内存对象上（如 `AskJobManager` 的作业槽 / 一个模块级 slot），随作业结束或撤回即清。

### 6. 分期与验收

**v1（最小可用 · 只作业进行中）**：

- 含：agent 工具 `review_summon(card_id?)` / `review_revoke()`（免审批）；`agent_ask_poll` 载荷追加 `pending_summons`（只增不改）；前端悬浮卡（右下固定、可拖拽、单卡槽、就地作答复用 R4.3）；全局开关 + 三道限流。
- **验收口径（可跑）**：
  1. **`agent 调呼出 ⇒ 悬浮卡出现 ⇒ 撤回 ⇒ 消失`**（作业进行中；撤回在下一次 250ms 轮询内生效）。
  2. **`呼出时搜不到答案`**：呼出载荷与前端取到的卡面里 `answer`/`accept`/`explain` 命中 **0**、cloze `front` 已挖空、含 `options`（复用 R4.2 的传输层直证手法）。
  3. **`重复呼出受频率限制`**：同一 `card_id` 在冷却窗内再呼出 ⇒ 被拒绝 / no-op（可断言）。
  4. **`作业结束后无通道`**：作业 `done` 后 agent 再无法呼出、前端也不再轮询 —— 即「v1 的能力边界」本身可断言。
  5. 就地作答落 `attempts.jsonl`（经 `review_submit_one`）、写评分经 `review_grade_one`；`cards.json` 不被呼出/撤回改动。
- **回滚**：从工具注册表移除 `review_summon`/`review_revoke` + 移除/停用前端悬浮卡模块（沿「文件末追加 / 行内替换」零漂移）；**把全局开关置「关」即等价停用**（保留代码、无交互）。

**v2（完整）**：

- 含：**面板打开时的低频空闲心跳**（≈5–10s）⇒ 作业结束后仍能**投递呼出**与**及时撤回**；撤回及时性由「无通道」提升到「≈ 心跳间隔」；可选多卡队列。
- **验收口径**：作业结束后 agent 经心跳仍能呼出/撤回（撤回在 ≈ 一个心跳间隔内生效）；**面板关闭时心跳必须停止**（断言无常驻定时器）。
- **回滚**：摘掉空闲心跳定时器（退回 v1 行为）。
