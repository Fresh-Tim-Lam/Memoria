# Agent 团队：教训库（Lessons）

> **用途**：把"踩过的坑"变成**可继承的判据**，而不是留在某次会话的对话里。
> **为什么要这个文件**：2026-10-24 一天之内，团队反复踩同一类坑（假绿 / 假红 / 修了等于没修），
> 而每次都是 Lead 重新发现一遍。**组织若没有学习机制，人员再多也只是重复劳动。**
> **维护**：每轮 Curator 复盘后追加；`scripts/agent/team_audit.py` 的 `lessons_stale` 检查会在
> 超过 21 天未更新时提醒。
> **读者**：所有 teammate 的 prompt 应引用本文件，尤其「派发前必读」三条。

## 0. 派发前必读（三条，违反即返工）

### L0.1 先算 ROI 再动手
**判据**：动手前先估算「收益 / 改动风险」，收益接近噪声就**停手回报**，不要"反正能改"。

**实例（2026-10-24）**：P0-b（`initKb` 不 await 分组标签）原是 P0，
但后端缓存落地后该段只剩 **43ms** ⇒ 改 `app.js` 是负收益。
agent 主动停手回报，改做 P1（收益 **1.9s**，是前者的 40 倍）。

**反面**：若照原计划改，会引入改动风险却只换 43ms。

### L0.2 先证红，再修
**判据**：每个修复必须有"**修复前该用例失败**"的实测输出。没有红证据的"修好了"不算数。

**实例**：
- `lexical_index` 缓存：失效后首次调用 **33.8ms**（必须慢，证明真在读盘）vs 热调用 **0.169ms**
- `coalesce_running`：同活两次提交 `executed 2→1`、墙钟 `1007ms→503ms`
- 历史事故：`p5perf_workload` 从未调 `W.reset()` ⇒ M1/M2 恒 0，**没有红证据就永远发现不了**

### L0.3 测试必须走被测路径
**判据**：改的代码不在生产路径上 ⇒ **等于没改**。

**实例**：`p5perf_workload2.mjs` 修完才发现它是**无入口死文件**，
真正在用的是 `p5perf_run2.mjs` + `_wl2_install.js.txt`（仍是旧静默 wrap）⇒ 必须再修一遍（task-82）。

**应用**：动手前先 `grep` 谁 import 它 / 谁调用它；报告里必须写"该路径由谁触发"。

## 1. 假绿与假红（检查可信性）

### L1.1 假绿的三种形态
| 形态 | 实例（都是本轮真实发生） | 修法 |
|---|---|---|
| **检查没有输入** | Curator 第二轮：机制未运行 ⇒ 检查"通过" | 检查必须有 `checked_count`，为 0 判 FAIL |
| **输入被人为裁剪** | Lead 手写快照只写 4 条任务 ⇒ FAIL=0；机器生成 80 条 ⇒ FAIL=5 | 检查输入必须机器生成，不可手写 |
| **同一数据两工具判定相反** | `dispatch_log.py` 允许 `no_report_reason` 豁免，`team_audit.py` S1 不认 ⇒ 判 FAIL（**假红**） | 同一判据只能有一个实现，或加常量表对齐 |

### L1.2 假红的成本同样高
**假红会让人学会忽略告警。** `team_audit` 三次误报都是因为**检查器的世界模型比现实窄**：
- §2.2 常驻成员被当"名册漏登记"
- `write_scope` 输入不足被当"无重叠"
- 按任务 spawn 的 ephemeral 执行者被当"漏登记"

**判据**：修检查器时问「**它假设了什么前提**」，而不只是「哪里报错」。

### L1.3 「总数正常 ≠ 规则在工作」
**实例**：`fidelity.mjs` 归一化规则坏掉时，**红绿两种情况的 `nondetStripped` 都是 28**。
⇒ 只看总数永远看不出问题 ⇒ **必须分规则统计**（`nondetStrippedByRule`）。

**判据**：任何"计数通过"的检查，必须能回答「**哪些条目贡献了这些计数**」。

### L1.4 canary 双列对照法
**问题**：某规则实测计数为 0，是「规则坏了」还是「样本里本来没这个模式」？

**修法**：喂一个**一定能命中的 canary 样本**。
```
canary=0            ⇒ 规则坏了（硬红 ruleNeverMatched）
canary=1 & 真机=0   ⇒ 规则正常，样本没这模式（合法）
```
**这一条把"永远不匹配的正则"从"静默 0"变成"可判定的状态"。**

### L1.5 断言必须打在用户可见输出上
**实例**：探针 spy `MemoriaApp.showFlashInfo` 抓不到提示（产品内部 `showFlashInfo` **不经门面**）
⇒ 32 条全红。改读 `#-flash-host` 的 **DOM** 后才真。
**判据**：内部 API 会重构，**用户可见行为才是契约**。

## 2. 静默失败（最危险的一类）

### L2.1 「没法测到」不能写成 0
**实例**：`p5perf` 的 wrap 失效后 `calls` 全 0 ⇒ 被读成"零工作量"。
**修法**：三态 `number | "unsupported"` —— `"unsupported"` 是**字符串**，任何求和/`==0` 都读不出零。

### L2.2 修静默失败 = 修对 + 让下次失败可见
只改对不够。必须让**同一失败再次发生时自己暴露**：
- 规则不匹配 ⇒ `ruleNeverMatched`（并**接入 `ok` 判定**，工具不可信则门禁不许绿）
- wrap 失败 ⇒ `wrapFailed[]`（不是静默 false）
- RPC 卡住 ⇒ 明确 reason（不是 undefined-resolve）

### L2.3 「看起来成功其实没做」
**实例（task-75 根因）**：`openFile` 早期调用**先**置 `openSeq++ / userNavigated=true`，**再**去做会失败的 RPC
⇒ 副作用已落下 ⇒ 启动自动打开被"用户已导航"作废 ⇒ **一篇文档都不打开且无任何报错**。

**判据**：**任何状态副作用之前，先做前置可用性判定。**
顺序错了，"失败"就会变成"污染"。

## 3. 通用机制误杀长生命周期工作

### L3.1 epoch / 代际失效会误杀"库级"作业
**实例（task-84）**：图谱、校验属**库级**工作，初始却排在 `bootAutoOpen()` 之前；
`openFile` 每次切文件都 `bumpEpoch()` ⇒ 把库级作业当"文件级陈旧作业"**丢弃**
⇒ 实测一轮图谱/校验 **45 秒都没跑**。

**修法**：
1. 排在首文档**之后**
2. **不带** `gen` / `dropStale`
3. 运行前比对**自己的身份**（`state.kbPath`），而不是复用别人的代际判据

**通用判据**：凡"随某个子操作失效"的机制，必须区分**作用域**
（这个工作属于文件？库？会话？应用？）。**用错作用域 ⇒ 静默不执行。**

### L3.2 缓存的两条铁律
- **失效判据必须覆盖所有影响结果的输入**（`(mtime_ns, size)` + 显式 save 失效 +
  外部进程改写；保守优于激进）
- **返回副本**（`dict(cached)`）—— 调用方原地改会**污染缓存**，这是最常见的坑

**证据（本轮）**：`returned_dict_is_isolated: true`、
`explicit_save_invalidates / external_write_invalidates / missing_file_rebuilds` 全 true。

### L3.3 「顺手优化」要算正确性风险
**实例**：后端 agent 发现启动时全库图谱审计跑 **3 次 ≈0.6s**，可加失效缓存消除 ——
**但判据错会产出错误的链接审计告警**（用户会以为文档链接坏了，比 0.6s 更糟）
⇒ **只报告不实施**，等明确验收口径。**这个判断是对的。**

## 4. 编辑器 / 渲染（Memoria 专项）

### L4.1 E30：只改 DOM 不改源码 ⇒ 重渲"回魂"
**判据**：每条交互断言必须同时验 **① 源码 `state.doc.body` ② 重渲后不回魂**。
**实例**：Ctrl+X 剪切、拖拽移动、原子块删除，全部要验"重渲 + 逐字节撤销恢复"。

### L4.2 结构化编辑必须失效行号缓存
`item.srcLine` / `list.itemSrcLine` 只在 AST↔源码 1:1 时有效。
任何结构编辑必须调 `_invalidateListItemLines(block)`（**递归**），否则出现幽灵空行。

### L4.3 原子块删除的唯一安全语义
`contenteditable=false` 的块（表格/代码/公式/mermaid）无法在其中放光标 ⇒
Chromium 把端点吸附到边界 ⇒ **"只选一半"在真实交互里不可表达**
⇒ 整块删除是安全且一致的（**不需要二次确认**，选中高亮就是视觉契约）；
但**必须给事后摘要提示**（长选区滚出视口时用户看不见）。

### L4.4 前端一切"读系统能力"都该走 RPC，不走浏览器权限
**实例**：`navigator.clipboard.readText()` 在 WebView2 需要权限（**弹窗卡住**）
且需要瞬时用户激活（右键菜单异步回调里手势已过期 ⇒ **静默失败**）。
⇒ 桌面应用应走后端系统 API（`system_clipboard.py`），浏览器 API 仅作回退。

## 5. 探针工程陷阱（实测汇总）

| 陷阱 | 现象 | 对策 |
|---|---|---|
| 折叠 range 的 `getBoundingClientRect()` | 全零 | 用非折叠 range 或元素 rect |
| 页面内 async 轮询 | `evalJS` awaitPromise 超时 | 轮询写在 **node 侧** |
| `openFile` 后立即读 `state.doc.body` | 拿到上一例的脏状态（预览缓存恢复晚一拍） | 等 promise + 校验与 pristine 一致（重试 ≤3） |
| `subprocess.run(text=True)` | 默认 cp1252，中文崩 | 必须 `encoding="utf-8"` |
| 纯 `Selection` API | 不触发产品 handler | 必须真实鼠标事件 |
| CDP `Input.dispatchKeyEvent` + `commands:['Copy'/'Paste']` | **挂死 target（45s 超时）** | 复制用真实 Ctrl+C + `execCommand` 兜底；粘贴用合成 `ClipboardEvent` |
| 真机窗口未前台 | Chromium 不把选区写入系统剪贴板 | 测量环境限制，需人工烟测；不要当产品回归 |
| `.ps1` 含非 ASCII | PS 5.1 按 cp1252 解析 ⇒ 报假的 `Missing closing '}'` | **纯 ASCII** + `PSParser` 校验 |
| Windows 64 位 ctypes | 默认 `c_int` 截断指针 ⇒ 访问违例 | `HANDLE/HGLOBAL/LPVOID` 显式 `restype` |

## 7. 风险分级（与 `dsh-agent-teams-contract.md §13` 配合）

| 级 | 判据 | 例子 | 协议 |
|---|---|---|---|
| **R0** | 可能丢失/损坏用户数据 | 删用户文件、清 KB、`git checkout` 掉 agent 未提交工作 | **立即停，问人** |
| **R1** | 单向门（可观察但难回滚） | 打包/发版/改 tag/强推/迁移数据 | **预验 + 预演 ≥3 失败模式 + 回滚方案 + 人确认** |
| **R2** | 可回滚（有 git/备份） | 普通代码改动 | 正常流程 + 验证 |

**本轮教训补充**：
- `git add <file>` 会**扫进同文件的并发改动** ⇒ 改多文件时逐文件核对 diffstat
- `git diff --numstat` 的**删除数 > 插入数**是"陈旧缓冲区覆盖"的信号 ⇒ 停手检查
- **绝不对 `src/**` 跑 `git checkout/restore/reset`**（曾两次摧毁 agent 未提交工作）

## 8. 组织层面的三个真实缺口（2026-10-24 自省）

1. **书面结构与实际运行结构不一致**：名册 8 个常驻 Owner，本轮**零产出**；
   实际是 Lead + 4 个一次性 deep 执行者。
   ⇒ 应明确「**按需专家池**」而非「常驻部门制」。
2. **缺独立验收**：本轮所有验收由 Lead 自做 ⇒ 存在"自己验自己"风险。
   ⇒ 应设独立 verifier（尤其对 R1 级改动）。
3. **缺知识沉淀**（本文件即为此补的第一块砖）。
