# AI 编程协作规范 -v0.1

> **用途**：定义具体开发场景（架构讨论、模块开发、测试、Debug、代码审查）中用户与 AI 的协作规则，确保开发过程可控、可验证、可追溯。
> **目标读者**：项目负责人（用户）与 AI Agent。
> **关联文档**：[meta-rules.md](../conventions/meta-rules.md) — 本规范遵循的元规则；[context-key.md](../conventions/context-key.md) — 上下文防火墙机制。

---

## 0. 通用协作规则（存疑对齐，适用于所有场景）

> 各场景的具体规则之上，有一条**贯穿一切场景的总则**：Agent 在遇到需求含糊、方案歧义、影响面存疑、需要用户拍板的对齐点时，应当停下当前工作先反问对齐，而不是靠猜测继续扩大执行。宁可多问一句，不可带着错误假设做完全部工作再返工。

### 触发反问的典型对齐点

- 任务描述含糊：目标不明确、验收标准缺失、范围边界不清
- 方案有多个合理选项，且彼此影响显著（如：先迁移哪个方向、文档落点、冲突处理策略）
- 改动影响面存疑：涉及多个文件/功能/规范文档，无法仅凭上下文自洽判定
- 需要用户拍板的外部事实：目标文件路径、命名规范、既有约定与现状冲突
- 大规模任务需要分批执行时：先对齐批次方向，再动手，避免整批做错

### 规则

| # | 规则 | 约束对象 | 说明 |
|---|------|---------|------|
| 1 | 存疑即停，先问后做 | Agent | 命中触发点时立即暂停实质改动；未对齐前不产出结论性修改（改代码/改规范文档/批量迁移均算） |
| 2 | 反问须具体、可低成本拍板 | Agent | 给出可选项（2–4 个）+ 推荐项 + 各选项的影响/代价，让用户一次点击即可决定；禁止抛空泛开放式问题 |
| 3 | 先用尽自解手段再问 | Agent | 能依据既有规范/文档/上下文自洽解决的，先自查自解；只有真正需要新决策或外部输入时才触发反问——反问是兜底，不是偷懒通道 |
| 4 | 对齐后按结果执行 | 双方 | 用户拍板后 Agent 立即按结果继续；若用户明确授权 Agent 自决，Agent 记录假设与理由再执行，不在同一点上反复追问 |
| 5 | 低风险事务不阻塞 | Agent | 可推进的低风险执行（读文件、自查、跑验证）正常进行；反问只用于会显著改变产出、返工成本高的分歧点 |

### 验证方式

- 检查触发点出现后，对话中是否有一次具体的对齐问答（含选项与推荐）后再动手
- 检查反问是否带选项/推荐，而非开放问句
- 检查 Agent 是否在无依据的情况下擅自做出了本可避免的方向性猜测

### 典型反例

```
用户：把剩下所有界面文案都 i18n 化。
AI：[未先确认分区批次与“console 日志/静态默认文案”边界，直接全量重写代码]
❌ 违反规则 1（方向与边界存疑未对齐即大规模执行）
```

## 场景 1：架构讨论 / 设计决策

> 用户在几个方案之间犹豫，或需要确定模块结构时，先学习后决策，产出 ADR，不产生代码。

### 触发条件

- 需要确定技术选型、模块划分、接口设计时
- 用户明确说"我们讨论一下 X 的设计"

### 前置条件

- 用户准备讨论的议题或问题

### 产出物

- **ADR（Architecture Decision Record）**：决策内容 + 理由 + 替代方案

### 规则

| # | 规则 | 约束对象 | 说明 |
|---|------|---------|------|
| 1 | 先学习，后决策 | 双方 | 用户不了解时可要求 AI 列出可行方案并解释权衡；AI 不得在学习阶段替用户决策 |
| 2 | 讨论阶段不生成代码 | Agent | 讨论阶段的产出是 ADR，不是代码。AI 不得在讨论中输出任何实现代码 |
| 3 | 必须产出 ADR | 双方 | 每次讨论必须有明确结论，记录决策内容、理由、被否决的替代方案 |
| 4 | 限时讨论 | 双方 | 单个议题的讨论上限为 3 轮对话（不含学习阶段）。第 4 轮必须产出结论或"暂缓" |

### 验证方式

- 检查每次讨论的对话记录，确认有明确的 ADR 输出（决策 + 理由 + 替代方案）
- 统计讨论轮次，超过 3 轮视为违反规则 4

### 典型反例

```
用户：帮我设计一个仿真环境。
AI：[直接生成 200 行代码]
❌ 违反了规则 2（讨论阶段不应生成代码）和规则 3（没有 ADR）
```

## 场景 2：模块开发 / 实现

> 架构决策已定，进入编码阶段。每次实现单一模块，AI 必须同时产出代码和测试，不引入未批准的依赖。

### 触发条件

- 架构 ADR 已产出，需要实现具体代码
- 用户有明确的接口签名或功能描述

### 前置条件

- 已完成场景 1（架构讨论），或在简单场景下用户能给出清晰的接口签名

### 产出物

- 代码文件 + 对应的单元测试文件

### 规则

| # | 规则 | 约束对象 | 说明 |
|---|------|---------|------|
| 1 | 每次只实现一个模块/函数 | 双方 | 用户限制任务粒度，AI 不得主动扩大范围。一个 prompt 只产出一个逻辑单元 |
| 2 | 用户必须在 prompt 中给出接口签名 | 用户 | 函数名、参数、返回值类型先定好，AI 只填实现。禁止"帮我写个 X 功能"这种模糊 prompt |
| 3 | AI 不得引入未批准的 import | Agent | 引入新的第三方库必须显式告知用户，用户批准后才能使用。非标准库 import 需单独列出 |
| 4 | AI 必须同时生成单元测试 | Agent | 代码和测试必须同时输出。只有代码没有测试的提交视为未完成 |

### 验证方式

- 检查本次对话是否只涉及一个模块文件的修改
- 检查 prompt 中是否包含了接口签名
- 检查输出中是否包含 import 声明列表和对应的测试文件
- 未附测试的回答直接打回要求补充

### 典型反例

```
用户：帮我实现一个机器人环境。
AI：输出 5 个文件、300 行代码、引入了 trimesh 库。
❌ 违反规则 1（超出了单一模块）、规则 3（未告知新依赖）
```

## 场景 3：测试编写

> 测试规范。核心方法：确定测试维度 → 笛卡尔积生成测试矩阵 → 覆盖输入选取、验证标准、内容正确性。

### 触发条件

- 模块开发完成后需要编写测试
- 单独为已有代码补测试
- Bug 修复前先写失败测试（见场景 4）

### 前置条件

- 被测代码的接口签名和功能说明已明确

### 产出物

- 测试文件 + 笛卡尔积测试表（注释或文档形式）

### 规则

| # | 规则 | 约束对象 | 说明 |
|---|------|---------|------|
| 1 | 测试必须覆盖三要素 | Agent | 每个测试必须包含：① 输入选取（选择哪些输入值） ② 验证标准（如何判断通过/失败） ③ 内容正确性（验证输出内容的完整正确） |
| 2 | 正反例验证 | Agent | 同时包含正常路径（正例）和异常/边界路径（反例）。仅有 happy path 的测试视为无效 |
| 3 | 多规模测试 | Agent | 当存在可量化的指标时（如物体数量、数组长度、迭代次数），覆盖至少 2 种不同规模（小 + 大 或 边界 + 正常） |
| 4 | 笛卡尔积测试表 | Agent | 识别测试的独立维度及其取值，穷举所有组合生成测试矩阵。AI 必须在测试文件开头或注释中列出维度×取值表 |

### 规则 4 详解：笛卡尔积测试表

AI 在生成测试时，必须先在注释中列出**维度×取值表**，然后为每个组合生成测试用例。

**示例**：测试一个机器人抓取函数的奖励计算

```
# 测试维度 × 取值表
# 维度        | 取值
# ------------+-------------------------
# 抓取距离    | 成功(0.01m), 接近(0.05m), 远离(0.5m)
# 物体重量    | 轻(0.1kg), 重(2.0kg), 超限(5.0kg)
# 摩擦力      | 低(0.1), 中(0.5), 高(0.9)
# ------------+-------------------------
# 组合数: 3 × 3 × 3 = 27 个测试用例
```

### 验证方式

- 检查测试文件中是否包含正例和反例
- 检查测试中是否有不同规模的输入
- 检查测试文件是否包含维度×取值表注释
- 运行测试确认全部通过（不通过说明被测代码有问题）

### 典型反例

```
# 一个测试用例测试了全部功能
def test_grasp():
    result = compute_reward(0.01, 0.1, 0.5)
    assert result > 0
❌ 违反了规则 2（无反例）、规则 4（无维度表、无笛卡尔积覆盖）
```

## 场景 4：Bug 修复

> 从失败测试开始，通过日志注入定位根因，原子化修复，失败则回滚。

### 触发条件

- 测试失败
- 运行时出现错误或异常输出
- 行为不符合预期

### 前置条件

- 用户提供错误描述、测试失败输出或运行日志

### 产出物

- 失败测试（新加或修改）
- 根因分析报告
- 修复代码（仅修改一处，仅修复一个 bug）

### 规则

| # | 规则 | 约束对象 | 说明 |
|---|------|---------|------|
| 1 | 失败测试优先 | 双方 | 必须先有一个能稳定复现 bug 的失败测试。没有失败测试的修复视为无效 |
| 2 | 日志注入分析根因 | Agent | AI 不得直接分析根因。流程：① AI 建议日志注入点（在哪个函数/行的前后加日志，输出什么变量） ② 用户确认注入点 ③ AI 实施日志注入 ④ 用户运行并返回日志 ⑤ AI 基于**实际日志输出**分析根因 |
| 3 | 根因确认后修复 | 双方 | AI 输出根因分析 → 用户确认分析正确 → AI 再修改代码。未经确认的修复直接打回 |
| 4 | 一改只修一 bug（原子修改） | 双方 | 每次修改只修复一个 bug。如果一个对话里涉及多个 bug，拆分为多个独立的修复轮次 |
| 5 | 修复失败则回滚 | Agent | 修复后测试仍失败 → 回滚所有修改，回到修复前状态。禁止在失败修复的基础上继续叠加修改 |

### 流程图

```
┌─ 编写失败测试（规则1）
├─ AI 建议日志注入点 → 用户确认（规则2）
├─ 运行并收集日志 → AI 分析根因（规则2）
├─ 用户确认根因分析（规则3）
│   ├─ 正确 → AI 修复代码（规则4）
│   └─ 错误 → 回到日志注入步骤
├─ 运行测试
│   ├─ 通过 → 完成
│   └─ 失败 → 回滚代码（规则5）→ 回到日志注入步骤
```

### 验证方式

- 检查是否有失败测试存在
- 检查修复代码是否只涉及一个逻辑改动
- 检查修复前后测试结果对比
- 回滚场景下，git diff 应能确认修改已被完全撤销

### 典型反例

```
用户：运行报错，帮我修一下。
AI：[直接改了 3 个文件]
❌ 违反规则 2（无日志分析）、规则 3（无根因确认）、规则 4（一次改了多处）
```

## 场景 5：代码质量改进 / 重构

> 在开发过程中发现当前的代码写法可以优化（可读性、可维护性、逻辑清晰度），AI 提供影响地图和方案对比，用户决策是否执行。

### 触发条件

- 用户发现某段代码的写法可以更好（如函数→类、全局变量→静态变量、遍历方式等）
- 用户主动询问 AI"这段代码有没有改进空间"

### 前置条件

- 用户指出具体的代码位置或模块
- 已有测试覆盖（用于验证重构不改变行为）

### 产出物

- 影响地图（涉及的所有代码位置、输入输出关系）
- 方案对比（替代方案 + 收益 vs 成本）
- 用户决策后执行重构的代码

### 规则

| # | 规则 | 约束对象 | 说明 |
|---|------|---------|------|
| 1 | AI 必须先绘制影响地图 | Agent | 列出重构目标涉及的所有代码位置、输入来源、输出去向，再提建议。未出示影响地图的建议视为无效 |
| 2 | 建议附带收益 vs 成本 | Agent | 量化说明：减少多少重复代码、降低多少复杂度、扩展性提升在哪，以及改造成本 |
| 3 | 禁止修改代码格式 | Agent | 除非用户明确要求，AI 不得改动缩进、空格、换行、引号风格等格式化内容。格式改动和逻辑改动必须分离 |
| 4 | 重构后测试全部通过 | 双方 | 任何已有测试失败说明重构改变了行为，须回滚。使用者确认重构前后行为一致 |

### 影响地图示例

```
【影响地图：将 reward 计算从函数重构为类】
涉及文件:
  - src/env/reward.py (当前函数, 需重写)
  - src/env/__init__.py (导出接口, 需更新)
  - tests/test_reward.py (测试用例, 需调整调用方式)
输入输出关系:
  - 输入: joint_pos, target_pos, grasp_state → 不变
  - 输出: reward_value (float) → 不变
  - 调用方: FrankaReachEnv.step() → 仅改动 import 和实例化方式
```

### 验证方式

- 检查 AI 建议中是否包含影响地图
- 检查 AI 建议中是否包含收益 vs 成本的对比
- 检查修改的 diff 中是否包含非逻辑的格式变更
- 重构后运行全部测试，确认 100% 通过

### 典型反例

```
用户：这段 reward 计算函数越来越复杂了，有没有改进空间？
AI：建议改成策略模式！[同时把文件里的缩进从4空格改成了2空格]
❌ 违反规则 3（修改了格式）、规则 1（没有影响地图和收-益成本分析）
```
