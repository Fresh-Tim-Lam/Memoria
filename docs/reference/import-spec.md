# 导入模块规格（0.3.0）

> **用途**：定义 Memoria 0.3.0 导入模块的目标场景、统一内容模型、三种导入源及其格式、增量与冲突策略、导入前清单预览，以及预留的 Agent 自调（harness）结构化反馈接口。作为实现、文档与验收的统一依据。
> **目标读者**：项目负责人 / AI Agent（实现导入模块、扩充导入源、对接外部整理流程）。
> **关联文档**：[to-dolist.md 附录 A/B](../to-dolist.md)（整理提示词与平面文件格式，本文收编并成为其事实来源）；[i18n.md](../conventions/i18n.md)（界面文案走语言包）；[architecture.md](../reference/architecture.md)（数据模型）。
> **状态**：场景已对齐（2026-09-04）；实现随 0.3.0 版本进行。
> 制定日期：2026-09-04。

## 1. 背景与目标

0.2.x 已完成单一「平面文件导入」（`---` 分段 .txt，AI 整理产物）并支持预扫描/冲突直导。0.3.0 将其扩展为面向三类真实使用场景的完整导入体系，并把「导入前清单预览 + 结构化反馈」作为对外（Agent harness）的稳定接口。

非目标（明确不做）：联网抓取网页、富文本自动整理（R03 独立待议）；正文内容重写/润色（导入不改语义）。

## 2. 使用场景与流程

### 场景 A：AI 协作整理导入
外部 Agent（或用户自己）产出平面文件（`---` 分段 .txt / 粘贴文本），导入后把零散知识并入库。

流程：选择/粘贴 → 预扫描 → **清单预览** → 直导或按冲突处理 → 结果报告。
- 增量重点：重复导入同源内容必须幂等（不产生重复 KP/文件/链接）。
- Agent 闭环：预览阶段可「复制结构化反馈」，供 Agent 自调后重新提供。

### 场景 B：已有 Markdown 目录迁移
把一批既有 `.md`（可能是纯文档、无 frontmatter/无概念标注）作为文件批量入库。

流程：选择目录或文件 → 扫描统计 → **清单预览** → 确认 → 拷贝/登记入库 → 结果报告。
- 无 frontmatter/无 concepts 的 .md：**仅纯文件入库**（正文原样保留，不自动生成 KP/链接，不写 sidecar）。
- 有 frontmatter（含 concepts/description）的 .md：按声明生成 sidecar 的 KP 记录（range 缺失时留待用户配置，不臆造行号）。
- 文件重名处理纳入冲突策略；正文内相对图片/链接路径按新落点归一。

### 场景 C：知识包分发 / 合并
他人导出的「完整知识库包」（md + `.memoria/sidecars/*.memoria.yaml` + `manifest`）导入并合并到当前库。

流程：选择包（目录/压缩包内目录）→ 解析 manifest 与文件集 → 预扫描冲突（文件级 + KP id 级）→ **清单预览** → 逐项处理 → 合并 → 报告。
- KP id 冲突、文件路径冲突、链接/边目标失效均需在预览中显式呈现并可处理。

## 3. 统一内容模型

所有导入源归一为：

- **正文**：标准 Markdown 文件（`.md`），内容原样保留（不删改、不重排正文语义）。
- **知识点 KP**：`id`（全局唯一 slug）/ `name`（标题文本）/ `weight` / `tags` / 建议 `range`（行区间，缺失可空，落库后由用户配置）。
- **链接与边**：正文 `[[id|文本]]` + sidecar `links/edges`（reference/extend/contain + 强度）。
- **待确认提议**：无法自动定稿的内容（如建议 range、冲突 id 需重命名）以提议进入待确认清单，不静默修改。

KP 为核心：场景 B 的「纯文件入库」属于显式例外（见 §2B），其余路径必须产出 KP 可解析的库结构。

## 4. 三种导入源格式

### A. 平面文件（AI 整理）
沿用 `---` 分段格式（收编 to-dolist 附录 B 为本文件事实来源，附录保持兼容性说明）：

```
---
description: 文件描述
concepts:
- id: kp-id
  name: 知识点名称
  weight: 1.0
  tags: [标签]

---
正文（可含 [[kp-id]] 链接）
```
要点：
- 段分隔 `---` 独占一行；每段 = 一个 `.md`（文件名 = 段内首个 KP id）。
- 兼容「围栏包裹/分批交付」：导入前规范化会拼接所有 ```围栏块，忽略围栏外的对话/进度标记（保留现有实现语义）。
- `##` 二级标题 = KP 一级；`###` 嵌套；正文 `##` 文本必须与 concepts.name 一致（不一致按现有规范校验并在预览中列出）。
- 增量导入 = 再喂相同内容 → 0 变更（幂等）。

### B. Markdown 目录 / 文件
- 输入：目录递归或文件多选（`.md`）。
- 已含 frontmatter（description + concepts）→ 建 sidecar KP（range 缺失留空并在预览标注「待配置范围」）。
- 无 frontmatter → 纯文件入库：正文落盘到目标路径，不写 sidecar、不生成 KP。
- 目标路径规则与冲突纳入 §5/§6。

### C. 知识库包（.md + sidecar + manifest）
目录布局（与库内布局一致，另附包级 `manifest`）：
```
bundle/
  manifest.yaml            # package: name/version/source_kp_count 等元信息（可选）
  *.md
  .memoria/
    sidecars/<file>.memoria.yaml
```
导入=合并语义：文件级冲突（同名不同内容）与 KP id 冲突显式呈现；正文/图片相对路径保持。

## 5. 增量与幂等

- 导入以「内容指纹」判断新增/变更：正文 `sha256` + sidecar 摘要。
- 重复导入（同指纹同路径）→ 跳过并计入「无变更」统计；不产生重复。
- 文件级策略沿用（依据内容差异判定，而非仅路径）：见 §6 冲突处理。

## 6. 冲突处理策略

统一冲突原语（预览与执行共用同一模型，每项可决策）：

| 冲突 | 可选动作 |
|---|---|
| 文件重名（同名 .md 已存在且内容不同） | 跳过 / 覆盖 / 重命名（加前缀保留两份） |
| KP id 与库内已有 KP 冲突 | 跳过（不导该 KP 所在文件）/ 覆盖（替换该 KP）/ 重命名（新 id，正文 [[]] 与 links 同步改写） |
| 目标目录不可写 / 路径非法 | 无动作（跳过）并列入失败 |

- 冲突报告可复制（同 Agent 反馈 JSON/Markdown 两形态）。
- 批量场景允许「应用到全部同类冲突」。

## 7. 导入前清单预览（核心交互）

导入执行前必须展示结构化预览；取消则不写入任何文件。预览包含：

- **摘要**：将新建 N 个文件 / 新增 K 个 KP / 涉及链接 M 条；其中新增/覆盖/跳过各多少。
- **文件清单**：每个目标文件：来源、落点路径、动作（新建/覆盖/重命名/跳过/无变更）、含 KP 数。
- **KP 清单**（展开）：id、name、tags、建议 range（缺失标注）、来源（concepts 声明/纯文件无 KP）。
- **链接/边影响**：涉及 `[[]]` 与 sidecar links/edges 的新增或改写点。
- **冲突区**：逐条列出（§6 表）并可操作。
- **待确认区**：自动生成的建议（如重命名 id、待配置 range）汇总。

## 8. Agent 自调接口（harness，预留给 agent-harness 子系统）

预览同时产出两种可导出形态（按钮「复制反馈」），内容与界面预览一致、契约稳定（0.3.0 冻结字段名）：

**形态 1：JSON 文本块**
```json
{
  "schema_version": "1.0",
  "import": {"kind": "flat_file|md_dir|kb_bundle", "source": "名称"},
  "summary": {"files_new": 0, "files_overwrite": 0, "files_skip": 0, "kp_new": 0, "links": 0},
  "files": [
    {"rel_path": "x.md", "action": "new", "kp_ids": ["kp-a"], "issues": []}
  ],
  "kp": [
    {"id": "kp-a", "name": "…", "tags": [], "range": null, "source": "concept", "issues": []}
  ],
  "conflicts": [
    {"kind": "kp_id_taken", "subject": "kp-a", "options": ["skip", "overwrite", "rename"]}
  ]
}
```

**形态 2：Markdown 清单**（人类可读，逐文件/KP/冲突呈现）。

- 二者可一键复制；用户可直接把文本回给外部 Agent，Agent 依 `issues`/`conflicts` 自行调整源文件后重导。
- 反馈接口为「只读导出」，不承载执行指令；执行仍由用户点击确认。

## 9. UI 流程

- 入口：工具栏「导入」下拉（默认平面文件）；场景 B/C 在导入对话框内切换源类型（选择 .txt 多选 / 目录或 .md / 知识库包目录）。
- 预览对话框：左「文件清单」右「详情与冲突」，底部「复制反馈（JSON/Markdown）」「取消」「确认导入」。
- 执行后：结果报告（新建/覆盖/跳过/失败 + 打开新文件链接）；若打开 KB 后建议「构建图谱」以同步链接边。
- 界面文案全部走 `t()`（i18n，zh/en 成对），新增键归 `import.*` / `import2.*`? 以 `import.*` 前缀按 sub 段组织并登记。

## 10. 后端 API（实现草图）

以现有 RPC 模式扩展（命名以最终实现为准）：

- `import_scan(kind, sources)` → 预览模型（文件/KP/冲突/issues/摘要）。
- `import_execute(kind, sources, decisions)` → 结果报告（decisions = 冲突处理映射 + 用户最终选择）。
- 场景 B：`resolve_md_sources(paths|dir)` 负责递归/文件判定与路径归一。
- 场景 C：`resolve_kb_bundle(dir)` 解析 manifest/sidecar 并比对库内。
- 幂等指纹复用于 `import_scan`。

现有「select_import_files / pre_scan_import / execute_import / conflict_report」保留兼容或迁移到新入口（迁移时登记变更）。

## 12. 程序内 Agent 提示词（维护与入口）

场景 A 的用户需要把「知识文件整理提示词」连同源文档一起发给外部 Agent。该提示词必须**程序内可取、可一键复制**，并与仓库文档保持单点维护：

- **单一事实源**：提示词正文存放于 `resources/agent-prompts/organize.zh-CN.md`（对应英文版 `organize.en.md` 如需要）。提示词正文**不抽 i18n 键**（它是内容不是界面文案）；界面外壳文案（标题/按钮/说明）走 `t()`。
- **同步规则**：修改提示词只改该文件；docs 侧的「知识文件整理提示词」文档（原 to-dolist 附录 A）迁移为指向该文件或由其生成，避免双份漂移。
- **程序内入口**：工具栏「导入」下拉新增「整理提示词」项 → 弹窗展示：提示词全文 + 使用说明（先复制提示词 → 连同知识文件发给 Agent → Agent 返回平面文件 → 用「平面文件导入」接收）+「复制」按钮（复制提示词文本）。
- **随包发布**：打包时该资源随 `resources/` 进入发布包，桌面/离线环境可访问。
