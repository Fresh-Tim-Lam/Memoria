> **目标读者**：项目负责人（用户）、所有后续 Agent（接手前先读本文件，避免重提已否决项或重复排期）。
> **关联文档**：[todo.md](../todo.md)（索引）、[docs/todo/README.md](README.md)（附件规则）、[ledger-maintenance.md](../conventions/ledger-maintenance.md)（台账规则）、[kg-ontology-v0.md](../design/kg-ontology-v0.md)（相关设计裁决）。
> **登记纪律**：① 只记**人提出**的（不是 Agent 自创）；② 时间用**约**或提交时间，不编；③ 状态严格取值：`已落地`（给 commit sha）/ `已派发`（给 task id）/ `待排期`（给理由）/ `已否决或已缩范围`（给谁裁、裁成什么）/ `待澄清`（需人补充什么）；④ commit sha 一律经 `git log` 核对。

## 3. 维护规则

1. **新增**：人提出新需求后，由 `todo-owner` 在 **24h 内**追加一行；不确定的写"待澄清"并列出缺什么。
2. **状态推进**：`待排期→已派发`（写入 task id）；`已派发→已落地`（写入 commit sha，必须 `git log` 核对）；否决/缩范围必须写"谁裁的、裁成什么"。
3. **禁止**：不删行（否决也保留原文与裁决）；不凭记忆写时间/sha；不把 Agent 自创当"人提出"。
4. **与 todo.md 的关系**：本文件是**人的需求原始台账**；`docs/todo.md` 是**工作项索引**。同一需求可同时出现在两处（本文件记"人说过什么/去了哪"，todo 记"当前怎么推进"），**不构成双事实源**。

### 跨域借调事故（2026-10-27 人指正 · 领导失职）

> 人原话：「别把现有的成员拉进会议了，据我看现在团队里面没有人是专门负责研讨的，更别说是为一个板块研讨」
> 「而且你扰乱了旧成员的本职，可能会干扰他们的上下文，说明你领导失职以及团队协议漏洞，
>   子成员也没有 stick to 自己角色，没有反向提醒」

#### 事故
为「agent 索引」一个板块，我把 6 个领域 Owner（arch-contract / todo-owner / agent-arch /
metrics-baseline / retrieval-researcher / corpus-analyst）拉进三轮研讨会
（Phase 1 提案 → Phase 3 异议 → 第二轮准备），每人产出 12–52 KB 文档。

#### 实际代价
```
① 本职停摆：架构契约 / 文档一致性 / agent 能力 / 度量基线 / 语料分析 各自的常驻工作被挤占
② 上下文被占：这些成员的上下文被该板块填满，回到本职已失去原有工作上下文
③ 产出质量不可靠（已实证）：单库外推（差点得出"迁移免费"）、口径混比（526 vs 1822 字）、
   算术当测量（10.94× 后被自证为 1.16×）—— 兼职研讨必然出现这类错
```

#### 领导失职（我的错，逐条）
```
L-A 把"人多"当成"严谨"：六方研讨看起来周全，实质是拿人数冒充对抗性
L-B 用"常驻成员"替代"专职研讨角色"：没先问"团队里谁专职做研讨"——答案是"没有"
L-C 无视本职影响：派任务时没评估"他停下手上的事，代价是多少"
L-D 事后才发现错：人提出后才改用专职小组，说明我没有角色边界这个检查项
```

#### 团队协议漏洞（需补，涉及团队契约，需人批）
```
P-A 缺【跨域借调规则】：领域 Owner 不得被拉入跨域研讨，除非 Lead 书面说明
    "为什么非他不可 + 本职影响评估 + 复归计划"
P-B 缺【专职角色识别】：每类工作开始前先问"团队里有没有专职做这个的角色"；没有则先招
P-C 缺【成员反向提醒义务】：成员收到越域任务时，必须回"这不在我域内，建议 X 来做"，
    不得直接开工；直接开工视为失职
P-D 缺【借调后的上下文复位】：借调结束应有"归位说明"，否则成员回到本职会带着错误前提
```
