# 人提出的想法 / 需求台账（ideas）

> **用途**：把本会话中**人提出的需求/想法**逐条落盘（原话或概括 + 提出时间 + 状态 + 去向），使"换会话/换人接手"时人说过的话仍然存在，而不是只停留在某个 Agent 的记忆里。
> **目标读者**：项目负责人（用户）、所有后续 Agent（接手前先读本文件，避免重提已否决项或重复排期）。
> **关联文档**：[todo.md](../todo.md)（索引）、[docs/todo/README.md](README.md)（附件规则）、[ledger-maintenance.md](../conventions/ledger-maintenance.md)（台账规则）、[kg-ontology-v0.md](../design/kg-ontology-v0.md)（相关设计裁决）。
> **登记纪律**：① 只记**人提出**的（不是 Agent 自创）；② 时间用**约**或提交时间，不编；③ 状态严格取值：`已落地`（给 commit sha）/ `已派发`（给 task id）/ `待排期`（给理由）/ `已否决或已缩范围`（给谁裁、裁成什么）/ `待澄清`（需人补充什么）；④ commit sha 一律经 `git log` 核对。

## 3. 维护规则

1. **新增**：人提出新需求后，由 `todo-owner` 在 **24h 内**追加一行；不确定的写"待澄清"并列出缺什么。
2. **状态推进**：`待排期→已派发`（写入 task id）；`已派发→已落地`（写入 commit sha，必须 `git log` 核对）；否决/缩范围必须写"谁裁的、裁成什么"。
3. **禁止**：不删行（否决也保留原文与裁决）；不凭记忆写时间/sha；不把 Agent 自创当"人提出"。
4. **与 todo.md 的关系**：本文件是**人的需求原始台账**；`docs/todo.md` 是**工作项索引**。同一需求可同时出现在两处（本文件记"人说过什么/去了哪"，todo 记"当前怎么推进"），**不构成双事实源**。

### 研讨会角色邀请纪律（2026-10-27 人指正）

> 人原话：「你开研讨会的时候别把一些其他角色的人拉进来啊，哪有"叫清洁工开会"的」

**规则**：研讨会只邀请【对某个研究问题有实质产出能力】的角色；
不相关角色不邀请，最多只做只读知会（不进会议、不产出提案、不占议题）。

**判据**：邀请前先问"他能回答哪个 R 号问题？答不出就不请"。

本轮正确的邀请：arch-contract（契约/锚点）、todo-owner（知识组织）、agent-arch（agent 检索）、
metrics-baseline（可测性）、retrieval-researcher（外部）、corpus-analyst（真实语料）

**下不为例**：不为"人多"凑数；不让无关角色参与裁决。
